# M1c — 표면 대체 (계획, 코딩 전)

기준일 2026-09-22.  선행: M1b 완료(`docs/M1B_PLAN.md` 10).
**이 문서는 코드보다 먼저 쓰였다.**

## 1. 이 칸의 한 줄

**Mesa 가 우리 표면에 그리게 하되, 그리는 것은 여전히 소프트웨어다.**

`Buffer`·`Stride`·`BoundTo`·`AppBuffer`·`Mirror`·`ReleaseBuffer` 여섯이 진짜가 된다.
하드웨어 삼각형은 **없다** — 그건 M1d 다.  색·깊이·텍스처를 한꺼번에 켜지 말라는 선례의
규칙을 지킨다.

그림은 **여전히 stock 과 픽셀 동일**해야 한다.  소프트웨어가 앱 버퍼 대신 우리 표면에 그리고,
`Mirror` 가 그것을 앱 버퍼로 되돌리기 때문이다.

## 2. M1b 가 남긴 측정과, 소스가 준 답

M1b 는 거절 8 건이 전부 `RASTER` 였고 마스크가 `0x106` 임을 쟀다.  그 정체:

| 비트 | 값 | 무엇인가 |
|---|---|---|
| `BLEND_BIT` | `0x002` | 내 시험 장면이 한 번 켠 것 |
| `DEPTH_BIT` | `0x004` | 우리가 아는 유일한 비트 |
| `ALPHABUF_BIT` | `0x100` | **우리가 `Buffer` 를 거절했기 때문에 켜져 있다** |

`ALPHABUF_BIT` 은 구현할 기능이 **아니다**.  이 포트의 `osmesa.c` 578–630 행이 이미
`if (accelBuf) { … UseSoftwareAlphaBuffers = GL_FALSE; NewState |= NEW_RASTER_OPS; }` 를
하고 있고, 주석이 이유까지 적는다 — 별도 알파 버퍼가 있으면 *"네 번째 바이트에 알파를 쓰는
백엔드의 알파가 모든 블렌드에서 무시된다."*  즉 **`Buffer` 가 성공하는 순간 스스로 꺼진다.**

**추측했다면 "알파 블렌딩을 구현해야 한다" 로 갔을 것이다.**  읽어서 갈랐다.

그리고 M1b 의 `seen` 은 **OR 누적**이라 어느 상태에 무엇이 켜졌는지 못 가른다 → 이 칸은
**상태 단위**로 기록한다.

## 2b. 호출 자리의 계약 — 직접 읽어 확인한 것

`openstep-mesa342/upstream/Mesa-3.4.2/src/OSmesa/osmesa.c` 를 열어 확인했다(행 번호는 그 파일):

| | 사실 | 행 |
|---|---|---|
| C1 | `wasBound` 는 **`Buffer` 보다 먼저** 물어진다 — 할당자의 첫 동작이 바인딩을 놓는 것이라, 나중에 물으면 무엇이 있었든 "아니오" 가 된다 | 546–553 |
| C2 | 조합은 **넷**이다: `(wasBound, accelBuf)` = (0,0)·(0,1)·(1,1)·(1,0).  마지막이 **거절-후-해제**이고 `osmesa_leave_accel` 을 부른다 | 561–572 |
| C3 | `osmesa_leave_accel` 은 **바인딩을 검사하지 않고** 맨 먼저 `Mirror()` 를 부른다 — 호출자 둘이 서로 다른 시점에 부르기 때문 | 359–375 |
| C4 | **그러므로 우리 `Mirror` 는 아무것도 바인드돼 있지 않을 때 불려도 안전해야 한다** | C3 의 따름 |
| C5 | 깊이 되돌림은 `UseSoftwareDepthBuffer` 가 거짓일 때만 — 우리가 `DepthBuffer` 를 거절하는 동안엔 **안 돈다** | 376–395 |
| C6 | 소프트웨어 알파 버퍼는 **일부러 다시 켜지 않는다**.  켜 봤더니 첫 clear 에서 죽었다(크기 조정이 이미 플래그를 끈 뒤라 아예 할당되지 않았다) | 398–407 |
| C7 | `ReleaseBuffer` 는 **두 곳**에서 온다 — `osmesa_leave_accel` 의 마지막(406)과 `OSMesaDestroyContext`(427).  후자는 그 전에 깊이 포인터를 프레임버퍼에서 **빼낸다**(우리 것은 malloc 이 아니므로) | 406·427 |
| C8 | `Stride` 와 `AppBuffer` 는 **픽셀 스토어 이탈** 경로에서 불린다(742·744), `AppBuffer` 는 **색 버퍼 조회**에서도(889) | 742·744·889 |

**C4 가 설계를 바꾼다**: `Mirror` 는 "바인드돼 있으면 복사한다" 가 아니라 **"바인드돼 있지 않으면 아무것도 하지 않는다"** 로 써야 한다.  그리고 게이트 F 는 네 조합을 **전부** 밟아야 한다 — 하나만 밟는 게이트는 선례가 다섯 중 넷을 놓친 그 게이트다.

## 3. 어떤 표면인가

카드의 **오프스크린 창**(R4c 가 연 `0x0029e000 .. 0x07c00000`, 문자 디바이스의 VRAM mmap 창).
화면에 보이는 프레임버퍼가 **아니다** — 선례가 "렌더링이 맞는지 모르는 채 화면 소유 문제를
붙이면 실패 원인이 두 겹이 된다" 고 못박는다.

## 4. 이 칸이 B3 의 주장을 바꾼다 — 명시한다

M1b 의 B3 는 가속 오브젝트의 미정의 심볼이 다섯 개뿐이고 **`mmap` 이 없으므로 그릴 수 없다**
였다.  M1c 는 `mmap` 을 **반드시** 들여온다.  그러므로 주장이 약해지는 것을 숨기지 않고 바꾼다:

> **M1b**: 이 라이브러리는 어디에도 그릴 수 없다.
> **M1c**: 이 라이브러리가 쓸 수 있는 곳은 **자기가 매핑한 창 하나뿐**이고, 그 창은 드라이버가
> `d_mmap` 으로 내주는 오프스크린 영역이며, 그 밖의 어떤 주소도 이 오브젝트에 없다.

새 B3 는 그래서 **두 부분**이다:
- **B3a** 미정의 심볼이 새 허용 목록 안이다(`mmap` 추가, 그 외 증가 없음).
- **B3b** `mmap` 은 **한 자리에서만** 불리고, 그 인자는 프로브가 `CAPS` 로 받은 창이며,
  상수 주소가 소스 어디에도 없다.

## 6. 게이트 (교차검토 뒤 다시 씀 — 8 절)

첫 판은 §1 을 증명하지 못했다.  가장 큰 셋: **거절 경로가 둘인데 하나만 겨냥했고**, 게이트가
**서로 다른 실행**이어도 되게 쓰여 있었고, *"하드웨어로 그리지 않는다"* 에 **실행 중 관측이
하나도 없었다**.

### A. 소스 규칙 (호스트, `check_hook`)

규칙마다 변이, **기준 PASS·각 변이 FAIL 같은 실행**.  M1b 의 규칙에 더해:

| | |
|---|---|
| A4 | `mmap` 은 **한 자리에서만** 불리고, 그 인자는 프로브가 `CAPS` 로 받은 창이다 |
| A5 | 소스에 **상수 카드 주소가 없다** |
| A6 | 바인딩(`bound`)과 소유(`owner`)는 **두 필드**다(V8) |
| A7 | `Mirror` 는 **바인드돼 있지 않으면 아무것도 하지 않는다**(C3·C4) |

### B. 빌드 (타깃)

| | |
|---|---|
| **B1·B2** | M1b 그대로: 훅 10 개 text 심볼, 멤버 15 자 충돌 없음 |
| **B3a** | 미정의 심볼이 새 허용 목록 안: M1b 의 다섯 **+ `_mmap` + `_vm_allocate`**, 그 외 증가 **0** |
| **B3b** | 실행 중 **살아 있는 매핑이 동시에 하나를 넘지 않는다** — 매핑·해제를 세고, 최대 동시값이 1 |

§4 의 *"그 밖의 어떤 주소도 이 오브젝트에 없다"* 는 **과한 주장이었다**: 앱 버퍼 주소는
`Buffer` 의 인자로 들어온다(osmesa.c 561–567).  주장을 고친다 — **상수 주소가 없고, 매핑은
하나뿐이며, 앱 버퍼는 넘겨받은 것 말고는 모른다.**

### C. 한 실행에 묶는다 (실기)

C·D·F·G 를 **하나의 승인 실행**으로 합친다.  실행마다 다르게 구는 구현을 막는 유일한 방법이다.
한 프로세스가 순서대로:

| # | 무엇 | 관측해야 하는 것 |
|---|---|---|
| 1 | 첫 바인드 | `Buffer` **수락 ≥ 1**, `wasBound` 는 0 이었음 |
| 2 | 그린다 | 픽셀이 stock 과 전수 동일 |
| 3 | **`ALPHABUF_BIT` 확인** | 같은 실행의 `rasterSeen != 0` 이고 그 안에 `0x100` 이 **없다** |
| 4 | 같은 크기로 재바인드 | `wasBound=1`, 수락 — 조합 (1,1) |
| 5 | **다른 크기로 재바인드** | 거절 — 조합 (1,0), `leave_accel` 이 돌고 `Mirror`·`ReleaseBuffer` 계수가 **는다** |
| 6 | 그 뒤 다시 그린다 | 픽셀이 여전히 stock 과 동일 |
| 7 | 문맥 **둘째** | 첫 문맥이 소유하므로 **거절**, 그리고 `wasBound` 가 0 인 채 거절 — 조합 (0,0) |
| 8 | 문맥 파괴 | `ReleaseBuffer` 계수가 또 는다(427 경로) |

그리고 **여섯 훅이 전부 실제로 불렸음**을 같은 실행의 계수로 요구한다:
`Buffer`·`BoundTo`·`Stride`·`AppBuffer`·`Mirror`·`ReleaseBuffer` **모두 > 0**(C8 이 `Stride`·
`AppBuffer` 의 자리를 말해준다 — 픽셀 스토어 이탈과 색 버퍼 조회).

### D. 하드웨어로 그리지 않았다 — **실행 중 관측**

정적 규칙(A1: `ctx->` 에 대입 없음)만으로는 §7 의 주장이 게이트를 갖지 못한다.  드라이버 자신이
모든 제출을 로그로 남기므로, 그것을 쓴다:

> 이 실행들 동안 커널 로그에 **`RDN-R7B submit` 줄이 0 개**다.

하드웨어에 무엇이든 보냈다면 그 줄이 생긴다.  픽셀 비교가 못 하는 인과를 이것이 준다.

### E. 스위치 (실기)

`RDNMesaAccelOff` 를 걸면 `Buffer` 수락 **0**, 매핑 **0**, 그림은 여전히 동일.

## 7. 이 칸이 하지 않는 것

- **하드웨어로 그리지 않는다** — `ctx->Driver.TriangleFunc` 는 여전히 건드리지 않는다.
- 깊이 표면을 대체하지 않는다(`DepthBuffer` 는 계속 거절) — 한꺼번에 켜지 않는다.
- 화면에 올리지 않는다.
- 드라이버를 바꾸지 않는다 → **재부팅을 쓰지 않는다**.

## 8. codex 교차검토 판정표 (회신 `kmxf9xma6`, 계획 단계·코딩 전)

인용 **전부 직접 열어 확인**했다.  그리고 그중 하나는 **내가 이 문서에 방금 쓴 사실이 틀렸다**는 것이었다.

| codex 주장 | 내 검증 방법 | 결과 |
|---|---|---|
| **`ReleaseBuffer` 는 406(leave_accel)과 427(DestroyContext) 두 곳에서 불린다** | 열었다 — 406 행이 `leave_accel` 의 마지막 줄이다.  **내 C7 은 427 만 적고 있었다**; 407 행에서 읽기를 멈춘 탓이다 | ✅ **채택 — 내가 틀렸다.**  C7 을 고쳤다 |
| `Buffer == NULL` 경로가 **둘**이고(`wasBound` 1/0), F 가 하나만 겨냥한다 | osmesa.c 553·561–576 대조.  맞다.  (F 를 "네 조합 전부" 로 고친 뒤였지만, **관측 없이 그림만 보는** 점은 그대로였다) | ✅ 채택 — C 의 8 단계에 `wasBound`·계수 관측을 넣었다 |
| `Stride`·`AppBuffer`·`ReleaseBuffer` 가 실제로 불렸다는 게이트가 없다 | `grep` 으로 호출 자리 확인: 742·744·889·406·427.  맞다 | ✅ 채택 — 여섯 훅 계수 > 0 요구, C8 에 자리를 적었다 |
| B3a/B3b 는 매핑의 **개수와 수명**을 제한하지 않는다 | §4 원문 대조.  맞다 — 한 자리를 여러 번 부르면 창이 여럿이 된다 | ✅ 채택 — B3b 를 "동시 살아있는 매핑 ≤ 1" 로 |
| §4 의 *"그 밖의 어떤 주소도 없다"* 는 과하다 — 앱 버퍼가 **인자로** 들어온다 | osmesa.c 561–567.  맞다 | ✅ 채택 — 주장을 "상수 주소 없음 + 매핑 하나 + 앱 버퍼는 넘겨받은 것뿐" 으로 |
| C·D·E·F·G 가 서로 다른 실행이라 실행마다 다르게 구는 구현을 못 막는다 | §6 원문.  맞다 — M1b 에서도 같은 지적을 받았고 이번엔 처음부터 나눠 써 버렸다 | ✅ 채택 — C·D·F·G 를 **한 승인 실행 8 단계**로 |
| *"하드웨어로 그리지 않는다"* 에 게이트가 없다 | §6·§7 대조.  정적 규칙 A1(`ctx->` 대입 금지)은 §6 A 안에 **있다**.  없는 것은 **실행 중 관측**이다 | ⚖️ **부분채택** — 정적 규칙은 이미 있었다.  없던 것을 더했다: **커널 로그에 `RDN-R7B submit` 0 줄**(드라이버가 모든 제출을 남기므로) |

**내가 찾은 것**: 하드웨어 미사용의 실행 중 증거로 **드라이버 자신의 로그**를 쓸 수 있다는 것은
codex 가 제안한 것이 아니다.  R7b 가 모든 제출에 한 줄을 남기게 해 두었으므로, 그 줄이 0 개라는
것이 *"아무것도 보내지 않았다"* 의 직접 증거가 된다.

## 9. 실기 — **M1c 완료** (빌드 `790030093`, 2026-09-22)

드라이버는 바꾸지 않았다.  Mesa 가 **카드의 오프스크린 VRAM** 에 그리고, `Mirror` 가 그것을
앱 버퍼로 되돌린다.  하드웨어 삼각형은 여전히 없다.

| 게이트 | 결과 |
|---|---|
| **A** 소스 규칙 | 규칙 9, 변이 **16/16** (`check_hook`) |
| **B1·B2** | 훅 10 개 text 심볼, 84 멤버 15 자 충돌 없음 |
| **B3a** | 미정의 심볼 **8 개**, 전부 허용 목록: `_open _close _ioctl _getenv _mmap _vm_allocate _task_self` + 링커 것 |
| **B3b** | `livemax=1` — 동시에 살아 있는 매핑이 둘이었던 적 없음 |
| **C** 한 승인 실행 | 아래 |
| **D** 하드웨어 미사용 | 커널 로그 `RDN-R7B submit` **17 → 17, 증분 0** |
| **E** 스위치 | `taken=0 maps=0`, 픽셀 세 버퍼 모두 stock 과 동일 |
| **F1·F2·F3** | 82 멤버 유지 +1, `osmesa.o` 만 다름, 전역 심볼 동일 |
| **G** | 색인으로 링크 |

### 한 승인 실행 (한 프로세스, 열두 단계)

```
bind1               taken +1   첫 바인드가 표면을 가져감
bind2               taken +1   같은 크기 재바인드도 가져감
getcolour/pixelstore           Stride·AppBuffer 가 불리는 두 경로(둘 다 BoundTo 뒤)
bind-second-refused taken +0   둘째 문맥은 못 가져감 -- OWNED
rebind1             taken +1   첫 문맥이 되찾음
bind3-refused       mirrors +1 크기 변경 거절 -> leave 경로가 미러하고
                    unmaps  +1 해제
destroy1            livemax=1  매핑은 끝까지 하나
```
픽셀 A·B·C **4096·4096·1024 전부 stock 과 동일**, 여섯 훅 **전부 실행**
(`Buffer=6 BoundTo=9 Stride=2 AppBuffer=2 Mirror=3 ReleaseBuffer=4`),
그리고 **`ALPHABUF_BIT` 이 켜졌다가(OR `0x0100`) 마지막 상태에서 사라졌다(`0x0000`)** —
M1b 의 측정이 여기서 닫혔다.

### 이 실행이 찾은 것 — 전부 내 설계 오류였다

| | |
|---|---|
| **미러가 그린 것을 버리고 있었다** | `Mirror` 가 `bound` 를 보는데, 거절 경로에서는 할당자가 **이미 바인딩을 놓은 뒤**라 늘 0 이다(osmesa.c 546-553).  조건을 "복사할 것이 있는가" 로 바꿨다.  첫 실행이 `mirrors=0 idle=1` 로 그걸 보여줬다 |
| **둘째 문맥 시험이 너무 늦었다** | 크기 거절 뒤에는 첫 문맥이 이미 표면을 놓았으므로, 둘째가 가져가는 것이 **옳다**.  `OWNED` 를 보려면 첫 문맥이 쥐고 있는 동안 물어야 한다 |
| **`Stride`·`AppBuffer` 를 한 번도 안 밟았다** | 둘 다 `BoundTo` 뒤에 있다(osmesa.c 741·888).  놓은 뒤에 불러서 0 이었고, *"여섯 훅이 진짜"* 가 실은 넷에 대한 주장이었다 |
| **`ALPHABUF` 를 누적 OR 로 물었다** | OR 은 커지기만 하므로 "사라졌는가" 를 원리상 답할 수 없다.  마지막 상태를 따로 기록한다 |
| 판정기의 절대 수치 | 시험에 단계를 더하니 넷이 깨졌는데 속성은 전부 성립했다 → **증분**으로 바꿨다 |

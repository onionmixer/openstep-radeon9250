## 1. M1x 가 잰 것 (한 조용한 팔, 제출 2,166 건)

커널 연산 **489.5 us/제출**:

| 구간 | us/제출 | 비중 |
|---|---:|---:|
| **stage2 ring** | 164.5 | **33.6 %** |
| **tail** | 153.5 | **31.4 %** |
| **stage1 ring** | 114.9 | **23.5 %** |
| preamble | 20.0 | 4.1 % |
| pixcache flush | 12.9 | 2.6 % |
| stage1 read-backs | 10.9 | 2.2 % |
| gates | 7.0 | 1.4 % |
| stage2 assemble | 5.8 | 1.2 % |

**내가 가장 유력하다고 적었던 stage1 되읽기는 2.2 % 였다** — 다섯 번째 빗나간 추정이다.

### 1-1. `tail` 은 `cpCheckBlock` 이고, 모형이 0.3 % 안에서 맞는다

그때의 `cpCheckBlock` 은 제출마다 **64 KiB 블록 전체를 워드 단위로** 훑었다
(지금은 §8 이 이 함수를 다시 썼고, 그 자리의 주석이 옛 모양을 적어 둔다 — `osrdn_cp.m:609-692`):
비-링 12,288 워드는 **워드마다 `cpBlockWord()` 를 부르고**, 링 4,096 워드는 `cpShadow`
와 하나씩 비교한다.  python 으로 영역별로 갈라 9.4 ns/워드를 곱하면:

| 영역 | 워드 | 비중 | ~us |
|---|---:|---:|---:|
| PTE(`osrdn_cp_pte` 호출) | 2,048 | 12.5 % | 19.3 |
| 가드 | 1,024 | 6.2 % | 9.6 |
| 예비 | 1,024 | 6.2 % | 9.6 |
| **카나리아** | **8,192** | **50.0 %** | **77.0** |
| 링 대 그림자 | 4,096 | 25.0 % | 38.5 |
| 합 | 16,384 | 100 % | **154.0** |

실측 `tail` 은 **153.5 us**.  **0.3 % 차이** — 이 구간이 무엇인지에 의문의 여지가 없다.

## 2. 세 후보 — 그리고 검사가 순위를 뒤집었다

| | 크기 | 안전 성질 | 판정 |
|---|---:|---|---|
| ① 1·2 단계를 한 번의 링 쓰기로 | 115 us | **바뀐다**(§3·§4), 그리고 §6 이 커널 변경 **아홉 개**를 찾아냈다 | **이 칸에서는 안 한다 — 분석만 남긴다** |
| ② `cpCheckBlock` 의 카나리아를 매 제출에서 빼기 | 77 us | **약해진다** — 카드가 링 밖에 쓴 것을 늦게 본다 | **안 한다**([[checker-discipline]]) |
| **③ `cpCheckBlock` 을 영역 루프로 — 비교는 한 건도 안 줄이고 워드당 함수 호출을 없앤다** | **미측정, 최대 154 us 중 상당** | **하나도 안 바뀐다** — 같은 입력에 같은 일곱 값 | **이 칸이 한다** |

③ 이 ① 보다 나은 이유는 크기가 아니라 **되돌릴 수 있음**이다.  ③ 은 인터페이스도,
링 산술도, 검증기도, `zstage` 도 건드리지 않는다.  같은 결과를 더 빨리 낼 뿐이고,
그것은 **호스트에서 증명할 수 있다**.

## 3. ① 이 바꾸는 것 — 전수로 센다

지금:

    1 단계: 프리픽스 13 워드 → 링 → 도어벨 → cpWait(RPTR) + cpWait(IDLE)
            → SCRATCH_REG0 되읽기 + 프리픽스 레지스터 9 개 되읽기
            → 둘 중 하나라도 어긋나면 CP_RC_CHECK_FAILED, **클라이언트 워드는 안 나간다**
    2 단계: 클라이언트 워드 + 꼬리 → 링 → 도어벨 → 대기 둘 → 픽스캐시 → 되읽기

합치면:

    한 번: 프리픽스 + 클라이언트 워드 + 꼬리 → 링 → 도어벨 → 대기 둘
           → 되읽기(프리픽스 검증 + 마커) → 픽스캐시 → 되읽기

| 걸려 있는 것 | 합친 뒤 |
|---|---|
| **프리픽스가 안 먹었으면 그리지 않는다** | **그리고 나서 안다.**  이것이 이 칸이 바꾸는 유일한 성질이고, §4 가 그것을 다룬다 |
| 프리픽스 레지스터 9 개 되읽기 | 그대로 한다 — 2.2 % 이고 값이 아니다 |
| 마커(`SCRATCH_REG0 == seed`) | 그대로.  다만 이제 **한 스트림 안에서** 프리픽스 뒤, 클라이언트 워드 앞에 놓인다 |
| 링 자리 | 합치면 한 번에 `13 + 2 + subWords + 10` 워드.  n=72 에서 1,141 워드, 패딩해 1,152 — python 으로 최악을 계산해 §5 에 |
| `zstage` 1/2 의 구분 | 3 은 남고 1·2 는 하나가 된다.  판정기가 `zstage` 를 읽는 자리를 전수로 고쳐야 한다 |

## 4. 프리픽스 검증 순서 — 무엇을 잃나

지금은 프리픽스가 레지스터에 **먹은 것을 확인한 뒤에야** 클라이언트 워드를 낸다.
합치면 둘이 한 스트림이라 확인은 **그린 뒤**가 된다.

**잃는 것**: 프리픽스가 안 먹은 채 클라이언트 삼각형이 그려지는 한 번의 제출.
**잃지 않는 것**: 그 사실을 아는 것 — 되읽기는 그대로 하고, 어긋나면 `failed` 를 걸어
**다음 제출부터 막는다**.  그림도 그 제출만 틀린다.

**이것이 받아들일 만한지**가 이 칸의 유일한 판단이고, 근거는 셋이다:

1. 프리픽스는 **우리가 만든 13 워드의 레지스터 쓰기**다.  클라이언트가 못 건드린다.
2. 실기에서 `prefixBad` 가 0 이 아니었던 적이 **한 번도 없다** — 로그를 전수로 세어 확인한다(§5).
3. 그리고 이것은 **손잡이 뒤에 둔다**: 기본은 오늘 그대로 두 단계, 클라이언트가 켜야 합친다.

## 5. 코딩 전 검사 — 전부 돌렸다

### 5-1. 프리픽스가 실기에서 실패한 적이 있나 — **없다, 7,068 건 전수**

    files scanned          : 155
    zclear verdict lines   : 7,068
    prebad values seen     : {'00': 7068}
    lines with prebad != 00: 0

`RDN-R6 zclear ... prebad=` 를 `build/` 아래 모든 `.drv`·`.log` 에서 python 으로 셌다.
**한 번도 0 이 아닌 적이 없다.**  §4 의 판단은 이 수 위에 선다.

### 5-2. 합친 스트림의 크기 — **여기서 계획이 틀린 것을 찾았다**

먼저 정정: 프리픽스는 **13 워드가 아니라 13 쌍, 즉 26 워드**다(R7 케이스;
R6 케이스는 11 쌍 22 워드).  `osrdn_cp.m:3229-3253` 을 세어 확인했다.
`build/r7/design3.py` 는 `PREFIX_WORDS = 22` 로 이미 맞게 적고 있었다.

그리고 `CP_R7_BATCH_MAX` 의 주석이 경고하고 있었다(`osrdn_cp.h:284-290`):
"드라이버의 10 워드 꼬리까지 **모든 write pointer 에서** 링에 들어가고,
**16 워드 더는 안 들어간다**".

`cpR6Submit` 을 그대로 python 으로 옮겨 모든 write pointer 에 대해 돌렸다
(`build/r7/design7.py`, 닫힌 형태를 링 64·128 에서 전수 대조해 PASS):

    today, the prefix alone   n=  26 roundup16=  32  unsafe write pointers:    0
    today, stage 2 alone      n=2028 roundup16=2032  unsafe write pointers:    0
    MERGED, full batch        n=2054 roundup16=2064  unsafe write pointers:   31  p in [2033, 2063]

규칙은 닫힌 형태로 나온다: **`roundup16(n) <= 2048` 이면 모든 시작점에서 안전**.
넘으면 끝까지 채운 PACKET2 패딩 위로 스트림 워드가 되감겨 덮어써지고, 카드는
`p` 부터 읽으므로 **PACKET2 자리에서 스트림 워드를 순서 밖으로 읽는다**.
`cpR6Submit` 에는 `len <= CP_RING_WORDS` 검사가 **없다**.

    biggest client batch the MERGED path takes from every pointer: 2010 words
      CP_R7_BATCH_MAX is 2016 -- the merge must lower it by 6 (a caps-visible change)
    the driver's array: merged worst 26 + 2016 + 12 = 2054;  CP_R6_WORDS 2064;  margin 10

즉 합치면 **클라이언트에게 보이는 상한을 2016 → 2010 으로 낮춰야** 하고,
배열 여유는 (23 이 아니라) **10 워드**가 된다.

### 5-3. `zstage` 를 읽는 자리 — 전수, **6 파일 13 줄** (8 이 아니었다)

python 으로 `.git`·`build/`·`ref/` 를 뺀 저장소 전체를 훑었다:

| 자리 | 하는 일 | 합친 뒤 |
|---|---|---|
| `osrdn_cp.h:566` | 필드 선언과 주석 `(1 prefix, 2 draw, 3 read)` | 주석을 고쳐야 한다 |
| `osrdn_cp.m:3254` | `c->zstage = 1;` (프리픽스 제출 직전) | 합친 경로에선 안 쓴다 |
| `osrdn_cp.m:3503` | `c->zstage = 2;` | 합친 경로의 첫 표시 |
| `osrdn_cp.m:3520` | `c->zstage = 3;` | 그대로 |
| `osrdn_cp.m:4150` | 연산마다 `c->zcase = c->zstage = 0;` | 그대로 |
| `osrdn_modelog.m:406` | `RDN-R6 zclear ... stage=%d ... prebad=%02x` | 그대로 — **판정기는 이 줄만 읽는다** |
| `world5.c:2287` | 정상 경로가 `zstage == 3` 로 끝나는지 | 그대로 통과해야 한다 |
| `world5.c:2519` | **프리픽스를 떨어뜨리면 `zstage == 1` 이고 `r6Draws == w0`** | **이 칸이 바꾸는 바로 그 성질** |
| `world5.c:2296`, `world5.c:2520` | 위 둘의 실패 메시지 | |
| `R6E_PLAN.md:206` | 연산마다 지워진다는 기록 | 그대로 |

**판정기(`judge_m1l.py`·`sim_r6.py`)에는 `zstage` 가 한 줄도 없다** — §3 표의 "판정기가
`zstage` 를 읽는 자리를 전수로 고쳐야 한다" 는 **틀렸다**.  고칠 곳은 드라이버 셋,
헤더 주석 하나, 호스트 시뮬 시험 하나다.

#### `world5.c:2519` — 짝을 지어야 한다

    EXPECT(rc == CP_RC_CHECK_FAILED && C.why == CP_WHY_PREFIX && C.zstage == 1 &&
           (C.prefixBad & 1UL) && r6Draws == w0 && C.failed && !C.latched, ...)

이 시험이 **"프리픽스를 잃으면 아무것도 안 그린다"** 를 증명하고 있다(`world5.c:2511-2519`).
합치면 손잡이가 켜졌을 때 `r6Draws == w0` 이 **설계대로** 깨진다.  그러므로:

- 손잡이 **끔**(기본): 이 시험은 **글자 하나 안 바꾸고 그대로 통과해야** 한다.
- 손잡이 **켬**: 짝 시험을 새로 둔다 — `rc == CP_RC_CHECK_FAILED`, `why == CP_WHY_PREFIX`,
  `prefixBad & 1`, `failed`, 그리고 **`r6Draws > w0`**(그렸다는 것을 시험이 못 박는다),
  이어서 **다음 연산이 `CP_WHY_FAILED` 로 거절**되는 것까지.

마지막 항은 소스에서 확인했다: `osrdn_cp.m:3045-3046` 이 `cpZclear` 의 문턱에서
`if (c->failed) return cpRefused(c, CP_WHY_FAILED, 0);` 를 한다.  걸쇠는 종결적이다
([[failure-latch-must-be-terminal]]).

## 6. 검사가 **설계를 깨뜨리는 것**을 찾았다 — 클라이언트가 프리픽스 레지스터를 덮는다

§3 은 합치는 비용을 "도어벨 하나와 대기 한 쌍" 이라고 적었다.  **틀렸다.**

프리픽스 되읽기가 보는 9 개 레지스터(`osrdn_cp.m:2293-2297`)와, 클라이언트가 쓸 수 있는
41 개 레지스터(`cpR7Allow`)를 python 으로 교차했다:

| 프리픽스 레지스터 | 주소 | 걸리나(`CP_R6_PRE_GATE`) | 클라이언트가 쓸 수 있나 |
|---|---|---|---|
| `RB3D_DEPTHOFFSET` | 0x1c24 | **예** | **예** |
| `RB3D_DEPTHPITCH` | 0x1c28 | **예** | **예** |
| `RB3D_COLOROFFSET` | 0x1c40 | **예** | **예** |
| `RB3D_COLORPITCH` | 0x1c48 | **예** | **예** |
| `RB3D_DEPTHXY_OFFSET` | 0x1d60 | **예** | **예** |
| `SE_VAP_CNTL_STATUS` | 0x2140 | 아니오 | 예 |
| `PP_CNTL_X` | 0x2cc4 | 아니오 | 예 |
| `PP_TXMULTI_CTL_0` | 0x2c1c | 아니오 | 예 |
| `SE_VTX_STATE_CNTL` | 0x2180 | 아니오 | 예 |

**아홉 개 전부 클라이언트가 쓸 수 있고, 걸리는 다섯 개도 전부 그렇다.**
`cpR7Verify` 는 이 중 넷(`coff`·`cpitch`·`zoff`·`zpitch`)을 **이름으로 추적하기까지 한다**
— 정상적인 클라이언트 스트림이 실제로 쓴다는 뜻이다(M1c 가 표면을 옮겼다).

### 6-1. 그래서 순진하게 합치면 무슨 일이 일어나나

    합친 스트림:  프리픽스(COLOROFFSET=A ...) → 클라이언트(COLOROFFSET=B ...) → 그리기 → 꼬리
    그 뒤 되읽기: COLOROFFSET 은 B 다.  cpR6PreWant 는 A 를 기대한다.
                  prefixBad |= 1<<2, 이는 게이트 0x10f 안 → c->failed = 1

`c->failed` 는 종결적이다(`osrdn_cp.m:3045-3046`).  **부팅이 끝날 때까지 모든 ZCLEAR 이
`CP_WHY_FAILED` 로 거절된다.**  그것도 오류 경로가 아니라 **평범한 경로**에서.
재부팅 한 번을 태우고, 하드웨어 고장처럼 보였을 것이다.

### 6-2. 고치는 방법 — 기대값을 "유효값" 으로

되읽기를 없애지 않는다.  **기대값을 바꾼다**: 각 레지스터에 대해

    기대값 = 검증된 클라이언트 스트림이 그 레지스터에 마지막으로 쓴 값,
             없으면 프리픽스가 쓴 값(오늘의 cpR6PreWant)

`cpR7Verify` 는 이미 스트림을 워드 단위로 걸어 `reg`·`val` 을 본다.  9 개짜리
`preLast[]` + `preSeen` 비트마스크를 채워 내보내면 된다 — 지금은 지역 변수라 밖으로
안 나올 뿐이다.

이렇게 하면 성질이 **약해지지 않고 오히려 는다**:

| | 오늘 | 합친 뒤 |
|---|---|---|
| 클라이언트가 **안 건드린** 레지스터 | 프리픽스 값을 확인 | **같다** |
| 클라이언트가 **덮은** 레지스터 | **아무것도 확인 안 한다**(되읽기가 클라이언트 워드 전에 끝난다) | **클라이언트가 말한 값이 실제로 들어갔는지 확인한다** |

오늘 프리픽스 값을 확인하는 것은 클라이언트가 덮을 레지스터에 대해서는 **의미가 없다** —
그리기 때의 값이 아니기 때문이다.  유효값 대조가 정확히 그리기 때의 값을 본다.

### 6-3. 마커는 안전하다

`SCRATCH_REG0`(0x15e0)과 `SCRATCH_REG0+8`(0x15e8)은 **`cpR7Allow` 41 개에 없다**(python 으로
확인).  클라이언트가 못 쓴다.  그러므로 `zreg0 == seed`(프리픽스가 소비됐다)와
`zreg2 == ~seed`(스트림이 끝까지 돌았다)는 합친 뒤에도 그대로 뜻을 갖는다.

### 6-4. 이 발견이 §2 의 셈을 바꾸나

바꾼다.  ① 은 "도어벨 하나" 가 아니라 **검증기에 상태를 하나 더 얹는 일**이다.
그래도 ② 보다는 낫다 — ② 는 카나리아를 **약화시키고**, ① 은 §6-2 대로면 검사를
**정밀화한다**([[checker-discipline]]).  값도 115 us 대 77 us 로 ① 이 크다.

## 7. codex 교차검토 — 판정표

물은 것: "§6-2 의 고침이 있다고 할 때, 두 제출이 하나가 되면 `cpZclear`/`cpR6Submit` 에서
**또 무엇이 조용히 바뀌나**" — (a) `cpR6Submit` 이 쓰는 필드, (b) 링 산술, (c) 두 제출 사이의
일, (d) `zstage`.  회신은 결론이 아니라 입력이다([[codex-cross-review-practice]]).

## 8. 그래서 이 칸이 하는 일 — `cpCheckBlock` 을 영역 루프로

`cpCheckBlock` 은 제출마다 12,288 워드를 훑으면서 **워드마다 `cpBlockWord()` 를 부른다**
(그 줄은 이제 없다 — 새 함수의 머리 주석이 옛 모양을 적어 둔다, `osrdn_cp.m:609-692`).
`cpBlockWord` 은 `off` 를 네 구간과 비교해 분기하고, 첫 구간에서는 `osrdn_cp_pte()` 를
**한 번 더** 부른다(`osrdn_cp.m:587-600`) — 그 함수는 남는다, `cpFillBlock` 이 아직
쓴다(`osrdn_cp.m:709`).

그런데 기대값은 영역마다 **닫힌 형태**다:

| 영역 | 워드 | 기대값 |
|---|---:|---|
| PTE | 2,048 | `e<4` 네 개와 `e==4` 하나만 특별하고, **나머지 2,043 개는 같은 상수**(`(phys+0x2000) & ~0xfff`) |
| 가드 | 1,024 | `CP_GUARD_HEAD` 와 `CP_PACKET2` 가 번갈아 |
| 예비 | 1,024 | `0x5b000000 \| i` (`osrdn_cp.m:162`) |
| **카나리아** | **8,192** | `0xc4000000 \| i` (`osrdn_cp.m:163`) — **블록의 50 %** |

그러므로 하나의 워드 루프를 **네 개의 영역 루프**로 가르면, 워드당 호출 하나와
분기 네 개가 **증분 하나와 비교 하나**가 된다.  **비교는 한 건도 줄지 않는다.**
`tableBad`·`guardBad`·`spareBad`·`canaryBad`·`pteSum`·`pteXor`·`ringBad` 일곱 값이
모두 같은 입력에 같은 값을 내야 하고, 그것이 이 칸의 게이트다.

### 8-1. 왜 이것이 ① 보다 안전한가

| | ① 합치기 | ③ 영역 루프 |
|---|---|---|
| 클라이언트에게 보이는 상한 | **2016 → 2010** | 안 바뀐다 |
| 검증기(`cpR7Verify`) | 새 거절 사유 + `preLast[9]` 반출 | 안 건드린다 |
| 링 산술 | 하나의 제출로, 새 상한 증명 필요 | 안 건드린다 |
| 프리픽스 게이트 | **그리기 뒤로 간다**(§4·§7) | 안 건드린다 |
| `zstage` 실패 귀속 | 잃는다 | 안 바뀐다 |
| 호스트에서 증명 가능한가 | 아니다 — 카드의 순서가 걸려 있다 | **그렇다 — 순수 함수다** |

#### 8-2-1. 등가를 어떻게 증명했나 — 참조 복사본이 아니라 **모델**로

계획은 옛 루프를 `cpCheckBlockRef` 로 남겨 나란히 돌리자고 했다.  **그렇게 하지 않았다.**
커널에 같은 일을 하는 코드를 둘 두면 둘 다 틀릴 수 있고, 텍스트도 늘어난다.
대신 호스트 시뮬(`world5.c`)에 **배치에서 새로 쓴 워드 단위 모델**을 두었다:

- `m1yWant(off)` — 영역별 기대값.  `cpBlockWord` 를 베끼지 않았다.
- `m1yModel(...)` — 옛 루프의 **모양 그대로** 블록을 한 워드씩 걸어 일곱 값을 낸다.

시험은 블록을 망가뜨리고 `CP_OP_RECORD`(이것이 `cpCheckBlock` 을 부른다)를 돌린 뒤
드라이버의 일곱 값과 모델의 값을 대조한다.  경우는:

| 경우 | 수 | 무엇을 잡나 |
|---|---:|---|
| 각 영역의 **경계 양쪽**과 양 끝 (표 6·가드 4·예비 4·카나리아 4) | 18 | 분할의 off-by-one |
| 링 안(건너뛰는 구간)의 워드 | 3 | 카나리아로 세면 안 되고 `ringBad` 로 가야 한다 |
| 깨끗한 블록 | 1 | 거짓 양성 |
| 비-링 **전부** 손상 | 1 | 각 영역의 **크기**(2048/1024/1024/8192)를 모델과 대조 |
| 링 **전부** 손상 | 1 | `ringBad == 4096` |
| PTE 의 **여섯 구별값 각각** 하나씩 | 6 | `e<4`·`e==4`·`e>=5` 를 뭉개는 분할 |
| **합** | **30** | 30 번의 `CP_OP_RECORD`, 매번 일곱 값 전부를 대조 |

#### 8-2-2. 변이 — 검사가 **발동한다**는 증거

`sim_r5.py` 에 여덟을 넣었고 전부 잡힌다:

    ok  M1y: the canary is indexed by the ABSOLUTE word, not the region-relative one
    ok  M1y: the canary loop stops one word short
    ok  M1y: the spare is indexed by the ABSOLUTE word
    ok  M1y: the guard's two words are swapped
    ok  M1y: the table folds entry 4 into the repeated value
    ok  M1y: the inlined ring-page arithmetic drifts from osrdn_cp_pte
    ok  M1y: the canary loop starts one word late (a clean block hides it)
    ok  M1y: the table skips entry 5 (a clean block hides it)

앞의 여섯 중 다섯은 **MAP 이 먼저 잡는다**(`cpMap` 도 `cpCheckBlock` 을 부르고 0 이
아니면 거절한다, `osrdn_cp.m:717`).  그래서 마지막 둘을 일부러 넣었다: **깨끗한 블록에는
보이지 않아** MAP 이 못 잡고, 오직 이 절의 적대적 블록만이 잡는다.  실제로 그렇게
보고된다 — `FAIL m1y 08000: ...`, `FAIL m1y 00000: ...`.

#### 8-2-4. 소스가 아니라 **실린 바이트**로 확인했다

`tools/r5/calls_in.py` 를 새로 써서 설치한 reloc 의 심볼 경계를 잡고 역어셈블했다:

    _cpCheckBlock        0x0084b4    436 B   calls: 1   ['_cpRing']
    _cpBlockWord         0x008434    108 B   calls: 1   ['_osrdn_cp_pte']
    _cpFillBlock         0x008668    220 B   calls: 4   ['_cpRing', '_cpBlockWord', '_cpCheckBlock', '_cpRefuse']

전에는 `_cpCheckBlock` 이 루프 안에서 `_cpBlockWord` 를 **12,288 번**, `_cpRing` 을
**4,096 번** 불렀다.  이제 **제출당 호출 하나**다 — `_cpRing` 도 루프 밖으로 나왔다.
**16,384 → 1.**

이 확인에서 두 번 틀렸고 둘 다 도구에 적어 두었다: 심볼표의 STAB 항목을 함수
경계로 읽어 "9 바이트짜리 함수"가 나왔고, `objdump` 의 stderr 를 버려서 실패한 실행이
**모든 함수에 대해 calls: 0** 이라는 자신만만한 오답을 냈다
([[checker-discipline]] 의 같은 모양).

#### 8-2-3. 이 변경이 새로 만든 위험 하나

`cpCheckBlock` 이 이제 `osrdn_cp_pte` 를 **부르지 않고 산술을 복제한다**.  둘이
갈라질 수 있다 — 옛 코드에는 없던 위험이다.  그래서 모델은 그 한 자리만은
`osrdn_cp_pte` 를 직접 부르고(`world5.c` 의 `m1yWant`), 변이
"the inlined ring-page arithmetic drifts from osrdn_cp_pte" 가 갈라짐을 잡는 것을
보였다.

### 8-3. ① 은 어디에 남나

§3~§7 이 그 분석이다.  다시 손대려면 커널 변경 **아홉 개**(§6·§7)를 한 묶음으로
해야 하고, 그중 둘(`CP_R7_BATCH_MAX`, 그리기 뒤 프리픽스 검증)은 되돌릴 수 없는
인터페이스·성질 변경이다.  **크기가 아니라 그것 때문에 미룬다.**

한계비 2.043 → 2.040 us/삼각형은 **안 움직였다**: 이 변경은 제출당이지 삼각형당이 아니므로
그래야 맞다.

18.6× ↔ 20.9× 로 흔들리지만 그것은 이 변경과 무관하다 — 판정기도 두 체제를 그렇게 표시한다.
이 칸의 값은 **조용한 팔의 고정비**에서 읽는다.

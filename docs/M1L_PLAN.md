# M1l — 빨라졌는가 (계획)

기준일 2026-09-22.  선행: M1k 완료(`docs/M1K_PLAN.md` 14).

M 사다리는 **속도를 위해** 존재하는데 열한 칸 동안 속도를 한 번도 재지 않았다.
가속이 소프트웨어보다 느릴 가능성은 추측이 아니다 — **우리가 전에 그것을 측정한
적이 있다**(아래 N4).  그러니 이 칸은 새 기능이 아니라 **측정**이다.

**측정 설계보다 먼저 읽었다.**  이번에는 참고를 세 갈래로 동시에 읽었다: Mesa 6.5.3
의 r200 DRI, radeon DDX/DRM, 그리고 **우리가 먼저 만든 Matrox 드라이버**.  아래
N1–N6 은 그 결과이고, 전부 원문을 열어 확인했다(인용은 `check_citations` 가 대조한다).

## 1. 참고가 이미 답한 것 — 재지 않는다

| | 사실 | 확인한 곳 |
|---|---|---|
| N1 | **우리 제출은 동기다.**  WPTR 을 쓴 뒤 RPTR 이 따라올 때까지, 그리고 idle 까지 스핀한다 | `osrdn_cp.m:2417-2441` |
| N2 | **참고 구현은 그러지 않는다.**  r200 은 `drmCommandWrite(DRM_RADEON_CMDBUF)` 를 부르고 **그냥 돌아온다** — 제출당 GPU 대기가 0 이다 | `r200_ioctl.c:145-148` |
| N3 | **드라이버가 이미 제출당 대기 시간을 마이크로초로 남긴다** — `cpWait` 가 `IOGetTimestamp` 로 재서 `w->us` 에 넣고, 로그가 `rptr=evals/limit/us` 로 찍는다 | `osrdn_cp.m:231-260`, `osrdn_modelog.m:473-481` |
| N4 | **이 문제를 전에 측정했다(Matrox).**  제출당 **85.4 us 고정** + 132.4 ns/dword, 그리고 **엔진 일은 프레임의 1% 미만** | `REMAINING_WORK.md:2853`, `M2_MESA_WARP_CONNECTION.md:57` |
| N5 | 같은 프로젝트에서 **오프스크린 가속이 소프트웨어보다 480 배 느렸고**, 되읽기를 좁힌 뒤에도 **12.1 배 느렸다** | `M19_MIRROR_COST_PLAN.md:1`·`:18`, `M21_NARROWED_MIRROR_PLAN.md:152-154` |
| N6 | OPENSTEP `gettimeofday` 는 **분해능 4 us, 호출 한 쌍이 4 us**; 벽시계라 **평균 말고 중앙값**; 계측은 **제출이 잦은 쪽에 더 무겁게 과금**된다 | `REMAINING_WORK.md:2486`, `openstep-mga-mesa-tiercost.c:30-32` |

**N1 과 N2 를 나란히 놓은 것이 이 칸의 출발점이다.**  참고는 제출을 던져 놓고 가고,
우리는 매 제출마다 카드가 다 그릴 때까지 기다린다.  그것은 R5 에서 **일부러** 고른
안전장치(읽어서 확인한 것만 진실로 친다)이고, 이 칸은 그 선택의 **값**을 숫자로 만든다.

**N4·N5 가 재는 대상을 바꾼다.**  "카드가 소프트웨어보다 빨리 래스터하는가" 는
물을 필요가 없다 — Matrox 에서 **소프트웨어 래스터라이저가 더 빨랐다**.  물어야 할 것은
**비용 모델**이다: 제출 한 번의 고정비와 삼각형 하나의 한계비.

## 2. 이 칸의 한 줄

**제출 한 번이 얼마이고, 삼각형 하나가 얼마인지를 잰다** — 그리고 M1k 의 배치가
그 고정비를 실제로 몇 번이나 아꼈는지 센다.

## 3. 무엇을 재는가

    t(n) = a + b·n        n = 한 제출에 든 삼각형 수

- **a** = 제출 고정비.  우리 경우 그 대부분이 **드레인+idle 대기**여야 한다(N1).
- **b** = 삼각형당 한계비(워드를 링에 넣고 카드가 그리는 시간).
- 적어도 **세 개의 n** 에서 재야 직선이 맞는지 알 수 있다.  최소자승은 python 으로.

그리고 **a 를 쪼갠다**.  이것이 N3 덕에 공짜로 되는 부분이다:

| 층 | 어디서 읽나 |
|---|---|
| 벽시계 제출 시간 | 응용의 `gettimeofday` |
| 그중 카드를 기다린 시간 | 드라이버 로그의 `rptr=…/…/us` 와 `idle=…/…/us` |
| 나머지 | ioctl·open/close·스트림 작성 |

세 층의 합이 맞지 않으면 그 자체가 결과다(Matrox 에서 "구간 합 ≠ 프레임 시간"이
54 fps 와 12 fps 를 갈랐다).

## 4. 이 칸이 하지 않는 것

- **제출을 비동기로 바꾸지 않는다.**  그것은 드라이버 변경이고 재부팅이며, 무엇보다
  **측정하지 않은 병목을 없애는 일**이다.  이 칸이 그 병목을 먼저 숫자로 만든다.
- **화면 전달을 재지 않는다.**  우리 시험은 오프스크린이고, Matrox 의 4.4 배는 전부
  전달 경로에서 나왔다(`M21_NARROWED_MIRROR_PLAN.md:265-266`).  전달은 별개의 칸이다.
- **계측을 켠 채로 판정하지 않는다**(N6).  판정 수치는 계측 없는 실행에서 나온다.

## 5. 코딩 전에 답해야 할 것

| | 질문 | 어떻게 답할 것인가 |
|---|---|---|
| P1 | 한 실행에 제출을 몇 번까지 할 수 있나?  커널 msgbuf 는 4 KB 이고 제출마다 로그가 여러 줄이다 — 넘치면 **앞이 잘린다** | 로그 줄 길이를 세어 python 으로 상한을 계산하고, 벽시계 팔과 드라이버 팔의 실행을 **분리**한다 |
| P2 | 배치를 끄는 손잡이는 어떻게 만드나 | 씨앗과 같은 방식(환경 변수)으로.  끄면 M1i 의 단발 경로를 그대로 쓴다 — 이미 있는 코드라 새 위험이 없다 |
| P3 | `n` 을 어디까지 올리나.  M1k 의 상한은 민짜 131 이고, VB 한 번은 최대 216 정점이다 | python 으로 겹치는 구간을 계산해 세 점을 고른다; 131 을 넘기려면 프레임을 나눠야 한다 |
| P4 | 중앙값을 내려면 표본이 몇 개 필요한가, 그리고 한 실행이 180 초 안에 끝나나 | N4 의 85 us 고정비를 우리 대기 시간 상한(`C_RPTR_US` 100 ms)과 함께 python 으로 풀어 상한 시간을 낸다 |

## 6. 측정 전에 측정이 끝났다 — 내 가설이 먼저 반증됐다

§3 은 "`a` 의 대부분이 드레인+idle 대기여야 한다"고 썼다.  **틀렸다.**

지난 실행들이 남긴 드라이버 로그가 이미 답을 갖고 있었다.  `build/` 아래 로그
153 개에서 `RDN-R5 wait` 줄 **6,339 개**를 뽑아 연산별로 갈랐다(python):

    op          n     rptr 중앙   rptr 평균   rptr 최대   idle 최대   len 중앙
    ZCLEAR    837         6        9.8        110         5        153
    SUBMIT     31        51       44.4         53         5       1024
    NEGCTL      3      2004     2003.7       2004         0          0
    ZPREP     837         0        0.0          0         0          0
    PLANE    3786         0        0.0          0         0          7

**그런데 이 ZCLEAR 행은 섞인 모집단이었다.**  로그의 `len=` 은 워드 수가 아니라
**케이스 번호**다(`cpZclear(c, base, arg, len)` 의 넷째 인자가 `zc` 다).  R6 사다리가
케이스 1..170 을 재는 데 같은 연산을 썼고, **클라이언트 제출은 `zc = CP_R7_CASE = 171`
하나**다(`osrdn_cp.h:285-290`).  갈라 보면:

    zc      n     rptr 중앙  rptr 평균  rptr 최대
    171   118        0.0       0.7        6      <- 클라이언트 제출 (M1d..M1k)
    162    54       52.0      52.6      110      <- R6l 배치 측정
    161    57       31.0      22.4       33
      6    58        6.0       6.1        7

**우리 클라이언트 제출이 카드를 기다리는 시간은 중앙값 0 us, 최대 6 us 다.**
섞어 세면 6 us 였고 갈라 세면 0 us 다 — 결론은 같지만 **더 강해진다**: 동기 제출이라는
설계는 값이 거의 안 나가고 있었다.  (`len=` 을 워드 수로 읽었다면 "153 워드 스트림"
이라는 없는 사실을 보고할 뻔했다.)

그러므로 제출 고정비는 다른 데 있다.  후보는 셋이고 전부 우리 쪽이다:

1. **제출마다 노드를 열고 닫는다**(`OSRDNMesaTri.c` 의 `triOpen`/`close`) — 드라이버의
   걸쇠가 한 번에 한 홀더만 허용해서 그렇게 만들었다.
2. ioctl 자체(블록 복사, 디스패치).
3. **커널이 스트림의 모든 워드를 검증한다**(`cpR7Verify`) — 이것은 `a` 가 아니라 `b` 다.

**이 표는 실기 실행 0 회로 얻었다.**  M1i 가 실기 셋을 태워 알아낸 것이 소스에 있었던
것과 같은 일이다([[read-the-reference-before-measuring]]).

> **M1q 의 정정(2026-09-23).**  위 118 건을 다시 세어 보니 **전부 17..57 워드**, 즉
> 삼각형 1~3 개짜리 제출이었다.  `build/` 전체에서 `RDN-R7B stage words=` 와 그 뒤
> `wait` 줄을 짝지으면 16 쌍이 나오고 역시 모두 57 워드 이하다.  **n=72(1,082 워드)
> 에서는 아무도 재지 않았다** — M1 사다리 로그에는 `RDN-R5 wait` 줄이 한 줄도 없다
> (python 으로 확인: 파일 0 개).  그러니 이 절의 결론은 **잰 자리에서만** 참이다.
> M1q 의 격자 팔이 그 빈 자리를 잰다(docs/M1Q_PLAN.md 7).

## 7. codex 교차검토 (계획 단계, 코딩 전)

물은 것 하나: *"제출 시간을 n 에 대해 재서 t(n)=a+bn 을 맞추면 a 는 제출 고정비,
b 는 삼각형 한계비이고, 드라이버가 찍는 대기 us 를 a 에서 빼면 카드 대기분이 나온다."*

| codex 주장 | 내 검증 (python) | 판정 |
|---|---|---|
| 스트림은 `W(n)=48+15n`(민짜)·`56+21n`(텍스처) 워드, 상한은 131·93 | 재계산: 131→2013, 132→2028; 93→2009, 94→2030.  정확 | ✅ |
| 사용자 버퍼가 4 KiB 페이지를 처음 넘는 곳은 민짜 **n=66**(B(65)=4092, B(66)=4152), 텍스처 **n=47** | 재계산해 같은 수 | ✅ |
| 시계: 1 % 는 `t ≥ 400 us`, 10 % 는 `40 us`; 호출 쌍 4 us 는 **`a` 만** 위로 민다 | `4/0.01=400`, `4/0.10=40`.  상수 오프셋이 절편에만 들어가는 것도 맞다 | ✅ |
| **`a` 에서 로그 대기를 빼는 것은 통계적으로 틀렸다** — `a` 는 외삽된 계수이고 로그 대기는 특정 `n` 의 표본이다.  표본마다 짝지어 `t−R−I` 를 따로 적합해야 한다 | 논리가 맞다.  설계를 그렇게 고친다 | ✅ 채택 |
| `b` 는 "삼각형 비용"이 아니라 **그 장면·그 경로의 한계 벽시계**다(복사·검증·래스터·메모리 트래픽이 전부 들어간다) | 우리 경우 `cpR7Verify` 가 워드마다 도는 것을 확인했으니 사실이다 | ✅ 채택 — 보고 문구를 그렇게 쓴다 |
| 가장 큰 **조용한 오류**는 커널 메시지 버퍼(4084 B)가 감긴 뒤 드라이버 기록과 사용자 표본을 **엉뚱하게 짝짓는 것**.  일련번호를 양쪽에 넣어 막아라 | 실측으로 더 나쁘다: ZCLEAR **한 번이 24 줄·2024 B**(중앙값)라 msgbuf 에는 **두 개**밖에 안 들어간다.  다만 우리 로그는 **syslog 로 빠져나가므로** 594 개가 온전히 남아 있었다 | ⚖️ 부분채택 — 일련번호는 넣되, 한계는 msgbuf 가 아니라 **syslogd 가 굶는가**다 |
| 10 us 폴링 간격이 대기 값을 계단으로 만든다 | 실측 `(evals, us)` 쌍이 그대로 보인다: 1→4..10 us, 2→25..29 us | ✅ |

**내가 틀렸던 것**: §3 의 "고정비 대부분이 카드 대기" (위 6 절).  codex 가 짚은 것이
아니라 로그가 짚었다.

## 8. 그래서 다시: 모르는 것은 카드가 아니라 우리 쪽이다

카드 대기는 이미 안다(6 us).  **모르는 것은 응용이 실제로 무는 벽시계**이고, 그것은
지금껏 아무 실행도 재지 않았다.  그러니 이 칸의 실기 실행은 하나만 답하면 된다:

> 삼각형 하나를 그릴 때 응용이 무는 시간은 얼마이고, 그중 카드가 아닌 부분은 얼마인가.

그리고 그 답은 M1k 의 값어치를 바로 준다 — 배치가 아낀 것은 `a` 의 배수이기 때문이다.

## 9. P1~P4 의 답 (전부 python)

**P1 — 한 실행에 제출을 몇 번?**  msgbuf 는 제약이 아니다.  실측으로 ZCLEAR 하나가
**24 줄·2024 B**(중앙값)라 4084 B 에는 두 개뿐이지만, **로그는 syslog 로 빠져나간다** —
과거 실행에서 594 개가 온전히 남았다.  진짜 제약은 **syslogd 가 굶는가**이고, 그건
드라이버가 오래 스핀할 때 생긴다(우리는 6 us 다).  그래도 **일련번호를 양쪽에** 넣어
짝짓기를 증명한다(codex 채택분).

**P2 — 배치를 끄는 손잡이**: 씨앗과 같은 환경 변수(`RDNMesaBatch=0`).  끄면 훅이
`osrdnInRender` 를 무시하고 M1i 의 단발 경로를 쓴다 — **이미 실기로 증명된 코드**라
새 위험이 없고, 켠 쪽과 끈 쪽이 같은 그림을 그려야 한다는 게이트가 그대로 산다.

**P3 — `n` 은 어디까지?**  배치 상한(131)이 아니라 **VB 가 먼저 묶는다**:

    usable = VB_MAX - VB_START = 216 정점
    GL_TRIANGLES  n_max = 72   (216 정점)     <- 리스트는 VB 가 상한
    GL_TRIANGLE_STRIP n_max = 214             <- 스트립은 배치(131)가 상한

그리고 **codex 가 예측한 4 KiB 페이지 경계 n=66 이 그 범위 안에 있다**:

    n=65  1023 워드  4092 B
    n=66  1038 워드  4152 B   <- 페이지를 넘는다
    n=72  1128 워드  4512 B

그래서 점을 이렇게 고른다: **{1, 18, 36, 60} 으로 직선을 맞추고**(전부 경계 아래),
**{66, 72} 로 그 직선의 예측을 검사한다**.  어긋나면 그 자리가 페이지 효과다 —
세 점짜리 설계가 못 보는 것을 네 점+두 검사점이 본다.

**P4 — 시계 한 번에 제출 몇 번?**  분해능 4 us·호출쌍 4 us 이므로 1 % 정확도는
`t ≥ 400 us` 를 요구한다.  제출 하나를 재면 안 된다:

    제출 한 번이  50 us 이면  한 시계 구간에 K ≥ 8 제출
                 100 us 이면              K ≥ 4
                 400 us 이면              K ≥ 1

그러므로 **K 번의 제출을 한 쌍의 `gettimeofday` 로 감싸고 나눈다**.  이것이 호출쌍
4 us 를 K 로 나눠 없애기도 한다.  전체 실행 시간은 180 초 제한의 1 % 도 안 된다
(5 점 × 25 반복이라도 카드 시간은 0.4 초 미만).  반복은 **점들 사이를 오가며** 섞고,
보고는 **중앙값**으로 한다(N6).

## 10. 측정 구간 안에 드라이버의 로그가 있다 (코딩 중에 확인)

r7b 클라이언트 제출 경로는 **제출마다 조건 없이** `begin` 한 줄 + `osrdn_cp_lines`
(실측 24 줄·2024 B)를 찍는다(`OSRDNDisplay.m:1297-1323`).  스위치는 없다.  그러니
우리가 재는 시간 안에 **syslog 쓰기 24 번**이 들어 있다.

이것을 숨기지 않고, **적합이 알아서 가르게** 둔다:

- 로그는 `n` 과 무관하게 제출당 한 번이므로 **절편 `a` 에만** 들어간다.
- 삼각형당 한계비 **`b` 는 로그가 섞이지 않는다**.

그래서 이 칸의 보고는 이렇게 쓴다: *"`b` 는 삼각형 하나의 한계 벽시계다.  `a` 는 오늘의
제출 고정비이고 **그 안에 드라이버의 디버그 로그 24 줄이 들어 있다**."*  로그를 끄면
`a` 가 얼마나 줄어드는지는 드라이버를 고쳐야 알 수 있고, 그건 재부팅이 필요한 다음 칸이다.

## 11. 첫 실행이 설계 결함을 잡았다 — `glEnd` 는 제출하지 않는다

실기 1 회차(`790081954`)의 계수기:

    t-accel:  triangles=18216  flushes=254  submitted=18216  delegated=0  outside=0

**삼각형 18,216 개가 제출 254 번**(평균 71.7)이다.  내 sweep 은 `glBegin`/`glEnd` 한
쌍마다 제출 하나를 기대했는데, Mesa 는 **여러 쌍을 한 정점 버퍼에 모아** 버퍼가 찰 때
렌더한다.  그러므로 **`n` 은 제출 크기를 전혀 통제하지 않았고**, 잰 것은 VB 가 차는
속도였다.  증거는 `n=1` 에서 가장 선명하다: 블록 하나가 0.9 us 로 나왔는데,
그 블록이 만든 삼각형들이 **다른 블록에서** 제출됐기 때문이다.

고친 방법은 한 줄이다: `glEnd` 다음에 **`glFlush`**.  `_mesa_Flush` 의 첫 동작이
`FLUSH_VB` 이고(`context.c:2029`, `types.h:2103-2105`), 그것이 파이프라인을 돌려
우리 `RenderFinish` 를 부르고, 그게 배치를 보낸다.

**이것은 Matrox 가 남긴 교훈과 같은 것이다** — 거기서도 제출 횟수를 정한 것은 배치
한계가 아니라 **렌더 괄호**였다(`REMAINING_WORK.md:2856-2858`).  다른 점은 그때는 프레임당
33.5 제출을 *관찰*했고, 여기서는 그 사실을 모른 채 *설계*했다는 것이다.

1 회차의 시간 수치는 **버린다**.  계수기가 그것들이 무엇을 쟀는지 말해 주었으므로
실행이 헛되지는 않았다 — 게이트가 아니라 계수기가 잡았다는 점은 기록해 둔다.

## 12. 결과 — 제출 고정비 13.56 ms, 삼각형 2 us (실기, 2026-09-22)

빌드 `790082120`, 실행 `790082134`, 재부팅 0 회.  `flushes=433` 은 설계한 수
(9 반복 × 6 점 × K 8 + 첫 장면 1)와 정확히 같다.  `outside=0`, `delegated=0`.

    t(n) = 13559.8 + 1.99 n   [us]     (n = 한 제출에 든 삼각형)

적합은 자기 점들을 **0 % 안에서** 설명하고, 페이지 경계 위의 두 점을 **0.06 % 안에서**
예측한다(n=66 실측 13699.0 대 예측 13691.4; n=72 실측 13731.1 대 예측 13703.4).
codex 가 경고한 페이지 효과는 **이 크기에서는 안 보인다** — 고정비가 너무 커서 묻힌다.

| n | 카드 | 소프트웨어 | |
|---|---|---|---|
| 1 | 13,557 us | 2.8 us | **소프트웨어가 4,930 배 빠르다** |
| 18 | 13,595 | 24.8 | 549 배 |
| 36 | 13,644 | 48.0 | 284 배 |
| 72 | 13,731 | 95.0 | 145 배 |

**고정비가 전부다.**  n=1 에서 시간의 **99.99 %**, n=72 에서도 **98.95 %** 가 `n` 과
무관한 부분이다.  그리고 그 고정비에서 **카드가 차지하는 몫은 0.04 % 이하**다
(대기 중앙값 0 us, 최대 6 us, 표본 118).  즉 **13.56 ms 는 전부 우리 쪽이다.**

**M1k 의 값어치는 이것으로 정해진다**: 삼각형 36 개를 하나씩 보내면 1,131,954 us,
모아 보내면 13,643 us — **83 배**.  배치는 고정비를 n 분의 1 로 만드는 일이었고,
고정비가 13.56 ms 이므로 그 일이 이 사다리에서 가장 값어치 있는 한 칸이었다.

**그래도 소프트웨어가 이긴다.**  Matrox 에서 본 것과 같은 결론이고(§1 N4·N5),
원인도 같은 자리에 있다 — 래스터가 아니라 **제출 한 번의 값**이다.

### 다음에 답해야 할 것: 13.56 ms 는 누구 것인가

후보는 둘이고 **둘 다 제출당 한 번**이라 적합이 못 가른다:

| | 후보 | 크기 짐작 |
|---|---|---|
| A | 드라이버가 제출마다 찍는 **로그 25 줄**(§10) | 13559/25 = **542 us/줄** |
| B | 라이브러리가 제출마다 **노드를 열고 닫는 것**(`triOpen`/`close`) | ? |

A 를 끄려면 드라이버를 고쳐야 하고 그건 재부팅이다.  **B 는 라이브러리만으로 가른다** —
같은 프로세스가 기술자를 들고 있는 것은 드라이버의 걸쇠가 막지 않는다(막는 것은 *다른*
열기다).  그러므로 다음 칸은 **B 를 먼저** 시험한다: 재부팅이 필요 없고, 결과가
어느 쪽이든 13.56 ms 의 주인을 좁힌다.

## 13. 후보 B 는 범인이 아니다 — 열고 닫기는 4 % 다 (실기, 재부팅 0 회)

빌드 `790082301`, 실행 `790082317`.  네 번째 팔을 더했다: 같은 배치·같은 장면인데
**노드를 들고 있는다**(`RDNMesaHold=1`).  계수기가 손잡이가 들었음을 증명한다 —
`opens=1` 대 `opens=434`.

    n     다시 열기        들고 있기        차이
    1      21141.6        13735.6       7406.0   <- 이상치, 아래
   18      14207.1        13770.6        436.5
   36      14274.2        13609.1        665.1
   60      14282.6        13656.6        626.0

**여섯 차이의 중앙값은 531 us 이고, 고정비 13,560 us 의 3.9 % 다.**  후보 B 는
범인이 아니다.  (n=1 의 7.4 ms 는 이상치다: 같은 점이 앞 실행에서 13,557 us 였고,
이번 적합이 **정당하게 FAIL 했다** — 판정기가 −99 us/삼각형 같은 기울기를 보고하는
대신 "직선이 아니다"라고 말했다.)

재현성: 두 실행의 같은 점끼리 **중앙값 4.5 % 차이**, 최대 55.9 %(그 이상치).
세 팔의 고정비 중앙값은 13,658 / 14,241 / 13,753 us 로 서로 4 % 안이다.

**그러므로 13 ms 의 주인은 후보 A 가 유력하다**: 드라이버가 제출마다 찍는 25 줄,
줄당 약 520 us.  열고 닫기 531 us 와 같은 자릿수라는 것도 같은 방향을 가리킨다 —
둘 다 **커널이 콘솔·로그에 말하는 비용**이다.

그것을 확인하려면 드라이버에서 그 로그를 끌 수 있어야 하고, **그것은 드라이버 변경이고
재부팅이다.**  여기까지가 재부팅 없이 갈 수 있는 끝이다.

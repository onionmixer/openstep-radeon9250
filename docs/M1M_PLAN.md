# M1m — 13 ms 의 주인을 밝힌다 (계획, 재부팅이 필요한 첫 칸)

기준일 2026-09-22.  선행: M1l 완료(`docs/M1L_PLAN.md` 12, 13).

## 1. 왜 이 칸인가

M1l 이 잰 것: **제출 고정비 13.56 ms**, 그중 카드 몫 0.04 % 미만, 열고 닫기 3.9 %.
남은 **약 13 ms** 의 유력한 주인은 드라이버가 제출마다 찍는 **25 줄**이다
(`OSRDNDisplay.m:1332-1358`, 줄당 약 520 us).  스위치가 없어서 **지금은 모든 측정이
그 로그를 함께 잰다** — 이 칸을 하지 않으면 앞으로의 모든 측정이 같은 값을 짊어진다.

## 2. 이 칸의 한 줄

**클라이언트 제출의 로그를 끌 수 있게 하고, 끈 채로 같은 sweep 을 다시 돌린다.**
결과가 13 ms 를 지우면 주인이 밝혀진 것이고, 안 지우면 후보가 하나 줄고 다음 후보
(ioctl 블록 복사, `cpR7Verify`, DriverKit 디스패치)로 간다.

## 3. 무엇을 바꾸는가 (최소)

기존 패턴을 그대로 쓴다 — `setIntValues` 파라미터에 매직 워드
(`OSRDNDisplay.m:102-103` 의 `RDNR5Cp`·`RDNR7Sub` 와 같은 꼴):

| | 바꾸는 것 |
|---|---|
| 1 | `OSRDN_QUIET_PARAM "RDNR7Quiet"`, 블록은 `{R7_MAGIC, quiet}` 두 워드 |
| 2 | `rdnState.r7Quiet` 한 칸 |
| 3 | r7b 제출 경로의 `IOLog("RDN-R5 begin ...")` 와 `osrdn_cp_lines(...)` 를 **그 플래그로 감싼다** |
| 4 | 조용히 지나간 제출 수를 **세어 둔다**(`rdnR7bQuiet`), 그리고 STOP·상태 줄에 한 번 찍는다 |

**다른 연산의 로그는 건드리지 않는다.**  `CP_OP_*` 경로(`OSRDNDisplay.m:703-717`)는
R5·R6 판정기들이 읽는 증거이고, 그것을 조용하게 만들면 사다리 아래 칸들이 판정 불가가 된다.

## 4. 이 칸이 하지 않는 것

- **제출을 비동기로 만들지 않는다.**  카드 대기는 이미 0 us 로 쟀다 — 고칠 것이 없다.
- **로그를 지우지 않는다.**  끄는 것은 실행 단위이고, 기본값은 **켜짐**이다.
  기본을 끔으로 두면 다음 실기 실패가 증거 없이 일어난다.
- 열고 닫기(531 us)를 고치지 않는다.  4 % 는 13 ms 다음이다.

## 5. 위험과 그 값

| | 위험 | 막는 법 |
|---|---|---|
| A | 드라이버가 안 올라온다 → 디스플레이 없는 부팅 | 설치 전 `nm -u` 심볼 검사, 변경은 파라미터 한 개·플래그 한 개로 국한 |
| B | 조용한 실행에서 실기 실패가 나면 증거가 없다 | 기본 켜짐, 그리고 **조용히 지나간 수를 세어** 상태 줄에 찍는다 |
| C | 매직 워드 없는 옛 도구가 새 파라미터를 건드린다 | 매직 검사는 기존 경로와 같은 모양으로 |

## 6. 코딩 전에 답해야 할 것

| | 질문 | 어떻게 |
|---|---|---|
| Q1 | `setIntValues` 의 블록 한도와 기존 파라미터의 인자 개수 검사 모양 | `OSRDNDisplay.m` 의 `RDNR7Sub`·`RDNR5Cp` 경로를 그대로 읽어 같은 꼴로 |
| Q2 | 파라미터를 누가 설정하나 — 러너의 op 도구인가 별도인가 | `build/r7b/r5op.sh` 가 무엇을 부르는지 읽고, 필요하면 그 도구에 verb 하나 |
| Q3 | 25 줄이 정말 13 ms 인가를 **끄기 전에** 더 좁힐 수 있나 | ZPREP 은 9 줄, 클라이언트 제출은 25 줄이다.  두 연산을 같은 실행에서 재면 줄당 비용이 나온다 — **드라이버 변경 없이** |
| Q4 | 조용 모드에서 M1d~M1k 판정기가 여전히 도는가 | 그 판정기들은 시험의 stdout 만 읽는다(확인 필요) |

**Q3 이 먼저다.**  드라이버를 고치기 전에 "줄당 520 us" 를 **다른 방법으로** 확인할 수
있으면, 이 칸은 확인된 사실을 고치는 일이 되고 실패할 여지가 줄어든다.

## 7. Q3 의 답 — 로그가 아니다.  **되읽기 검증이다.** (실기, 재부팅 0 회)

Q3 대로 **드라이버를 고치기 전에** 갈랐다.  `RDNMesaPoison=1` 팔은 매 스트림의
워드 0 을 망가뜨려 커널이 **워드 0 에서 거절**하게 한다(호스트 오라클로 예측:
`0xffffffff` → `why=6 packet3 opcode 0xff00`).  같은 ioctl, 같은 25 줄 로그,
**일은 하나도 안 한다.**

실행 `790082620`, 다섯 팔:

    n     전체 제출      워드0 거절     거절/전체
    1      14166.6        158.9         1 %
   18      14212.1        199.8         1 %
   36      13642.4        243.0         2 %
   60      13707.1        299.6         2 %
   72      13723.1        332.0         2 %

**로그와 고정 경로를 합쳐 1–2 % 다.**  §1 의 가설(로그가 13 ms)은 **틀렸다.**
그리고 거절 팔도 계수기가 약속을 지켰다: `failed=433 replayed=18217 nosw=0` —
거절된 삼각형 18,217 개를 전부 소프트웨어가 그렸다.

### 그러면 누구인가 — 읽어서 찾았다

`cpZclear` 는 그리기 뒤에 **결과를 되읽어 digest 를 만든다**:

    for (k = 0; k < 2; k++) {                       /* 두 번 */
        cpR6Digest(c, depthOff/4, CP_R6_BUF_WORDS, &c->dDepth[k]);   /* 4096 워드 */
        cpR6Digest(c, colorOff/4, CP_R6_BUF_WORDS, &c->dColor[k]);   /* 4096 워드 */

**제출당 2 × 2 × 4096 = 16,384 회의 uncached VRAM 읽기.**  산술이 맞는다:

    13540 us / 16384 = 826 ns      14212 us / 16384 = 867 ns

2000 년대 PCI 의 uncached 32 비트 읽기 한 번이 그 정도다.  n 과 무관하고(그래서
적합이 평평했다), 거절되면 도달하지 않는다(그래서 poison 팔이 1 %다).

**이것은 M1h 가 이미 한 번 한 일이다.**  바로 열 줄 아래에 같은 이유의 건너뛰기가
있다 — 256 KiB 전체 스캔은 `zc == CP_R7_CASE` 일 때 건너뛴다("삭제가 아니라 건너뛰기:
그것으로 측정한 케이스들은 그대로 측정한다").  **digest 두 벌이 남아 있었을 뿐이다.**

소비자를 확인했다: digest 줄(`zd`/`zc`)을 읽는 것은 **R6 오라클들**이고,
**M1 판정기는 하나도 안 읽는다**(시험의 stdout 만 읽는다).

## 8. 그래서 바꾸는 것 (세 줄)

`cpZclear` 의 digest 루프에 M1h 와 **같은 모양의** 건너뛰기를 더한다:

- `zc == CP_R7_CASE` 이면 `cpR6Digest` 두 벌을 건너뛴다.
- 건너뛴 사실을 상태에 남긴다(`c->digestSkipped`), 로그 한 칸에 찍는다.
- R6 케이스는 **한 글자도 안 바뀐다**.

기대: 제출 고정비 13.5 ms → **0.2–0.4 ms**(poison 팔이 그 바닥을 이미 쟀다).
그러면 n=72 에서 카드 14 ms → 0.4 ms 가 되고, 소프트웨어 0.095 ms 와의 거리가
145 배에서 **약 4 배**로 줄어든다.

## 9. codex 교차검토 (코딩 전)

| codex 주장 | 내 검증 | 판정 |
|---|---|---|
| **13.5 ms 는 75 Hz 프레임(13.33 ms)에 가깝다 — vblank 동기일 수 있다** | CP 경로의 대기 종류는 **넷뿐**이다: `W_FIFO`·`W_IDLE`·`W_RPTR`·`W_DC`(`osrdn_cp.m:156-159`).  `vblank`·`VLINE`·`CRTC_STATUS`·`VSYNC` 는 그 파일에 **0 건** | ❌ **기각** — 근거 있음.  다만 물어볼 만한 질문이었다 |
| 826–867 ns 는 **상한**이다 — 총 시간을 전부 그 읽기에 돌린 값이니까 | 맞다.  실제 값은 **제거된 시간 / 16384** 로만 나온다 | ✅ 채택 — 보고 문구를 그렇게 |
| **거절 팔은 성공 경로의 바닥을 못 준다** — 검증 통과·링 복사·플러시·제출·정리가 빠져 있다 | 맞다.  §8 의 "0.2–0.4 ms" 예측은 근거가 약하다 | ✅ 채택 — **예측을 지우고 "재서 안다"로 바꾼다** |
| 두 패스는 **시간적 안정성 검사**다(두 번 읽어 달라지면 찢어진 버퍼) | 사실이다.  다만 그 비교는 **드라이버가 아니라 호스트의 R6 오라클**이 한다 — 클라이언트 경로에서는 아무도 안 본다.  그래도 **버리기엔 아까운 검사**다 | ⚖️ 부분채택 |
| uncached 읽기가 **사실상 펜스**로 동작했을 수 있다 — 없애면 순서가 바뀔 수 있다 | 반증할 수단이 없다.  명시적 `DC_FLUSH_ALL` + `W_DC` 대기가 앞에 있지만, "그것으로 충분한가"는 우리가 증명한 적 없다 | ✅ 채택 — **완전 제거 대신 표본**으로 |

### 그래서 §8 을 고친다: **지우지 말고 줄인다**

클라이언트 경우에 digest 를 **건너뛰지 않고 표본만** 뜬다 — 두 패스는 그대로,
버퍼마다 4096 워드 대신 **64 워드**:

    비용: 2 패스 x 2 버퍼 x 64 워드 = 256 회 읽기 (지금은 16,384 회)

- **펜스가 남는다**(구멍을 계속 건드린다).
- **찢어짐 검사가 남는다**(두 패스가 여전히 다를 수 있다).
- **R6 케이스는 한 글자도 안 바뀐다**(전체 4096 워드 그대로).
- 예상 절감은 **읽기 64 분의 1**.  남는 값이 얼마인지는 **재서 안다** — 예측하지 않는다.

표본 창은 버퍼의 **앞 64 워드**가 아니라 **그려진 자리를 포함**해야 뜻이 있다.
시험이 그리는 삼각형은 원점 근처이므로 앞 64 워드가 그 안이다 — 그 사실을 게이트로 박는다.

**재부팅은 사용자 몫이다.**  부팅 뒤에 할 일:

1. `BUILD=<새 mesa 빌드> bash build/m1l/run_m1l.sh` — 다섯 팔을 그대로 다시.
2. `python3 tools/mesa/judge_m1l.py build/m1l/<run>/prof` — 고정비가 얼마로 내려갔나.
3. **제거된 시간 / 16384 = uncached 읽기 한 번의 진짜 값**(codex 채택분: 826–867 ns 는 상한이었다).
4. 로그의 `dw=64` 로 새 드라이버가 돌고 있음을 확인(옛 드라이버면 `dw` 가 아예 없다).
5. 그리고 **M1d~M1k 그림 판정기를 다시 돌려** 화면이 한 화소도 안 바뀌었는지 본다 —
   이 칸은 속도만 바꾸기로 한 칸이다.

## 11. 결과 — 고정비 13.56 ms → **1.60 ms** (실기, 부팅 1 회)

드라이버 `cd7e0f5e`, 실행 `790085103`.  로그에 `dw=64` 가 찍혀 새 경로가 돈 것이 확인된다.

    t(n) = 1604.3 + 1.96 n   [us]        (전: 13559.8 + 1.99 n)

| n | 전 | 후 | 배수 |
|---|---|---|---|
| 1 | 13,542 | **1,601** | 8.5 |
| 18 | 13,588 | 1,648 | 8.3 |
| 36 | 13,612 | 1,673 | 8.2 |
| 60 | 13,674 | 1,721 | 8.0 |
| 66 | 13,691 | 1,735 | 7.9 |
| 72 | 13,698 | 1,743 | 7.9 |

한계비는 **1.99 → 1.96 us 로 그대로**다 — digest 는 고정비였으니 그래야 맞다.
소프트웨어와의 거리는 **144 배 → 18.3 배**(n=72).

**그림은 한 화소도 안 바뀌었다**: 일곱 모드 전부 `judge_m1d: PASS`, 그리고 옛 드라이버
실행(`790077690`)과 화소를 맞대어 **28,672 중 0 차이**.  이 칸은 속도만 바꾸기로 했고
그대로 되었다.

## 12. 그러다 더 큰 것을 봤다 — **로그는 syslogd 가 따라올 때만 비싸다**

새 부팅의 측정은 **이봉이 아니라 전이**였다.  모든 팔이 실행 도중 낮은 상태로 떨어진다:

    t-poison  10.0 ms x 4 회  ->  0.73 ms x 5 회
    t-accel   11.9 ms x 5 회  ->  1.60 ms x 4 회
    t-hold     5.0 ms x 7 회  ->  1.57 ms x 2 회

원인을 셌다: 이번 실행의 제출 약 1,700 건 중 `/usr/adm/messages` 에 남은
`RDN-R5 begin` 줄은 **파일 전체를 통틀어 814 줄**이다.  **대부분이 버려진다.**
전이 지점은 syslogd 가 배달을 포기하는 순간이고, 그 전까지는 제출마다 **약 10 ms** 가
더 든다.

**M1l 의 13.56 ms 는 오래 켜 둔 기계에서 쟀다** — syslogd 가 이미 포화라 로그가
싸 보였고(poison 158~330 us), 그래서 §7 에서 "로그는 1~2 %" 라고 적었다.  그 결론은
**그 상태에서만** 맞다.  갓 부팅한 기계에서는 로그가 제출당 10 ms 다.

판정기를 고쳤다: 중앙값 대신 **두 상태를 갈라 둘 다 보고**한다(`split()`).
세 무리(바닥·로그·이상치)가 나오므로 낮은 쪽으로 재귀한다 — 그러지 않으면 n=72 의
바닥이 1,743 대신 6,620 으로 읽혔다.

## 13. 남은 1.60 ms 의 내역과 다음 칸

| | 몫 | 어떻게 알았나 |
|---|---|---|
| 고정 경로(ioctl + 살아남은 로그 + 열고 닫기) | **728~897 us** | poison 팔의 바닥 |
| 그중 열고 닫기 | **36 us** | accel−hold 바닥 차이(n=72) |
| 받아들여진 뒤의 일(링 복사·워드 검증·표본 digest 256 회·플러시/대기) | **~880 us** | accel−poison 바닥 차이 |

그러므로 다음으로 값이 큰 것은 **로그를 끌 수 있게 하는 것**이다 — 포화 상태에서 0.7 ms,
배달 상태에서 10 ms 이고, **측정 자체를 불안정하게 만드는 원인**이기도 하다.
그것이 M1m §3 이 원래 하려던 일이고, 드라이버 변경이라 부팅이 한 번 더 든다.

# M2f — 열고닫기의 값은 로그였다 (재부팅 없는 칸 + 드라이버 칸)

## 1. 무엇을 찾았나

`rdnDevOpen`(`OSRDNDisplay.m:129-188`)과 `rdnDevClose`(`OSRDNDisplay.m:216-240`)가
**무조건 `IOLog` 한다**.  `quiet` 게이트는 제출 경로에만 있고(`OSRDNDisplay.m:1308`)
열고닫기는 안 덮는다.

그래서 노드를 안 잡는 팔은 **제출마다 로그 줄 둘**을 더 낸다.  판정기가 "열고닫기" 라
부르는 수가 세 실행에서 **642.9 / 657.2 / 26.9 us** 로 나온 이유다(24 배).
잡는 팔은 세 번 다 같았다(1528.2 ~ 1551.8, 폭 23.6) — **흔들린 것은 안 잡는 팔뿐**이고,
그 팔만 그 두 줄을 제출마다 낸다.

M1n 이 이 모순을 이미 적어 두었다(`M1N_PLAN.md:154`): "로그 747 + 열고닫기 652 가
'판정 전 전부' 인 326 보다 컸다."  그때는 **순서** 탓으로 두었다.  원인은 순서가 아니라
**게이트 밖의 `IOLog`** 였다.

## 2. 두 칸으로 나눈다

### 2-1. M2f-a — 재부팅 없이, **조용한 팔로 다시 잰다**

오늘 그 수를 내는 짝은 `t-accel`(로그 켬, 안 잡음) 대 `t-hold`(로그 켬, 잡음)뿐이다.
둘 다 제출마다 드라이버의 25 줄을 내므로, 차이를 재는 자 자체가 syslogd 를 타고 흔들린다.

새 팔 하나: **`t-qhold` = `t-quiet` + 노드 잡기.**  제출 로그는 둘 다 꺼져 있으므로
차이에 남는 것은 **열고닫기 두 syscall + 그 둘의 `IOLog` 둘**뿐이다.  M2d 가 세운
자 둘(조용한 표류, 값 없는 손잡이)과 나란히 보고한다.

이 칸은 드라이버를 안 건드린다.  러너에 팔 하나, 판정기에 짝 하나.

### 2-2. M2f-b — 드라이버: **그 두 줄도 `quiet` 를 따른다** (재부팅)

#### 먼저, 내가 처음 쓴 것은 **컴파일도 안 된다**

    if (!rdnCp.quiet)              /* <- 이렇게 쓸 수 없다 */
        IOLog("RDN-R4 open ...");

`rdnCp` 는 **인스턴스 변수**(`OSRDNDisplay.h:23`)이고 `rdnDevOpen` 은 **파일 범위의
static C 함수**(`OSRDNDisplay.m:179-180`)다 — `self` 가 없으니 그 이름이 안 보인다.
그 경로가 쓰는 것은 전부 파일 범위 static 이다(`rdnVmapNonce`·`rdnVmapOpens`·
`rdnR7bHeld`, `OSRDNDisplay.m:150-175`).

#### 다리는 이미 있다 — 새로 놓지 않는다

`rdnR7bInstance`(`OSRDNDisplay.m:163`)가 그것이다.  `d_ioctl` 이 이미 그것으로 객체에
들어간다(`OSRDNDisplay.m:264`).  설치 순서도 안전한 쪽이다:
콜백 등록 → `rdnR7bInstance = self`(`OSRDNDisplay.m:1438`) → `rdnVmapState = OSRDN_VMAP_ON`(`OSRDNDisplay.m:1439`),
그리고 열기 경로는 `rdnVmapState != ON` 이면 **객체를 건드리기 전에** 거절한다(`OSRDNDisplay.m:184`).
그러니 **성공 경로에서는 인스턴스가 반드시 있다.**

C 함수에서 ivar 은 여전히 못 보므로 작은 메서드 하나를 둔다 — `d_ioctl` 이 쓰는 것과
같은 모양이다:

    if (![rdnR7bInstance r7bQuiet])
        IOLog("RDN-R4 open ... ok ...");

#### 그런데 **플래그를 그냥 읽으면 안 된다** (codex 가 잡음, python 으로 재현)

`osrdn_cp_quiet_take`(c5c1c36f 판 osrdn_cp.m 2476-2486행)는 리스를 **다 쓴 뒤에도 플래그를 안 지운다** —
지우는 것은 **그 다음 제출**이다:

| | quiet | budget | 생 `quiet` 읽기 |
|---|---:|---:|---|
| `quiet 3` 직후 | 1 | 3 | QUIET |
| 제출 3 뒤 | 1 | **0** | **QUIET** ← 리스는 끝났는데 |
| 제출 4 뒤 | 0 | 0 | speak |

**클라이언트가 거기서 제출을 멈추면 플래그는 영원히 1 이다.**  그러면 열고닫기가
영원히 조용해진다 — `osrdn_cp.h:98` 가 리스를 둔 바로 그 실패를 다시 만든다.

그래서 **리스까지 같이 본다**.  두 필드를 읽고 아무것도 안 바꾸는 함수 하나:

    int osrdn_cp_quiet_peek(const osrdn_cp_state *c)
    { return c != 0 && c->quiet && c->quietBudget != 0UL; }

#### 그리고 **거절 줄은 언제나 말한다**

`quiet` 는 노드를 **잡고 있는 동안에도** 걸릴 수 있다(`d_ioctl` → `cpQuiet`,
`osrdn_cp.m:2942`).  그 사이에 다른 클라이언트가 열려다 거절당하면 그 **거절 줄이
사라진다** — 그리고 그것이 바로 `judge_r7b.py:107` 이 요구하는 줄이다.

거절은 드물고 **증거**다.  그러니 손잡이는 **성공 줄에만** 건다:

    if (거절) { ...; IOLog("... refused ..."); return ENXIO; }   /* 언제나 */
    ...
    if (!quiet)   IOLog("... ok ...");                            /* 손잡이 뒤 */

**게이트가 읽는 것**: `check_vmap_log.py:168` 은 minor 0 `ok` 와 minor 1
`refused` 를 하나씩 요구하고, `judge_r7b.py:107` 은 `refused` 하나를 요구한다.
거절은 무조건 남고, 두 게이트는 `quiet` 를 **한 번도 안 낸다**.

**부팅당 상한(cap)은 쓰지 않는다.**  상한은 한 부팅 안의 실행들끼리 결합을 만든다:
M1l 실행이 먼저 상한을 다 쓰면 그 뒤에 도는 R4 게이트가 자기 줄을 못 본다.
리스로 막은 `peek` 에는 그 결합이 없다 — 리스가 끝나면 스스로 말한다.

### 2-2b. codex 교차검토 — 판정표

| codex 주장 | 내 검증 방법 | 판정 |
|---|---|---|
| `rdnCp` 는 ivar 이고 두 진입점은 `self` 없는 static C 함수라 그 식은 성립 안 한다 | **codex 회신 전에 내가 먼저 잡아 §2-2 를 고쳐 뒀다**(`OSRDNDisplay.h:23`, `OSRDNDisplay.m:179-180`) | ✅ 사실 |
| 다리는 `rdnR7bInstance` 이고, 콜백 등록 → 인스턴스 대입(`OSRDNDisplay.m:1438`) → 상태 ON(`OSRDNDisplay.m:1439`) 순서라 성공 경로에서는 유효하다 | 셋 다 열었다.  거절 경로가 객체를 안 건드리는 것도 `OSRDNDisplay.m:184` 에서 확인 | ✅ **채택** — 내가 새로 놓으려던 `rdnCpPtr` 을 버리고 이것을 쓴다 |
| **생 플래그는 리스보다 오래 산다** — 마지막 제출이 budget 을 0 으로 만들어도 `quiet` 는 다음 제출까지 1 | 함수 본문을 읽고 **python 으로 재현**(위 표).  제출이 멈추면 영원히 1 | ✅ **채택 — 내 §2-2 의 "결합이 없다" 는 거짓이었다** |
| **`quiet` 가 걸린 채 다른 열기가 거절되면 그 거절 줄이 사라지고, 그것이 `judge_r7b.py:107` 이 요구하는 줄이다** | `d_ioctl`(`OSRDNDisplay.m:264`) → `cpQuiet`, 그리고 거절 경로(`OSRDNDisplay.m:184-222`) | ✅ **채택** — 거절은 무조건 말한다 |
| 직접 읽기가 리스를 안 깎는 것 자체는 맞다 | `osrdn_cp_quiet_take` 이 `quietBudget--` 한다(c5c1c36f 판 osrdn_cp.m 2486행) | ✅ 사실 — 그래서 `peek` 도 아무것도 안 바꾼다 |
| 두 게이트의 자체시험 고정물은 quiet 를 안 걸고 시작한다 | `judge_r7b.py:123` 의 고정물을 열었다 | ✅ 사실 |

**내가 틀렸던 것 둘**: (1) ivar 을 C 함수에서 읽으려 했다(스스로 잡음), (2) **생 플래그에
결합이 없다고 적었다 — 리스보다 오래 살아서 있다**(codex 가 잡음).

## 3. 기대값 — 그리고 그것이 기대인 이유

조용한 팔들의 고정비(491 / 431 / 269 / 210)는 **이미 그 두 줄을 포함한다**.
이번 부팅의 실측 열고닫기 26.9 us 가 그 몫이라면, M2f-b 뒤에 조용한 팔의 고정비가
**약 27 us 내려가야 한다**(210 의 13 %).

800 us 가 아니라 27 us 인 이유: 로그 한 줄은 syslogd 가 배달 중이면 ~400 us, 버리는
중이면 ~13 us 다([[measurement-discipline]]).  측정 팔들이 210 us 로 재졌다는 것
자체가 그 구간에서 syslogd 가 **버리는 쪽**이었다는 증거다 — 배달 중이었다면 두 줄만으로
800 us 였을 테니.  **이 추론은 M2f-b 로 검증된다**: 안 내려가면 내 모형이 틀린 것이다.

## 4. 이 칸이 **안 하는** 것

- **제출 로그의 기본값은 여전히 안 건드린다**(docs/PRERELEASE_LOG_DEFAULT.md).
  한 번에 둘을 뒤집으면 못 가른다.
- **열고닫기를 없애지 않는다.**  노드를 잡고 있는 것이 빠르다는 것은 이미 알지만,
  그것은 Mesa 쪽 정책이고 이 사다리의 주제가 아니다.

## 6. M2f-a 실측 (2026-09-24, 부팅 `073b1f5e`, run 790202535) — **예상과 반대**

| 짝 | 안 잡음 | 잡음 | 차이 |
|---|---:|---:|---:|
| 제출 로그 **켬**(`t-accel` 대 `t-hold`) | 1573.5 | 1526.1 | **+47.4** (잡는 쪽이 빠름) |
| 제출 로그 **끔**(`t-quiet` 대 `t-qhold`) | 490.1 | **658.8** | **−168.7** (잡는 쪽이 **느림**) |

노드를 잡는 것은 **일을 빼는 것**이다 — 제출마다 open 하나, close 하나, 그리고 그 둘의
로그 줄 둘.  그런데 조용한 짝에서는 잡는 쪽이 **150 us 더 든다**.

### 6-1. 잡음이 아니다 — 다리·블록 전부에 고르게 있다

    leg 2  : +139 +151 +149 +144 +137 +165
    leg 4  : +168 +155 +148 +154 +168 +163
    leg 8  : +134 +133 +164 +167 +154 +133
    leg 16 : +151 +167 +168 +145 +146 +153
    leg 32 : +168 +156 +140 +148 +169 +149

30 칸 전부 +133 ~ +169.  **삼각형당도 화소당도 아니고 제출당 상수**다.
같은 실행의 조용한 표류는 −2 us 였다.

### 6-2. 확인해서 **버린** 가설

| 가설 | 확인 | 결과 |
|---|---|---|
| 잡은 채 다른 열기가 거절돼 그 `IOLog` 를 문다 | 이 부팅 로그의 `minor=N refused` 줄을 셌다 | **0 건** — 기각 |
| 팔이 다른 장면을 그린다 | 두 팔 다 `triangles=91086`, `maps=1` | 기각 |
| 잡기 손잡이가 다른 것도 바꾼다 | `osrdn_tri_hold_enabled` 은 `triOpen`/`triClose` 두 곳에서만 읽힌다(`OSRDNMesaTri.c:377-402`) | 기각 |
| 리스가 도중에 끊겼다 | 두 팔 다 `quiet 5000`, 제출 2,167 | 기각 |

**미해결이다.**  제출당 150 us 짜리 상수가 "일을 덜 하는" 쪽에만 붙어 있다.

### 6-3. 그래서 판정기가 그것을 값으로 못 찍게 했다

음수 "비용" 은 값이 아니라 모순이다.  판정기는 이제 그 경우 **FAIL** 하고
"holding the node made it SLOWER" 라고 말한다 — M2a 의 "고정비가 올라갔다" 가드와 같은
모양이다.  자체시험으로 양방향 확인.

이 수가 풀리기 전까지 **"열고닫기는 N us" 라고 적지 않는다**.  M2f-b(로그를 게이트
뒤로)는 그것과 독립이므로 그대로 간다 — 오히려 그것이 이 수를 가르는 데 필요하다:
로그가 꺼지면 남는 차이는 syscall 뿐이다.

그러니 160 us 는 표류도 순서도 아니고 **잡기 손잡이가 켜진 그 팔에만** 있다.

### 7-2. 커널/유저랜드 가르기는 **실패했다**, 그리고 왜인지 안다

계획은 같은 팔을 hold 0/1 로 돌리고 드라이버의 단계 누적기를 `tdump` 로 비교하는 것이었다.
두 번 돌렸다:

1. **첫 판은 거짓 증거를 냈다** — 두 단계 줄이 **바이트 단위로 동일**했다.  측정이 아니라
   `grep ... | tail -1` 이 **같은 줄을 두 번** 읽은 것이다([[log-as-evidence]]).
2. **둘째 판은 옳게 거부했다** — 덤프 전 로그 길이를 찍고 그 뒤 줄만 읽게 했더니
   **두 번 다 비었다**.  줄이 안 온 것이다.

원인: 타깃의 `/usr/adm/messages` 가 12 분째 안 자란다(마지막 줄 `last message repeated
3 times`).  syslogd 가 중복을 접고 있고, 밀린 줄이 언제 도착할지 모른다.
**지금 이 채널로는 못 잰다.**  (타깃 시계는 5 일 느릴 뿐 로그 자체는 이 부팅 것이다 —
마지막 줄이 `build=c3fb18a2`.)

| 끔 | 잡음 | **0** | 658.8 |

잡으면 **어느 쪽이든 로그 줄 둘이 준다**.  그런데 로그가 켜져 있을 땐 +47.4 us 이득,
꺼져 있을 땐 **−168.7 us 손해** — **부호가 뒤집힌다**.  두 행의 차가 216.1 us 다.

### 7-4. **M2f-b 가 바로 그 판별기다**

M2f-b 는 `안 잡음` 팔에서도 그 두 줄을 없앤다.  그러면 마지막 두 칸의 차이는
**syscall 두 개뿐**이 된다.

- 로그가 원인이었다면 두 칸이 **모이고**, 둘 다 650 근처가 된다.
- 안 모이면 내 모형이 다른 데서 틀린 것이고, 그때 다시 설계한다.

**그러므로 이 수는 재부팅 뒤 첫 측정에서 판정된다.**  그 전까지 "열고닫기는 N us" 라고
적지 않는다.

## 8. M2f-b 실기 — **되돌렸다**

`2faf27d3` 로 두 번 돌리고 M2e 판(`c3fb18a2`)과 비교했다.

### 8-1. 같은 값이어야 할 팔 일곱 개가 갈라졌다

조용하고, 계측기 켜고, WBINVD 켜고, 서로 다른 손잡이는 **0 으로 측정된 것**(스핀)이거나
삼각형당 일만 건드리는 것들이다.  n=1 블록은 같은 수여야 한다:

| 실행 | 드라이버 | 퍼짐 |
|---|---|---:|
| 790202535 | `c3fb18a2` (M2e) | **2.5 us** |
| 790215947 | `2faf27d3` (M2f-b) | **210 us** |
| 790216462 | `2faf27d3` (M2f-b) | **213 us** |

두 무리(≈467 과 ≈677)로 갈라지고, **어느 팔이 어느 무리에 앉는지가 같은 부팅의 두 실행
사이에서 바뀐다**:

| 팔 | 790215947 | 790216462 |
|---|---:|---:|
| t-stage | **677** | 469 |
| t-spin | 467 | **668** |
| t-quiet | 467 | **665** |
| t-qhold | **652** | 443 |

### 8-2. 어느 수가 오염이고 어느 수가 아닌가 — **한 번 더 세고 고친다**

처음에 "세 실행의 열고닫기 −159.8 / +22.2 / +222.0 은 전부 갈라짐" 이라고 적었다.
**틀렸다.**  퍼짐과 나란히 놓고 보면:

| 실행 | 드라이버 | 일곱 팔 퍼짐 | t-quiet | t-qhold | 차 |
|---|---|---:|---:|---:|---:|
| 790202535 | `c3fb18a2` (M2e) | **2.5** | 490.5 | 650.2 | **+159.8** |
| 790215947 | `2faf27d3` (M2f-b) | 210.0 | 467.2 | 652.2 | +185.0 |
| 790216462 | `2faf27d3` (M2f-b) | 213.0 | 665.3 | 443.3 | −222.0 |

**첫 줄은 깨끗한 기계에서 잰 것이다** — 일곱 팔이 2.5 us 안에 모여 있다.  거기서도
노드를 잡는 쪽이 **160 us 더 든다**.  그러니 §6 의 관측은 **살아 있다**: 일을 덜 하는
팔이 더 비싸다는 그 수수께끼는 M2f-b 와 무관하게 실재한다.

오염된 것은 **뒤의 두 줄**뿐이고, 그 둘의 +185·−222 는 값이 아니다.
그리고 §7-4 의 "M2f-b 가 판별기다" 는 틀렸다 — 판별은커녕 기계를 이중 상태로 만들었다.

세 실행을 가로질러 변하지 않은 것: **WBINVD 224 / 226 / 221 us**.

### 8-3. 되돌림과, 대신 남긴 것

- **드라이버는 되돌렸다.**  두 `IOLog` 는 다시 무조건이다.  이유를 코드 자리에 적어 두어
  다음 사람이 같은 것을 다시 하지 않게 했다.  `osrdn_cp_quiet_peek`·`r7bQuiet`·
  `m2f-openlog` 규칙·world5 절도 함께 걷어냈다.
- **게이트는 남겼다**: 판정기가 그 일곱 팔의 퍼짐을 먼저 재고, **40 us 를 넘으면 아무것도
  값으로 안 찍는다**.  이 게이트가 있었으면 −159.8 을 보고하지 않았다.
  790202535 는 통과(2.5), 790215947·790216462 는 FAIL.
- `t-qhold` 팔은 남긴다.  팔 자체는 옳고, 오염이 없을 때 쓸 수 있다.

**미해결 둘**: (1) 깨끗한 기계에서도 노드를 잡으면 제출당 160 us 가 더 드는 이유 —
§6-2 에서 네 가설을 기각했고 아직 답이 없다.  (2) 왜 그 가드가 기계를 이중 상태로 만드는지.  추측하지 않는다 —
`quiet` 를 쓰는 진입점이 하나 늘었다는 것과 `objc_msgSend` 가 제출마다 둘 는다는 것이
후보이고, 다음에 이 자리를 건드릴 땐 **먼저 퍼짐 게이트를 보고** 설계한다.

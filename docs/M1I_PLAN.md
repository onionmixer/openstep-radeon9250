# M1i — 첫 하드웨어 깊이 검사 (계획)

기준일 2026-09-22.  선행: M1h 완료(`docs/M1H_PLAN.md` 13).
**이 문서는 코딩 전에 쓴다.**

## 1. 이 칸의 한 줄

**겹친 삼각형 둘을 `GL_DEPTH_TEST` 를 켠 채 그려서, 가까운 쪽이 이기는 것을
색 버퍼로 확인한다.**  깊이 버퍼를 읽어 보이는 것도, `glReadPixels(GL_DEPTH_COMPONENT)`
도 이 칸이 아니다.

## 2. 먼저 — 지금 상태는 틀려 있었고, 이미 닫았다

| | 사실 | 확인한 곳 |
|---|---|---|
| K1 | 분류기는 `RM_DEPTH` 를 `RM_KNOWN` 에 넣고 16 비트 폭을 받아들였다 → **깊이를 켠 응용이 TAKE 되었다** | `OSRDNMesaClass.c` |
| K2 | 그런데 프롤로그는 `R200_Z_ENABLE` 과 `R200_Z_WRITE_ENABLE` 을 **끈다** | `docs/M1D_PLAN.md` 4d |
| K3 | 즉 깊이를 켠 그림이 **깊이 검사 없이** 그려졌다.  시험이 깊이를 켠 적이 없어 안 드러났을 뿐이다 | — |

**이미 고쳤다**: `OSRDN_WHY_DEPTH` 라는 이름으로 거절한다(`OSRDNMesaClass.h:47`).
비트는 `RM_KNOWN` 에 그대로 둔다 — 마스크가 틀린 게 아니었다.
**이 칸은 그 사유를 지우는 칸이다.**

## 3. 이 칸을 부술 수 있는 것 — 배치가 다르다

| | 사실 | 확인한 곳 |
|---|---|---|
| K4 | **Mesa 의 소프트웨어 깊이 버퍼는 선형**이다: `array [Width*Height]` | `types.h:1380` |
| K5 | **카드의 깊이는 타일**이다.  16 비트 배치는 Mesa 의 `mba_z16` 과 같다(R6f 실측) | `depth_oracle.py:265` |
| K6 | R200 의 `RB3D_DEPTHPITCH` 에는 **타일을 끄는 비트가 없다**.  색 버퍼에는 `COLOR_TILE_ENABLE`·`COLOR_MICROTILE_ENABLE` 이 있고 깊이 쪽에는 피치·HyperZ·엔디안뿐이다 | `r200_reg.h:83-92`, `:215-216` |

**따라서 `DepthBuffer` 훅이 카드의 깊이 표면 포인터를 돌려주면 안 된다.**  Mesa 는 그것을
선형으로 읽고 카드는 타일로 쓴다.  훅 자리는 이미 있고(`osmesa.c:604`), 지금은 0 을
돌려주어 거절한다(`OSRDNMesaStubs.c:32`) — **이 칸에서도 계속 거절한다.**

## 4. 그래서 설계는 "카드가 깊이를 소유한다"

- 깊이 검사도 깊이 쓰기도 **전부 카드에서** 일어난다.  Mesa 의 깊이 버퍼는 할당되지만
  쓰이지 않는다 — 우리 삼각형 함수가 소프트웨어 래스터라이저를 대신하므로
  소프트웨어 깊이 경로는 애초에 실행되지 않는다.
- 이것이 성립하려면 **그 프레임의 모든 삼각형이 카드로 가야** 한다.  M1h 가 그것을
  가능하게 했고, 판정기가 `delegated +0` 으로 매번 확인한다.
- 깊이 버퍼는 창 안의 자리(`CP_R6_DEPTH_OFF` 와 같은 눈금, `osrdn_cp.h:312`)에 두고,
  **프레임 앞에서 CPU 가 실측 타일 배치로 채운다**.  드라이버가 R6g 에서 이미 같은
  방식으로 한다(`cpMbaZ16`).

## 6. 이 칸이 하지 않는 것

- 깊이 버퍼를 응용에 보여 주는 것(`glReadPixels`), `glClear(GL_DEPTH_BUFFER_BIT)` 의
  일반 경로, 24 비트 깊이, 스텐실.
- 드라이버 변경.  **필요 없다고 본다**: 깊이 레지스터는 클라이언트 허용 목록에 있고
  (R6f 가 그 경로로 쟀다), 클리어는 CPU 가 창에 쓴다.  Q4 가 그것을 확인한다.

## 7. Q1·Q3 의 답 (python)

**Q1 — 깊이 표면의 자리.**  16 비트 타일 배치(`mba_z16`, 피치 64)의 64×64 는
**정확히 8192 바이트**를 차지한다(최대 바이트 주소 0x1ffe).  창은 256 KiB 이고 색은
`[0, 0x4000)`, 텍스처는 `0x20000` 에 있으므로 **`0x10000`** 이 둘 다에서 떨어져 있다:
`[0x10000, 0x12000)`.  (수는 전부 `tools/r6/depth_oracle.py` 의 `mba_z16` 으로 계산했다.)

**Q3 — 클리어 값.**  실측 변환은 `floor(z · 2ⁿ)`(클램프)이고 16 비트는 24 비트의
상위 16 비트다.  `glClearDepth(1.0)` 의 기본값은 따라서 **0xffff**(far), 0.5 는 0x8000.
`z·(2ⁿ−1)` 계열이 아니다 — R6a 의 "0.5 → 0x800000 이니 반올림" 은 오독이었고 R6f 가
앵커 64 개로 갈랐다.  즉 **Mesa 의 CPU 쪽 변환(`d * 0xffff`)을 오라클로 쓰면 어긋난다.**

## 8. R6g 가 이미 답해 둔 것 — 그리고 그것이 여는 새 질문

R6f 의 다음 칸 R6g 가 판정 쪽을 이미 쟀다(부팅 04f45b10):

- 비교 함수 여덟 개가 규약대로 동작하고, **비교는 버퍼에 들어갈 내림한 정수로** 한다.
- `Z_WRITE_ENABLE` 0 이면 색만 써지고 깊이는 그대로.  `RB3D_CNTL.Z_ENABLE` 0 은
  판정도 깊이 쓰기도 없앤다(색은 써진다) — **M1d 가 이 두 비트를 끈 이유**이고,
  이 칸이 되돌릴 것이 정확히 그 둘이다.
- **같은 제출 안에서 두 그리기 사이에 대기·캐시 비움이 필요 없다**: 앞 그리기가 쓴
  깊이를 뒤 그리기가 그대로 읽는다.

| | 새 질문 | 왜 새로운가 |
|---|---|---|
| Q6 | **제출이 다르면** 어떤가?  M1h 전에는 프레임당 제출이 하나였으므로 "같은 제출 안" 이 곧 "프레임 안" 이었다.  이제 삼각형마다 제출이 따로이고, 제출 끝에는 캐시 비움과 새 프롤로그(=`DEPTHOFFSET` 재기록)가 있다 | R6g 의 실측은 **한 제출 안**의 이야기다.  제출을 건너 깊이가 보이는지는 **아무도 재지 않았다** — 이 칸의 첫 실기가 그것을 본다 |

Q6 이 "아니오" 로 나오면 이 칸의 설계가 바뀐다(삼각형 여럿을 **한 제출**에 묶어야
한다).  그러므로 **Q6 을 첫 실기의 첫 질문으로 놓는다**: 겹친 삼각형 둘을 각각 제출해
가까운 쪽이 이기는지 본다 — 이기면 Q6 은 "예" 이고, 지면 그 자리에서 답이 나온다.

## 9. codex 교차검토 (요청 `kd0hk7vlv`) — 깊이를 선형으로 만드는 비트가 있는가

물음은 하나였다: "깊이 배치를 선형으로 바꾸는 비트를 전수 열거하라."
내 열거는 먼저 독립으로 마쳤고(헤더의 `DEPTH|ZSTENCIL|HYPERZ|SURFACE|TILE|…` 전수),
회신은 **차집합 확인용**으로만 썼다.

| codex 주장 | 내 검증 | 결과 |
|---|---|---|
| `RB3D_DEPTHPITCH` 에 타일 비트가 없다(피치·HyperZ·엔디안뿐) | 같은 결론, 내가 먼저 얻었다 | ✅ 사실 |
| 색에는 `COLOR_TILE_ENABLE`·`COLOR_MICROTILE_ENABLE` 이 있고 깊이에는 대응물이 없다 | 같다 | ✅ 사실 |
| `DEPTH_XZ_OFFEST_ENABLE` 은 원점 선택이지 배치가 아니다 | `RB3D_CNTL` 비트 9, `Z_ENABLE` 비트 8 바로 옆.  출하 드라이버는 `DEPTHXY_OFFSET` 을 0 으로 둔다(`r200_state_init.c:697`) | ✅ 사실 |
| **`SURFACE0_INFO` 의 `R200_SURF_TILE_DEPTH_16BPP` 로 메모리 컨트롤러가 CPU 구멍 주소를 변환해 주면 CPU 는 타일 깊이를 선형처럼 볼 수 있다** | `radeon_reg.h:1607` 에 `(5 << 16)` 으로 실재한다 — **내 열거에 없던 것** | ✅ **채택(사실로)** |

**그런데 우리에겐 닫혀 있다.**  이 프로젝트의 CP 는 `SURFACE_CNTL` 이
`SURF_TRANSLATION_DIS`(0x100)가 **아니면 거절한다**(`osrdn_cp.m:3208`).  변환을 끄는 것은
의도된 선택이고, R6 의 모든 측정이 "CPU 가 raw 메모리를 본다" 는 전제 위에 서 있다.
표면 변환을 켜면 그 주소 모형이 통째로 달라진다.

**그러므로 이 칸은 여전히 `mba_z16` 으로 쓴다.**  표면 변환은 **이름 붙여 남겨 둔
선택지**이고(깊이를 Mesa 와 공유해야 할 날이 오면 그 길이 있다), 열려면 드라이버의
게이트와 R6 측정의 전제를 함께 다시 봐야 한다.

## 10. 실기 결과 — PASS (2026-09-22, 드라이버 `436c03c0`, 재부팅 0 회)

라이브러리 빌드 `790070613`, 실행 `790070623`.  일곱 조합
(플랫·구로·플랫+블렌드·구로+블렌드·텍스처·multi·**depth**) 전부 `judge_m1d: PASS`,
독립 재계수도 일곱 전부 0 불일치.

**Q6 의 답: 예 — 깊이는 제출을 건너 살아남는다.**  카드가 남긴 버퍼를 읽어 확인했다:

```
zrow 04  ffff c000 c000 c000 c000 c000 c000 c000 c000 ffff ...
zrow 16  ffff c000 c000 4000 4000 4000 4000 4000 4000 4000 ffff ...
```

`c000` = 49152(먼 삼각형 z = 0.75), `4000` = 16384(가까운 z = 0.25), 나머지 far.
두 번째 제출이 첫 번째가 쓴 깊이를 읽고 판정했다.  R6g 는 **한 제출 안**에서만 이것을
쟀고, M1h 로 삼각형마다 제출이 갈린 뒤로는 미지였다.

| 게이트 | 값 |
|---|---|
| 카드에 닿은 삼각형 | `submitted +2`, `delegated +0` |
| 깊이 유닛 | `depthSent +2`, 클리어 1 회·되읽기 0 오류 |
| 그림 | **872/872 이 실측 규칙과 정확히 일치** |
| 소프트웨어와의 차이 | **0 화소** |

## 11. 이 칸이 태운 실기 세 번 — 전부 "값"이었다

**(1) 정점 z 가 Mesa 의 단위였다.**  `VB->Win.data[i][2]` 는 [0,1] 이 아니다 — Mesa 가
이미 `DepthMaxF` 를 곱해 둬서 창 z 0.75 가 **49151.25** 로 온다.  카드는 [0,1] 을 받아
`floor(z·2ⁿ)` 을 스스로 한다.  스케일된 값을 보내니 모든 화소가 0xffff 로 클램프돼
far 버퍼와의 비교에서 전부 떨어졌다 — **삼각형 둘이 제출됐는데 아무것도 안 그려졌다.**
계수기는 전부 "예" 였고 그림만이 알았다.  고침: Mesa 자신의 나눗셈(`feedback.c` 171).
규칙 `m1i-z-is-scaled` 와 변이로 박았다.

**(2) 깊이 형식이 24 비트였다.**  R6 측정 스트림의 `ZSTENCILCNTL` 이
`DEPTH_FORMAT_24BIT_INT_Z`(필드 = 2)를 싣고 있었고, 나는 비교 함수와 쓰기 비트만 바꾸고
그 필드를 그대로 뒀다.  카드는 32 비트 깊이를 `mba_z32` 주소에 쓰고 클리어·주소표는
`mba_z16` 을 썼다 — 한 버퍼 위에 배치 둘.  증상은 **`y ≥ 32` 에서 그림이 딱 잘리는 것**
이었고(16 비트 버퍼의 뒤쪽 절반), 카드가 남긴 깊이를 읽어서야 정체가 보였다.
고침: ON 값이 형식 필드를 지우고 16 비트를 넣는다.  그리고 자기검사가 **ON 값의 형식과
주소표가 같은 폭인지** 확인한다.

**(3) 시험이 깊이 버퍼를 안 지웠다.**  Mesa 의 깊이 버퍼는 초기화되지 않으므로
**스톡 링크가 아무것도 안 그렸고**, 두 그림이 전 화소에서 달랐다 — 가속 버그처럼 보이는
시험 버그.  고침: `glClear(… | GL_DEPTH_BUFFER_BIT)`.

*그 셋의 공통점: **하드웨어는 매번 시키는 대로 했다.**  틀린 것은 우리가 준 값이었고,
계수기는 전부 "예" 였다.  잡은 것은 언제나 그림 쪽 게이트였다.*

### 남겨 둔 것

라이브러리가 **설치 때 카드 깊이를 지우는 것은 GL 의미가 아니다.**  이 칸의 단순화이고
(§6), 그 차이가 (3) 에서 소프트웨어와의 불일치로 드러났다.  일반 `glClear` 경로는
다음 칸의 몫이다.

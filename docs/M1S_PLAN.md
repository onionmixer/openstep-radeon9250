# M1s — 남은 유저랜드를 **이등분**한다

재부팅 없음.  라이브러리 손잡이 하나(`RDNMesaNullSend`)와 러너·판정기.

## 1. 왜 또 재는가 — 두 번 연속 추정이 빗나갔다

| 칸 | 추정 | 실측 | 비 |
|---|---:|---:|---:|
| M1p 캐시 금지 창에 쓰기 | +593 us/블록 | −7 us | **0.01 배** |
| M1r 보낸-삼각형 링 21 워드 | 0.21 us/삼각형 | 0.123 us | 0.59 배 |

둘 다 같은 방법이었다 — **소스에서 연산을 세고 마이크로벤치의 속도를 곱했다**.  이
기계에서는 그 곱이 안 맞는다: M1r 의 10 ns 는 "적재 + **부동소수 덧셈** + 저장" 이었고
실제 연산은 정수 워드 복사였다.  그래서 남은 약 1.08 us/삼각형은 **세지 않고 자른다**.

## 2. 자르는 자리

훅은 위에서부터 이렇게 간다: 분류 → 상태 읽기 → **정점 세 개 조립** → 이 라이브러리의
보내기 경로 → (실패하면) Mesa 의 소프트웨어 함수.

`RDNMesaNullSend=1` 은 **조립 바로 다음**(`OSRDNMesaHook.c:1066`)에서 떨어뜨리고,
떨어진 삼각형은 아래의 위임 경로(`OSRDNMesaHook.c:1101-1107`)가 소프트웨어로 그린다.  훅이 하던 일은 전부 그대로
하고, tri 단위와 ioctl 만 안 한다.

| 팔 | 무엇이 들어 있나 |
|---|---|
| `t-stock` | Mesa 소프트웨어만 (훅 없음) |
| `t-nullsend` | **훅 전부** + 소프트웨어 그리기 |
| `t-poison` | 훅 + tri 단위 + ioctl + 커널의 거절 + 소프트웨어 되돌림 |
| `t-quiet` | 전부 (카드가 그린다) |

    훅 자체           = nullsend - stock
    tri 단위 + ioctl  = poison  - nullsend
    진짜 보내기       = quiet   - nullsend + stock     (소프트웨어 그리기를 되더함)

**뺄셈마다 소프트웨어 그리기가 양쪽에 하나씩 있어 상쇄된다** — M1p 에서 되돌림 루프를
"창에 쓰기" 라고 잘못 이름 붙였던 실수를 설계로 막은 것이다.

## 3. 증인 — 팔이 정말 안 보냈다는 것

시계가 아니라 **계수기**가 말한다.  이 팔에서 `submitted` 는 **0** 이어야 하고 훅의
`entered` 는 0 이 아니어야 한다.  판정기는 둘 다 확인하고, 하나라도 어긋나면 값을 내놓지
않고 FAIL 한다.  손잡이 상태 자체도 `step=knobs ... nullsend=1` 로 전사에 남는다.

## 4. 읽는 법

| 관측 | 뜻 |
|---|---|
| `nullsend - stock` 이 크다 | 값은 **훅** 안에 있다 — 분류·상태 읽기·정점 조립.  Mesa 의 디스패치도 여기 포함 |
| `poison - nullsend` 가 크다 | 값은 **tri 단위와 ioctl** 에 있다 — 배치 부기, 창 쓰기, 시스템 호출 |
| 둘 다 작다 | 1.08 us 라는 잔차 자체가 틀렸다.  그러면 차감한 셋(카드 대기·커널·채우기) 중 하나를 다시 잰다 |

## 5. 안전

측정 팔일 뿐 운용 모드가 아니다.  기본값은 꺼짐이고, 켠 팔은 **아무것도 카드로 보내지
않으므로** 그림은 순수 소프트웨어다 — 카드 상태를 건드리지 않는다.  M1q 의 화소 게이트는
이 팔에서도 그대로 돌며 소프트웨어 기하를 확인한다.

## 6. 실기 결과 (run 790100497, 부팅 `0710c8bb`, 빌드 `1790100436`, **재부팅 0 회**)

증인부터.  `t-nullsend.out` 이 스스로 말한다:

    step=knobs   sentlog=1 batch=1 nullsend=1
    step=end     triangles=91086 delegated=91086 nosw=0
    step=end-tri entered=0 submitted=0

훅에 91,086 번 들어갔고 **전부 소프트웨어로 넘겼으며 tri 단위에는 한 번도 안 들어갔다**.

> 판정기를 먼저 고쳐 두지 않았으면 이 팔을 실패로 읽을 뻔했다.  첫 판은
> `step=end-tri entered=` 를 "훅이 돌았나" 의 증거로 삼았는데, **그건 tri 단위의 계수기**
> 이고 이 팔에서는 당연히 0 이다.  훅의 계수기는 `step=end ... triangles=` 다.
> 실행 결과를 기다리지 않고 소스를 읽어 잡았다.

### 6-1. 기울기 (다리 4, 저-군집 5, 제출당 `us = a + b·n`)

| 팔 | a (us) | **b (us/삼각형)** |
|---|---:|---:|
| `t-stock` | 2.3 | 1.373 |
| `t-nullsend` | 2.2 | **2.161** |
| `t-poison` | 159.7 | 2.555 |
| `t-nosent` | 529.1 | 1.895 |
| `t-quiet` | 528.9 | 2.001 |

    훅 자체          = 2.161 - 1.373 = **+0.788 us/삼각형**
    tri 단위 + ioctl = 2.555 - 2.161 = **+0.394 us/삼각형**

군집 크기 4~7 에서 훅 0.718~0.788, 단위 0.389~0.396 으로 안정적이다.

### 6-2. 그리고 모형이 닫혔다

다섯 항을 **각각 따로** 재서 더하면 세 팔의 실측을 모두 맞힌다:

| 몫 | us/삼각형 | 비중 | 어떻게 쟀나 |
|---|---:|---:|---|
| **훅** (분류·상태 읽기·정점 15 워드 조립) | 0.788 | **39.2 %** | M1s: nullsend − stock |
| **카드의 스트림 읽기** (46 ns/워드 × 15) | 0.690 | **34.3 %** | M1q: 커널이 제 시계로 잰 대기 |
| **tri 단위 + ioctl** (창에 쓰기·배치 부기) | 0.394 | **19.6 %** | M1s: poison − nullsend |
| **보낸-삼각형 링** (순수 계측) | 0.123 | 6.1 % | M1r: quiet − nosent |
| **카드의 채우기** (1.7 ns/화소 × 10) | 0.017 | 0.9 % | M1q: 다리 쓸기 |
| 합 | **2.012** | | |

    poison 예측 = 훅 + 단위 + 소프트웨어 = 2.555   실측 2.555   차 -0.000
    quiet  예측 = 훅 + 단위 + 링 + 카드   = 2.012   실측 2.001   차 +0.011
    nosent 예측 = quiet − 링             = 1.889   실측 1.895   차 -0.006

**세 팔 모두 0.5 % 안에서 맞는다.**  한계비 2.00 us 는 이제 전부 이름이 있다.

### 6-3. 훅의 0.788 us 는 산술이 아니다

M1r 이 훅의 산술 전부를 **50 ns** 로 쟀다.  0.788 us 의 6 % 다.  위임 비용
(`osrdnSlotOf` 는 슬롯 넷을 도는 루프 + 간접 호출 하나, `OSRDNMesaHook.c:1101-1107`)도
수십 ns 규모다.  남는 것은 **메모리 접근**이다 — 삼각형마다

- `ctx->Light.ShadeModel`, `ctx->Texture.ReallyEnabled`, `ctx->Color.BlendEnabled`,
  `ctx->Depth.Test` — **서로 다른 캐시 줄**에 있는 네 필드
- `osrdn_surf_shifts()` — 다른 오브젝트로의 호출 + 포인터 넷에 쓰기
- `VB->Win.data[idx[i]][0..2]`, `VB->ColorPtr->data[...]` — Mesa 정점 버퍼 포인터 추적

**이 중 앞의 둘은 렌더 패스 안에서 바뀔 수 없다.**  다음 칸(M1t)은 그것을
`RenderStart` 로 끌어올리는 손잡이 하나다 — 그리고 **또 세어서 맞히지 않는다**, 손잡이를
달고 잰다.

# M1n — 제출 로그를 끌 수 있게 한다 (계획, 재부팅이 드는 칸)

기준일 2026-09-22.  선행: M1m 완료(`docs/M1M_PLAN.md` 11, 12, 13).

## 1. 왜

M1m 이 남긴 고정비는 **1.60 ms** 이고 그중 **0.73~0.90 ms 가 "받아들여지기 전"**,
즉 ioctl + 로그 + 열고 닫기다(열고 닫기는 36 us 뿐).  그리고 M1m §12 가 더 큰 것을
찾았다: **로그 비용은 상수가 아니다.**

    갓 부팅(배달 중)     제출당 약 10 ms
    오래 켠 뒤(포화)      제출당 약 0.7 ms

같은 코드가 부팅 상태에 따라 7 배 다르게 측정된다.  그래서 이 칸은 속도만의 문제가
아니라 **측정 가능성의 문제**다 — 로그를 못 끄면 앞으로의 모든 수가 "어느 상태에서
쟀는가" 에 매달린다.

그리고 로그의 **증거 가치는 이미 환상이다**: 이번 실행의 제출 약 1,700 건 중
`/usr/adm/messages` 에 남은 `RDN-R5 begin` 은 파일 전체를 통틀어 814 줄이었다.
대부분은 이미 버려지고 있다.

## 2. 이 칸의 한 줄

**클라이언트 제출의 로그를 op 하나로 껐다 켤 수 있게 한다.**  기본은 켜짐.

## 3. 어떻게 — 새 파라미터가 아니라 **새 op 하나**

M1m §3 은 `setIntValues` 파라미터를 새로 만들자고 했다.  op 도구를 읽고 나니
**그럴 필요가 없다**: 도구는 이미 `{CP_MAGIC, op, arg, len}` 을 보내고
(`rdnr5cp.m:185`), 드라이버는 그것을 `op` 로 분기한다(`osrdn_cp.m:4223-4262`).
op 를 하나 더 넣는 쪽이 표면이 훨씬 작다.

| | 바꾸는 것 | 줄 수 |
|---|---|---|
| 1 | `CP_OP_QUIET 14`, `CP_OP_LAST` 13 → 14 | 2 |
| 2 | `osrdn_cp_state` 에 `int quiet; unsigned long quietSwallowed;` | 2 |
| 3 | `cpQuiet(c, arg)` — 플래그만 세운다.  **로그는 안 찍는다**(규칙 `r5-quiet` 가 `osrdn_cp.m` 의 `IOLog` 를 금지한다) | ~6 |
| 4 | 디스패치에 `else if (op == CP_OP_QUIET)` 한 줄 | 1 |
| 5 | r7b 제출 경로(`OSRDNDisplay.m:1332-1358`)의 두 `IOLog` 를 `if (!rdnCp.quiet)` 로 감싸고, 삼킨 수를 센다 | ~6 |
| 6 | `osrdn_cp_lines` 의 상태 줄에 `quiet=` 와 `swallowed=` 를 덧붙인다 | 2 |
| 7 | op 도구와 `cpOpNames[]` 에 이름 `quiet` | 2 |

**다른 연산의 로그는 안 건드린다.**  `CP_OP_*` 경로의 로그는 R5·R6 판정기의 증거다.

## 4. 이 칸이 하지 않는 것

- 로그를 **지우지** 않는다.  기본은 켜짐이고, 끄는 것은 한 실행 안에서만이다.
- 열고 닫기(36 us)를 고치지 않는다.  1.60 ms 중 2 % 다.
- 받아들여진 뒤의 ~0.88 ms 를 건드리지 않는다.  이 칸이 끝나면 그게 제일 큰 몫이 되고,
  그때 무엇인지부터 **재서** 안다.

## 5. 위험

| | 위험 | 막는 법 |
|---|---|---|
| A | 조용한 실행에서 실기 실패가 나면 증거가 없다 | 기본 켜짐 + **삼킨 수를 세어** 끌 때·켤 때 찍는다 |
| B | `CP_OP_LAST` 를 늘리면 **INJECT 분기가 흔들린다** — 지금 마지막 `else` 가 INJECT 다 | 새 op 를 INJECT **앞에** 명시적으로 넣는다.  그리고 `cpOpNames[]` 크기가 `CP_OP_LAST+1` 이므로 이름을 반드시 채운다 |
| C | 옛 op 도구가 새 op 이름을 모른다 | 도구는 빌드마다 새로 만들어진다(`target-build-r2b0.sh` 7 단계).  `r5op.sh` 는 설치 표시자를 따라간다 |
| D | 드라이버가 안 올라온다 | 설치 전 `nm -u`, `sim_r5`, 소스 규칙, 그리고 변경은 플래그 하나 |

## 7. Q1·Q2 의 답 (읽기, 코딩 전)

**Q1 — `CP_OP_LAST` 를 쓰는 자리는 넷뿐이다**(전수 grep):

    osrdn_cp.m:2910     범위 밖 op 거절
    osrdn_cp.m:2951     연산 뒤 CSQ 기록의 조건
    osrdn_modelog.m:252 cpOpNames 의 크기 (M1z 이후 크기 없이 선언)
    osrdn_modelog.m:248 이름을 못 붙이는 범위

**그리고 지금 "분기 없는 in-range op" 는 `CP_OP_INJECT`(9) 하나뿐이다.**  python 으로
정의된 op 13 개와 명시 분기를 대조해 확인했다 — `STOP`·`RECORD` 는 걸쇠 검사보다
**앞에서** 처리되고, `LOAD`..`PLANE` 이 명시 분기이며, 마지막 `else` 에 떨어지는 것은
INJECT 뿐이다.  그러므로 **14 에 명시 분기를 주면 아무 op 도 자리를 바꾸지 않는다.**

**자리는 걸쇠 검사 *뒤*에 둔다.**  그러면 **걸쇠가 걸린 드라이버는 QUIET 을 거절한다** —
실패한 드라이버는 증거를 덜 남길 것이 아니라 더 남겨야 한다.  의도한 선택이다.

**Q2 — `rdnCp` 는 살아 있는 상태가 맞다.**  `osrdn_mode_cp(mode, base, cp, …, copy)` 가
`cp` 를 그대로 `osrdn_cp_run` 에 넘겨 **고치고**, 끝에 `*copy = *cp` 로 스냅샷만 뜬다
(`osrdn_mode.m:1470-1504`).  그러므로 한 op 에서 세운 `cp->quiet` 는 다음 ioctl 에서
읽힌다.

덧붙여 읽어서 알게 된 것: `osrdn_mode_cp` 는 `STOP`·`RECORD`·`REC3D` 가 아닌 op 에
`snapshotValid && modeWritten` 을 요구한다(`osrdn_mode.m:1487-1489`).  그러니 **QUIET 은
모드가 써진 뒤에만 듣는다** — 정상 부팅에서는 문제가 없고, 아니면 `CP_RC_NOT_LIVE` 로
정직하게 실패한다.

## 8. codex 교차검토 (코딩 전)

| codex 주장 | 내 검증 | 판정 |
|---|---|---|
| **op 10(REC3D)은 분기가 없어 오늘도 INJECT 로 흘러간다** | `osrdn_cp.m:4218` 에 `else if (op == CP_OP_REC3D)` 가 **있다**.  codex 에는 사슬의 꼬리만 보여 줬고 그 부분을 추측했다 | ❌ **기각** |
| 마지막 `else` 는 **op 를 안 본다** — in-range 인데 분기 없는 값은 무엇이든 INJECT 가 된다 | 사실이다.  오늘은 그런 값이 9 뿐이라 무해하지만, **와일드카드인 것은 맞다** | ✅ 채택 — `op == CP_OP_INJECT` 를 **명시**하고 끝에 거절 분기를 둔다.  그러면 §5 의 위험 B 가 **사라진다** |
| **`cpRefuse` 는 `c->rc` 를 안 세운다** → 거절된 연산이 앞 연산의 `rc` 를 물고 있을 수 있다 | 사실이다(`cpRefuse` 는 `why`·`gateValue` 만 세우고 0 을 반환).  `cpRefused` 는 `CP_RC_REFUSED` 를 반환하지만 디스패치의 거절 분기는 `(void)cpRefuse(...)` 를 쓴다 | ✅ 사실 — **이 칸에서는 안 고친다**(기존 판정기들의 기대를 바꾼다).  기록해 두고 따로 다룬다 |
| C89 고정 크기 배열이라 이름 한 칸을 빠뜨리면 **조용히 널 포인터**가 된다 | 맞다.  칸 수가 `CP_OP_LAST + 1` 이라 모자라면 0 으로 채워진다 | ✅ 채택 — **소스 규칙으로** 칸 수와 마지막 이름을 센다 |
| 플래그가 **무기한**이다 — 도구가 죽으면 로그가 영영 꺼진 채 남는다 | 우리 러너는 끄고 켜지만, 죽으면 그렇다 | ✅ 채택 — **커널이 강제하는 임대**: `QUIET` 이 `len` 을 예산으로 받고, 그만큼의 제출을 삼킨 뒤 **스스로 켜진다** |
| 두 로그 호출 사이에 플래그가 바뀌면 하나만 나갈 수 있다 | `begin` 줄은 **claim 밖에서** 찍힌다(`OSRDNDisplay.m:1324` 주석: 행을 오프라인에 두려고 일부러) | ✅ 채택 — 제출당 **한 번만 읽어** 지역 변수에 담고 두 결정에 같은 값을 쓴다 |
| 끄기 전에 **로그 소비자를 전수 조사**하라 | M1m 에서 했다(M1 판정기는 드라이버 로그를 안 읽는다).  Q3 로 다시 한다 | ✅ 채택 |

**그래서 §3 을 고친다**: 와일드카드를 없애고, `QUIET` 에 **예산**을 주고, 플래그는
제출당 한 번만 읽는다.  줄 수는 늘지만 전부 "조용히 틀릴 수 있는 곳" 을 지운다.

## 9. Q3 의 답, 그리고 러너가 거짓말하던 한 줄

드라이버 로그를 읽는 검사기는 **열한 개**이고 전부 R 사다리 것이다
(`r2b0`·`r3`·`r4`·`r5`·`r6`·`r7`).  **M1 판정기는 하나도 안 읽는다.**

덤으로: `run_m1d.sh:117` 이 `dmesg | grep RDN | tail -20` 으로
"드라이버 자신의 시선" 을 보여 준다고 적어 놓고 **아무것도 안 보여 준다** —
이 기계의 `dmesg` 는 `Can't get kernel namelist` 로 실패한다(실측).  로그는
`/usr/adm/messages` 로 간다.  다음에 손볼 때 고친다.

## 10. 상태 — 설치 완료, **재부팅 대기** (2026-09-22)

바꾼 것(계획 §3 을 §8 의 교차검토대로 고쳐서):

- `CP_OP_QUIET 14`, `CP_OP_LAST` 13 → 14
- **`len` 하나가 임대다**: `quiet N` 은 N 회를 삼키고 **스스로 켜진다**, `quiet 0` 은 지금 켠다.
  도구가 `arg` 에 씨앗을 넣으므로 on/off 를 거기 두면 **항상 off 로 읽혔을 것**이다.
- `osrdn_cp_quiet_take()` — 제출당 **한 번만** 읽고, 임대를 쓰고, 다 쓰면 로그를 돌려준다
- 디스패치의 **와일드카드 `else` 를 없앴다**: `op == CP_OP_INJECT` 를 명시하고 끝에 거절
- 이름표 둘(`cpOpNames`, 도구의 `opNames`)에 `quiet`, 그리고 **컴파일 시간 고정**:
  칸 수가 안 맞으면 컴파일이 거절한다(호스트에서 실제로 거절되는 것을 확인)

| 게이트 | 결과 |
|---|---|
| 소스 규칙 `m1n-quiet` | 변이 **5/5 포착**, `check_r5_src: PASS` |
| 가짜 CP 시뮬레이터 | `sim_r5: PASS` |
| 타깃 빌드(+`nm -u`) | `OSRDNBUILD PASS stamp=b652f3e2 runid=790086837`, 심볼 20 |
| 호스트 릴로크 게이트 | `check_reloc_r2b0: PASS` |
| 설치 | `INSTALL DONE runid=790086837`, `closed=yes fresh live` |

**부팅 뒤**: `bash build/m1l/run_m1l.sh` 가 이제 **여섯 팔**을 돈다 — stock / batched /
nobatch / held / poisoned / **quiet**.  `t-accel` 과 `t-quiet` 의 차이가 곧
**드라이버 로그 25 줄의 값**이다.  그리고 M1d 의 일곱 모드로 화소가 안 바뀐 것을 다시 본다.

## 11. 결과 — 스위치는 됐고, **로그는 생각보다 싸다.  진짜 몫은 다른 데 있다**

드라이버 `b652f3e2`, 부팅 1 회, 실행 세 번(`790089509`·`790089625`·`790089718`).
`op=quiet r=0` — 새 op 가 켜고 끈다.

### 먼저, 측정이 나를 속일 뻔했다

첫 실행은 "로그 25 줄 = 제출당 747 us, 32 %" 라고 말했다.  그런데 같은 실행의
다른 수들과 안 맞았다 — 로그 747 + 열고닫기 652 가 "판정 전 전부" 인 326 보다 컸다.

그래서 **같은 팔을 처음과 마지막에 한 번씩** 돌려 봤다(`t-accel` 과 `t-accel2`,
변수는 순서뿐).  차이가 **612~622 us** 였다.  **팔 사이의 차이는 그 자보다 커야
의미가 있다** — 로그 차이(−450)는 그보다 작았다.  즉 첫 실행의 "747 us" 는
**순서였지 로그가 아니었다.**

우리 Matrox 기록에 답이 있었다: `AB BA`(`openstep-mga-mesa-tiercost.c:30-32` 가
같은 이유로 중앙값을 쓴다).  그대로 넷을 붙여 돌렸다(on, off, off, on).
두 차이가 **−450 과 +730 으로 부호가 반대**로 나왔고, 평균은 +135 us 다 —
**입력이 1,200 us 어긋난 평균이라 못 믿는다.**  이 설계로는 못 가른다.

### 세 실행을 통틀어 **살아남은** 수

    팔                 run1    run2    run3      (n=1 의 정상 바닥)
    t-hold             1565    1566    1565      <- 세 번 다 같다
    t-quiet / t-ab3    1480    2060    1474
    t-accel            2189    1611    1610
    t-poison            159     160     731

- **로그를 끈 가장 낮은 바닥 1474 us**, 켠 채 노드를 든 팔이 세 번 모두 1565 us.
  열고 닫기는 따로 43 us(지난 부팅 36).  **로그는 100 us 안팎이다** — 실행마다
  600 us 씩 흔들리는 바닥 위에서는 더 좁히지 못한다.
- **10 ms 라던 수는 부팅 직후 몇 초의 상태**였다(syslogd 가 아직 배달할 때).
  정상 상태에서는 작다.

### 그러니 진짜 몫은 여기다

    워드 0 에서 거절(판정 전 전부)            159 us
    로그 끄고 받아들여진 제출                1474 us
    -> 판정 뒤에 일어나는 일                 1314 us   = 제출의 89 %
       그중 표본 digest(2x2x64 회 uncached)    212 us
       설명 안 되는 나머지                   1102 us

로그 off 의 비용 모델: **t(n) = 1475 + 1.89 n us**.

**다음 칸은 그 1.1 ms 다.**  후보는 링 복사, 워드 검증(단, 그건 `b` 에 들어간다),
`cpFence` 의 캐시 플러시, `DC_FLUSH_ALL` + `W_DC` 대기, 드라이버가 앞에 붙이는 프리픽스,
`cpR6Submit` 의 링 패딩.  **짐작하지 말고 재서** 가른다 — poison 팔이 그랬듯이,
경로를 잘라 보는 팔을 하나 더 만들면 된다.

### 이 칸이 헛되지 않은 이유

로그가 작다는 것을 **알게 된 것**이 결과다.  그리고 스위치는 남는다: 앞으로의 모든
측정에서 **부팅 상태에 따라 7 배 흔들리던 교란을 끌 수 있다**.  덤으로 디스패치의
와일드카드가 사라졌다.

# M2e — 빠른 길을 **기본값**으로 (드라이버, 재부팅 필요)

## 1. 왜

M2a·M2d 가 제출마다의 `WBINVD` 를 두 번 잤다: **−221 us**(run 790188919), **−227 us**
(run 790191988).  클라이언트 고정비의 **45 %** 다.  그런데 그것은 **손잡이 뒤에만** 있다 —
`nowb` 는 기본 0 이라 **아무도 안 켜면 클라이언트는 여전히 낸다**.  측정만 하고 안 쓰는 값이다.

근거는 세 갈래이고 전부 이 저장소 안에 있다:

| 근거 | 내용 |
|---|---|
| 형제 드라이버 | 이 머신에서 도는 우리 드라이버 다섯(intel1000·emu10k1·ac97·matrox·mdh10)이 **캐시 명령 0 건**으로 DMA 한다.  가장 강한 것은 기가비트 NIC 의 양방향 서술자 링이다 |
| 상류 | `radeon_cp.c` 의 제출 경로는 배리어 하나뿐이고, `ati_pcigart.c` 는 평범한 PCI 분기에 NOSNOOP 을 안 붙인다 |
| 실측 | `t-stage` 대 `t-nowb` 가 **기록된 삼각형 8 개를 워드 단위로 동일**하게 냈다 — 두 실행에서 |

남는 것은 `cpSubmitFence` 의 **직렬화 + posting 읽기**로, 상류가 하는 것과 같다.

## 2. 이 칸이 하는 일

### 2-1. 기본값을 **0 이 안전한 쪽**으로 뒤집는다 (초기화 줄을 안 쓴다)

먼저 전수 조사(grep, 드라이버 `.m`/`.h` 전부):

| `noWb` 를 만지는 자리 | |
|---|---|
| `osrdn_cp.h:650` | 필드 선언(M2e 뒤엔 `doWb`) |
| `osrdn_cp.m:757` | **유일한 읽기** — M2e 전엔 `if (!c->noWb)`, 지금은 `if (c->doWb)` |
| `osrdn_cp.m:2978` | **유일한 대입** — `cpNoWb` |
| `osrdn_modelog.m:329` | 상태 줄 출력(지금은 `!c->doWb`) |

초기화는 **없다**.  기본 0 은 `OSRDNDisplay.m:355-360` 의 **바이트 단위 0 채우기**에서
온다 — 그 루프는 `initFromDeviceDescription` 맨 앞, `[super initFromDeviceDescription:]`
**앞**에 있다.

그러니 `rdnCp.noWb = 1` 을 한 줄 넣는 방법은 **그 루프 뒤에 있어야만** 맞고, 나중에 누가
또 지우는 코드를 넣으면 조용히 깨진다.

**대신 뜻을 뒤집는다**: 필드를 `doWb` 로 하고 `1` 일 때만 `WBINVD` 를 한다.

    /* 오늘 */                          /* M2e */
    int noWb;                           int doWb;
    if (!c->noWb) wbinvd();             if (c->doWb) wbinvd();
    c->noWb = (on != 0) ? 1 : 0;        c->doWb = (on != 0) ? 0 : 1;   /* nowb 1 = 하지 마라 */

**0 으로 채워진 상태가 곧 빠른 길**이 된다.  초기화 줄이 필요 없고, 지금 있는 0 채우기도,
앞으로 누가 넣을 0 채우기도 **기본값을 깨뜨릴 수 없다**.

바깥 이름(`nowb` 연산, 로그의 `nowb=`)은 **그대로 두고** 출력만 `!c->doWb` 로 한다 —
기존 팔·판정기·게이트가 읽는 문자열이 안 바뀐다.  바뀌는 것은 **값**뿐이고,
기본이 `nowb=1` 로 찍히는 것이 바로 "기본값이 정말 바뀌었다" 는 로그 증거다(§2-3).

손잡이는 그대로 남는다 — `nowb 0` 이 옛 동작을 되돌리고, 그것이 이 변경의
**되돌림 경로**다(재부팅 없이).

### 2-1b. codex 교차검토 — 판정표

codex 에게는 §2-1 의 **옛 판**("초기화에서 `noWb = 1`")을 물었다.  답은 그 판을 정밀하게
만들어 주었고, 동시에 **왜 그 판을 버려야 하는지**를 보여 준다.

| codex 주장 | 내 검증 방법 | 판정 |
|---|---|---|
| 넣을 자리는 `cpReset` 의 `c->resetDone = 1` **바로 앞**(`osrdn_cp.m:1070-1071`) | 열었다: `c->wptr = rp;` 다음 줄이 `c->resetDone = 1;` | ✅ 사실 |
| 성공 반환에 넣으면 늦다 — `resetDone` 뒤에도 `CP_RC_POST` 로 나가는 길이 둘 있다(`osrdn_cp.m:1078-1081`) | 열었다: `cpWait` 실패와 `cpMapGate` 실패가 각각 `return CP_RC_POST` | ✅ 사실 |
| 제출은 그 앞에 못 온다 — `cpStart` 가 `resetDone` 을 요구하고(`osrdn_cp.m:1131-1132`) `CP_ST_RUNNING` 은 `osrdn_cp.m:1153`, 클라이언트 경로는 `osrdn_cp.m:3043` 에서 그것을 요구 | 셋 다 열었다(검토 당시 번호로는 845·858·2500, 내 암산이 859 라고 했다가 grep 으로 정정) | ✅ 사실 |
| `noWb` 를 만지는 자리는 읽기·대입·선언 셋뿐이고 whole-state `bzero`/`memset` 은 이 파일에 없다 | 내 grep 전수와 **일치**(§2-1 의 표) | ✅ 사실 |
| `cpLatch`(`osrdn_cp.m:464-472`, M3j 뒤 덤프는 `cpLatchDump` 254–)·`cpStop`(`osrdn_cp.m:1336`)·`osrdn_cp_quiesce`·연산마다의 지움이 그것을 안 건드린다 | `cpLatch` 를 열어 두 줄만 바꾸는 것을 봤고, 나머지는 **대입이 하나뿐**이라는 전수로 자동 | ✅ 사실 |
| 대입 한 줄은 바꾸지 말 것 — 바꾸면 `nowb 0` 되돌림이 깨진다 | — | ⚖️ **부분채택**: 뜻을 뒤집으면 그 한 줄(`osrdn_cp.m:2978`)은 **바뀌어야** 하고, 되돌림은 그대로 산다(`nowb 0` → `doWb = 1`) |
| **`cpReset` 에 넣으면 리셋마다 기본값이 되살아나 `nowb 0` 을 조용히 되돌린다**(codex 가 스스로 단 단서) | 같은 판단 | ✅ **채택 — 그래서 그 판을 버린다** |
| 두 "DEFAULT IS OFF" 주석이 낡는다 | 둘 다 열었다(검토 당시 빌드 `ff8ab8b5` 의 `osrdn_cp.h` 114 행과 `osrdn_cp.m` 477 행): "len != 0 turns the skip ON.  The DEFAULT IS OFF" 와 "the default is OFF and c->noWb must be turned on deliberately" | ✅ **채택** — 둘 다 고쳤고, 되돌아오면 FAIL 하는 규칙을 박았다 |

**결론**: codex 의 자리 분석은 전부 맞지만, 그 분석이 필요하다는 것 자체가 그 판의
약점이다 — 기본값이 **리셋 수명주기에 묶인다**.  `doWb` 뒤집기는 리셋·래치·정지·재열기
어느 것도 보지 않아도 되고, codex 가 마지막에 단 "리셋마다 되살아나면 되돌림이 깨진다"
는 문제도 안 생긴다.  **§2-1 의 뒤집기를 간다.**

### 2-2. 팔은 **자기 손잡이를 스스로 말한다**

오늘 팔들은 앞 팔이 남긴 상태를 **물려받는다**.  기본값이 바뀌면 그 상속이 조용히 뜻을
바꾼다: `t-stage` 는 "WBINVD 켬" 이라고 적혀 있지만 실제로는 "기본값이 무엇이든 그것" 이다.

**계획을 쓰면서 "둘 다 이미 그 연산을 낸다" 고 적었는데, 세어 보니 틀렸다.**
러너를 기계로 훑어(각 팔 앞 30 줄에서 `nowb`/`time` 연산을 찾아) 나온 표:

| 팔 | `nowb` | `time` |
|---|---|---|
| t-stock, t-quiet, t-nosent, t-nullsend, t-inline, t-nullinl, t-group, **t-stage** | 물려받음 | 물려받음 |
| t-accel, t-nobatch, t-hold, t-poison | 물려받음 | 1 |
| t-nowb | 1 | 물려받음 |
| t-spin | (앞 팔의 복원이 우연히 인접) | 물려받음 |
| t-notime | 물려받음 | 0 |
| t-bothoff | 1 | 물려받음 |
| t-accel2 | 0 | 1 |
| t-stage2 | 물려받음 | 1 |

**기준 팔 `t-stage` 조차 두 손잡이를 다 물려받는다.**  오늘은 맞는 값을 물려받고 있을
뿐이고, 기본값이 바뀌면 그 상속의 뜻이 통째로 바뀐다.

그래서 러너에 함수 하나를 넣는다:

    knobs() {           # $1 = nowb, $2 = time -- 팔마다 자기 상태를 말한다
        ...
    }

그리고 **판정기의 짝이 쓰는 모든 팔**이 그것을 부른다.  짝은 "손잡이 하나만 다르다" 를
전제로 값을 찍는데, 그 전제가 지금은 **팔의 순서**에 실려 있다.  함수로 옮기면 팔을
옮기거나 새 팔을 끼워도 전제가 안 깨진다.

검사: 러너를 **스텁 `$OP` 로 실제 실행**해서 각 팔 직전에 두 연산이 나갔는지 순서를
대조한다([[checker-discipline]] — 텍스트 규칙은 런타임 값을 못 본다).

이것은 M2c 가 계측기에서 한 일(`time 1` 을 첫 팔 앞에서 한 번)의 **일반화**이고,
그때의 방식은 여전히 상속이었다는 점에서 이 칸이 그것도 고친다.

### 2-3. 판정기는 **기본값을 읽어 확인**한다

드라이버의 상태 줄이 `nowb=` 를 찍는다(M2a).  판정기에 규칙 하나: 이 부팅의 **첫**
상태 줄이 `nowb=1` 이어야 한다 — 기본값이 정말 바뀌었는지 **로그로** 확인한다.
(설치한 빌드가 옛것이면 0 으로 나오고, 그러면 이 부팅의 모든 팔은 옛 기본값이다.)

## 3. 이 칸이 **안 하는** 것

- **제출 로그(`quiet`)의 기본값은 안 건드린다.**  그것이 실은 더 큰 값이다 — 로그 켠 팔의
  절편이 1575 us, 끈 팔이 492 us 로 **1,085 us/제출**(M2d 6).  하지만 지금 이 사다리는
  그 로그로 측정한다: 기본을 끄면 모든 게이트가 눈이 먼다.  그리고 `quiet` 는 **리스**라서
  기본값을 뒤집으면 "도구가 죽으면 조용한 채로 남는다" 던 설계 근거가 뒤집힌다
  (`osrdn_cp.h:98`).  **출시 전 항목으로 따로 적는다.**
- **두 제출 합치기.**  M1y 가 미룬 그대로.  오늘 값은 대략 `put`/2 + 이름없는몫/2 ≈ 29 us
  (M2d 6-2)이고, 스트림 합치기는 PACKET2 패딩과 겹치는 자리가 있어 설계가 필요하다.
- **도어벨·posting 의 40 us.**  그 자리의 상당 부분이 계측기 자신이라 손잡이를 켠 채로는
  못 가른다(M2d 6-1).  M2e 뒤에 따로.

### 4-1. 코딩 중에 잡은 것 셋

1. **`bootDoWb` 를 `boot()` 직후에 읽으면 부족하다.**  codex 가 제안한 자리(`cpReset`)에

2. **모형의 `nowb 0` 을 START 뒤에 두면 MAP 게이트가 깨진다.**  연산마다 지워지는 필드를

**잡고 있는 팔은 세 번 다 같다**(1528.2 ~ 1551.8, 폭 23.6).  **안 잡는 팔만 607 us
흔들린다.**  그러니 그 차이는 열고닫기의 값이 아니다.

### 7-1. 원인은 코드에 있었다

`rdnDevOpen`(`OSRDNDisplay.m:129-188`)과 `rdnDevClose`(`OSRDNDisplay.m:216-240`)가
**무조건 `IOLog` 한다**.  그리고 `quiet` 게이트는 **제출 경로에만** 있다
(`OSRDNDisplay.m:1308`) — 열고닫기는 안 덮는다.

그래서 노드를 **안 잡는** 팔은 제출마다 `IOLog` 를 **둘** 더 내고, 그 값은
syslogd 가 배달 중이냐 버리는 중이냐에 따라 한 줄에 ~400 us 와 ~13 us 사이를 오간다
([[measurement-discipline]]).  잡는 팔은 그것을 **한 번만** 낸다.

M1n 이 이미 이 모순을 적어 두었다(`M1N_PLAN.md:154`): "로그 747 + 열고닫기 652 가
'판정 전 전부' 인 326 보다 컸다."  그때는 원인을 못 찾고 순서 탓으로 두었다.
**원인은 순서가 아니라 게이트 밖의 `IOLog` 였다.**

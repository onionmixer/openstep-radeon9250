# M1h — 한 프레임에 삼각형 하나보다 많이 (계획)

기준일 2026-09-22.  선행: M1g 완료(`docs/M1G_PLAN.md` 9).
**이 문서는 코딩 전에 쓴다.**  그리고 이 칸은 **드라이버를 고치므로 재부팅이 필요하다** —
M1d 부터 M1g 까지 네 칸이 재부팅 0 회로 끝난 자리에서, 여기가 그 끝이다.

## 1. 이 칸의 한 줄

지금은 **제출 한 번에 ZPREP 한 번**이다.  러너가 프로세스 시작 전에 ZPREP 을 한 번
돌리므로, 한 프로세스가 카드로 보낼 수 있는 삼각형은 **하나**다.  나머지는 전부
소프트웨어로 떨어진다(M1d 첫 실기에서 `REFUSED=2` 로 실제로 그랬다).
이 칸은 그 제한을 없앤다.

## 2. 왜 지금인가 — 깊이가 이것을 먼저 요구한다

`docs/M1_NEXT_DECISION.md` H1–H3 이 이미 적어 둔 것:

- 앞의 네 칸(플랫·구로·블렌드·텍스처)은 전부 **화소 단위**라 삼각형 사이에 흐르는
  상태가 없다.  폴백한 삼각형은 소프트웨어가 똑같이 그리고, 그림은 맞는다.
- **깊이는 다르다.**  삼각형 둘이 겹칠 때 하나는 카드의 깊이 버퍼로, 다른 하나는
  Mesa 의 깊이 버퍼로 판정되면 서로를 못 본다.  "삼각형을 잃지 않는다" 로는 부족하고
  **같은 버퍼로 판정**해야 한다.

그러므로 순서는 **먼저 여러 삼각형, 그 다음 깊이**다.  두 개를 한 칸에 넣으면
실패했을 때 어느 쪽인지 못 가린다(M1g 가 "한 칸에 규칙 둘" 을 피한 것과 같은 이유).

## 3. 지금 코드가 무엇을 막고 있나 (읽어서 확인한 것)

| | 사실 | 확인한 곳 |
|---|---|---|
| J1 | 클라이언트 제출은 `CP_OP_ZCLEAR` 로 실려 온다 | `osrdn_cp.h:87` |
| J2 | ZCLEAR 은 `zprepped` 가 아니면 `CP_WHY_NOT_PREPPED` 로 거절한다 | `osrdn_cp.m:3195-3196` |
| J3 | 그리고 성공하면 **그 자리에서 소비한다** — "one ZCLEAR per ZPREP" | `osrdn_cp.m:3215` |
| J4 | `zprepped` 를 세우는 것은 ZPREP 뿐이고, 그것은 **CPU 가 256 KiB 를 패턴으로 채우고 되읽어** 확인한 결과다 | `osrdn_cp.m:2509`, `osrdn_cp.h:86` |
| J5 | 그 256 KiB 는 창 전체이므로 **텍셀도 색 표면도 함께 지워진다** | `docs/M1_NEXT_DECISION.md` H4 |
| J6 | ZPREP 은 드라이버 연산이라 라이브러리가 부를 수 없다(ioctl 은 CAPS 와 SUBMIT 둘뿐) | `docs/M1D_PLAN.md` 4e |

**J5 가 이 칸의 모양을 정한다**: "제출마다 ZPREP" 은 답이 될 수 없다.  그러면 제출마다
텍셀과 이미 그린 화소가 지워진다.  즉 **ZPREP 을 더 자주 부르는 것이 아니라, 클라이언트
제출이 ZPREP 을 요구하지 않게 하는 것**이 맞는 방향이다.

## 4. 코딩 전에 답해야 할 것

여기부터는 **아직 답이 없다.**  코딩 전에 하나씩 닫는다.

| | 질문 | 어떻게 답할 것인가 |
|---|---|---|
| Q1 | `zprepped` 는 R6a 의 깊이-클리어 실험이 자기 되읽기를 위해 세운 전제인가, 아니면 클라이언트 경로도 그 패턴에 의존하는가? | `osrdn_cp.m` 의 ZCLEAR 본문을 `zc == CP_R7_CASE` 분기 기준으로 전수로 읽어, 패턴을 읽는 곳이 전부 R6 전용 케이스 뒤에 있는지 확인 |
| Q2 | 한 부팅에서 제출을 여러 번 하면 무엇이 또 막는가? 씨앗(`CP_WHY_SEED`)·`rptr==wptr`·`cpIdleGate`·`cpPoisonHolds` 중 반복에 취약한 것 | 각 조건을 코드에서 읽고, 반복 제출로 깨지는 것이 있는지 python 으로 열거 |
| Q3 | 링 공간: 제출마다 `CP_R6_WORDS` 를 쓰는가, 아니면 누적인가? 프레임당 수십 삼각형이면 넘치는가? | `cpR6Submit` 의 워드 회계를 읽고 최악 프레임을 python 으로 계산 |
| Q4 | 로그: 제출마다 IOLog 를 남기면 **커널 msgbuf 4 KB** 를 넘긴다(MSG_BSIZE 4084) | 제출당 로그를 줄이거나 N 회마다 요약하는 형태를 정한다 |
| Q5 | 판정: 지금 판정기는 "제출 정확히 1 회" 를 요구한다(`judge_m1d`).  여러 번이 되면 그 게이트는 무엇으로 바뀌는가 | 게이트를 **보낸 삼각형 수 == 그린 삼각형 수**로 바꾸고, 그림은 전부를 겹쳐 예측 |

## 5. 이 칸이 하지 않는 것

- 깊이(다음 칸).  이 칸은 **여러 삼각형이 같은 그림에 들어가는 것**까지만 한다.
- 드라이버의 R6 경로 변경.  R6a–R6m 의 측정은 그 경로로 얻었고, 바꾸면 그 증거가
  그 코드의 것이 아니게 된다.  건드리는 것은 **클라이언트(R7) 경로의 전제**뿐이다.

## 6. 재부팅

`osrdn_cp.m` 변경 → 빌드 → **설치 전 `nm -u` 심볼 검사**
→ 설치(`closed=yes fresh live`) → **재부팅 요청**.  재부팅은 사용자 몫이다.

## 7. Q1 의 답 — 패턴은 클라이언트 경우의 **판정에 쓰이지 않는다** (소스에서, python 으로)

`cpZclear`(`osrdn_cp.m:2489-3215`) 안에서 ZPREP 패턴(`c->alias` 와 `cpR6Pattern`)을
읽는 자리는 일곱 곳이고, 각각의 **감싸는 조건**은 이렇다:

| 줄 | 감싸는 조건 | 클라이언트 경우에 도달? |
|---|---|---|
| 2407 | `cs->gidx != 0` (R6g 깊이 미리 채우기) | **아니오** |
| 2455 | `cs->tidx != 0` (R6h 텍스처 올리기) | **아니오** |
| 2640-2641 | 없음 — 3 단계가 깊이·색 버퍼의 **다이제스트**를 뜬다.  패턴 비교는 호출 **안쪽**(`osrdn_cp.m:2460`)에 있다 | **예** |
| 2642-2657 | 없음 — 3 단계가 256 KiB 전체를 훑어 `restChanged` 를 센다 | **예** |
| 2661-2680 | `drawn` (R6d 커버리지 맵) — R7 경우는 `drawn` 이 참이다(`osrdn_cp.m:3112`) | **예** |
| 2697·2709 | `drawn && cs->lanes != 0` (R6e 바이트 평면) | **아니오** |
| 2730 | `cs->tidx != 0` (R6h 텍스처 되읽기) | **아니오** |

도달하는 세 곳은 **전부 측정 출력**이다: 다이제스트(`dDepth`·`dColor`), `restChanged`, `cov`.
다이제스트는 로그로만 나가고(`osrdn_modelog.m` 의 `cpDigestLine`) 판정에 쓰이지 않는다.  3 단계 뒤에 남은
실패 경로는 스크래치 레지스터의 `CP_WHY_MARKER` 뿐이고, 패턴을 근거로 거절하는 곳은
없다.  즉 **`zprepped` 는 R6a 가 자기 되읽기를 위해 세운 전제이고, 클라이언트 경로의
정확성은 그것에 기대지 않는다.**

**내 첫 열거는 불완전했다.**  `cpZclear` 의 **본문 텍스트만** 훑어 `alias`·`cpR6Pattern`
을 찾았고, 다이제스트처럼 **호출 안쪽에서** 패턴을 읽는 곳을 놓쳤다(codex 교차검토
`k01fhnbul` 가 지적, 원문 `osrdn_cp.m:2380-2449` 을 열어 확인함).  결론은 바뀌지
않지만 — 다이제스트도 로그일 뿐이다 — **부재를 주장하려면 호출을 따라가야 한다.**

**왜 "아니오" 라고 말할 수 있나**: 클라이언트 경우는 케이스 표의 **마지막 행(171)**이고,
구조체 39 필드를 그 행의 39 개 초기값에 python 으로 맞춰 읽으면
`gidx = tidx = lanes = dsrc = grid = 0` 이다.  손으로 센 것이 아니다.

### 덤 — Q3 이 이미 답을 하나 얻었다

3 단계는 **제출마다 256 KiB 를 두 번, 캐시 없이** 읽는다(2638 의 `for (k = 0; k < 2; k++)`),
그리고 그 앞에 깊이·색 다이제스트가 각각 한 번 더 읽는다.
지금은 제출이 프레임당 하나라 보이지 않았지만, 이 칸의 목적은 그것을 수십으로 늘리는
것이다.  그러므로 이 칸은 **클라이언트 경우에서 R6 측정 단계를 건너뛰는 것**을 함께
해야 한다 — 없애는 것이 아니라, 그 측정을 요구한 경우들에만 남긴다.

## 8. Q2 의 답 — 반복 제출을 막는 것들 (소스에서)

`cpZclear` 가 그리기 전에 지나는 관문을 순서대로 읽었다.  반복에 대해 셋으로 갈린다.

**(a) 반복과 무관 — 매번 같은 답을 준다**: 상태가 `CP_ST_RUNNING` 인가, `key3d`·`alias`
가 있는가, 케이스 번호가 범위 안인가, R7 검증기, 워드 수, `cpPoisonHolds`,
`SURFACE_CNTL`.

**(b) 반복이 정상적으로 지나간다 — 단 조건이 붙는다**
- **씨앗**: `seed == 0` 이거나 **직전과 같으면** 거절(`CP_WHY_SEED`).  라이브러리는
  환경값에서 시작해 제출마다 올린다(M1d).  프레임당 수십 제출이면 씨앗도 수십 개가
  필요하고, 그건 이미 그렇게 되어 있다.
- **`rptr == wptr`**: 링이 따라잡았을 때만 진행(`CP_WHY_NOT_CAUGHT_UP`).  앞에
  `cpIdleGate` 가 있으므로 순차 제출에서는 만족한다 — 다만 **제출마다 유휴를 기다린다**는
  뜻이고, 그것이 이 칸의 속도 상한이다.

**(c) 반복에 결정적 — `c->failed` 는 부팅 동안 절대 안 지워진다**
`osrdn_cp.m:3046-3047` 에서 `failed` 면 `CP_WHY_FAILED` 로 거절하고, 코드 어디에도
`failed = 0` 이 없다(전수 grep).  이것은 의도된 종결 걸쇠이고 그대로 두어야 한다 —
하지만 **프레임 중간의 마커 실패 하나가 그 부팅의 3D 를 끝낸다**는 뜻이다.
지금은 프레임당 제출이 하나라 "한 번 실패 = 한 그림 실패" 였다.  이 칸 뒤에는
**"한 번 실패 = 그 부팅 끝"** 이 된다.  그러므로 이 칸은 실패율을 0 으로 유지하는
것이 기능 자체보다 중요하고, 판정기는 `failed` 가 섰는지를 따로 봐야 한다.

## 9. Q3 의 답 — 링은 재사용된다, 한계는 제출 하나의 크기다

`cpR6Submit`(`osrdn_cp.m:2404-2452`)은 `wptr` 에 쓰고, `rptr` 이 목표에 닿을 때까지
기다리고, 끝에서 `CP_PACKET2` 로 패딩하며 4096 워드를 **돈다**.  제출이 끝날 때마다
유휴까지 기다리므로 **누적 소진이 없다** — 프레임당 제출 수에는 링이 상한이 아니다.

상한은 둘이다:
1. **제출 하나가 `CP_R6_WORDS`(2064) 워드**를 넘을 수 없다(`osrdn_cp.h:260`).
   삼각형 하나는 지금 77 워드이므로 여유가 크다.
2. **제출마다 유휴를 기다린다.**  그것이 이 칸의 속도를 정하고, 프레임당 삼각형이
   많아질수록 이게 비용이 된다 — 3 단계의 256 KiB 훑기와 함께 §7 의 "측정 단계를
   건너뛴다" 가 여기서도 이유가 된다.

## 10. Q4·Q5 — 결정

**Q4 (로그)**: 제출마다 IOLog 한 줄이면 프레임 하나가 커널 msgbuf(MSG_BSIZE 4084)를
넘긴다.  그러므로 드라이버는 **제출마다 찍지 않는다**: 실패했을 때와, 연산 끝의
요약(제출 수·마지막 why·마지막 씨앗)만 남긴다.  삼각형별 증거는 **라이브러리 쪽
계수기**가 들고 있고(이미 그렇다), 시험이 한 번에 찍는다.

**Q5 (판정)**: `judge_m1d` 의 "제출 정확히 1 회" 게이트는
**`submitted == 라이브러리가 보냈다고 말한 삼각형 수`** 로 바뀐다.  그림 예측은
보낸 삼각형을 **순서대로 겹쳐** 만든다(지금은 하나뿐이라 겹침이 없었다).
`c->failed` 가 섰는지도 새 게이트가 된다(§8 (c)).

## 11. 이제 코딩 — 그리고 거기서 재부팅

Q1–Q5 가 닫혔다.  다음 행동은 `osrdn_cp.m` 을 고치는 것이고, 그것은 설치이고,
**재부팅이다.**  순서: 검토·수정 → 호스트 모의(`sim_r6.py` 계열로 클라이언트 경우의
새 경로를 돌려 본다) → 빌드 → **설치 전 `nm -u`** → 설치(`closed=yes fresh live`)
→ **사용자에게 재부팅 요청**.

| 카드에 닿은 삼각형 | **`submitted +3`**, `delegated +0` |
| 세 쪽의 등식 | `submitted +3 == 라이브러리가 보낸 3 == 시험이 그린 3` |
| 그림 | **820/820 화소가 실측 래스터 규칙과 정확히 일치** |
| 소프트웨어와의 차이 | **0 화소** (T3 이 T1 을 덮은 자리 포함) |
| 잃은 삼각형 | `nosw = 0`, `거절 0 + 미결속 3 + 투영 0 == 위임 3` |
| 링 | 매핑 1 회 |

M1d 가 "제출 1 회" 를 주장으로 삼아야 했던 이유가 사라졌다.  라이브러리는 고치지
않았다 — 제출마다 씨앗을 올리는 코드가 이미 있었고(`mesa/OSRDNMesaTri.c`),
막고 있던 것은 드라이버의 전제뿐이었다.

## 14. 이 칸이 태운 실행 한 번 — 낡은 고정값

첫 실행은 여섯 조합이 **전부** 실패했다.  전사만 보면 라이브러리가 고장난 것처럼
보였다: `installs=0`, 분류기의 사유가 전부 `-`(가속 없음), 씨앗 0.

진짜 원인은 `build/r7b/r5op.sh` 가 **옛 빌드 경로(`790003982`)와 옛 스탬프
(`4529cb57`)를 본문에 박아** 둔 것이었다.  새 드라이버가 올라오자 옛 도구가
`RDNR5 exit=4 state ... build=436c03c0` 으로 **정당하게** 거부했고 — 그 게이트는
있어야 한다 — 러너는 그 결과를 **인쇄만 하고 확인하지 않아** 그냥 지나갔다.
CP 가 안 올라갔고, 탐침은 `NOT_RUNNING`, 모든 모드가 "가속 없음" 으로 거절됐다.

고친 것 둘:

1. **`r5op.sh` 가 설치 표시자를 따라간다.**  `build/r2b0/*/INSTALLED` 중 가장 최근
   것의 `rdnr5cp` 와 그 `BUILD_PASS` 스탬프를 쓴다.  스탬프 대조는 도구가 계속
   한다 — 스크립트가 **지난달 답을 먹이지 못하게** 했을 뿐이다.
2. **러너가 전처리 op 와 ZPREP 을 검사한다.**  빈 줄이거나 `r=0` 이 아니면 그
   자리에서 멈춘다.  "CP 없이 도는 실행은 아무것도 판정하지 않는다."

*교훈은 M1g 의 것과 같은 모양이다: **두 쪽이 각자 옳았고**(도구는 바르게 거부했고
러너는 op 를 바르게 불렀다) **이음매를 아무도 안 봤다.***

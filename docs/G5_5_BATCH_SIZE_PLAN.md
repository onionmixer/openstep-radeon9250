# G5-5 — 배치 크기: 링에 둘을 띄우면 빨라지나 (라이브러리 knob 하나 + 측정, 재부팅 없음)

G5-2 §11: 수락 제출의 23 % 가 링 자리를 기다렸다(평균 1.35 ms).  본문 4,080 워드는 링(4,096)에 하나만 들어가므로, 다음 제출은 앞 제출이 거의 다 그려질 때까지 쓰지 못한다(rptr 은 그리기 속도로 전진, G5-2 §3-1).  배치를 줄이면 둘 이상이 뜬다 — 그러나 제출마다 꼬리의 WAIT_UNTIL(idle)·캐시 비우기(`osrdn_cp.m` 의 꼬리)와 프롤로그·커널 고정비가 붙으므로 **카드 일과 CPU 일이 함께 는다**.  어느 쪽이 이기는지는 추론으로 못 정한다 — 잰다.

## 1. 산수 (python)

| 배치 워드 N | 제출 하나의 링 워드(프리픽스 32 + 본문 N+12 을 16 배수로) | 링에 들어가는 제출 |
|---|---|---|
| 4,068 (지금) | 4,112 | 1 |
| 2,032 | 2,080 | 1 |
| 1,350 | 1,408 | 2 |
| 1,000 | 1,056 | 3 |
| 680 | 736 | 5 |

2,032 로는 여전히 하나다(프리픽스와 패딩).  둘이 뜨는 첫 값은 ~1,350.

## 2. knob — `RDNMesaBatchWords=N`

`triRoomWords`(`OSRDNMesaTri.c`)가 배치 상한의 유일한 출처다(주석: "the real bound is whatever the DRIVER says ... and whatever the window is big enough for, whichever is smaller").  knob 이 있으면 그 값과 셋 중 작은 것.  256 미만은 무시(프롤로그 + 한 삼각형보다 작아지면 배치가 한 삼각형도 못 담는다) — 무시된 값은 RDN-A 줄에 찍는다.  한 번 읽어 저장.

검사: `sim_batch` 에 knob 을 켠 실행 하나 — 모든 스트림이 N 이하이고, 삼각형이 하나도 빠지거나 겹치지 않는다(기본 실행의 스트림들을 이은 삼각형 열과 같다).

## 3. 측정 (사용자 gcdsd, GLQuake `+map start` 300 프레임, `RDNMesaTime=1 RDNMesaTimeSplit=150`)

N ∈ {기본, 1,350, 1,000} 을 **번갈아 두 바퀴**(A B C A B C) — 같은 장면이 실행마다 흔들리므로(G5-0) 한 쌍으로는 판정하지 않는다.  읽는 것: 월드 구간 프레임 ms, 제출·present ms, 제출 수; 실행 전후 커널 `RDN-R5 async` 줄의 차(자리 대기 수·us).  판정: 두 바퀴 모두 기본보다 월드 프레임이 **1 ms 이상** 빠른 N 이 있으면 그것을 기본값 후보로(다음 칸에서 기본 변경), 없으면 기본 유지 — 카드가 병목이라는 뜻.

## 4. codex 에 묻는 것 (코딩 전, 한 주장)

"`triRoomWords` 를 min(…, N) 으로 줄이면 모든 배치 스트림이 N 워드 이하가 되고(세그먼트·프롤로그·truncation 포함), 삼각형을 잃거나 두 번 보내지 않는다 — 배치 경로의 모든 상한 판단이 이 함수를 거친다."

## 5. codex 교차검토 판정 (2026-09-29, `gpt-6-astra`, 코딩 전)

| codex 주장 | 내 검증 | 판정 |
|---|---|---|
| `triRoomWords` 가 유일한 상한은 아니다 — 삼각형 267·세그먼트 256 한도가 따로 있다 | `OSRDNMesaTri.c` 의 `osrdn_tri_batch_joins` 를 열었다 | ⚖️ 사실, 줄이는 방향이라 영향 없음 |
| 스트림이 N 이하로 유지된다: 첫 삼각형·같은 상태·새 세그먼트 모두 `triB.room` 으로 판단 | 세 판단식을 열었다 | ✅ 반증 안 됨 |
| N ≥ 256 이면 가장 큰 첫 삼각형(60 + 2 + 3×7 = 83)이 들어간다 | `OSRDNMesaTriTable.h` 의 상수를 열었다 | ✅ |
| 잃지 않음은 호출자 규약(합칠 수 없으면 flush 후 추가)에 달렸다 | 훅의 F1 분기를 열었다 — 오늘 4,068 에서 쓰는 같은 규약 | ✅ 채택(규약 확인) |

## 6. 구현과 측정 (2026-09-29, 부팅 ee4b61a6, 라이브러리 790644383)

- `RDNMesaBatchWords`: `triRoomWords` 에서 min, 256 미만은 무시하고 RDN-A 에 `batchwords`·`batchwords_ignored`.  `sim_batch`: 하네스의 `getenv` 대역이 이 이름에 답하게 하고(처음엔 모든 이름에 "424242" 를 돌려줘 knob 이 **읽히지 않은 채** 실패했다 — 대역을 먼저 봐야 했다), N=300 에서 모든 스트림 ≤ 300·가장 긴 것 296, knob 을 무시하는 변이가 잡힌다.
- 측정 `build/g55/run.log`(A B C A B C, `judge_g55`):

| 배치 상한 | 월드 프레임 ms (1·2 바퀴) | 제출/프레임 | 자리 대기 (python) |
|---|---|---|---|
| 드라이버 기본(4,068) | 15.31 / 15.28 | 4.6 | 22 %, 5.4 ms/프레임 |
| 1,350 | 15.54 / 15.11 | 13.1 | 17 %, 4.9 ms/프레임 |
| 1,000 | 15.13 / 15.09 | 17.6 | 17 %, 4.9 ms/프레임 |

- **판정: 기본 유지.**  어느 상한도 두 바퀴 모두에서 1 ms 이상 빠르지 않다.  CPU 는 배치 크기와 무관하게 프레임당 ~5 ms 를 카드를 기다리며 보낸다 — **카드가 병목**이다.  더 작은 배치는 기다림을 조금 줄이지만 제출이 4 배가 되어 그만큼 CPU 고정비가 는다.  다음 성능 지렛대는 카드 일 자체(제출마다 꼬리의 WAIT_UNTIL idle·캐시 비우기, 화소 채움)이고, 이 칸 밖이다.

## 7. 곁들여: timedemo (남은 작업 2, 코드 없음)

`run-glquake-timedemo.sh glquake_radeon 640 480 120`(사용자 gcdsd, 소프트웨어 대조군 없이 — 화면 점유를 줄이려고): **4,527 프레임 111.7 초 = 40.5 fps**, `revoked: 0` (`build/g55/td-radeon-640x480.log`).  G4-10 때는 120 초 안에 끝나지 않던 측정이 처음으로 완주했다 — 가속이 온전해진 뒤라 이 숫자가 의미를 가진다([[timedemo-only-when-accel-is-complete]]).

# M1j — `glClear` 의 일반 경로 (계획)

기준일 2026-09-22.  선행: M1i 완료(`docs/M1I_PLAN.md` 10).
**이 문서는 코딩 전에, 그리고 측정 설계보다 먼저 쓴다.**

## 1. 참고가 이미 답하는 것 — 여기서 닫히면 실기로 안 간다

사용자 지적(2026-09-22)에 따라 **순서를 바꿨다**: 잴 것을 정하기 전에 읽는다.
M1i 가 태운 실기 세 번은 전부 아래 같은 자리에 적혀 있던 것들이었다.

| | 사실 | 확인한 곳 |
|---|---|---|
| L1 | `glClear` 는 `Driver.Clear(ctx, ddMask, all, x, y, w, h)` 를 부르고, **그 함수가 돌려준 비트만 소프트웨어로 지운다**.  즉 훅이 처리한 비트는 **빼고 돌려주면** 된다 | `buffers.c:279-281` |
| L2 | `Depth.Mask` 가 0 이면 Mesa 가 **깊이 비트를 아예 뺀다** — 우리가 볼 일이 없다 | `buffers.c:265-267` |
| L3 | ~~**`Driver.Clear` 는 한 번만 설치된다**~~ — **틀렸다, 아래 참조** | `osmesa.c:2005` |

### L3 은 틀렸다 — 줄은 찾고 **어느 함수 안인지**를 안 봤다

`ctx->Driver.Clear = clear;` 는 `osmesa.c:2005` 이 맞다.  전수 grep 도 맞았다(그 한 줄뿐).
틀린 것은 **그 줄이 `osmesa_update_state` 안에 있다**는 것을 안 본 것이다 — 일회성
설치 함수가 아니라 **매 상태 갱신마다 도는 함수**다.  우리 훅은 같은 함수의 스무 줄
뒤(`osmesa.c:2027`)에서 불리므로 **첫 설치는 살아남고**, 두 번째 갱신이 Mesa 것을
되돌려 놓는다.  "한 번만 설치" 가드를 달아 뒀더니 그 뒤로 영영 우리 것이 아니었다.

**실측이 그렇게 말했다**: `cli=1 clc=0` — 설치 1 회, 호출 0 회.

**고친 설계**: 삼각형 함수와 **똑같이 매번 재설치**한다.  의미 있는 가드는 하나뿐이다 —
**우리 포인터를 저장하지 말 것**(체인이 자기를 부른다).

*이것은 `docs/M1H_PLAN.md` 7 에서 `cpR6Digest` 를 놓친 것과 같은 실수다: 줄을 찾고
호출/둘러싼 문맥을 안 따라갔다.*

**그리고 L1·L2 는 여전히 이 칸의 모양을 정한다.**  삼각형 훅은 `state.c` 가 매 `UpdateState` 마다
`Driver.TriangleFunc` 를 지우기 때문에 **매번 다시 설치**해야 했다.  `Driver.Clear` 는
그렇지 않다 — 한 번 세우고, **앞사람의 포인터를 저장해 우리가 안 하는 비트는 그대로
넘긴다**.  M1d 가 소프트웨어 삼각형 함수를 저장해 폴백으로 쓴 것과 같은 모양이고,
같은 이유로 "우리가 처리한 것 + 넘긴 것 = 요청받은 것" 이 게이트가 된다.

## 2. 이 칸의 한 줄

**`glClear(GL_DEPTH_BUFFER_BIT)` 가 카드의 깊이 버퍼를 지운다.**
지금은 라이브러리가 **설치할 때** 지운다 — 그건 GL 의미가 아니고, M1i 에서 스톡
링크와의 불일치로 드러났다(`docs/M1I_PLAN.md` 11-(3)).

## 3. 그래서 재야 하는 것은 무엇인가

L1–L3 이 인터페이스를 전부 닫았으므로 **이 칸에는 새로 잴 하드웨어 규칙이 없다.**
남는 것은 우리 쪽 계약이고 호스트에서 검사한다:

- 요청받은 비트 = 우리가 처리한 비트 + 앞사람에게 넘긴 비트 (계수기로)
- 깊이를 우리가 지웠으면 `Depth.Clear` 를 **실측 변환**(`floor(z·2ⁿ)`)으로 옮긴다 —
  Mesa 의 `d * 0xffff` 가 아니다(R6f 가 실측한 규칙, 값은 `docs/M1I_PLAN.md` 7 에 계산해 뒀다)
- 설치는 한 번, `leaves`/`installs` 로 확인

실기는 **한 번**이면 된다: 지금의 "설치 때 지우기" 를 떼고도 깊이 그림이 같은지.

## 4. 이 칸이 하지 않는 것

색 비트(Mesa 의 소프트웨어 클리어가 우리 표면에 직접 쓰고, M1c 이후 계속 맞다),
스텐실·누산기, `glScissor` 가 켜진 부분 클리어.

## 5. 실기 결과 — PASS (2026-09-22, 드라이버 `436c03c0`, 재부팅 0 회)

라이브러리 `790072853`, 실행 `790072864`.  일곱 조합 전부 `judge_m1d: PASS`,
독립 재계수도 전부 0 불일치.  깊이 칸: `zclear=1 zclearbad=0 cli=3 clc=1`,
**872/872 일치·소프트웨어와 0 화소 차이**.

**설치 때 지우던 것이 없어졌다.**  이제 `glClear` 가 지운다 — GL 이 말하는 대로이고,
소프트웨어 링크와 같은 시점이다.

## 6. 이 칸이 고친 판단 둘 — 둘 다 실기가 말해 줬다

**(1) L3 이 틀렸다(§1 정정 참조).**  `Driver.Clear` 는 매 `UpdateState` 마다 Mesa 것으로
돌아간다.  줄은 맞게 찾고 **둘러싼 함수**를 안 봤다.  `cli=1 clc=0` 이 그것을 말했다.
→ 삼각형 함수처럼 **매번 재설치**한다.

**(2) 깊이 비트를 "가져가는" 설계를 버렸다.**  처음에는 반환에서 깊이 비트를 빼서
Mesa 가 자기 버퍼를 안 지우게 하고, 그것을 "우리가 그리는 상태일 때" 로 막아 뒀다.

- **발동하지 않았다**: 이 장면은 깊이를 켜기 **전에** 지운다(`cli=3 clc=1 zclear=0`).
  그리고 그건 장면의 잘못이 아니다 — 실제 프로그램은 시작할 때 한 번 켜고 매 프레임
  지운다.
- **가져가는 쪽이 위험하다**: 클리어와 삼각형 사이에 *누가 그리는지* 가 바뀔 수 있다.
  상태 하나가 거절되면 소프트웨어가 **아무도 안 지운 버퍼**로 판정한다 — M1i 의 버그가
  반대 방향으로.

→ **카드 것을 지우고 비트는 넘긴다.**  Mesa 도 자기 것을 지운다.  비용은 대개 쓰이지
않는 버퍼를 한 번 훑는 소프트웨어 패스 하나, 대신 **어느 쪽도 오래된 값으로 남지 않는다.**

## 7. 읽기 먼저가 실제로 아낀 것

L1(`buffers.c:279-281`, 돌려준 비트만 소프트웨어가 지운다)과 L2(`buffers.c:265-267`,
`Depth.Mask` 가 0 이면 Mesa 가 이미 뺀다)는 **읽기만으로 닫혔고 실기가 필요 없었다.**
L2 덕에 코드에서 마스크 검사 한 줄이 빠졌다.

틀린 것은 L3 하나였고, 그 이유는 "참고를 안 읽어서" 가 아니라 **"읽은 줄의 문맥을 안
봐서"** 였다 — 다음 칸에서는 인용할 때 **둘러싼 함수와 그것이 불리는 시점**을 함께 적는다.

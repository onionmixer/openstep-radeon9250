# M3a — 주전자: 실제 GL 응용이 카드로 그려지는가 (G1 게이트 3)

**이 문서는 코딩 전에 쓴다.**  드라이버는 안 바꾼다 — **재부팅 없음**.

## 1. 왜

`PLAN.md` §M 의 G1 게이트 3 은 주전자 데모다.  지금까지의 M 사다리는 전부 **우리가 만든
합성 장면**(`test/osrdn-mesa-tri.c`)으로 쟀다.  실제 응용 — 조명, 평가기(`glEvalMesh2`)가
만든 사각형 스트립, 깊이 — 이 `libGL_radeon.a` 로 그려지는 것은 **한 번도 보인 적이 없다**.

## 2. 독립성 — matrox 에 의존하지 않는다 (사용자 지시, 2026-09-24)

- 소스는 이 트리에 새로 쓴다: `test/osrdn-mesa-teapot.c`.  matrox 의 헤더·라이브러리·
  스크립트·경로를 **하나도** 쓰지 않는다.
- 주전자 기하는 **Mesa 3.4.2 자신의** `widgets-mesa/demos/tea.c` 581-730 행
  (`patchdata`·`cpdata`·평가기 루프)에서 **빌드 때** 잘라 온다.  그 구간은 파일의 두 번째
  저작권 블록(529 행, Mark J. Kilgard 1994 / SGI 1993) 안이고, 그 고지는 이 프로젝트의
  `NOTICE` 에 전문으로 싣는다.  잘라 온 헤더 파일은 커밋하지 않는다.
- 검사 규칙: 데모 소스와 빌드 줄에 `matrox`·`MGA`·`OSMGA`·`openstep-matrox` 가 나오면 FAIL.

## 3. 경로 — 소스에서 확인한 것

| | 사실 | 확인한 곳 |
|---|---|---|
| P1 | `glEvalMesh2(GL_FILL)` 은 사각형이 아니라 **삼각형 스트립**을 만든다 — "네 점이 한 평면이라는 보장이 없어서" | `eval.c:2945-2949` |
| P2 | 스트립 렌더러는 새 정점마다 `RENDER_TRI` → `ctx->TriangleFunc` 를 부른다.  클리핑·`DD_SW_SETUP` 경로도 끝은 `ctx->Driver.TriangleFunc` 다 — Mesa 쪽에 우리 훅을 건너뛰는 경로는 없다 | `render_tmp.h:150-166`, `vbrender.c:540-546`, `vbrender.c:313-322` |
| P3 | 우리 묶음 경로(`RenderVBRawTab`)는 `GL_TRIANGLES` 만 덮는다 — 스트립은 **삼각형별 경로**로 온다 | `OSRDNMesaHook.c:1260` |
| P4 | 깊이는 **카드가 소유한다**(M1i): 그 프레임의 **모든** 삼각형이 카드로 가야 깊이가 맞다.  하나라도 소프트웨어로 빠지면 그 삼각형은 Mesa 의 (안 쓰이는) 깊이 버퍼로 판정된다 | `docs/M1I_PLAN.md` 4 |

**그러므로 P4 가 이 칸의 전제다.**  그림을 보기 전에 계수기로 "전부 카드로 갔다" 를 먼저
확인한다 — 폴백만으로도 주전자는 **맞게 그려진다**(`PLAN.md` §M 게이트 3 의 경고).

## 5. 판정 — 그림 전에 계수기

**A. 카드가 그렸는가**(하나라도 어기면 FAIL, 그림은 판정하지 않는다):

처음 안(`entered > 0`, `submitted == entered`, 거절 0)은 **구멍이 있다** — 내가 훅을 읽다 찾았다:
UpdateState 가 어떤 상태를 거절하면(`osrdnHookInstall(ctx, 0)`, `leaves++`) 우리 삼각형
함수가 **설치되지 않고** Mesa 자신의 소프트웨어 함수가 남는다.  그 상태에서 그려진 삼각형은
`entered` 에 **안 잡힌다** — 위 셋이 다 참이면서 일부가 소프트웨어로 그려질 수 있다.

그래서 **계수기와 무관한 기대값**을 쓴다.  `tea.c` 의 그리기 루프(`tea.c` 686-725)는 패치
10 개를 p·q 로 두 번, 그중 6 개를 r·s 로 두 번 더 그린다 = **`glEvalMesh2` 32 번**, 각각
`grid × grid` 칸, 칸마다 삼각형 둘(§3 P1).  그러므로 한 장면에

    Mesa 가 TriangleFunc 를 부르는 수 = 64 × grid²      (python: grid 10 → 6,400)

판정:
- `submitted == 64 × grid²` — **정확히 같아야 한다**.  모자라면 어딘가로 샜다.
- 훅의 `delegated == 0`, `noSoftware == 0`, 삼각형 단위의 거절 사유 전부 0.
- `depthsent > 0`, `smoothsent > 0`(조명 → 구로).

면적 0 삼각형(뚜껑 꼭대기처럼 제어점이 모이는 곳)을 미리 봐주지 않는다.  그것이 어딘가로
빠지면 이 판정이 FAIL 하고, 그때 원인을 판다 — 판정을 미리 느슨하게 하지 않는다
([[checker-discipline]]).

**B. 그림**(두 PPM, 같은 크기):
- 덮인 화소(지운 색이 아닌 화소) 수가 두 그림에서 서로 **2 % 안**.
- 색이 다른 화소는 **테두리여야 한다**: 다른 화소마다, 3×3 이웃 안에 두 그림 중 한쪽에서만
  덮인 화소가 있거나, 채널 차가 **2 이하**.  카드의 래스터 규칙(1/16 절삭·top-left)과
  소프트웨어의 규칙이 다르므로 테두리는 다를 수 있다(R6d), 속은 구로 반올림만큼만.
- 통계는 전부 출력한다: 다른 화소 수, 그중 테두리 몫, 최대 채널 차.
- 그리고 **내가 두 그림을 직접 본다**(PNG 로 바꿔서).

## 8. C7 이 말하는 것 — 뒷면 컬링이 가속을 통째로 끈다

`DD_SW_SETUP` = `DD_TRI_CULL | DD_TRI_CULL_FRONT_BACK | DD_TRI_OFFSET | DD_TRI_LIGHT_TWOSIDE |
DD_TRI_UNFILLED` 이고, 분류기는 이 중 **하나만 서도** `OSRDN_WHY_TRI_SETUP` 으로 상태 전체를
거절한다.  그러면:

- **`glEnable(GL_CULL_FACE)`** 를 켠 응용은 **삼각형 하나도 카드로 안 간다.**  실제 응용은
  대부분 켠다.
- 양면 조명, `glPolygonOffset` 도 같다.

이 데모는 셋 다 끄고 그린다(한 면 조명, 컬링 없음, offset 없음) — 그래야 경로를 잰다.
**그러나 이것은 G1 의 열린 항목으로 남긴다**: Mesa 의 `render_triangle` 은 컬링·오프셋·양면
색을 **처리한 뒤** `Driver.TriangleFunc` 를 부르므로(`vbrender.c:298-322`), 원칙적으로 그 비트들은
거절 사유가 아닐 수 있다.  M3a 뒤의 칸에서 따진다.

## 9. 코딩 전에 멈춘다 — 깊이 경로는 64×64 에 묶여 있고, 그보다 크면 막는 것이 없다

데모 크기를 정하려고 표면 한계를 읽다가 찾았다(**소스를 읽어서 찾은 것이다 — 아직 실기에서
돌려 본 것은 아니다**).

| | 사실 | 확인한 곳 |
|---|---|---|
| S1 | 카드 쪽 깊이 버퍼는 **64×64 고정**: 피치 64, 8 KiB, 64×64 타일 표 | `OSRDNMesaTriTable.h` 43-46 (`OSRDN_TRI_DEPTH_W/H/PITCH`, `DEPTH_BYTE_OFF 0x10000`) |
| S2 | 삼각형 프롤로그는 깊이 피치를 표면과 **상관없이 늘 64** 로 쓴다 | `OSRDNMesaTri.c` 359-363 |
| S3 | 색 표면은 가로·세로 16384 까지 받는다 — 크기 검사는 이것뿐 | `OSRDNMesaTri.c` 307-310 |
| S4 | 분류기는 깊이를 **폭(16 비트)과 비교 함수로만** 본다 — 표면 크기는 안 본다 | `OSRDNMesaClass.c` 118-128 |
| S5 | 창 배치: 색 0, 깊이 0x10000(64 KiB), 텍스처 0x20000(128 KiB) | `OSRDNMesaTriTable.h` 43·449 |

**그러므로 깊이를 켠 표면이 64×64 보다 크면 아무 거절 없이 카드로 가고, 깊이가 조용히 틀린다**
(python): 가로 64 를 넘는 열은 피치 64 때문에 다음 행으로 겹치고, 세로 64 를 넘는 행은 8 KiB
깊이 영역 밖으로 나간다.  256×256 이면 색 표면 자체가 깊이 영역을 덮는다.

M 사다리의 하네스는 전부 **64×64**(`test/osrdn-mesa-tri.c` 40-41)라서 이 경계를 한 번도 넘지 않았다.

### 9-1. 그래서 순서를 바꾼다

1. **먼저 막는다**(라이브러리만, 재부팅 없음): 분류기가 `깊이 켬 && (폭 > 64 || 높이 > 64)` 를
   거절한다 — 새 사유 하나.  그러면 큰 깊이 응용은 **소프트웨어로 깨끗하게** 떨어진다.
   틀리게 그리는 대신 느리게 맞게 그린다.
2. **그다음 주전자를 64×64 로** — 지금 지원하는 경로를 실제 기하로 잰다.  그리고 128×128 로
   한 번 더 — 1 의 거절이 **실제로 걸려 전부 소프트웨어로 가는지** 본다.
3. **진짜 G1 일은 그 뒤다**: 깊이 버퍼를 표면 크기에 맞추는 것(피치 = 표면 피치, 크기는 창에서).
   지금 창(색 0 ~ 깊이 64 KiB)으로는 색이 128×128 까지밖에 안 들어간다 — 창 배치부터 다시 짜야
   하는 큰 칸이다.

## 10. 9-1 의 1 번 — 계획 (코딩 전)

**분류기가 `깊이 켬 && (그림 버퍼 폭 > 64 || 높이 > 64)` 를 거절한다.**  라이브러리만 — 재부팅 없음.

| 자리 | 바꾸는 것 |
|---|---|
| `OSRDNMesaClass.h` | 입력에 `drawWidth`·`drawHeight`, 사유 `OSRDN_WHY_DEPTH_SIZE 11`, `OSRDN_WHY_REASONS 12` |
| `OSRDNMesaClass.c` | 깊이 판정 바로 뒤에 한 가지 — 한계는 **`OSRDN_TRI_DEPTH_W`/`_H`** 를 쓴다(새 64 를 쓰지 않는다; 이미 `OSRDNMesaTriTable.h` 를 include) + 이름 표에 `"DEPTH_SIZE"` |
| `OSRDNMesaHook.c` | UpdateState 가 `ctx->DrawBuffer->Width/Height` 를 채운다(같은 파일이 이미 삼각형 상태에 같은 두 값을 읽는다) |

| `tools/mesa/sim_class.py` | `WHY` 에 `DEPTH_SIZE: 11`; 줄 셋 — 깊이 64×64 **받음**, 깊이 65×64·64×65 **거절 DEPTH_SIZE**, 깊이 끔 128×128 **받음**; 마스크 순회는 64×64 로; 변이 하나(가드를 지우면 줄이 실패) |
| `tools/mesa/sim_texrun.py` | 사유 줄의 기대 문자열에 `DEPTH_SIZE=0` |

### 10-1. 스스로 따진 것

- **행 길이(`rowLength`)는 상관없다** — 깊이는 피치 64 로 x<64, y<64 만 쓰므로 한계는 그림 버퍼
  크기다.  `yUp` 도 행 수를 바꾸지 않는다.
- 깊이를 **안 켠** 큰 표면은 그대로 받는다 — 깊이가 없으면 64 에 묶이지 않는다.
- 거절되면 훅이 설치되지 않고 **그 상태의 삼각형은 전부 소프트웨어**로 간다 — M1i 의 전제
  ("프레임의 모든 삼각형이 한쪽") 가 지켜진다.
- 크기가 바뀌면(`OSMesaMakeCurrent` 에 다른 크기) Mesa 가 상태를 다시 계산하므로 UpdateState 가
  다시 불려 새 크기로 판정한다 — codex 에 확인을 받는다.

### 11-1. 바뀐 설계 — 분류기가 아니라 `triPrologue`

`OSRDNMesaTri.c` 의 `triPrologue` 에 한 줄:

    if (depth && (width > OSRDN_TRI_DEPTH_W || height > OSRDN_TRI_DEPTH_H))
        return 0UL;           /* -> OSRDN_TRI_ARGS: "a size or pitch we cannot express" */

- 그리는 **순간의** 크기와 깊이를 본다 — 낡은 판정도, NULL 도 없다(`osrdnTriStateOf` 가
  렌더 시점에 `DrawBuffer` 를 읽고, 그때는 바인드가 끝나 있다).
- **모든** 카드 전송이 지나므로 묶음 경로도 막힌다.
- 사유는 **`ARGS` 를 그대로** 쓴다 — 헤더의 뜻("표현할 수 없는 크기나 피치")이 정확히 이것이고,
  새 사유를 만들면 이름 표 둘과 판정기들이 같이 움직인다.
- 거절된 삼각형은 훅이 소프트웨어로 넘긴다(M1d 의 약속: 거절해도 잃지 않는다).  그 크기에선
  **모든** 삼각형이 거절되므로 프레임이 한쪽(소프트웨어)으로 모인다 — M1i 의 전제가 지켜진다.
- 소프트웨어 깊이 버퍼는 지워져 있다: 우리 Clear 훅은 카드 깊이를 지우고 **비트를 Mesa 에도
  넘긴다**(`OSRDNMesaHook.c:728`, M1j 의 설계).
- 대가: 64 를 넘는 깊이 응용은 삼각형마다 거절·위임을 거친다 — **느리지만 맞다**.  빠르게 하는 것은
  9-1 의 3 번(표면 크기에 맞춘 깊이)이다.

분류기·UpdateState·이름 표는 **안 건드린다.**

### 13-1. 주전자는 실제 GL 프로그램으로 카드에서 그려진다

| 크기 | 판정 | 계수기 |
|---|---|---|
| **64×64** | **CARD** | 6,400 개 전부 카드로(`submitted == 64·10²`), 위임 0, 거절 0, 깊이 6,400·구로 6,400 |
| **128×128** | **GUARD** | 6,400 개 전부 `ARGS` 로 거절 → 소프트웨어, 카드로 간 것 0 — **§11 의 가드가 실기에서 선다** |

그림:
- 128×128: 스톡 프로그램과 **바이트 단위로 같다**(전부 소프트웨어가 그렸으니 그래야 한다).
- 64×64: 4,096 중 549 가 다르다 — 1 만큼 456, 2 만큼 53, 그 이상 40(최대 75).  **2 를 넘는 40 개는
  하나도 2×2 블록을 이루지 않는다** — 뚜껑 이음매·바닥 가장자리·손잡이의 한 픽셀 폭 선 위에 있다.
  두 그림을 나란히 **눈으로 봤다**: 구별이 안 된다(모양·조명·손잡이 가림·뚜껑 꼭지).

### 13-2. 판정기를 실측으로 고친 곳

§5 B 의 "안쪽은 2 이하" 는 **재지 않고 정한 문턱**이었고, 테두리를 실루엣으로만 봤다.  첫 실행이
메시 **안쪽 모서리** 40 픽셀에서 실패했다.  잡으려는 실패(가림이 틀려 패치 하나가 바뀜)는
**면적**을 바꾸므로, 규칙을 "2 를 넘는 차이가 **2×2 블록**을 이루면 FAIL" 로 정밀화했다 —
자체시험에 3×3 면적(FAIL)과 한 픽셀 선(통과)을 둘 다 넣었다.

### 13-3. 첫 실행이 드러낸 것 — `glFinish` 뒤의 응용 버퍼는 비어 있다

첫 실행의 가속 그림은 **4,096 픽셀 전부 (0,0,0)** — 지우기 색도 없었다.  우리 라이브러리는
색 표면을 바꿔치기하고 응용 배열로는 `osmesa.c` 576·746·892 에서만 되돌린다.  `glFinish` 는
그중이 아니다.  데모는 `OSMesaGetColorBuffer` 로 읽게 고쳤다(하네스와 같은 계약).

**그러나 보통의 OSMesa 프로그램은 `glFinish` 뒤에 자기 배열을 그냥 읽는다** — 그런 프로그램은
`libGL_radeon.a` 에서 빈 그림을 본다.  `PLAN.md` §M 의 요구("`glFinish` … 동기화")가
**채워지지 않았다.**

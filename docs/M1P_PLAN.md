# M1p — 워드를 캐시 메모리에 쓴다 (계획, 재부팅이 드는 칸)

기준일 2026-09-23.  선행: M1o 완료(`docs/M1O_PLAN.md` 9).

## 1. 참고가 이미 푼 문제였다

M1o 가 고정비를 530 us 로 내렸고 **한계비는 네 칸 내내 안 움직였다**(1.90 us/삼각형).
그중 **1.03 us(54 %)** 가 클라이언트가 워드 15 개를 **캐시 금지 매핑**에 쓰는 값이다
(69 ns/워드).  이번엔 우리 소스가 아니라 **참고**에 물었고, 답이 있었다.

| | 참고가 하는 것 | 확인한 곳 |
|---|---|---|
| A | DRI 클라이언트의 커맨드 버퍼는 **매핑이 아니다** — 컨텍스트 구조체 안의 `char cmd_buf[16*1024]`, 즉 **보통 캐시 메모리** | `r200_context.h:712-717` |
| B | 커널은 그것을 **`copy_from_user` 로 읽는다**.  이유가 주석에 있다: *"검사한 값과 쓰는 값 사이의 경쟁을 피하려고"* — **TOCTOU** | `radeon_state.c:2855-2860` |
| C | 워드를 GART 에 직접 쓰는 무복사 경로는 **존재하지만 root 전용**이고 주석이 **"insecure"** 라고 적는다 | `radeon_state.c:2476-2481` |
| D | 디바이스 매핑에 가는 것은 **대량 정점 페이로드뿐**이고, 캐시 메모리에서 조립한 뒤 **`rep movsl` 한 번**으로 쏟는다 | `r200_maos_arrays.c:153-162` |
| E | 클라이언트가 쓰는 버퍼에 **write-combining 을 요청하지 않는다** — r200 트리·DDX src 에 `DRM_WRITE_COMBINING` **0 건** | grep |

**우리는 참고가 한 번도 안 하는 일을 하고 있다**: 삼각형마다 워드 15 개를 캐시 금지
페이지에 하나씩 쓴다.

## 2. 그리고 우리 설계는 이미 절반이 같다

참고가 복사하는 이유(TOCTOU)는 **우리에게도 그대로 있다** — 우리도 워드를 전수 검증하고,
검증 뒤 클라이언트가 못 고치게 해야 한다.  그래서 **우리 커널은 이미 복사한다**:
`osrdn_cp_stage` 가 매핑된 페이지에서 CP 블록으로 옮긴다(`OSRDNDisplay.m:1308`·`OSRDNDisplay.m:1282`).

    참고:  클라이언트가 **캐시 메모리**에 쓴다  → 커널이 copy_from_user → 검증 → 링
    우리:  클라이언트가 **캐시 금지 매핑**에 쓴다 → 커널이 복사        → 검증 → 링

**다른 것은 클라이언트 버퍼의 캐시 속성 하나뿐이다.**  그리고 `copyin` 은 이 커널에 있다
(`prototypes.h:35`).

## 3. 이 칸의 한 줄

**클라이언트가 자기 캐시 메모리에 스트림을 쌓고, ioctl 이 그 포인터를 넘기고, 커널이
`copyin` 한다.**  `d_mmap` 창은 **지우지 않는다** — 둘을 같은 부팅에서 번갈아 재려고 남긴다.

| | 바꾸는 것 |
|---|---|
| 1 | `osrdn_r7b_submit2` — 기존 블록 + `unsigned long words`(사용자 포인터) |
| 2 | 새 ioctl `OSRDN_R7B_IOC_SUBMIT2`(크기가 다르니 번호도 다르다).  **기존 SUBMIT 은 그대로 둔다** |
| 3 | 드라이버: `copyin(words, kernel buffer, nwords*4)` 한 번, 그 다음은 지금과 같은 길 |
| 4 | 라이브러리: 손잡이 `RDNMesaCopyin=1` 이면 새 길, 아니면 지금 길 |

**두 길을 같은 프로세스 안에서 번갈아** 재면 M1n 이 겪은 **팔 순서 교란**(620 us)이
사라진다 — 그게 이 설계에서 제일 값진 부분이다.

## 4. 위험

| | 위험 | 막는 법 |
|---|---|---|
| A | `copyin` 이 나쁜 포인터에 실패 | 반환값을 보고 거절.  그게 정상 계약이다 |
| B | ioctl 블록이 128 B 한도(`IOCPARM_MASK`)를 넘음 | 지금 블록이 몇 바이트인지 **세어서** 확인(Q1) |
| C | 새 ioctl 번호가 옛 도구와 충돌 | 크기가 다르면 번호가 다르다.  옛 SUBMIT 을 남기므로 옛 도구는 그대로 |
| D | 드라이버가 안 올라옴 | `nm -u`·`sim_r5`·`sim_r6`·소스 규칙, 그리고 변경은 경로 하나 추가 |

## 5. 코딩 전에 답해야 할 것

| | 질문 | 어떻게 |
|---|---|---|
| Q1 | 새 블록이 128 B 안에 드나 | `sizeof` 를 python 으로 세어 본다(필드 수 × 4) |
| Q2 | `copyin` 이 스플림(spl)·블로킹 제약을 거는가 | `prototypes.h` 와 driverkit 문서를 읽는다.  ioctl 문맥에서 안전한가 |
| Q3 | 기대 이득 | **예측하지 않는다.**  두 길을 번갈아 재면 차이가 곧 답이다 |
| Q4 | 라이브러리가 캐시 메모리를 어디서 얻나 | 이미 `vm_allocate` 를 쓴다(`triMap`).  같은 걸로 버퍼 하나 더 |

## 6. Q1·Q2 의 답 (코딩 전)

**Q1 — 블록 크기.**  `osrdn_r7b_submit` 은 `unsigned long` **아홉 개 = 36 바이트**다
(magic·version·nwords·seed·status·why·at·word·drawn).  포인터 하나를 더하면
**열 개 = 40 바이트**.  `IOCPARM_MASK` 의 128 바이트 한도에 한참 못 미치고,
그 뒤로도 **워드 21 개**가 더 들어간다.  경계는 멀다.

**Q2 — `copyin` 은 있다**: `prototypes.h:35`.  반환값이 실패를 알린다.
다만 **어디서 부르느냐**가 문제다 — 하드웨어 클레임을 쥔 채로 잠들 수 있는 호출을
하면 안 된다.  그래서 **`copyin` 을 클레임 앞에서** 한다: ioctl 핸들러가 먼저
사용자 워드를 커널 버퍼로 옮기고, **그 다음에** `osrdn_mode_cp` 로 들어간다.
지금 코드도 같은 모양이다 — `osrdn_cp_stage` 가 클레임 밖에서 돌고
(`OSRDNDisplay.m:1308`·`OSRDNDisplay.m:1282`), 클레임은 그 뒤에 잡힌다.

## 7. codex 교차검토 (코딩 전)

| codex 주장 | 내 검증 | 판정 |
|---|---|---|
| **`copyin` 은 클레임·raised spl 밖에서만 안전하다** — 페이지 폴트가 잠들 수 있다.  쥔 채 부르면 설계가 무너진다 | 우리 코드는 이미 그 모양이다: `osrdn_cp_stage` 가 `OSRDNDisplay.m:1308`·`OSRDNDisplay.m:1282` 에서 돌고 클레임은 `OSRDNDisplay.m:1330` 의 `osrdn_mode_cp` 에서 잡힌다.  **`copyin` 은 856 자리에 간다** | ✅ 채택 — 가장 중요한 조건 |
| **곱하기 전에 `nwords` 를 묶어라**(정수 넘침) | 이미 묶는다: `n > OSRDN_R7B_MAX_WORDS` 가 `OSRDNDisplay.m:1308`, 곱은 그 뒤 | ✅ 이미 있음 |
| **`sizeof(struct) <= IOCPARM_MASK` 를 컴파일 시간에 박아라.**  128 에서 크기 필드가 **0 으로 감기고**, 4.3BSD 디스패처는 구조체를 복사하지 않고 **인자 포인터를 첫 필드 자리에 놓는다** — 조용한 런타임 오작동 | 크기는 40 바이트라 여유가 크지만, **조용한 실패 모양**이 정확히 이 프로젝트가 싫어하는 것이다 | ✅ 채택 — M1n 의 이름표처럼 `typedef char …[cond?1:-1]` |
| **손잡이를 초기화 때 한 번 읽으면 안 된다** — 같은 프로세스 안에서 팔을 교대하려면 **시행마다** 골라야 한다 | **진짜 결함이다.**  우리 손잡이 셋(`triBatchOn`·`triHoldOn`·`triPoisonOn`)이 전부 `< 0` 일 때만 읽는 래치다(`OSRDNMesaTri.c:355`·`OSRDNMesaTri.c:781`·`OSRDNMesaTri.c:1236`).  그대로 두면 M1p 의 교대 측정이 **불가능**하다 | ✅ **채택** — 설정자를 만든다 |
| `A B A B` 는 여전히 B 가 늘 뒤다.  **ABBA 나 무작위**로 | M1n 에서 이미 배운 것.  ABBA 로 | ✅ 채택 |
| 교대가 못 없애는 교란 목록(정렬·페이지 수·TLB·캐시 오염·ioctl 디코딩·링 백프레셔…) | 반증 수단이 없다.  **버퍼를 페이지 정렬하고 미리 만져 두는 것**만 채택하고, 나머지는 보고에 한계로 적는다 | ⚖️ 부분채택 |
| 절감이 작을 수 있는 이유(고정 `copyin` 오버헤드, 쓰기 할당, 캐시 오염, 느린 역사적 `copyin`, 여분의 staging 복사) | **staging 을 하나 더 만들지 않는다** — `copyin` 의 목적지를 **지금 쓰는 그 페이지**(`rdnR7bVirt`, 우리 커널 메모리)로 한다.  그러면 그 뒤 경로가 **한 글자도 안 바뀐다** | ✅ 채택 — 설계가 더 작아졌다 |

### 설계 확정

1. `osrdn_r7b_submit2` = 기존 아홉 워드 + `words`(사용자 주소).  **40 바이트**, 컴파일 시간 고정.
2. 새 ioctl `OSRDN_R7B_IOC_SUBMIT2`.  옛 것은 그대로.
3. 드라이버: `OSRDNDisplay.m:1308` 자리(클레임 밖)에서 `copyin(words, rdnR7bVirt, n*4)`, **그 뒤는 기존 코드 그대로**.
4. 라이브러리: `osrdn_tri_set_copyin(int)` — **시행마다** 고를 수 있는 설정자.  환경 변수는 초기값만.
5. 시험: 한 프로세스 안에서 **ABBA** 로 교대.

### 검사가 잡은 것 둘

1. **`check_hook` 의 "ioctl 은 한 번"** — 뜻은 "배치와 단발이 같은 길로 간다" 였다.
   이제 ioctl 이 둘인 이유는 **버퍼가 둘**이라서다.  규칙을 **둘이되 한 함수 안**으로
   정밀화했다(`enclosing` 으로 확인).
2. **`sim_batch` 의 harness 가 두 경로에 같은 배열을 주고 있었다** — `vm_allocate`
   스텁이 늘 `win` 을 돌려줘서 case H 가 아무것도 시험하지 않았고, "엉뚱한 버퍼를
   보낸다" 는 변이가 **통과했다**.  크기로 갈라 두 버퍼를 주자 잡힌다.
   *검사가 통과한다고 검사가 있는 것은 아니다.*

**부팅 뒤**: `run_m1l.sh` 가 이제 블록마다 두 경로를 **A B B A 로 교대**하고,
판정기가 **인접 쌍의 중앙값**으로 차이를 낸다 — M1n 을 망친 620 us 드리프트가 상쇄된다.
그리고 M1d 일곱 모드로 화소 불변을 본다.

## 9. 결과 — **가설이 반증됐다.  캐시 금지 쓰기는 비싸지 않다** (실기, 2026-09-23)

드라이버 `0dc06c26`, 라이브러리 `790095727`, 실행 `790095745`.

한 블록 안에서 두 경로를 **A B B A 로 교대**하고 인접 쌍의 중앙값을 냈다:

    n      쌍     창 − 캐시(중앙값)   삼각형당      가설이 예측한 값
    1       9          +5 us          +0.63        +1.03
   18       9          +2             +0.01        +1.03
   36       9         −12             −0.04        +1.03
   60       9        −272             −0.57        +1.03
   66       9          −5             −0.01        +1.03
   72       9          −9             −0.02        +1.03

**캐시 금지 쓰기가 삼각형당 1.03 us 라면, n=72 의 한 블록에서 창 쪽이 `8 × 72 × 1.03`
= +593 us 느려야 한다.  실측은 −9 us 다.**  부호도 흔들린다.  **그 비용은 없다.**

### 내 분해가 어디서 틀렸나

M1o §7 은 `창에 쓰기 = poison − software` 라고 했다.  틀렸다 — **poison 팔은
되돌림 루프도 돈다**.  그 팔에서는 배치가 **매번** 실패하므로 훅이 저장해 둔 삼각형을
하나씩 소프트웨어 함수로 다시 그린다(`osrdnFlushBatch` 의 replay).  그 부기가 평소
경로에는 없는데, 나는 그것을 "창에 쓰기" 라고 이름 붙였다.

**A B B A 는 그 오류를 잡으라고 만든 것이고, 실제로 잡았다.**  두 팔이 replay 를
똑같이 갖고 있으면 차이에서 상쇄되는데, poison 과 accel 은 그렇지 않았다.

### 그래서 지금 아는 것

- 한계비는 카드 **1.90~2.00** 대 소프트웨어 **1.28 us/삼각형**.  **어디인지는 다시 모른다.**
- **창에 쓰는 비용은 아니다**(위).
- 남은 후보: 훅의 삼각형당 일(부동소수 → IEEE 비트, 15 워드 조립), 커널의 **워드별
  검증**(`cpR7Verify`), 링 복사.

### 다음 칸은 재부팅이 안 든다

**마지막 워드를 망가뜨리는 팔**을 더하면 갈린다: 워드 0 거절은 검증을 안 하고,
마지막 워드 거절은 **전수 검증을 하고** 그리기·링·digest 는 안 한다.  두 팔 모두
replay 를 똑같이 도니 **차이가 곧 워드별 검증 비용**이다.  라이브러리 손잡이 하나다.

### 이 칸이 산 것

속도는 못 얻었다.  대신 **같은 프로세스 안에서 두 경로를 교대로 재는 장치**를 얻었고,
그것이 첫 사용에서 **내 잘못된 분해를 잡아냈다**.  그림은 그대로다 —
일곱 모드 PASS, 28,672 화소 중 **0 차이**.

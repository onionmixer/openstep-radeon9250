# M1g — 깊이인가 텍스처인가, 그리고 어느 쪽이 재부팅을 부르는가

기준일 2026-09-22.  선행: M1f 완료(`docs/M1F_PLAN.md` 9).
**이 문서는 코딩 전에, 어느 칸을 먼저 할지 정하려고 쓴다.**

M1d·M1e·M1f 는 셋 다 재부팅 없이 끝났다.  다음 칸도 그럴 수 있는지를 **먼저** 묻는다 —
"해 보고 안 되면 그때" 는 이 프로젝트에서 부팅 하나를 태우는 방식이다.

## 1. 깊이에는 앞의 세 칸에 없던 문제가 있다

| | 사실 | 확인한 곳 |
|---|---|---|
| H1 | **제출 한 번에 ZPREP 한 번**이고, ZPREP 은 **드라이버 연산**이라 라이브러리가 부를 수 없다(ioctl 은 CAPS 와 SUBMIT 둘뿐) | `docs/M1D_PLAN.md` 4e, `osrdn_r7b.h` |
| H2 | 그래서 한 프레임에 삼각형이 둘 이상이면 **첫 번째만 카드로 가고 나머지는 폴백**한다 — M1d 첫 실기에서 실제로 그랬다(`REFUSED=2`) | `docs/M1D_PLAN.md` 8 |
| H3 | 폴백은 Mesa **자신의 소프트웨어 깊이 버퍼**를 쓴다.  우리가 `DepthBuffer` 훅을 거절하고 있기 때문이고, 그건 M1c 가 일부러 그렇게 한 것이다 | `OSRDNMesaStubs.c`, `docs/M1C_PLAN.md` 7 |

**따라서 깊이를 켜면 색이 아니라 가림이 틀린다.**  삼각형 둘이 겹칠 때 하나는 카드의
깊이 버퍼로, 다른 하나는 Mesa 의 깊이 버퍼로 판정된다 — 서로를 못 본다.
M1d 가 세운 약속("거절해도 삼각형을 잃지 않는다")은 여전히 지켜지지만, **깊이에서는
잃지 않는 것으로 충분하지 않다.**  같은 버퍼로 판정해야 한다.

*앞의 세 칸에서는 이게 문제가 아니었다*: 평면·구로·블렌드는 전부 **화소 단위 연산**이라
삼각형끼리 공유하는 상태가 없다.  폴백한 삼각형은 그냥 소프트웨어가 똑같이 그린다.
깊이는 이 사다리에서 **처음으로 삼각형 사이에 상태가 흐르는 기능**이다.

### 고치려면 드라이버를 고쳐야 한다 → 재부팅

`-r7bSubmit:` 이 제출마다 스스로 준비하게 만들어야 한다(지금은 `cs->zprepped` 를 요구하고
ZCLEAR 이 그것을 소비한다).  그건 `OSRDNDisplay.m`/`osrdn_cp.m` 변경이고, 설치이고,
**재부팅이다.**

## 2. 텍스처에는 그 문제가 없다

텍스처도 화소 단위다 — 삼각형 사이에 흐르는 상태가 없다.  폴백한 삼각형은 소프트웨어가
같은 텍스처로 그린다(Mesa 가 텍스처 이미지를 갖고 있으므로).

필요한 것과, 재부팅이 필요한지:

| | 무엇이 필요한가 | 재부팅? |
|---|---|---|
| 텍스처 표면 | 창 안의 다른 자리.  클라이언트가 `PP_TXOFFSET_0` 을 쓸 수 있다(허용 목록에 있음, python 확인) | 아니오 |
| 텍셀 올리기 | CPU 가 창에 쓴다.  M1f 가 **CPU 가 쓴 것을 카드가 읽는다**를 이미 증명했다(목적지 `ffbf8040`) | 아니오 |
| 매핑 | M1c 는 색 표면 크기만 매핑한다.  텍스처까지 닿으려면 **창을 더 넓게** 매핑해야 한다 — 라이브러리 안의 변경 | 아니오 |
| 규칙 | R6h·R6i 가 표본 위치·이중선형 필터를 실측해 뒀다 | — |

### 그리고 그것을 인터페이스에서 확인했다 (python)

| | 사실 |
|---|---|
| H5 | 검증기의 `PP_CNTL` 값 규칙은 **유닛 1–5 만** 막는다(`PP_CNTL_TEX_1_5 = 0x3e0`).  `TEX_0_ENABLE` 은 `0x10` 이라 걸리지 않고, 우리 값 `0x1000` 에 얹은 `0x1010` 은 `value_ok` 를 통과한다 |
| H6 | `PP_TXOFFSET_0`(0x2d00)·`PP_TXFORMAT_0`(0x2c04)·`PP_TXFILTER_0`(0x2c00)·`PP_TXSIZE_0`(0x2c0c)·`PP_TXPITCH_0`(0x2c10) 이 **전부 클라이언트 허용 목록에 있다** |

즉 텍스처 유닛 하나는 **드라이버를 건드리지 않고** 켤 수 있다.  이것은 짐작이 아니라
`verify_oracle` 에 직접 물어본 답이다.

**그러므로 다음 칸은 텍스처다.**  깊이는 그 뒤, 드라이버를 고치는 칸과 함께 간다.

## 3. 덤으로 알게 된 것

| | 사실 | 확인한 곳 |
|---|---|---|
| H4 | **`ZPREP` 은 창 256 KiB 전체를 패턴으로 채운다**(`CP_R6_ALIAS_BYTES = 0x40000`, alias 는 `[winStart, +256 KiB)`) | `osrdn_cp.h:281` · `osrdn_cp.h:462`, `osrdn_cp.m:2502` |

이것은 M1d 이후 매 실행에서 일어나고 있었다 — 러너가 가속 실행 직전에 `zprep` 을 돌리므로,
**M1c 의 색 표면도 매번 그 패턴으로 덮였다.**  그림이 맞았던 이유는 시험이 곧바로
`glClear` 를 하기 때문이고, 그건 우연이 아니라 순서 덕이다.  텍스처 칸에서는 이게
직접 문제가 된다: **텍셀을 올린 다음 ZPREP 이 돌면 텍셀이 지워진다.**  올리는 순서는
`zprep → 텍셀 → 제출` 이어야 한다.

*(H4 는 "ZPREP 이 깊이만 건드린다" 고 짐작했다면 텍스처 칸에서 부팅 하나를 태웠을 종류다.
이름이 Z-prep 이라고 Z 만 건드리지 않는다.)*

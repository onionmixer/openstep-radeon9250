# M1f — 블렌딩 (계획, 코딩 전)

기준일 2026-09-22.  선행: M1e 완료(`docs/M1E_PLAN.md` 9).
**이 문서는 코드보다 먼저 쓰였다.**

## 1. 이 칸의 한 줄

**알려진 목적지 위에 블렌딩된 삼각형 하나가 카드로 가고, 그 그림이 R6j 가 실측한
블렌드 산술과 화소 단위로 같다.**

## 2. 왜 깊이나 텍스처가 아니라 블렌드인가

셋 다 분류기가 지금 거절한다.  블렌드를 먼저 하는 이유는 **표면이 하나도 늘지 않기
때문**이다:

| | 무엇이 더 필요한가 | 판단 |
|---|---|---|
| 깊이 | 창 안에 **두 번째 표면**, 그리고 소프트웨어 폴백은 Mesa 자신의 **선형** 깊이 버퍼를 쓰는데 카드 것은 **타일**(R6f) — 섞이면 어긋난다.  게다가 가림을 보이려면 제출 두 번이 필요하고 그건 ZPREP 두 번이며, 그 사이 드라이버의 `CP_OP_ZCLEAR` 프리픽스가 깊이를 지우는지부터 읽어야 한다 | **나중** |
| 텍스처 | 텍스처 표면 + 업로드 경로 + `PP_TX*` 한 무더기 | 나중 |
| **블렌드** | **아무것도** — 목적지는 우리가 이미 그리는 색 표면이고, 소프트웨어 클리어가 그걸 **알려진 상수**로 만든다 | **이 칸** |

## 3. 직접 읽어 확인 (계산은 전부 python)

| | 사실 | 확인한 곳 |
|---|---|---|
| G1 | `BLEND_BIT = 0x002`, 그리고 Mesa 는 **앱이 켤 때만** 그 비트를 세운다(`if (ctx->Color.BlendEnabled)`).  *(M1b 가 잰 `0x106` 을 "보통의 OSMesa 기본 상태" 로 읽을 뻔했는데, 열어 보니 **그 시험이 직접** `glEnable(GL_BLEND)` 을 부른다 — `osrdn-mesa-render.c:113`.  게다가 거기 쓰인 조합이 `SRC_ALPHA/ONE_MINUS_SRC_ALPHA` 로 **R6j 가 잰 바로 그것**이다.)* | `types.h:1450`, `state.c:810`, `osrdn-mesa-render.c:113` |
| G2 | `RB3D_BLENDCNTL`(0x1c20)은 **클라이언트 허용 목록에 있고**, `value_ok` 에 이 레지스터 규칙이 없다(=값 제한 없음) | python 으로 `verify_oracle.ALLOW`·`value_ok` 조회 |
| G3 | 인코딩은 `(src << 16) | (dst << 24) | (comb << 12)` — **시프트는 읽었다**(22 로 짐작했다가 틀렸다) | `r200_reg.h:89` · `:90` |
| G4 | 드라이버의 경우 표 `cpR6G` 열 10 에 R6j 가 **실제로 보낸 일곱 조합**이 있고, 전부 이름으로 해독되며 `SRC_ALPHA/ONE_MINUS_SRC_ALPHA/ADD_CLAMP` 를 되만들면 `0x27260000` 과 정확히 일치한다 | `osrdn_cp.m:1832`, python 으로 해독·재구성 |
| G5 | `RB3D_CNTL` 비트 0 이 `ALPHA_BLEND_ENABLE`; **우리 서두에는 `BLENDCNTL` 이 아예 없고** 그 비트도 0 이다(`0x1802`) | `r200_reg.h:186`, 생성된 표 |
| G6 | 실측 산술: 항마다 `(색 × (F+1)) >> 8` **버림**, 합 **클램프**; `SUB_CLAMP` 은 원본−목적지; `ROUND_ENABLE` 무관 | `docs/R6J_PLAN.md`, [[r200-measured-rules]] |
| G7 | R6j 의 독립 구현이 `build/r6j/indep_r6j.py` 에 통째로 있다(`factor()` + 산술) — M1f 의 두 번째 구현으로 **다시 쓸 수 있고**, 판정기와 공유하지 않는다 | 그 파일 |
| G8 | **블렌드와 깊이는 참조 드라이버에서 구조적으로 독립이다**: `r200_set_blend_state` 는 `ROP|ALPHA_BLEND|SEPARATE_ALPHA` **만** 마스크해 `Z_ENABLE` 을 보존하고, `GL_DEPTH_TEST` 는 `Z_ENABLE` **만** 토글한다.  즉 "블렌드 켜고 깊이 끈" 상태는 이 드라이버가 평범하게 만들어 내는 조합이다 | `r200_state.c:205` · `:2004` |
| G9 | **에라타**: *"make sure that blend function and blend equation are set to their default value if color blending is not enabled, since at least blend equations GL_MIN and GL_FUNC_REVERSE_SUBTRACT will cause wrong results otherwise for unknown reasons."*  → **블렌딩이 꺼져 있어도 `BLENDCNTL` 은 기본값(ONE/ZERO/ADD_CLAMP)이어야 한다** | `r200_state.c:195-198` |

**G9 는 M1f 만의 문제가 아니다.**  우리 서두는 `BLENDCNTL` 을 **한 번도 쓰지 않는다**(G5) —
그 레지스터는 이전 연산이 남긴 값을 그대로 이고 있다.  M1d·M1e 의 그림이 정확했던 것은
이번 부팅에서 그 값이 무해했다는 뜻이지 **우리가 정한 값이어서가 아니다.**
그래서 M1f 는 **블렌드를 켜든 끄든 `BLENDCNTL` 을 항상 쓴다** — 끌 때는 참조가 말하는
기본값을 쓴다.  통제하지 않던 입력 하나가 통제 아래로 들어온다.

| G10 | Mesa 3.4.2 는 **RGB 와 알파 블렌드 함수를 따로** 가질 수 있다(`BlendSrcRGB`/`BlendDstRGB` 와 `BlendSrcA`/`BlendDstA`, `GL_INGR_blend_func_separate`).  그런데 우리가 쓸 `RB3D_BLENDCNTL` 은 **함수 쌍이 하나뿐**이다(분리 알파는 참조의 `drmSupportsBlendColor` 경로에서 `RB3D_ABLENDCNTL`/`CBLENDCNTL` 로 가고, 그 레지스터들은 우리 허용 목록에 없다) | `types.h:361` · `:363`, `r200_state.c:224` |
| G11 | 그리고 `BlendEquation` 도 있다 — `ADD` 말고 `SUB`·`MIN`·`MAX` 등이 될 수 있는데 R6j 는 `ADD_CLAMP` 와 `SUB_CLAMP` 만 쟀다 | `types.h:365`, `osrdn_cp.m:1832` 열 10 |

**그러므로 분류기는 세 가지를 더 봐야 한다**: `BlendSrcA == BlendSrcRGB`,
`BlendDstA == BlendDstRGB`(아니면 표현할 수 없다), 그리고 `BlendEquation` 이 잰 것 중
하나일 것.  *분리 알파를 안 걸렀으면 알파만 다른 블렌드를 RGB 함수로 그렸을 것이다 —
그림이 조용히 틀리는 종류다.*

### 3b. 스스로 반박해 본다

| 의심 | 확인 | 결론 |
|---|---|---|
| 목적지를 카드가 정말 볼 수 있나(CPU 가 쓴 것을) | R6g 가 **CPU 깊이 프리필**을 카드가 읽게 했다(`CP_WHY_PREFILL` 이 그 게이트) — 선례가 있다.  그래도 게이트로 확인한다 | 게이트 C 가 답한다 |
| R6j 는 `RB3D_CNTL = 0x1903`(깊이 켜짐)에서 쟀는데 우리는 `0x1803`(깊이 꺼짐) | 다른 유닛이라 산술이 달라질 이유는 없다 — **그러나 이것은 추론이다**.  codex 에 물을 한 가지로 고른다 | §4 |
| 어떤 blend 조합까지 받나 | **한 조합만**: `SRC_ALPHA / ONE_MINUS_SRC_ALPHA / ADD_CLAMP`.  R6j 가 잰 일곱 중 하나이고, Mesa 의 기본이자 M1b 시험이 쓰는 것이다(G1).  나머지 여섯은 **잰 값이 있어도** 이 칸에서 받지 않는다 — 조합 하나에 실기 실행 하나(ZPREP 하나)가 필요하니 일곱을 한 칸에 넣으면 부팅 예산이 아니라 **판정의 폭**이 흐려진다.  분류기를 표로 써서 다음 칸이 줄만 늘리면 되게 한다 | 분류기의 표 |
| 목적지가 검정이면 블렌드가 보이나 | 안 보인다(대부분의 항이 0).  **클리어를 검정이 아닌 상수로** 한다 | §5 |
| 알파 목적지는? | 색 표면은 ARGB8888 이라 알파도 있다.  `DST_ALPHA` 계열은 R6j 가 안 쟀으므로 **거절 목록**에 둔다 | 표에 없음 = 거절 |

## 4. codex 에 물을 한 가지

**"R6j 가 `RB3D_CNTL=0x1903`(Z_ENABLE 켜짐)에서 측정한 블렌드 산술이, 같은 스트림에서
`0x1803`(Z_ENABLE 꺼짐)일 때도 같다고 볼 근거가 참조 소스에 있는가?"**
— 좁고 국지적이며, 틀리면 게이트 C 가 통째로 무의미해지는 전제다.

## 4b. codex 교차검토 판정 (요청 `k6q0q91q6`) — Z_ENABLE 하나만 물었다

**결론: 근거 없음 = 우리 전제가 성립한다.**  인용 **14 개를 전부 열었고 전부 정확**했다.

| codex 주장 | 내 검증 방법 | 결과 |
|---|---|---|
| `Z_ENABLE` 이 블렌드 산술에 영향을 준다는 코드·주석·에라타가 **없다** | 나도 G8 로 같은 결론에 먼저 도달해 있었다(핸들러가 서로의 비트를 보존) | ✅ **채택** |
| `r200_set_blend_state` 가 `Z_ENABLE` 을 마스크에 안 넣는다 (`r200_state.c:202`·`:205`) | 이미 열었다 | ✅ 사실 |
| 깊이 핸들러는 `Z_ENABLE` 만 토글 (`:2002`), 비교·쓰기는 **다른 레지스터**(`ZSTENCILCNTL`)에 있다 (`:344`·`:395`) | 네 줄 다 정확.  후자는 내가 안 짚은 보강이다 | ✅ **채택** |
| `RB3D_CNTL` 안에서 두 비트에 상호 조건이 없다 (`r200_reg.h:181-194`) | 블록 전체를 열었다 — 단순 독립 비트 나열 | ✅ 사실 |
| color cache 와 Z cache 는 **다른 레지스터·다른 매크로**로 비운다 (FreeBSD `radeon_drv.h:1942`·`:1962`, Linux `radeon_drv_linux.h:1947`) | 세 줄 다 정확 | ✅ 사실 |
| Linux 검증기는 `Z_ENABLE` 을 **깊이 버퍼가 필요한지**에만 쓴다 (`r100.c:2248`) | 정확 | ✅ 사실 |
| **DDX 의 R200 composite 경로가 `RB3D_CNTL = colorformat | ALPHA_BLEND_ENABLE` 로 — Z 없이 — 블렌딩한다** (`radeon_render.c:872`·`:884`) | 두 줄 정확.  그리고 **그 파일 전체에 `Z_ENABLE`·`ZSTENCILCNTL` 이 한 번도 안 나온다**(전수 grep, 0 건) | ✅ **채택 — 내가 못 찾은 가장 직접적인 반대 근거** |
| 달라질 수 있는 것은 산술이 아니라 **깊이에서 탈락하던 화소가 블렌드까지 온다**는 점뿐 | 맞는 구분이다.  우리는 두 경우 모두 깊이를 끄므로 해당 없음 | ✅ 사실, 우리에겐 무관 |
| "실리콘에 문서화 안 된 에라타가 없음은 증명 못 한다 — 그건 추측" | 스스로 표시했다.  게이트 C 가 바로 그것을 실기에서 확인한다 | ✅ 정직한 한계 표시 |

**이번에도 기각할 항목이 없었고, 인용은 14/14 정확했다.**  세 번째로 같은 관찰이 반복된다:
질문이 좁고 국지적일수록 답이 낫다.  그리고 이번 회신의 값어치는 **동의**가 아니라
`radeon_render.c` 였다 — 내 근거는 "드라이버가 두 비트를 따로 쓴다"(구조)뿐이었는데,
codex 는 **Z 없이 블렌드만 쓰는 실제 출하 경로**(사례)를 가져왔다.

## 5. 설계

1. **서두에 슬롯 둘** — `SLOT_BLENDCNTL` 과, `RB3D_CNTL` 을 이미 있는 리터럴에서 슬롯으로
   승격(`SLOT_RB3D_CNTL`).  생성기가 **R6j 가 보낸 값들**을 표로 내보낸다; 손으로 적지 않는다.
2. **`osrdn_tri_send` 에 `blend` 인자** — 0 이면 지금처럼(블렌드 끔), 아니면 조합 번호.
3. **훅** — `ctx->Color.BlendEnabled` 와 `BlendSrcRGB/BlendDstRGB` 를 읽어 조합 번호로
   옮기고, 표에 없으면 **분류기가 거절**한다(훅이 고르는 게 아니라 분류기가 판정한다).
4. **분류기** — `RM_KNOWN |= RM_BLEND`, 그리고 `blendMode` 입력을 추가해 **표에 있는 조합만**
   받는다.  새 사유 `OSRDN_WHY_BLEND_MODE`.
5. **판정기** — 원본 색(평면/구로)을 구하고, 목적지(클리어 상수)와 G6 의 산술로 블렌드한다.
6. **시험** — `glClearColor` 를 검정이 아닌 값으로, `glEnable(GL_BLEND)`,
   `glBlendFunc(GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA)`, 삼각형 하나.

### 5b. 보낼 정확한 값 (python 으로 계산)

| | 값 | 비고 |
|---|---|---|
| `RB3D_CNTL`, 블렌드 끔 | `0x00001802` | 지금(M1d/M1e) 그대로 |
| `RB3D_CNTL`, 블렌드 켬 | **`0x00001803`** | `| ALPHA_BLEND_ENABLE`.  R6j 가 잰 `0x1903` 과 **`Z_ENABLE` 한 비트만** 다르다 — §4 가 그 한 비트를 묻는 이유다 |
| `BLENDCNTL`, 블렌드 끔 | **`0x20210000`** | ONE/ZERO/ADD_CLAMP.  G9 가 요구하는 기본값이고, **R6j 가 실제로 보낸 행 20(J1)과 같은 값**이다 — 지어내지 않았다 |
| `BLENDCNTL`, 블렌드 켬 | **`0x27260000`** | SRC_ALPHA/ONE_MINUS_SRC_ALPHA/ADD_CLAMP, R6j 행 23 |

색 형식 칸은 세 경우 모두 6(ARGB8888)으로 그대로다.

### 5c. 알파 255 면 블렌드는 항등이다 — 게이트가 실패할 수 있어야 한다 (python)

`SRC_ALPHA/ONE_MINUS_SRC_ALPHA` 에 실측 산술 `(c × (F+1)) >> 8` 을 넣으면,
원본 알파가 **255** 일 때 인자는 `(c × 256) >> 8 = c` 와 `(d × 1) >> 8 = 0` 이 되어
**결과가 원본 그대로**다.  계산:

| 원본 | 결과 (목적지 `(64,128,191,255)`) | |
|---|---|---|
| `(255,0,0,255)` | `(255,0,0,255)` | **항등 — 블렌드가 안 보인다** |
| `(255,0,0,128)` | `(160,64,95,191)` | 블렌드됨 |
| `(255,64,32,255)` | `(255,64,32,255)` | **항등** |
| `(16,255,128,170)` | `(31,213,149,198)` | 블렌드됨 |
| `(64,32,255,85)` | `(63,95,212,198)` | 블렌드됨 |

**그러므로 시험의 원본 알파는 255 미만이어야 한다.**  평면 모드는 `glColor4f(..., 0.5)`
같은 값을 쓰고, 구로 모드는 M1e 의 세 알파 중 첫 정점이 255 이므로 그것도 낮춘다
(255/170/85 → 예: 200/170/85).  이걸 안 했으면 **블렌드를 안 켠 구현도 게이트를
통과했을 것이다.**

## 6. 게이트

- **A** 호스트: 규칙·변이.  새 규칙 — 블렌드 값은 **생성된 표에서만** 오고, 표에 없는 조합은
  분류기가 거절하며, 훅은 조합을 **고르지 않고 옮기기만** 한다.
- **B** 호스트: 블렌드를 켠 스트림이 `verify_oracle` 를 통과한다(생성기 자체검사).
- **C** 실기: 그림이 **목적지 상수 × 실측 블렌드 산술** 예측과 화소 단위로 같다.
  이것이 CPU 가 쓴 목적지를 카드가 읽었다는 증거이기도 하다.
- **D** 측정: 소프트웨어와의 차이.  구로일 때는 M1e 의 **채널당 1** 경계가 계속 적용된다.
- **E** 실기: `glDisable(GL_BLEND)` 면 M1e 와 **같은 그림**(블렌드가 켜질 때만 달라야 한다).
- **F** 실기: M1d 의 불변식 전부 — 손실 0, `refused + notBound == delegated`, 매핑 1.

## 7. 구현 순서

1. 생성기: 두 슬롯 + R6j 값 표 + B 게이트.
2. 삼각형 단위: `blend` 인자.
3. 분류기: `RM_BLEND` + `blendMode` + 새 사유.  훅: 상태를 읽어 옮기기만.
4. 판정기: 블렌드 예측.  독립 재계수: `indep_r6j.py` 의 산술을 다시 구현해 대조.
5. 호스트 검사 → 타깃 빌드 + `nm -u` → 실기.

## 8. 이 칸이 하지 않는 것

- 깊이·텍스처를 켜지 않는다.
- R6j 가 재지 않은 blend 조합을 받지 않는다.

### 게이트 D 가 드디어 하나의 규칙이 됐다

M1d 에서 "내부 차이 0", M1e 에서 "구로면 1", 그리고 여기서 블렌드가 더해지자 또 어긋났다

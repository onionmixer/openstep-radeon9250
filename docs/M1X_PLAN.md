# M1x — 커널의 366 us 를 **재고** 나서 자른다

드라이버 변경이지만 **동작을 하나도 바꾸지 않는다** — 시계를 읽어 기록할 뿐이다.
설치까지 하고 재부팅을 요청한다.

## 1. 왜 이 칸인가

M1w 를 쓰다가 산수가 방향을 바꿨다.  제출당 비용은 n=72 에서 **고정 530 + 한계 149 us**,
**고정비가 78 %** 다.  그 고정비를 이미 측정된 팔들로 갈랐다(python, run 790113565):

| 몫 | us/제출 | 어떻게 |
|---|---:|---|
| 라이브러리만, ioctl 없음 | 2.0 | `t-nullsend` 절편 |
| + ioctl 진입·커널 게이트·워드 0 거절 | 162.5 | `t-poison` − `t-nullsend` |
| **+ 나머지 커널 연산** | **365.8** | `t-quiet` − `t-poison` |

M1q~M1v 다섯 칸이 쫓은 것은 나머지 21 % 쪽이었다.  **큰 덩어리는 여기 있다.**

## 2. 그런데 그 366 us 가 무엇인지 모른다

소스에서 셀 수 있는 것을 세어 값을 매겨 봤다:

| 이름 붙는 것 | 크기 | 비중 |
|---|---:|---:|
| `*copy = *cp;` — 제출마다 상태 구조체 통째 복사(`osrdn_mode.m:1473`).  실기에서 잰 크기 **5,524 B = 1,381 워드** | 8~28 us | 2~8 % |
| 소스에서 센 uncached MMIO 읽기 약 32 개 × 830 ns | 27 us | 7 % |
| **합쳐도** | | **≤ 15 %** |

**85 %가 이름이 없다.**  그리고 이 프로젝트에서 "소스를 세고 속도를 곱하는" 방법은
**네 번 연속 빗나갔다**([[measurement-discipline]]).  M1w 의 첫 설계도
그렇게 세다가 전초의 `cpWait(W_IDLE)` 를 빼먹어 무너졌다.

**그러니 다섯 번째로 세지 않는다.  커널이 제 시계로 스스로 재게 한다.**

## 3. 그런데 계기의 절반은 **이미 드라이버 안에 있었다**

새로 달기 전에 읽었다.  `osrdn_cp_run` 은 연산 진입에서 `IOGetTimestamp(&t0)` 를 찍고
끝에서 `c->elapsedUs = cpElapsedUs(t0, t1)` 를 넣는다(`osrdn_cp.m:4113-4121`,
`osrdn_cp.m:4273-4276`).  그리고 **MMIO 접근을 매크로로 가로채 세고 있다**:

    static unsigned long cpIoRd, cpIoWr;
    #define rdnMmioRead32(b, o)      (cpIoRd++, rdnMmioRead32((b), (o)))
    #define rdnMmioWrite32(b, o, v)  (cpIoWr++, rdnMmioWrite32((b), (o), (v)))

둘 다 이미 로그로 나온다(`osrdn_modelog.m:358-371`).  **이미 받아 둔 격자 로그에서** 바로
읽었다(python, `build/m1l/790098040/prof/t-grid.drv`):

| 스트림 워드 | MMIO 쓰기 | MMIO 읽기 | 연산 us | 읽기 × 830 ns | 그 비중 |
|---:|---:|---:|---:|---:|---:|
| 63 | 5 | 37 | 1,440 | 30.7 | **2.1 %** |
| 318 | 5 | 38 | 1,456 | 31.5 | 2.2 % |
| 588 | 5 | 38 | 1,452 | 31.5 | 2.2 % |
| 948 | 5 | 39 | 1,518 | 32.4 | 2.1 % |
| 1,038 | 5 | 40 | 1,444 | 33.2 | 2.3 % |

**MMIO 는 2.2 % 다.**  내가 소스에서 센 32 개와도 맞는다(37~40).  상태 복사는 ≤ 8 %.
**그러니 366 us 의 90 % 는 MMIO 도 복사도 아니고, 커널 안의 평범한 CPU 일이다** — 이
프로젝트가 유저랜드에서 네 번 찾아낸 것과 같은 모양이다.

### 3-1. 그리고 저 1,440 us 는 **로그가 켜진** 연산이다

`elapsedUs` 는 로그보다 앞에서 끝난다(`osrdn_cp_lines` 는 `osrdn_mode_cp` 가 반환한
뒤 `OSRDNDisplay.m` 에서 불린다).  그런데도 1,440 us 다 — 로그가 꺼진 팔의 커널 몫은
366 us 인데.  **차이는 앞 연산의 25 줄을 syslogd 가 배달하며 훔쳐 가는 CPU 다**
([[measurement-discipline]]).

**따라서 단계를 로그로 찍어서 재면 안 된다** — 재는 행위가 재는 대상을 세 배로 만든다.
(교차검토도 "logging-on 과 quiet 은 같은 실험이 아니다" 라고 같은 곳을 짚었다.)

## 4. 그래서 설계 — **모아서 한 번에 내놓는다**

| | |
|---|---|
| 기록 | 클라이언트 경로의 체크포인트 여덟 개에서 `IOGetTimestamp`.  **기존 `cpElapsedUs` 를 그대로 쓴다** — 새 단위 처리도, 새 64 비트 산술도, 새 출력 형식도 없다(교차검토 (a) 가 통째로 사라진다) |
| 누적 | `c->tAcc[8]` 에 구간별로 더하고 `c->tAccN++`.  **연산당 로그는 없다** |
| 내놓기 | `quiet` 이 끝난 **뒤** 상태 줄 하나로 한 번.  즉 측정은 **완전히 조용한 상태**에서 이뤄진다 |
| 경계 | 체크포인트 0 은 `cpR7Verify` **직후**(`osrdn_cp.m:3154-3155`) — 거기가 `t-poison` 이 되돌아가는 자리이므로, 구간 합이 366 us 버킷과 **같은 범위**가 된다(교차검토 (b) 채택) |

## 5. 위험

| 위험 | 막는 법 |
|---|---|
| `IOGetTimestamp` 의 단위·64 비트 산술·출력 형식 | **손대지 않는다.**  이미 있는 `ns_time_t` + `cpElapsedUs(t0,t1)` 를 그대로 쓴다 — 그 함수는 `t1<=t0`, 32 비트 넘침, `cc 2.7.2.1` 의 long long 비교 버그까지 이미 처리해 둔 것이다(`osrdn_cp.m:170-184`) |
| 계기 자체가 재는 것을 바꾼다(호출 비용, MMIO 사이에 지연 삽입) | 제출당 여덟 번.  `cpWait` 이 대기마다 두 번, 제출당 대기가 넷이니 오늘도 여덟 번이다 — python 으로 세면 한 팔에서 **17,280 회가 17,280 회 더 는다**.  즉 **정확히 두 배**이고 작지 않다.  그래서 **`sum(구간)` 을 같은 연산의 `elapsedUs` 와 대조**한다: 계기가 장치 대기를 줄였다면 합이 작게 나오고, 계기 자신이 비싸면 크게 나온다.  둘 다 결과다(교차검토 (c) 채택) |
| 구조체가 커져 제출마다 더 복사된다 | +9 워드 / 1,381 = **+0.65 %**.  같은 표가 그 복사의 값도 알려 준다 |
| `t0` 앞·`t7` 뒤가 안 보인다 | 그래서 `t0` 을 `cpR7Verify` 직후에 둔다 — `t-poison` 이 되돌아가는 바로 그 자리.  그 앞은 **이미 162.5 us 버킷으로 따로 재어져 있다** |
| 동시 제출이 누적기를 덮어씀 | `osrdn_mode_cp` 가 `modeClaim` 으로 직렬화하고, 못 잡으면 `CP_RC_BUSY` 로 되돌아간다(`osrdn_mode.m:1450-1451`).  한 번에 하나뿐이다 |
| 로그가 측정을 세 배로 만든다 | **연산당 로그를 안 찍는다**(§4).  누적만 하고 quiet 이 끝난 뒤 한 번 읽는다 |
| 누적기가 넘침 | 구간마다 `unsigned long` 에 us 를 더한다.  4,294 초까지 안전 — 한 실행이 2,160 제출 × 366 us = 0.8 초다.  python 으로 확인했다 |
| 측정 전용 코드가 출하 경로에 남음 | 남는다.  대입 아홉 개이고, 다음 칸이 자르고 나면 **그 효과를 재는 도구**가 된다 |

### 5-1. 읽는 법

| 관측 | 다음 |
|---|---|
| 한 구간이 합의 40 % 이상 | 거기를 읽고 자른다 |
| 되읽기 구간(`t4-t3`, 프리픽스 레지스터 9+1 개)이 큼 | **R6 시절의 검증**이고 클라이언트에겐 필요 없다.  가장 자르기 쉬운 자리 |
| 고르게 퍼짐 | 자를 한 곳이 없다 — 그러면 클라이언트 경로를 R6 검증 없이 다시 쓰는 것이 유일한 길이고, 이 표가 **무엇을 얼마나 버리는지** 말해 준다 |
| 구간 합이 366 us 보다 많이 작음 | 계기가 장치 대기를 줄였거나 버킷 경계가 안 맞는 것.  **둘 다 확인 가능**하다 — `elapsedUs` 와 대조하고, `t0` 위치를 다시 본다 |

## 6. codex 교차검토 판정표 (모델 `gpt-5.6-sol`, 계획 단계, 코딩 전)

| codex 주장 | 내 검증 | 판정 |
|---|---|---|
| **`IOGetTimestamp` 의 단위·64 비트·포맷이 위험하다**(커널 스택 손상까지) | 새로 다룰 필요가 없다 — `cpElapsedUs` 가 이미 있고 그 함수가 그 함정들을 이미 막아 놨다 | ✅ **채택 — 새 산술을 안 쓴다** |
| **366 us 는 유저랜드 왕복에서 뺀 값이라 `t0..t7` 과 범위가 다를 수 있다** | 맞다.  `t0` 을 `cpR7Verify` 직후, 즉 `t-poison` 이 되돌아가는 자리에 둔다 | ✅ **채택 — 설계 변경** |
| **logging-on 과 quiet 은 같은 실험이 아니다** | 맞고, 이미 받아 둔 로그가 그것을 보인다: 로그 켠 연산이 1,440 us, 로그 끈 팔의 커널 몫이 366 us | ✅ **채택 — 로그 대신 누적·1 회 보고** |
| 계기가 MMIO 사이에 지연을 넣어 장치 대기를 줄일 수 있다 | 가능하다.  `sum` 대 `elapsedUs` 대조를 판정 절차에 넣었다 | ✅ 채택 |
| 구조체가 커져 복사·캐시·스택이 바뀐다 | +0.65 %.  스택이 아니라 파일 정적이다(`rdnCp`, `rdnCpCopy`) | ⚖️ 부분채택 — 크기를 적어 둔다 |
| 동시 제출이 필드를 덮어쓴다 | `modeClaim` 이 직렬화한다 | ❌ **기각 — 소스** |
| `t0` 앞·`t7` 뒤는 안 보인다 | 맞다.  그 구간은 **이미 따로 재어져 있다**(162.5 us) | ⚖️ 부분채택 |
| 구간 합이 366 과 다르다고 곧바로 "숨은 구간" 은 아니다 | 맞다.  §5-1 의 마지막 줄에 그대로 적었다 | ✅ 채택 |
| MMIO 32 개의 위치를 8 구간으로는 못 가른다 | 그럴 필요가 없어졌다 — **MMIO 는 전체의 2.2 %** 이고 이미 세어져 있다 | ❌ **기각 — 이미 측정됨** |

## 7. 구현 (드라이버, 동작 무변경)

| 파일 | 바뀐 것 |
|---|---|
| `osrdn_cp.h` | `CP_T_MARKS 9` / `CP_T_STAGES 8`; 상태에 `tAcc[8]`·`tAccN`·`tDump[8]`·`tDumpN`(+18 워드, 1,381 → 1,399 = **+1.3 %**); `CP_OP_TDUMP 15`, `CP_OP_LAST` 14 → 15 |
| `osrdn_cp.m` | `cpTMark(c,&t,mark)` — **기존 `cpElapsedUs` 를 부른다**, 새 산술 없음; 클라이언트 경로에 마크 여덟 개; `cpTDump` 가 스냅샷을 만들고 누적기를 **0 으로** 되돌린다 |
| `osrdn_modelog.m` | `RDN-R5 tstage ...` 한 줄, **`CP_OP_TDUMP` 일 때만**.  `n=` 앞에 `tstage` 가 있어 연산 줄 모양이 아니다 |
| `rdnr5cp.m` | `tdump` 이름과 `OP_COUNT` 15 → 16 |
| `check_r5_src.py` | **규칙을 뜻에 맞게 고쳤다** — "QUIET 이 마지막 op" 에서 "**`CP_OP_LAST` 가 가장 큰 op**" 로.  M1n 이 쓸 때는 같은 말이었고 TDUMP 가 붙으면서 갈라졌다.  변이 둘로 양방향 증명(더 크게·더 작게) |

### 7-1. 왜 `tAccN` 이 마지막에만 오르나

일찍 되돌아간 연산은 어떤 구간에는 기여하고 어떤 구간에는 안 했다.  그것까지 세면
없는 몫이 여덟 구간에 고루 퍼진다.  **끝까지 간 연산만** 센다.

## 8. 측정 절차 (재부팅 뒤)

러너에 팔 하나를 더했다 — `t-stage`:

    quiet 5000          로그를 끈다 (측정은 조용한 상태에서)
    zprep
    rdntri-accel ... p  2,160 제출, 드라이버가 여덟 구간을 누적
    quiet 0             로그를 켠다
    tdump               한 줄로 내놓고 누적기를 0 으로

판정기가 `RDN-R5 tstage` 줄을 읽어 **제출당 마이크로초와 비중**으로 찍는다.  자체검사
둘로 발동을 보였다: 구간 합이 366.0 us 로 나오는 것, 그리고 **`ops=0` 은 "0 이었다" 가
아니라 실패**라는 것.

## 9. 이 칸이 답할 수 없는 것

- **`t0` 앞**(ioctl 진입·게이트 이전·`cpR7Verify`)은 안 잰다.  그 구간은 이미 따로
  162.5 us 로 재어져 있다.
- **`t7` 뒤**(모드 클레임 해제, 상태 복사, ioctl 복귀)도 안 잰다.  상태 복사는 크기를
  실측해 뒀으므로(1,399 워드) 다음 칸이 거기서 시작할 수 있다.
- 구간 합이 366 us 와 다르면 **그 자체가 결과다** — 계기가 장치 대기를 줄였거나 버킷
  경계가 어긋난 것이고, 둘 다 `elapsedUs` 와 대조해 갈린다.

## 10. 계기를 지키는 규칙 (`check_r5_src` 의 `m1x-stage-marks`)

계기는 **틀려도 드라이버가 안 죽는다** — 대신 엉뚱한 구간의 시간을 조용히 보고하고,
그것은 믿어지기 때문에 크래시보다 나쁘다.  그래서 규칙으로 박았다:

| 규칙 | 변이로 증명 |
|---|---|
| 마크가 `0..CP_T_STAGES-1` 을 **순서대로 한 번씩** | 마크 5 를 6 으로 바꾸면 잡힌다 |
| 모든 마크가 `if (timing)` 뒤에 있다 | 가드 하나를 `if (1)` 로 바꾸면 잡힌다 — 안 그러면 **R6 케이스의 시간이 클라이언트 버킷에 섞인다** |
| `tAccN` 이 **끝에서 한 번만** 오른다 | `+= 0` 으로 바꾸면 잡힌다 |

세 변이 모두 `m1x-stage-marks` 로 잡히는 것을 확인했다.

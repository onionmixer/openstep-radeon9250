# R2c 계획 — 종료를 기다리지 않고 복귀를 판정한다 (개정 0, 2026-09-16)

## 1. 왜 필요한가

R2b 는 진입을 증명했지만 **복귀는 아직 판정되지 않았다**(결과 문서 §7-3).  복귀는 종료 경로에서만
돌고, 종료 중에는 `IOLog` 가 디스크에 닿지 않는다.  그리고 다음 부팅이 멀쩡한 것은 증명이 아니다 —
소프트 재부팅도 VGA BIOS POST 가 카드를 다시 프로그램하므로, 복귀가 아무것도 안 했어도 같아 보인다.

복귀는 이 드라이버에서 **가장 위험한 절반**이다(진입이 실패하면 화면만 깨지지만, 복귀가 틀리면
콘솔을 잃는다).  증명 없이 남겨 둘 수 없다.

## 2. 무엇을 만드는가

부팅 중에 **한 번만**, 운영자가 telnet 에서 명령 하나로:

1. `osrdn_mode_revert` 를 부른다(카드를 콘솔 상태로 되돌린다),
2. 되돌린 **직후에 스냅샷 대상 레지스터를 전부 되읽어** 스냅샷과 대조한다,
3. `osrdn_mode_enter` 를 다시 불러 화면을 되살린다,
4. 그 대조 결과를 로그로 낸다.

2 번이 판정이다.  종료 때 도는 것과 **같은 함수**를 부르므로, 여기서 항등이면 종료 복귀도 항등이다.

## 3. 반드시 지켜야 하는 제약 (출처를 열어 확인함)

### 3-1. 이 경로에서 `IOSleep` 을 쓰면 안 된다

`doc/driverkit.md` 의 실측 표(293–298 행)는 문맥마다 블로킹 가부가 다르다고 적는다:
kern_loader 로드와 driverLoader probe 에서는 **가능**, **네트워크 스택 ioctl 에서는 불가 —
머신이 멈춘다**(2026-07-20, `ifconfig` 가 부른 `-resetAndEnable:` 안에서 4 초를 기다렸다).
이유는 "네트워크 스택의 락/SPL 을 쥔 채 자면 돌아오지 못한다" 이다.  같은 문서는 짧은 정착에는
`IOSleep` 대신 **`IODelay`(어떤 SPL 에서도 안전)** 를 쓰라고 못박는다.

**정정해 둘 것**: Matrox 대체 드라이버의 주석은 이것을 "IOSleep in an ioctl context stops the
machine ... this harness is entered through setIntValues:" 로 **더 넓게** 옮겨 적었다
(`OpenStepMGAReplacementDisplay.m:996-1001`).  측정된 표는 *네트워크 스택* ioctl 만 말하고,
같은 문서는 "첫 가설(로드 문맥의 IOSleep)은 틀렸고 단계 시험이 반증했다" 고도 적는다.
디스플레이 드라이버의 `setIntValues:` 가 그런 락을 쥐는지는 **미확인**이다.
그래서 우리는 넓은 쪽을 **보수적으로 채택**한다: 이 경로에서는 자지 않는다.

현재 `osrdn_mode.m` 은 세 곳에서 잔다: PLL 잠금 대기(`IOSleep(5)`, 50 ms 한도), 복귀 정착
대기(`IOSleep(5)`, 100 ms 한도), 그리고 시험 패턴 노출(`IOSleep(50)`, 2 s).

### 3-2. 커널은 `setIntValues:` 를 직렬화하지 않는다

Q12 에서 확인한 사실이다.  진입·복귀가 겹쳐 돌면 스냅샷이 깨지므로 **우리 걸쇠가 필요하다**.
기록 경로(`osrdn_record_request`)가 이미 같은 모양을 쓴다: 가면 씌운 test-and-set 으로
"진행 중 아님 + 이 부팅 횟수 한도 + 걸쇠 없음" 을 한 번에 본다.  그 모양을 그대로 쓴다.

### 3-3. 선례

Matrox 대체 드라이버는 `setIntValues:` 로 들어오는 하드웨어 작업을 이미 가지고 있다
(`OpenStepMGAReplacementDisplay.m:5506-5508`: "Callers reach this through IODeviceMaster's
setIntValues:, the same path the window server already uses for brightness and gamma").
새로운 종류의 통로가 아니다.

## 4. 설계

### 4-1. 대기 정책을 상태에 둔다

`osrdn_mode_state` 에 입력 필드 `noSleep` 을 더한다.  세 대기 지점은 모두 하나의 헬퍼를 지난다:

```
static void modeWaitTick(const osrdn_mode_state *mode)   /* 한 번의 양보/지연 */
{
    if (mode->noSleep)
        IODelay(MODE_TICK_US);      /* 어떤 SPL 에서도 안전 */
    else
        IOSleep(MODE_TICK_MS);
}
```

한도 자체(50 ms·100 ms)는 그대로다 — 기다리는 물리 현상이 같기 때문이다.  바뀌는 것은
**기다리는 방법**뿐이다.  `enterLinearMode`·`revertToVGAMode` 경로는 `noSleep = 0` 그대로다.

### 4-2. 시험 패턴 노출은 순환 경로에서 건너뛴다

2 초를 도는 것은 운영자가 보라고 있는 것이다.  순환에서는 화면을 되살리는 것이 목적이므로
노출을 건너뛴다(`mode->skipShow`).  2 초짜리 busy-wait 를 만들지 않는 이유이기도 하다.

### 4-3. 복귀가 끝나면 되읽는다

`osrdn_mode_revert` 의 마지막에 스냅샷 대상 13 개 MMIO + 5 개 PLL 을 되읽어 기존
`verifyGot`/`verifyPll` 에 넣고 `verifyBad` 를 세운다.  **새 필드도, 새 로그 형식도 필요 없다**:
`osrdn_mode_lines` 가 이미 `snap=` 과 `got=` 을 나란히 찍는다.  복귀 뒤의 그 줄이 곧 판정이다.

읽기만 더하는 것이므로 `revert-runs-through`(복귀는 중간에 멈추지 않는다)와
`entry-subset-revert`(진입이 쓴 것은 전부 복귀가 되돌린다) 규칙은 그대로 성립한다.

### 4-4. 통로

새 파라미터 `RDNR2bCycle` 을 `setIntValues:` 에 더한다.  게이트는 순서대로:

1. 인자 개수·매직이 맞을 것,
2. 인스턴스 표의 옵트인 키가 `Yes` 일 것,
3. MMIO 가 매핑되어 있을 것,
4. `snapshotValid` 이고 `modeWritten` 일 것(진입이 성공한 뒤에만 뜻이 있다),
5. 걸쇠가 없을 것,
6. test-and-set 으로 **이 부팅에 한 번**.

거절은 전부 하드웨어를 건드리지 않고 반환 코드로 알린다.

### 4-5. 실패했을 때

- 복귀가 항등이 아니면: 그 사실이 로그에 남는다.  그래도 **다시 진입한다**(화면 복구가 우선).
- 다시 진입이 실패하면: 진입은 이미 스스로 복귀한다(12-4).  화면은 콘솔 타이밍에 남고
  WindowServer 는 800×600 을 그리므로 깨져 보인다 — telnet 은 살아 있고 복구는 재부팅이다.
- 어느 쪽이든 걸쇠가 서서 두 번째 순환은 없다.

## 5. 호스트 검사 (코드 전에 만든다)

- **소스 규칙**: `osrdn_mode.m` 에 `IOSleep` 직접 호출이 **헬퍼 한 곳 말고는 없을 것**,
  헬퍼는 `noSleep` 을 볼 것, 순환 경로가 노출 루프를 건너뛸 것, 통로 게이트 6 개가 전부 있을 것.
- **시뮬레이터**: 진입 → 순환(복귀·되읽기·재진입) → 종료 복귀까지 돌려서
  (a) 순환 뒤 카드가 **모드 상태**로 돌아와 있을 것, (b) 순환의 되읽기가 스냅샷과 같을 것,
  (c) 두 번째 순환이 거절될 것, (d) `noSleep` 일 때 `IOSleep` 이 **한 번도 안 불릴 것**
  (가짜 세계가 센다).  변이: 복귀가 레지스터 하나를 빠뜨리면 (b) 가 잡는다.
- **역어셈블 게이트**: 호출자 규칙에 새 함수가 늘어나면 목록에 추가하고, 늘지 않으면 그대로.

## 6. 실기 절차

재부팅이 필요 없다.  지금 돌고 있는 활성 구성 그대로:
설치(`Active Drivers` 를 VGA 로 되돌린 뒤) → operator Configure 전환 → 재부팅 1 회 →
telnet 에서 순환 1 회 → 로그 회수 → 판정.

## 7. 아직 답이 없는 것

- `setIntValues:` 가 어떤 락/SPL 을 쥐고 오는지 **모른다**.  그래서 자지 않는다(3-1).
  `IODelay` 로 100 ms 를 도는 것이 그 문맥에서 허용되는지도 엄밀히는 미확인이다 —
  다만 같은 문서가 `IODelay` 를 "어떤 SPL 에서도 안전" 이라고 적는다.
- WindowServer 가 그리는 도중에 CRTC 를 바꾸는 것이므로, 순환 중 화면이 한순간 깨진다.
  이것은 예상된 것이고 판정에 쓰지 않는다.

## 8. 교차검토 전에 내가 직접 찾은 것 (2026-09-16)

계획을 쓰면서 소스를 읽다가 나온 것들이다.  codex 회신과 섞이지 않게 여기 따로 적는다.

### 8-1. 대기 루프 셋이 **시간으로만** 제한된다 — 하나는 종료 복귀 경로에 있다

`osrdn_mode.m` 의 대기 루프 다섯 중 PLL 원자갱신 둘(118·144 행)은 **반복 횟수로도** 제한되어
`atomicWriteLoops`/`atomicReadLoops`·`Limit` 로 증거를 남긴다.  나머지 셋은 아니다:

| 행 | 무엇 | 한도 |
|---|---|---|
| 171 | PLL 잠금 정착 | `MODE_PLL_SETTLE_US` 50 ms, **경과 시간만** |
| 496 | 시험 패턴 노출 | `MODE_SHOW_US` 2 s, 경과 시간만 |
| 553 | **복귀 정착** | `MODE_REVERT_SETTLE_US` 100 ms, 경과 시간만 |

셋 다 `IOGetTimestamp` 가 전진한다는 가정 위에 서 있다.  전진하지 않으면 `for (;;)` 를 영원히 돈다.
그리고 553 행은 **종료 경로**다 — 거기서 멈추면 종료가 끝나지 않는다.

지금까지 종료 복귀가 두 번 무사히 돌았으므로(결과 §7-2 의 `f94ce36c` → `df5f7425`) **그 문맥에서는
시계가 전진한다**.  하지만 그것은 실측 2 회이지 보장이 아니고, R2c 는 이 코드를 **다른 문맥**으로
가져간다.  → **셋 다 원자갱신 루프와 같은 모양으로 반복 횟수 한도를 준다.**

### 8-2. 소스 주석 하나가 자기 근거보다 넓다 (우리 것)

`osrdn_mode.m` 의 59 행은 "IOGetTimestamp is never read at raised spl" 이라고 적는다.  참인 것은
**우리 코드가 spl 을 올리지 않는다**는 것뿐이고, **불러 주는 쪽의 spl 에 대해서는 아무 말도 못 한다**.
종료 때 커널이 어떤 spl 로 `revertToVGAMode` 를 부르는지 우리는 모른다.  주석을 사실에 맞게 좁힌다.

### 8-3. 되읽기가 VGA 코어를 안 본다 — 가장 큰 구멍

§4-3 의 되읽기는 MMIO 13 + PLL 5 = **18 개**다.  그런데 복귀는 `osrdn_vga_put` 으로 VGA 코어
(MISC·SEQ 0–4·CRTC 0–0x18·GR 0–8·ATTR 0–0x14)와 팔레트 256 항목도 되돌린다.  그쪽은
**아무도 확인하지 않는다**.  시뮬레이터는 보지만 실기에서는 안 본다.

VGA 코어야말로 "콘솔을 잃는다" 가 실제로 일어나는 자리다.  → 되읽기를 **스냅샷과 같은 방법으로
한 번 더 떠서(`vgaTake` 상당) 바이트 단위로 대조**하는 데까지 넓힌다.  비용은 포트 읽기 수십 회다.

### 8-4. 걸쇠 하나로는 모자란다

§4-4 의 test-and-set 은 **순환끼리**의 경합만 막는다.  커널은 언제든 `enterLinearMode` 나
`revertToVGAMode` 를 부를 수 있고 우리 RPC 스레드와 직렬화되지 않는다(Q12).  순환이 복귀와
재진입 사이에 있을 때 커널이 끼어들면 스냅샷 대신 우리 모드가 카드에 남는 창이 생긴다.
→ 걸쇠는 **순환 전용이 아니라 "시퀀스 진행 중" 공용**이어야 하고, 깃발을 만지는 구간만
`splhigh`/`splx` 로 감싼다(대기는 그 밖에서 — `IOGetTimestamp` 를 올린 spl 에서 읽지 않기 위해).

### 8-5. §2 의 문장을 좁혀야 한다

"종료 때 도는 것과 **같은 함수**를 부르므로, 여기서 항등이면 종료 복귀도 항등이다" 는 **과한
주장**이다.  같은 것은 *레지스터 복원 논리*뿐이고, 다른 것은 문맥이다: spl, 시계가 전진하는지,
WindowServer 가 살아 있는지, 팔레트를 그 사이 누가 바꿨는지.  정확히는:

> 이 순환은 **복원 논리가 스냅샷을 되돌린다**는 것을 증명한다.  종료 문맥에서도 그 논리가 같은
> 결과를 낸다는 것은 증명하지 않는다 — 문맥 차이는 8-1·8-2 로 따로 막는다.

### 9-1. 검증 중에 내가 추가로 찾은 것

Matrox 코드를 열어보다 나왔다: 그 드라이버는 **콘솔이 텍스트 모드였으면 복원을 거부한다**
(`OpenStepMGAReplacementDisplay.m` 7622–7629 행 주석: 텍스트 모드면 스냅샷에 문자 발생기 평면이
없어서, 복원이 타이밍만 되돌리고 아무것도 못 읽게 만들 수 있다).  **우리 스냅샷에도 문자 발생기
평면이 없고, 우리에겐 그 게이트가 없다.**  실측 세 부팅 모두 `attr10=01`(그래픽 모드)이었으므로
지금까지는 문제가 없었다.  게이트를 추가한다.

## 10. 개정 1 — 판정을 반영한 설계

1. **복귀 증거를 따로 담는다**: `revertGot[13]`·`revertPll[5]`·`revertVga`(코어 + 팔레트 요약)·
   `revertBad`.  재진입의 `modeVerify` 가 건드릴 수 없다.  로그도 `revert` 줄을 따로 낸다.
2. **되읽기를 스냅샷 전체로 넓힌다**: MMIO 13 + PLL 5 + **VGA 코어 61 바이트 + 팔레트 256 항목**.
   방법은 스냅샷과 같은 경로(`osrdn_snap_take` 상당)로 한 번 더 떠서 바이트 대조.
3. **되읽기는 PLL 인덱스를 반드시 되돌린다** — `osrdn_snap_take` 가 하는 것과 같은 모양으로.
   **같은 수정을 `modeVerify` 에도 한다**(지금 도는 코드의 결함, 판정 3).
4. **걸쇠는 시퀀스 공용**으로 하고 `splhigh`/`splx` 로 감싼 test-and-set 으로만 만진다
   (대기는 그 밖에서).  `enterLinearMode`·`revertToVGAMode`·순환이 같은 깃발을 본다.
   순환이 **복귀와 재진입 사이**에 있는 동안 들어온 커널 복귀는 "나중에 카드가 리니어로 남는" 경로이므로,
   순환은 그 창에서 커널 복귀가 왔다는 사실을 기록하고 **재진입하지 않는다**.
5. **대기 루프 셋에 반복 횟수 한도**를 준다(내 8-1).  `noSleep` 일 때는 `IODelay` 로 돈다.
6. **텍스트 모드 게이트**를 진입·복귀 양쪽에 둔다(9-1).
7. 증명 범위를 문서에 좁혀 적는다: 이 순환은 **복원 논리가 스냅샷을 되돌린다**는 것만 증명한다.
   래퍼 순서·`super` 가 바꾸는 상태·종료 문맥의 spl 은 증명하지 않는다.
8. 예산을 정직하게 적는다: 통상 **200 ms**, 최악 **600 ms** 의 busy-wait.  그 문맥에서 그것이
   안전한지는 **미확인**이다 — 그래서 순환은 부팅당 1 회이고 운영자가 부를 때만 돈다.

## 11. 구현 완료 (2026-09-16)

§10 의 여덟 항목이 모두 코드에 들어갔고 `hostcheck-r2b` 6 단계 · `check-all` 이 통과한다.
시뮬레이터 검사 27 건(기준 10, 변이 17) — 변이는 전부 잡힌다.

- **대기**: `IOSleep`·`IODelay` 가 `modeWaitTick` 한 곳으로 모였고, 다섯 루프 전부 **시간·횟수
  두 한도**를 갖는다.  (8-1 정정: `loops` 는 세기만 했지 탈출 조건이 아니었다 — 원자갱신 둘도
  시간 한도뿐이었다.)
- **PLL 인덱스**: `modePllRead` 가 읽기 전 인덱스를 저장하고 뒤에 되돌린다.  `modeVerify` 에도
  적용했다 — **이미 실기에서 도는 빌드의 결함**이었다.  시뮬레이터가 "로그가 말하는 값 = 레지스터가
  든 값" 을 불변식으로 확인한다.
- **복귀 되읽기**: `wantRevertCheck` 일 때만, `osrdn_snap_take` 로 두 번째 스냅샷을 떠서
  MMIO 13 + PLL 5 + VGA 61 바이트 + 팔레트 256 항목을 대조한다.  **종료 경로에서는 켜지 않는다**
  (그 경로는 기계가 이미 통과시킨 그대로 둔다).
- **걸쇠**: `splhigh` 로 감싼 시퀀스 공용 claim.  커널 복귀가 순환 중에 오면 하드웨어를 건드리지
  않고 `kernelRevertSeen` 만 세우며, 순환은 그때 **재진입하지 않는다**.
- **텍스트 콘솔**: 진입 거절(`MODE_WHY_TEXT_CONSOLE`).
- **통로**: `RDNR2bCycle` 파라미터 + 매직 `0x52324358`, 부팅당 1 회.  도구는
  `rdnr2b0 <runid> <build> cycle`.
- **도구의 발행 모드 상수**가 생성 헤더와 같은지 `check_tool_mode.py` 가 본다(도구는 타깃에서
  그 헤더 없이 컴파일된다 — literal 이 어긋나면 도구의 게이트 자체가 거짓말이 된다).
  이 검사가 **기존 1024×768 잔재**를 잡았다.

### 11-1. 실기 절차

1. 패킹 → 타깃 빌드 → 호스트 reloc 게이트.
2. `restore.sh`(활성 드라이버 밑에서는 설치가 거절된다) → `restored` 판정 → 설치(`fresh`).
3. 새 기준선 스냅샷 → `precheck` → 복원 묶음 스테이징.
4. operator: Configure 에서 VGA → OSRDNDisplay, 저장·닫기 → 주차·`activate`·`same` → 재부팅.
5. 부팅 뒤 telnet 에서 **순환 1 회**: `rdnr2b0 <runid> <build> cycle`.
   화면은 한순간 깨졌다가 돌아온다(복귀 → 재진입).  그것이 정상이다.
6. 로그의 `cycle`·`back`·`backpll` 줄로 판정한다.

## 12. 첫 순환의 결과와, 그것이 드러낸 것 (2026-09-16, 부팅 `fa953617`, 빌드 `b08717c1`)

### 12-1. 실측

`rdnr2b0 789550530 b08717c1 cycle` → `r=0`, 화면이 깜빡였다가 돌아왔고 telnet 은 살아 있었다.

```
RDN-R2B cycled boot=fa953617 live=1
RDN-R2B cycle n=1 why=0 checked=1 cwhy=0 bad=2 vga=0 palette=0 kernel=0
```

- **VGA 코어 61 바이트 전부 일치, 팔레트 256 항목 전부 일치.**  복귀가 콘솔을 잃지 않는다는
  가장 중요한 부분은 깨끗하다.
- MMIO 13 + PLL 5 중 16 개 완전 일치.  어긋난 둘:

| 레지스터 | 스냅샷 | 되읽기 | xor |
|---|---|---|---|
| `CRTC_OFFSET` | `00000000` | `40000000` | `40000000` |
| `CRTC_OFFSET_CNTL` | `10000000` | `50000000` | `40000000` |

python 으로 분해하면 **둘 다 "스냅샷 값 그대로 + bit 30"** 이다.  복원한 값은 정확히 들어가 있고
비트 하나가 더 서 있었다.

### 12-2. 그 비트

`ref/upstream/unpacked/xf86-video-ati-6.14.6/src/radeon_reg.h` 456 행:
`RADEON_CRTC_OFFSET__GUI_TRIG_OFFSET (1<<30)`.  같은 트리의
`radeon_driver.c` 4170–4181 행은 `CRTC_OFFSET` 에 쓴 뒤 **그 비트가 내려갈 때까지 기다린다**
(주석 "wait for offsets to catch up with hw", 100 만 회 한도 + `usleep(1000)`).
`CRTC_OFFSET_CNTL`(0x0228) 의 bit 30 은 그 헤더에 **정의가 없다** — 우리 실측이 같은 자리에서
같은 모양으로 움직이는 비트를 보여줄 뿐이다.

### 12-3. 지금 다시 읽어 본 것

레코드 경로(읽기 전용 계측, 런 789550531)로 같은 두 레지스터를 다시 읽었다:
`CRTC_OFFSET=00000000`, `CRTC_OFFSET_CNTL=00000000` — **bit 30 은 내려가 있다.**

### 12-4. 내 해석과, 그 해석의 약한 고리

해석: **복귀는 옳고, 되읽기가 너무 일찍 읽었다.**  복귀는 4.8 에서 CRTC 를 막 켠 직후에 읽는데
오프셋 래치는 다음 수직 귀선에서 일어난다.  진입 쪽 되읽기가 깨끗했던 것도 같은 이유로 설명된다 —
진입은 시험 패턴 480000 번 쓰기를 지난 뒤에 읽으므로 래치가 이미 끝나 있다.

**약한 고리(스스로 적어 둔다)**: 12-3 의 재읽기는 순환이 **이미 재진입한 뒤**의 값이다.
재진입이 두 레지스터를 다시 썼으므로, "복귀 뒤에 비트가 내려갔다" 를 직접 본 것은 아니다.
본 것은 "쓰기 뒤 어느 시점에 비트가 내려간다" 까지다.  다른 설명이 남아 있는지 검토가 필요하다.

### 12-5. 제안하는 수정

1. `modeRevertCheck` 가 되읽기 **전에** `CRTC_OFFSET` 의 bit 30 이 내려가기를 **한도를 두고**
   기다린다(참고 구현과 같은 모양, 우리 `modeWaitUs` 의 두 한도 방식).
2. 그래도 서 있으면 **복원 실패로 세지 않고** 별도 사실(`revertOffsetPending`)로 기록한다.
   값 비교 자체는 **마스크 없이** 엄격하게 둔다 — 진짜 값 차이는 여전히 실패여야 한다.
3. **종료 경로는 건드리지 않는다.**  이 대기는 `wantRevertCheck` 일 때만 돈다.  종료 복귀는
   기계가 이미 통과시킨 모양 그대로 둔다.
4. 시뮬레이터에 세계 둘을 더한다: 가짜가 `CRTC_OFFSET` 쓰기에 bit 30 을 세웠다가 N 번째 읽기에
   내리는 세계(대기가 동작함을 증명), 그리고 **영영 안 내리는 세계**(한도에 걸리고 `pending` 으로
   기록되며 값 비교는 그대로 엄격함을 증명).

### 12-6. 교차검토에 물을 것

- 12-4 의 약한 고리: 이 데이터로 "복원은 옳다" 를 결론지어도 되는가, 아니면 다른 설명이 있는가.
- `CRTC_OFFSET_CNTL` bit 30 을 `CRTC_OFFSET` bit 30 과 같은 것으로 다뤄도 되는가(정의가 없다).
- 대기를 넣는 자리가 되읽기 앞이 맞는가, 아니면 복귀의 CRTC 복원 직후가 맞는가.
- 종료 경로에 대기를 넣지 않기로 한 판단이 옳은가 — 반영 대기 중에 전원이 꺼지면 무엇이 남는가.

### 12-7. 교차검토 전에 내가 참고 구현에서 직접 확인한 것

- **참고 구현의 복원 경로에는 대기가 없다.**  `legacy_crtc.c` 116–117 행의
  `RADEONRestoreCrtcBase` 는 `CRTC_OFFSET_CNTL` 을 쓰고 `CRTC_OFFSET` 을 쓰고 **바로 끝난다**.
  12-2 에서 인용한 대기(`radeon_driver.c` 4170–4181)는 복원이 아니라 **메모리 맵을 바꾸고 엔진을
  리셋한 뒤**의 특수 경로다.  → 종료 경로에 대기를 넣지 않기로 한 12-5.3 은 참고 구현의 복원과
  같은 모양이라는 뜻이고, 근거가 "우리 판단" 에서 "참고와 일치" 로 올라간다.
- **참고 구현의 저장은 우리와 같다.**  `legacy_crtc.c` 541–542 행은 두 레지스터를 `INREG` 로
  그대로 저장한다 — bit 30 이 서 있으면 그것까지 저장했다가 되쓴다.  그 구현이 그렇게 해도 된다고
  본다는 뜻이다.
- **다만 새 모드를 만들 때는 0 에서 조립한다**: 같은 파일 773–787 행의 `RADEONInitCrtcBase` 는
  `crtc_offset_cntl` 을 0 에서 시작해 플래그만 OR 한다.  즉 이 기계 스냅샷의 bit 28(`10000000`)은
  참고 구현이라면 버렸을 값이다.  우리 쪽이 더 엄격하다.
- **NetBSD 는 이 레지스터들에 0 을 쓴다**(`radeonfb.c` 2582–2583).  대기는 없다.
- **수정이 곧 측정이다**: 12-4 의 약한 고리("재진입 뒤에 읽어서 직접 못 봤다")는 12-5.1 을 넣으면
  닫힌다 — 되읽기 앞의 대기가 **몇 번 돌아 비트가 내려갔는지** 기록하므로, 다음 순환은
  "복귀 뒤에 비트가 내려간다" 를 직접 보여준다.  그 값은 0 일 수도 있다(이미 내려가 있었다).

| 2 | `CRTC_OFFSET_CNTL` bit 30 을 "같은 상태 비트" 라 부를 수 없다 | xf86 `radeon_reg.h` 456·462 행과 NetBSD `radeonfbreg.h` 504·510 행을 둘 다 열었다 — **두 헤더 모두 bit 30 을 `CRTC_OFFSET`(과 `CRTC2_OFFSET`)에만 정의**하고, `CRTC_OFFSET_CNTL` 의 정의는 bit 0 의 `TILE_LINE_SHIFT` 부터 시작한다 | ✅채택.  "경험적으로 같이 관측된 비트" 로만 부른다 |
| 3 | 대기는 되읽기 **앞**이 맞다(오프셋 쓰기 직후가 아니라) | 복귀는 오프셋 쓰기 뒤에도 PLL 재프로그램·100 ms 정착·CRTC 복원·VGA·DAC 가 남아 있다 — 쓰기 직후에 기다리면 "중간 상태에서 내려갔다" 만 증명한다 | ✅내 12-5.1 이 맞았다고 확인해 줌 |
| 4 | 종료 경로를 그대로 두는 것은 타당 | 내가 12-7 에서 이미 확인한 것과 같다(`legacy_crtc.c` 116–117, `radeonfb.c` 2582–2583) | ✅내 판단 확인 |
| 5 | 12 절의 다섯 문장이 사실이 아니라 추론 | 아래 13-1 | ✅전부 채택 |
| 6 | 12-5.2 가 자기모순 — "마스크 없이 엄격 비교" 와 "실패로 세지 않는다" 는 함께 설 수 없다 | 내 `modeRevertCheck` 는 원시 불일치마다 `revertBad++` 한다 | ✅채택.  원시 집계는 그대로 두고 **결론을 따로 분류**한다 |

### 13-1. 사실로 적었지만 추론이었던 것 (정정)

- "복원한 값은 정확히 들어가 있다" → 관측된 것은 **"bit 30 을 뺀 모든 비트가 일치했다"** 뿐이다.
- "VGA·팔레트가 일치하므로 콘솔을 잃지 않는다" → 강한 방증이지만 **콘솔이 실제로 쓸 만했다는
  증명은 아니다**(그 부팅에서 콘솔로 돌아가 본 적이 없다).
- "두 bit 30 이 같이 움직인다" → 같은 값으로 **한 번 함께 관측됐을** 뿐이다.
- "오프셋 래치는 다음 수직 귀선에 일어난다" → 근거를 열어 보니 xf86 자신도 단정하지 않는다.
  `radeon_driver.c` 6099–6104 행: "**possibly** because crtc will pick up the new offset value
  at the end of each scanline, but the new offset_cntl value **only after a vsync**".
  즉 (a) 추측이고, (b) **두 레지스터가 서로 다른 시점에 갱신된다**고 적는다 — 이것은 내가
  둘을 한 덩어리로 본 것에 대한 **독립적인 반증**이다.
- "쓰기 뒤 어느 시점엔 내려간다" 조차 과하다 → 본 것은 **재진입이 두 레지스터를 다시 쓴 뒤에
  내려가 있었다** 까지다.

### 13-2. 개정 2 — 분리 측정을 하는 설계

`modeRevertCheck` 를, 재진입 **전에** 다음을 하도록 바꾼다(순서가 증명의 전부다):

1. `CRTC_OFFSET` 과 `CRTC_OFFSET_CNTL` 을 **대기 전에** 그대로 기록한다(`revertOffsetFirst[2]`).
2. `CRTC_OFFSET` 의 bit 30 이 내려가기를 **두 한도(시간·횟수)** 로 기다리며 **돈 횟수를 센다**
   (`revertOffsetTurns`), 끝까지 서 있으면 `revertOffsetPending = 1`.
3. 그다음에 스냅샷 전체를 떠서 **마스크 없이** 비교한다(원시 불일치는 `revertBad` 그대로).
4. **결론을 따로 분류한다** (`revertVerdict`):
   - `0` 깨끗함,
   - `1` **판정 보류**: 어긋난 것이 `CRTC_OFFSET`·`CRTC_OFFSET_CNTL` 뿐이고 각각의 xor 가
     정확히 bit 30 일 때.  "복원 실패" 라고 부르지 않는다.  **다만 `CRTC_OFFSET_CNTL` 쪽은
     아직 근거가 없으므로 이 보류에 포함된다는 사실 자체를 줄로 남긴다.**
   - `2` 진짜 불일치.

이 순서가 13 절 1 번의 대안 가설을 가른다:

- bit 30 이 **재진입 전에** 내려가고 두 워드가 스냅샷과 같아지면 → 내 해석이 지지된다.
- 재진입 뒤에야 내려가면 → **대안이 이긴다**(복귀의 갱신은 완료된 적이 없다).
- `CRTC_OFFSET` 만 내려가고 `CRTC_OFFSET_CNTL` 의 bit 30 이 남으면 → **둘은 같은 것이 아니다**.

세 결과 모두 한 줄의 기록으로 갈린다.  그러니 이번 수정은 고치는 일이 아니라 **재는 일**이다.

## 14. 다음 순환의 판정 기준 (실행 **전에** 고정한다, 2026-09-16)

결과를 보고 기준을 정하면 그것은 판정이 아니다.  다음 순환이 낼 두 줄

```
RDN-R2B cycle n=1 why=.. checked=.. bad=.. vga=.. palette=.. kernel=.. verdict=..
RDN-R2B trig first_off=........ first_cntl=........ turns=.... pending=..
```

만으로 아래 표가 갈린다.  `first_*` 는 **대기 전·재진입 전**의 값이고, `back`/`backpll` 줄은
대기 **뒤**의 값이다.  둘의 차이가 이번 실험의 전부다.

| 관측 | 뜻 | 다음 행동 |
|---|---|---|
| `verdict=0`, `turns=0`, `first_off` 에 bit 30 **없음** | 지난번 관측이 재현되지 않았다.  복귀는 깨끗했고 그때는 타이밍이 달랐을 뿐 | 복귀 판정 **통과**로 기록.  13-1 의 정정은 그대로 둔다(한 번의 비재현은 설명이 아니다) |
| `verdict=0`, `turns>0`, `first_off` 에 bit 30 **있음** | **내 해석이 맞다**: 복귀 뒤 비트가 서 있었고, **재진입 전에** 내려갔으며, 두 워드가 스냅샷과 같아졌다 | 복귀 판정 **통과**.  12-4 의 약한 고리가 닫힌다 |
| `verdict=1`, `pending=1` | 한도 안에 안 내려갔다.  **복귀 실패가 아니라 미결**이다 | 재진입 전 상태를 더 오래 지켜보는 별도 실험이 필요하다.  종료 경로는 건드리지 않는다 |
| `verdict=1`, `pending=0`, `back CRTC_OFFSET` 은 일치하는데 `CRTC_OFFSET_CNTL` 만 bit 30 | **두 비트는 같은 것이 아니다**(13-1 두 번째 정정이 맞았다) | `CRTC_OFFSET_CNTL` 상위 비트를 별도 미확인 항목으로 올린다 |
| `verdict=2` | 스냅샷으로 돌아가지 않은 **진짜 값**이 있다 | 복귀 판정 **실패**.  어느 레지스터인지 `back` 줄로 특정하고, 그 부팅에서는 더 건드리지 않는다 |
| `checked=0` | 되읽기가 스냅샷을 못 떴다(`cwhy` 가 이유) | 판정 불가.  기록만 하고 복원·재부팅 |
| `kernel=1` | 커널이 순환 중에 복귀를 요구했다 | 순환은 재진입하지 않았다.  화면은 콘솔 상태다.  정상 동작이며 판정은 다음 기회로 |

어떤 결과든 **화면이 안 돌아오면** telnet `sh /me/rdn-r2b0/restore.sh` → 재부팅이 회수 경로다.

## 15. 첫 분리 측정의 결과 (2026-09-16, 부팅 `f96405d1`, 빌드 `294002e0`)

```
RDN-R2B trig first_off=40000000 first_cntl=50000000 turns=42 pending=0
RDN-R2B back CRTC_OFFSET      snap=00000000 got=00000000
RDN-R2B back CRTC_OFFSET_CNTL snap=10000000 got=10000000
RDN-R2B cycle n=1 why=0 checked=1 cwhy=0 bad=0 vga=2 palette=0 kernel=0 verdict=2
```

### 15-1. §14 표의 두 번째 갈래 — 내 해석이 맞았다

- **대기 전**: 두 워드 모두 bit 30 이 서 있었다(`40000000`, `50000000`) — 첫 순환과 **정확히 재현**.
- **42 번 돌자 내려갔고**, 그것은 **재진입 전**이다.
- 그 뒤 두 워드가 스냅샷과 **완전히 일치**했다(`bad=0`).

따라서 13 절 1 번의 대안 가설("재진입이 덮었거나 완료시켰을 뿐")은 **반증되었다**.
복귀는 두 오프셋 레지스터를 제대로 되돌리고, 첫 순환의 되읽기는 단지 **너무 일찍 읽었다**.
`CRTC_OFFSET_CNTL` 의 bit 30 도 함께 내려갔다 — 정의는 여전히 없으므로 **관측이 둘로 늘었을 뿐**
이지만, 두 번 다 함께 움직였다.

### 15-2. 새로 드러난 것 — VGA 코어 바이트 둘이 안 돌아온다

MMIO 18 개와 팔레트 256 항목은 전부 일치하는데 **`vga=2`** 다.  분류기는 옳게 동작해
오프셋 쪽은 보류로 두고 이것을 `verdict=2`(진짜 불일치)로 올렸다.

**되읽기를 VGA·팔레트까지 넓히지 않았으면 영영 안 보였을 종류다**(교차검토 1 차 지적 2).

첫 순환이 `vga=0` 이었던 것은 대기 없이 즉시 읽었기 때문이고, 이번엔 약 21 ms 뒤에 읽었다.
그 사이에 무엇이 그 두 바이트를 바꾸는지는 **모른다** — 지금 로그는 개수만 찍는다.
→ 다음 빌드가 **어느 바이트인지 이름을 찍는다**(`backvga kind=.. index=.. snap=.. got=..`,
kind 1 MISC 2 SEQ 3 CRTC 4 GR 5 ATTR).  가짜 카드에 "무언가 바꿔 놓았고 복원이 못 되돌리는"
세계를 넣어 이름 찍기가 동작함을 증명했고, 이름을 빼는 변이가 잡힌다.

### 15-3. 내 설계 구멍 — 순환이 화면을 덮었다

순환의 재진입이 진입 절차를 그대로 타면서 **10 단계의 시험 패턴을 프레임버퍼 전체에 다시 그렸다.**
`skipShow` 는 2 초 대기만 건너뛰게 만들었지 그리기는 건너뛰지 않았다.  WindowServer 는 다시 그릴
이유가 없어 **시험 패턴이 화면에 남았고, operator 는 화면을 못 보니 GUI 로 회수할 수도 없었다**
(재부팅으로 회수).  내가 "로그아웃하시라" 고 안내한 것도 같은 이유로 틀렸다.

- **수정**: 순환은 패턴을 그리지 않는다.  모드 전환은 프레임버퍼를 지우지 않으므로
  **안 그리는 것이 곧 데스크톱을 되살리는 것**이다.
- **증명**: 시뮬레이터가 순환 중 프레임버퍼 쓰기 0 을 확인하고, 되돌리는 변이는
  `480000 framebuffer words over the desktop` 으로 잡힌다.

### 15-4. 설치 절차 변경 (operator 결정, 2026-09-16)

> "불필요하게 Generic SVGA 로 전환작업 같은거 하지 마세요.  그냥 설치만 다시 하면 나머지는
> 제가 알아서 하겠습니다."

설치기 게이트 2("적재되도록 설정된 드라이버 밑에서 번들을 갈아치우지 않는다") 때문에 그동안
`restore.sh` → 설치 → Configure 재전환을 돌았다.  이제 **`live` 옵트인**을 둔다:

- `live` 없이는 **여전히 거절**한다(검사가 두 경우를 모두 확인한다).
- `live` 면 진행하고, 그 사실을 화면과 `INSTALLED` 표지에 **기록**한다.
- 받아들일 수 있는 이유: 돌고 있는 드라이버는 이미 메모리에 있어 이 부팅은 영향이 없고,
  후보는 `.new` 에 통째로 만들어 한 번의 rename 으로 들어가며, 옛 번들은 `.prev` 에 남고,
  다음 부팅이 깨진 번들을 만나면 `driverLoader` 가 `VGA.config/Default.table` 로 넘어간다.

## 16. 두 번째 분리 측정이 찾은 것 — 속성 팔레트를 못 읽고 있었다 (2026-09-16)

부팅 `e5dd9d7c`, 빌드 `c3254f87`.  이번엔 순환이 화면을 덮지 않았고(수정 확인), operator 도
"다시 화면이 잘 보입니다" 로 확인했다.

```
RDN-R2B cycle n=1 why=0 checked=1 cwhy=0 bad=0 vga=7 palette=0 kernel=0 verdict=2
RDN-R2B trig first_off=40000000 first_cntl=50000000 turns=54 pending=0
RDN-R2B backvga kind=5 index=00 snap=01 got=00
RDN-R2B backvga kind=5 index=01 snap=00 got=01
RDN-R2B backvga kind=5 index=02 snap=00 got=01
RDN-R2B backvga kind=5 index=08 snap=01 got=00
RDN-R2B backvga kind=5 index=0c snap=01 got=00
RDN-R2B backvga kind=5 index=0d snap=00 got=01
```

- 오프셋 트리거는 **세 번째 재현**이고 매번 재진입 전에 내려갔다(`turns=54 pending=0`).
- MMIO 18 개·팔레트 256 항목은 전부 일치.  어긋난 7 개는 **전부 kind 5 = 속성 제어기**,
  그리고 이름이 찍힌 6 개가 모두 **`0x00`–`0x0d`, 즉 내부 팔레트 구간**이다.

### 16-1. 원인 (참고 구현이 자기 코드로 말해 준다)

`openstep-matrox-remade` 의 `OpenStepMGAReplacementDisplay.m` 1824–1828 행:

> "Reading also needs the palette address source bit CLEAR, because with it set the sixteen
> palette entries are not addressable -- and clearing it blanks the screen for as long as it
> stays clear.  X.Org's generic VGA save does exactly this and accepts the blank."

같은 파일 1900–1907 행의 코드가 그대로 한다: 속성 읽기 루프 **앞**에 `ATTR_INDEX <- 0x00`
(PAS 끔), 21 개를 읽고, **뒤**에 `0x20`(PAS 켬).  그 파일의 `osmgaReadAttr` 는 인덱스를
**PAS 없이** 쓴다(`osmgaW8(base, MGA_ATTR_INDEX, idx)`), 우리 루프의 `| (pas & VGA_PAS)` 가
바로 그 차이다.  **쓰기 경로도 마찬가지다**: 같은 파일 4737–4741 행이 적재 전에 명시적으로
PAS 를 끈다("attribute controller (PAS off during load)").  우리 `osrdn_vga_put` 은 인덱스
바이트의 bit 5 가 0 이라 결과적으로 같은 상태에서 쓴다.

**확인하지 못한 것**: 위 인용이 근거로 드는 "X.Org's generic VGA save does exactly this" 는
이 워크스페이스 미러에 `vgaHW` 소스가 없어 **1 차 출처로 확인하지 못했다**.  Matrox 프로젝트의
산문으로만 남겨 둔다.

**우리 `vgaTake` 는 PAS 를 보존한 채 읽는다** (`k | (pas & VGA_PAS)`).  콘솔은 PAS=1 이므로
내부 팔레트 16 개는 주소 지정이 되지 않는다.  따라서

- 우리 **스냅샷의 ATTR 0x00–0x0F 는 한 번도 유효했던 적이 없고**,
- 되읽기도 같은 이유로 유효하지 않으며,
- 두 번의 무효한 읽기가 일치할 이유가 없다.  `vga` 가 0 → 2 → 7 로 들쭉날쭉했던 것이 이것이다.

그리고 `osrdn_vga_put` 은 PAS 를 끄고 쓰므로 **쓰기는 유효**하다 — 즉 복귀는 **한 번도 유효하게
읽은 적 없는 값을 콘솔의 속성 팔레트에 써 넣어 왔다.**  이것이 "콘솔을 잃는" 부류다.
R2b 이후 종료 복귀가 매번 그렇게 했고, 다음 부팅이 멀쩡했던 것은 VGA BIOS POST 가
카드를 다시 프로그램하기 때문일 뿐이다(§7-3 에서 적은 그 한계가 여기서 실제로 문제가 된다).

### 16-2. 제안하는 수정

1. `vgaTake` 의 속성 루프를 참고 구현과 같은 모양으로 바꾼다:
   상태 포트 읽기 → `ATTR_INDEX <- 0x00`(**PAS 끔**) → 21 개 읽기 → 상태 포트 읽기 →
   `ATTR_INDEX <- 원래 pas`.  루프 안에서는 지금처럼 매번 플립플롭을 리셋하고 인덱스를
   **PAS 없이** 쓴다.
2. `osrdn_vga_put` 은 그대로 둔다(이미 PAS 를 끄고 쓰고, 끝에 PAS 를 복원한다).
3. 대가: 읽는 동안 화면이 깜깜해진다.  참고 구현도 X.Org 도 그것을 받아들인다 —
   진입의 스냅샷은 모드를 새로 프로그램하기 직전이고, 순환의 되읽기는 깜빡임이 이미 있는 구간이다.
4. 검사: 가짜 카드의 속성 제어기에 **PAS 규칙을 넣는다** — PAS 가 서 있으면 팔레트
   0x00–0x0F 는 읽어도 쓴 값이 아닌 것을 돌려준다.  그러면
   - 지금 코드는 스냅샷·되읽기가 어긋나 **잡히고**,
   - 고친 코드는 일치한다.
   PAS 를 안 끄는 변이가 그 세계에서 실패해야 한다.

### 16-3. 이 발견이 나온 경로 (기록)

이 결함은 **되읽기를 VGA 까지 넓혔기 때문에만** 보였다(1 차 교차검토 지적 2).  그리고 어느
바이트인지 이름을 찍게 만들었기 때문에 **원인을 특정할 수 있었다** — 개수만 있었을 때는
"VGA 두 개가 이상하다" 에서 더 나아갈 수 없었다.

### 17-1. 사실로 적었지만 추론이었던 것 (정정)

- "콘솔은 PAS=1 이다" → **되읽기 쪽은 확실**하다(`osrdn_vga_put` 이 방금 0x20 을 강제했다).
  **부팅 스냅샷 쪽은** R2b-0 에서 한 번 `attri=20` 으로 측정됐을 뿐이고, 지금 스냅샷 구조체는
  그 값을 **보관하지 않는다** → 고칠 때 **PAS 를 스냅샷에 기록**한다.
- "팔레트 스냅샷은 한 번도 유효한 적이 없다" → **그 부팅에서 PAS 가 서 있었을 때만** 참이다.
- "두 무효한 읽기가 일치할 이유가 없다 → 그래서 0→2→7" → 위 2 번.  미설명으로 남긴다.
- "이것은 콘솔을 잃는 부류다" → 위험 판단이다.  실제로 이번 순환은 **화면을 되돌려 놓았다**.
- "X.Org 도 그렇게 한다" → Matrox 주석의 주장이고 이 워크스페이스에 `vgaHW` 소스가 없다.
  **하지만 이제 그 주장에 기대지 않아도 된다 — 사양서가 직접 말한다.**

### 17-2. 개정 3 — 고칠 것

1. `vgaTake` 의 속성 구간: `splhigh` → 상태 포트 → `ATTR_INDEX <- 0x00`(PAS 끔) →
   21 개를 **PAS 없는 인덱스**로 읽기 → 상태 포트 → `ATTR_INDEX <- 원래 pas` → `splx`.
2. **스냅샷에 `vgaAttrPas` 를 기록**한다(17-1 첫 항목).
3. `osrdn_vga_put` 은 그대로.  주석만 "비디오를 다시 켠다" 로 고친다.
4. 가짜 카드: PAS=1 이면 `0x00`–`0x0F` 의 **쓰기는 무시되고 읽기는 사양서대로 `0xff`** 를 낸다.
   `0x10`–`0x14` 는 PAS 와 무관하다.  그러면 지금 코드는 스냅샷이 전부 `0xff` 가 되어
   **복원이 세계의 진짜 속성 파일과 달라지고**, 기존의 "복원 = 항등" 검사가 잡는다.

## 18. PAS 수정 뒤 다음 순환의 판정 기준 (실행 전에 고정, 2026-09-16)

| 관측 | 뜻 |
|---|---|
| `vga=0`, `verdict=0` | **복귀가 스냅샷 전체를 되돌린다** — 잠긴 레지스터를 읽던 것이 유일한 원인이었다.  R2c 의 목적 달성 |
| `vga>0` 이고 이름이 전부 `0x00`–`0x0F` | PAS 를 껐는데도 팔레트가 안 맞는다 → **다른 원인**이 있다.  `0→2→7` 의 불안정성(17-1 세 번째)과 같은 뿌리일 수 있다 |
| `vga>0` 이고 이름에 `0x10`–`0x14` 가 섞임 | 게이트와 무관한 레지스터가 안 돌아온 것 → 복원 순서·플립플롭 문제 |
| `backvga` 에 `got=ff` 가 보임 | 읽기가 여전히 잠긴 상태였다 — 수정이 그 경로를 다 덮지 못했다 |

`osrdn_snap` 이 이제 `vgaAttrPas` 를 담으므로, "콘솔이 PAS=1 이었다" 는 다음 부팅부터
**추론이 아니라 기록**이 된다.  그 값은 `vga` 줄에 찍지 않으므로(줄 예산) 필요하면 다음 빌드에서
더한다.

또 하나 확인할 것: **부팅 진입 때 시험 패턴이 보이는가.**  빌드 `c3254f87` 부팅에서 operator 가
"시험패턴 없이 바로 진행됐다" 고 했는데, 그 부팅의 진입은 `skipShow=0` 이라 패턴을 그렸어야 한다.
원인 미확인 — 모니터가 새 타이밍에 동기하는 데 2 초 이상 걸려 노출 구간을 통째로 놓쳤을 가능성이
가장 크지만 **측정된 바 없다**.  화면이 정상으로 올라왔고 `bad=0` 이므로 기능 문제는 아니다.

## 19. R2c 판정 — 복귀가 증명되었다 (2026-09-16, 부팅 `dee96850`, 빌드 `dbd73dcd`)

```
RDN-R2B cycle n=1 why=0 checked=1 cwhy=0 bad=0 vga=0 palette=0 kernel=0 verdict=0
RDN-R2B trig first_off=40000000 first_cntl=50000000 turns=54 pending=0
```

`backvga` 줄은 **한 줄도 없다**.

### 19-1. 무엇이 증명되었나

복귀 직후, **재진입 전에**, 카드가 스냅샷과 **바이트 단위로 같다**:

| 대상 | 개수 | 결과 |
|---|---|---|
| MMIO | 13 | 전부 일치 |
| PLL | 5 | 전부 일치 |
| 팔레트 | 256 | 전부 일치 |
| VGA 코어(MISC·SEQ·CRTC·GR·ATTR) | 61 | 전부 일치 |

이것이 R2c 의 목적이었다.  종료를 기다리지 않고, 로그가 닿지 않는 경로를 추측하지 않고,
**복원 논리가 스냅샷을 되돌린다**는 것을 기계 위에서 확인했다.

**증명 범위는 좁게 적어 둔다**(13 절 4 번): 이것은 *복원 논리*의 증명이다.  종료 문맥에서 같은
결과가 난다는 증명은 아니다 — 그때의 spl 도, `super` 가 먼저 바꾸는 것도 우리가 모른다.

### 19-2. `0 → 2 → 7 → 0`

PAS 수정 전 세 번의 순환이 VGA 불일치를 0, 2, 7 개로 냈고, 수정 뒤에는 **0 개**다.
잠긴 레지스터를 읽던 것이 **유일한 원인**이었다는 강한 증거다.  다만 RV280 이 PAS=1 에서
무엇을 돌려주는지는 여전히 **측정한 바 없다**(사양서의 "all 1s" 는 그 구현의 것이고 우리 카드는
`00`/`01` 을 냈다).  더 캐지 않는다 — 잠긴 레지스터를 읽지 않는 것이 답이고, 이제 읽지 않는다.

### 19-3. 오프셋 트리거

`turns=54 pending=0` 으로 **네 번째 재현**.  매번 복귀 뒤에 서 있다가 재진입 전에 내려갔다.
15-1 의 결론은 그대로다.

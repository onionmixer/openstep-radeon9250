# M1v — 삼각형마다 부르지 말고 **한 무리씩** 받는다

재부팅 없음.  훅과 러너·판정기만.

## 1. 왜 이것인가 — 기계어가 방향을 정했다

M1u §0 이 `otool -tV` 로 읽은 것:

    _osrdnHookTriangle = 388 명령
      그중 정점 루프 0x6a0..0x855 = 128 명령, 삼각형당 3 회 = 384
      나머지 260 명령(분류·상태 읽기·표면 질의·분기·위임 준비)은 **삼각형마다 처음부터**
      삼각형당 호출 24, 부동소수 명령은 함수 전체에 셋

한 종류씩 없애는 칸은 세 번 다 "거의 0" 이었다(M1p 0.01 배, M1r 0.59 배, M1t ≈0):
비용이 어느 한 종류에 몰려 있지 않고 **수백 개의 평범한 명령에 퍼져** 있기 때문이다.
그러니 지레는 **그 260 명령에 분모를 주는 것**이다.

## 2. Mesa 가 이미 그 문을 열어 두었다

`Driver.TriangleFunc` 말고 **한 무리를 통째로 받는 자리**가 있다
(`dd.h:848-854`):

    render_func *RenderVBClippedTab;
    render_func *RenderVBCulledTab;
    render_func *RenderVBRawTab;
    /* These function tables allow the device driver to rasterize an
     * entire begin/end group of primitives at once. */

- 원형은 `void (*)(struct vertex_buffer *VB, GLuint start, GLuint count, GLuint parity)`
  (`types.h:140-143`).
- 표는 **11 칸**, 프리미티브로 색인한다: points·lines·line_loop·line_strip·
  **triangles(4)**·tri_strip·tri_fan·quads·quad_strip·poly·noop (`render_tmp.h:267-279`).
- `gl_render_vb` 가 `VB->CullMode` 를 보고 셋 중 하나를 골라 `tab[prim](VB, start, next,
  parity)` 를 부른다(`vbrender.c:650-667`).
- **드라이버가 NULL 로 두면 Mesa 가 자기 기본표를 꽂는다**(`vbrender.c:747-756`).

### 2-1. 기본표를 어떻게 얻나 — **`UpdateState` 에서는 못 얻는다**

Mesa 의 기본표는 `vbrender.c` 안의 `static` 이라 이름으로 못 잡는다.  꽂힌 뒤에 포인터를
읽어 복사하는 수밖에 없는데, **언제 읽느냐가 문제다.**  `gl_update_state` 를 열어 보면
순서가 이렇다(`state.c:1105-1136`):

    ctx->Driver.RenderVBRawTab = NULL;      <- 표를 **지우고**
    ctx->Driver.UpdateState(ctx);           <- 우리 훅이 여기서 불린다 (표는 NULL)
    ...
    gl_set_render_vb_function(ctx);         <- Mesa 가 **그 다음에** 기본표를 꽂는다

**그러니 우리 `UpdateState` 안에서는 복사할 것이 없다.**  거기서 우리 표를 꽂으면 Mesa 는
"NULL 이 아니니 그대로 두자" 하고 넘어가고, 우리에겐 위임할 기본 함수가 없어진다 —
나머지 열 칸이 NULL 인 표로 다른 프리미티브가 오면 그대로 죽는다.

**설치는 `RenderStart` 에서 한다.**  `gl_render_vb` 는 표를 고른 **뒤**(667-684) 에
`RenderStart` 를 부르므로(699-700), 그 시점에는 Mesa 의 기본표가 이미 꽂혀 있다.  거기서
복사하고 한 칸만 바꿔 설치하면 **다음 무리부터** 우리 함수가 받는다.  상태가 바뀌면
`gl_update_state` 가 다시 NULL 로 지우고 Mesa 가 기본표를 다시 꽂으므로, 우리는 다음
`RenderStart` 에서 다시 설치한다 — **스스로 복구되는 모양**이고, 우리가 설치하지 못한
동안에는 지금의 `TriangleFunc` 경로가 그대로 돈다.

> 이것은 실기 실행 한 번을 아낀 발견이다.  소스를 먼저 읽지 않았으면 `UpdateState` 에서
> 복사하는 코드를 짜고, NULL 을 복사하고, 그 다음 프리미티브에서 죽었을 것이다.
> [[read-the-reference-before-measuring]]

## 3. 계약을 소스에서 확정했다 (추측 아님)

Mesa 의 기본 `GL_TRIANGLES` 렌더러 전문(`render_tmp.h:126-141`):

    for (j = start + 2; j < count; j += 3)
        RENDER_TRI( j-2, j-1, j, j, 0 );

그리고 **raw** 표가 쓰는 `RENDER_TRI`(`vbrender.c:540-546`):

    if (parity) ctx->TriangleFunc( ctx, i1, i2, i, pv );
    else        ctx->TriangleFunc( ctx, i2, i1, i, pv );

여기서 확정되는 것 넷:

| 물음 | 답 | 근거 |
|---|---|---|
| 셋째 인자는 개수인가 **끝 색인**인가 | **끝 색인** — 루프가 `j < count` 다.  개수로 읽으면 무리를 잘못 자른다 | `render_tmp.h:126-141` |
| `parity` 는 쓰이나 | `(void) parity;` — **GL_TRIANGLES 는 안 쓴다**(스트립이 쓴다).  기본 루프도 0 을 넘긴다 | `render_tmp.h:126-141` |
| `VB->Elt` 간접이 있나 | raw 경로엔 **없다** — 색인이 그대로 정점 번호다 | `vbrender.c:540-546` |
| 그 `RENDER_TRI` 가 정말 raw 것인가 | 그렇다 — `TAG(x) x##_raw` 가 552 에서 정의되고 562 에서 템플릿을 include 한다.  575 의 것은 `x##_clipped` 용이고 `gl_render_clipped_triangle2` 로 간다 | `vbrender.c:552-562` |
| 정점 순서와 provoking vertex | `TriangleFunc(ctx, j-2, j-1, j, **j**)` | 위 두 줄 |

**그리고 하나 더**: 기본 함수는 결국 **`ctx->TriangleFunc` 를 삼각형마다 부른다** —
즉 우리 훅이다.  "기본 함수에 위임 = 소프트웨어" 가 **아니다**.  위임은 **지금의
삼각형별 경로로 돌아가는 것**이고, 그래서 안전하다.

## 4. 이 칸이 하는 일

손잡이 `RDNMesaGroup=1`(기본 꺼짐).  켜면 **raw 표의 `GL_TRIANGLES` 칸 하나**가 우리
함수가 된다:

    void osrdnRenderVBTriangles(VB, start, count, parity)
        1. 한 번만: 분류·ctx 상태 읽기·표면 질의  →  못 받을 상태면
           **아무것도 건드리지 않은 채** 저장해 둔 기본 함수를 같은 인자로 부르고 끝
        2. for (j = start + 2; j < count; j += 3)
               삼각형 하나를 처리한다 — **오늘의 훅 본체에서 상태 부분만 뺀 것**

`osrdnHookTriangle` 은 **상태를 계산해 그 본체를 부르는 얇은 껍질**이 된다.  본체가 한
벌이므로 두 경로가 갈라질 수 없다 — `reserve`/`add` 를 가를 때와 같은 규율이다.

### 4-1. 전부 아니면 전무가 **필요 없다**

교차검토가 가장 크게 걱정한 것은 "무리 중간에 거절하면 앞부분은 이미 보냈고 위임하면
두 번 그려진다" 였다.  그런 경우가 **생기지 않는다**: 삼각형마다의 판단과 되돌림이
지금과 똑같이 **삼각형 단위로** 남아 있기 때문이다.  무리 단위 거절은 §4 의 1 번뿐이고,
그때는 **아직 한 워드도 안 썼다**.

    clipped·culled 표는 건드리지 않는다 — 우리가 이미 거절하는 경우들이다.

## 4. 왜 이것이 크다고 보나 (그리고 그 추정을 믿지 않는 법)

260 명령이 삼각형당 한 번에서 무리당 한 번으로 간다.  M1s 가 잰 훅 값 0.88 us 를 명령 수로
나눠 보면 그 260 이 0.3~0.4 us 쯤이다 — **그러나 이 계산은 네 번째 추정이고, 앞의 셋은
전부 빗나갔다**([[measurement-discipline]]).  그래서 §6 의 판정은
**추정한 값이 아니라 손잡이의 실측 차이**로만 한다.

## 5. 값이 안 바뀐다는 증명

M1t 이 만든 장비를 그대로 쓴다:

1. **보낸 워드** — `t-group` 과 `t-quiet` 의 `tri k w0 w1 ...` 줄이 **워드 하나까지** 같아야
   한다.  판정기가 다르면 값을 안 내놓고 실패한다.
2. **화소** — 정답 장면을 손잡이 켜고 돌려 28,672 화소를 바이트로 대조.
3. **계수기** — `triangles`·`submitted`·`batched`·`delegated` 의 합이 같아야 한다.
   이 칸은 특히 `delegated` 가 중요하다: 무리째 거절하면 그 무리의 삼각형이 전부
   소프트웨어로 가야 하고, 하나라도 사라지면 `noSoftware` 가 0 이 아니게 된다.
4. **고정비** — 두 팔의 절편이 다르면 비교 불가로 실패(M1t 규칙).

## 6. 읽는 법

| 관측 | 판정 |
|---|---|

| 한계비가 0.2 us 이상 내려간다 | 삼각형당 반복되던 앞부분이 값이었다.  다음은 정점 루프 자체 |
| 0.05 us 미만 | 앞부분도 아니다.  그러면 훅의 값은 **정점 루프 128 명령 × 3** 에 있고, 남은 길은 그 루프를 줄이는 것뿐 |

## 7. 위험

| 위험 | 막는 법 |
|---|---|
| 표를 통째로 바꾸면서 다른 프리미티브가 망가짐 | **한 칸만** 바꾼다.  나머지는 Mesa 가 꽂은 포인터를 그대로 복사 |
| Mesa 가 아직 기본표를 안 꽂았을 때 복사함 | **소스가 답했다**(§2-1): `UpdateState` 시점엔 NULL 이다.  설치는 `RenderStart` 에서만 하고, 그때도 표가 NULL 이면 **설치하지 않고** 지금 경로로 남는다 |
| 상태 변경이 우리 표를 지움 | 지우는 게 맞다 — `gl_update_state` 가 NULL 로 만들고 Mesa 가 기본을 다시 꽂는다.  우리는 다음 `RenderStart` 에서 다시 설치하고, 그 사이 무리는 `TriangleFunc` 경로로 간다.  **두 경로가 같은 그림을 그린다는 것이 이미 게이트에 있다** |
| 무리 거절 시 삼각형이 사라짐 | 저장한 기본 함수에 **같은 인자 그대로** 넘긴다.  `noSoftware` 가 0 이어야 하고 `delegated` 가 그 무리 수만큼 늘어야 한다 |
| `parity`·`start`·`count` 를 잘못 해석해 정점 순서가 틀림 | `GL_TRIANGLES` 는 parity 를 안 쓴다(스트립이 쓴다).  그래도 **보낸 워드 대조**가 정점 순서를 비트로 잡는다 |
| 훅은 호스트 C89 게이트가 안 덮는다 | 타깃 빌드를 먼저 |

## 9. 실기 결과 (run 790113565, 부팅 `070a4ce3`, 빌드 `1790113501`, **재부팅 0 회**)

`judge_m1l: PASS`.

### 9-1. 동작했고, 아무것도 안 잃었다

    step=end-group groups=2165 declined=0 lost=0 tris=91085 installs=2
    step=end-tri   entered=91086 submitted=91086

무리 **2,165 개**(삼각형 42.1 개/무리)가 우리 칸으로 왔고, 91,085 삼각형이 그 경로로
그려졌다.  `entered` 가 하나 더 많은 것은 **표가 설치되기 전의 첫 무리**가 삼각형별
경로로 간 것 — 설계한 그대로다.  `declined=0`, `lost=0`, 그리고

    t-quiet vs t-group: 기록된 여덟 삼각형이 **워드 하나까지 같다**

### 9-2. 값 — **작다**

    t-quiet 2.065  →  t-group 1.989      = **-0.076 us/삼각형**
                                           훅 값(0.924)의 8.2 %, 한계비의 3.7 %

§6 의 표로는 "그 사이"(0.05~0.2)다.  **네 번째로 추정이 빗나갔다** — §4 가 260 명령을
0.3~0.4 us 로 봤는데 실측은 0.076 이다.  다만 앞의 셋과 달리 **부호가 맞고 값이 0 이 아니다.**

무리당 42.1 삼각형이므로 절감분은 사실상 preamble 전부다:

    삼각형당 preamble ≈ 0.076 / (1 - 1/42.1) ≈ **0.078 us**

즉 훅의 0.92 us 중 **끌어올릴 수 있었던 부분은 0.078 us 뿐**이었다.  나머지는 정점 루프와
**끌어올려지지 않는 보내기 경로**(`batch_joins`·`batch_add`·`pend` 부기)에 있다 — 그 둘은
삼각형마다 해야 하는 일이다.

### 9-3. 기본값은 꺼둔다

3.7 % 는 진짜지만, 이 칸이 덮은 것은 **raw 표의 `GL_TRIANGLES` 한 칸**이다.  스트립·팬·
클립된 경로는 여전히 삼각형별 경로로 가고(옳지만 이 규모로 시험되지 않았다), 그래서
손잡이는 **꺼진 채**로 둔다.  켜는 결정은 그 경로들까지 게이트에 올린 뒤에 한다.

### 9-4. 그래서 라이브러리 쪽 남은 것

    훅 0.92 = preamble 0.078 + 정점 루프·보내기 경로 0.85
    tri 단위 + ioctl 0.37
    합쳐 1.29 us 가 유저랜드, 한계비 2.07 의 62 %

정점 루프는 M1t 이 호출을 빼 봤고(≈0), M1r 이 산술을 재 봤다(0.05).  **남은 것은 그
루프의 명령 수 자체**이고, 그것을 줄이는 길은 정점당 워드를 줄이는 것(15→12)뿐이다.
그 전에 **카드의 스트림 읽기 34 %** 가 더 크다 — 그쪽은 드라이버 변경이고 재부팅이 든다.

# M1g — 텍스처 (계획, 코딩 전)

기준일 2026-09-22.  선행: M1f 완료(`docs/M1F_PLAN.md` 9), 그리고 어느 칸을 먼저 할지는
`docs/M1_NEXT_DECISION.md` 에서 정했다 — **깊이는 재부팅을 부르고 텍스처는 부르지 않는다.**
**이 문서는 코드보다 먼저 쓰였다.**

## 1. 이 칸의 한 줄

**CPU 가 창에 올린 텍스처를 카드가 읽어 삼각형 하나에 입히고, 그 그림이 R6h·R6i 가
실측한 표본 위치·필터 규칙과 화소 단위로 같다.**

## 2. 이 칸이 유난히 근거가 많은 이유

R6h·R6i 가 **같은 하드웨어에서 같은 배치로** 이미 쟀다.  그러니 이 칸의 사실표는
참조 드라이버가 아니라 **우리 자신의 측정**에서 온다.

| | 사실 | 확인한 곳 |
|---|---|---|
| T1 | 텍스처는 **선형·행우선**이다.  드라이버가 CPU 로 텍셀을 쓰는 줄이 그대로 말한다: `al[(texOff + vv * stride) / 4 + u] = texel(u, vv)` | `osrdn_cp.m:3336` |
| T2 | **하드웨어가 읽는 줄 간격은 `max(폭 × 4, 32)` 바이트다** — CPU 가 어떻게 썼든 상관없이.  R6h 의 경우 XF 는 4×4 를 **16 바이트 간격으로 써서** 그것을 드러냈다: 가정 16·64 는 153 불일치, **32 는 0**.  드라이버 표의 `stride` 열(XF 는 16)은 *CPU 가 쓴 간격*이지 하드웨어가 읽는 간격이 아니다 — **그 둘을 같은 것으로 읽으면 폭이 8 미만인 텍스처의 줄이 조용히 섞인다** | `R6H_PLAN.md:135` |
| T3 | `PP_TXSIZE_0 = (w−1) | ((h−1) << 16)`; 8×8 이면 `0x00070007`.  드라이버 표의 값이 그대로 그것이다(python 으로 디코드 확인) | `osrdn_cp.m:1865` 표, `R6H_PLAN.md:18` |
| T4 | `PP_TXPITCH_0 = 바이트 피치 − 32`, 그리고 피치·오프셋은 **32 바이트 정렬** | `R6H_PLAN.md:18` (xf86 EXA 선례) |
| T5 | **그런데 POT 텍스처에서는 하드웨어가 `TXSIZE`·`TXPITCH` 를 읽지 않는다** — 크기는 `TXFORMAT` 의 log2 칸에서 온다.  **추론이 아니라 실측**이다: 경우 XE 를 줄 간격 64 로 저장하고 피치 32 를 보냈더니 **폭 기준 예측과 0 불일치, 피치 기준 예측과 210 불일치**였다 | `R6H_PLAN.md:135` · `R6H_PLAN.md:48` |
| T6 | `PP_TXFORMAT_0`: 형식 비트 0–4(ARGB8888 = 6), `NON_POWER2` 비트 7, 폭 log2 비트 8–11, 높이 log2 비트 12–15 | `R6H_PLAN.md:16` |
| T7 | R6h 는 텍스처를 **별칭 + 0x20000** 에 두었다.  M1c 의 색 표면은 `winStart + 0` 에서 16 KiB 이므로 겹치지 않는다 | `R6H_PLAN.md:31` |
| T8 | **인터페이스가 막지 않는다**: 검증기의 `PP_CNTL` 값 규칙은 유닛 1–5 만 막고(`0x3e0`), `TEX_0_ENABLE`(0x10)은 통과한다.  `PP_TXOFFSET_0`·`TXFORMAT_0`·`TXFILTER_0`·`TXSIZE_0`·`TXPITCH_0` 이 전부 클라이언트 허용 목록에 있다 | python 으로 `verify_oracle` 조회, `docs/M1_NEXT_DECISION.md` H5·H6 |
| T9 | 표본 위치는 **픽셀 중심(+½)** 이고 선형 ST 로는 가릴 수 없다 — 원근을 넣어야 갈린다 | `R6I_PLAN.md:199` |
| T13 | **그런데 `tex_oracle.MEASURED` 는 아직 폐기된 값(모서리, `Fr(0)`)을 담고 있다.** 정정된 값은 `persp_oracle.MEASURED_OFF = 1/2` 다.  판정기가 앞의 것을 집으면 **R6h 의 기하에서는 맞고 일반적으로는 틀린** 예측을 한다 — 이 칸에서 실제로 집을 뻔했다.  그 상수에 경고 주석을 달았고, **판정기는 `persp_oracle.MEASURED_OFF` 를 읽어 쓰며 그 값이 ½ 인지 자기검사한다** | `persp_oracle.py:302`, `R6I_PLAN.md:199` |
| T10 | 이중선형 필터: 축마다 k/64 절삭, `(a(64−k) + b·k + r) >> 6`, r 은 가로 48 · 세로 32 | [[r200-measured-rules]] |

| T11 | **텍스처 스트림 전체가 이미 오라클에 있다**: `tex_oracle.draw_words(case, seed, win)` 이 상태·텍스처 여섯 레지스터·클립·`3D_DRAW_IMMD_2`·**7 워드 정점 `(x, y, z, w, 색, s, t)`** 를 통째로 만든다.  `SE_VTX_FMT_1 = 2`(유닛 0 에 두 성분)이고 검증기의 `cpR7VertexWords` 가 2+1+1+1+2 = **7** 을 계산해 개수를 대조한다 | `tex_oracle.py:187-217`, `osrdn_cp.m:2686` · `osrdn_cp.m:2859` |
| T12 | **게이트 B 를 미리 통과시켰다**: 그 스트림에서 드라이버 꼬리와 `WAIT_UNTIL` 쌍을 뺀 **클라이언트 형태 71 워드**가 `verify_oracle.verify()` 를 **`why=0`** 으로 통과한다 — python 으로 실행 | python |

**T12 가 이 칸의 실현 가능성을 닫는다**: 텍스처 삼각형은 **드라이버를 건드리지 않고**
지금 있는 R7b 통로로 제출된다.  T8 이 "레지스터가 허용된다" 였다면 T12 는 "스트림 전체가
통과한다" 다.

## 3. 이 칸을 부술 수 있는 것 — 먼저 적어 둔다

| 위험 | 왜 위험한가 | 어떻게 막나 |
|---|---|---|
| **ZPREP 이 텍셀을 지운다** | ZPREP 은 창 **256 KiB 전체**를 패턴으로 채운다(`M1_NEXT_DECISION.md` H4).  러너는 가속 실행 **직전에** zprep 을 돌린다 | 텍셀은 **프로세스 안에서**, 즉 zprep 뒤에 올린다.  라이브러리가 올리므로 순서는 자동으로 맞지만, **게이트가 그걸 확인해야 한다**(올린 뒤 되읽기) |
| M1c 는 색 표면 크기만 매핑한다 | 텍스처 자리(+0x20000)에 CPU 로 쓸 수 없다 | 표면 단위가 **창 전체**를 매핑하고 색 표면은 그 안의 오프셋 0 으로 둔다.  `m1c-one-mapping` 은 "매핑 하나" 를 세는 규칙이므로 **넓히는 것은 규칙 위반이 아니다** — 다만 규칙 문구를 "하나, 그리고 그 하나는 CAPS 가 준 창" 으로 정밀화한다 |
| POT 에서 피치를 안 읽는다(T5) | 줄 간격을 `max(w×4,32)` 가 아닌 값으로 두면 **조용히 줄이 섞인다** | 줄 간격을 T2 로 고정하고, 생성기가 그 계산을 하고, 판정기가 같은 계산으로 예측한다 |
| 표본 위치를 선형 ST 로 재면 못 가른다(T9) | 게이트가 통과해도 아무것도 증명 못 한다 | 시험 삼각형의 ST 를 **텍셀 경계에서 떨어뜨리고**, python 으로 안전 화소를 세어 충분한지 먼저 확인한다(R6h 가 XG 에서 안전 화소 0 을 낼 뻔한 일이 있다) |
| 필터를 최근접으로 두면 T10 이 안 시험된다 | 이중선형 규칙이 미검증으로 남는다 | 이 칸은 **최근접만** 한다.  이중선형은 다음 칸 — 한 칸에 규칙 둘을 넣으면 실패가 어느 쪽인지 못 가린다 |

## 4. codex 에 물을 한 가지

**"CPU 가 비디오 메모리에 선형으로 쓴 이미지를 R200 텍스처 유닛이 그대로 읽는가, 아니면
타일/스위즐 배치가 필요한가?  `PP_TXPITCH`·`PP_TXSIZE` 의 단위와 정렬 요구는?"**
(요청 `k3bm7t7wc`, 발신 완료.)  우리 자신의 실측(T1–T5)이 이미 답을 갖고 있으므로,
이 회신은 **확인용**이다 — 어긋나면 우리 측정이 이기고, 어긋난 자리를 기록한다.

## 4b. codex 교차검토 판정 (요청 `k3bm7t7wc`) — 배치 하나만 물었다

인용 **16 개를 전부 열었고 전부 정확**했다.

| codex 주장 | 내 검증 방법 | 결과 |
|---|---|---|
| 선형 row-major 로 쓰면 되고 타일링은 필요 없다 | 우리 T1 과 같다(드라이버가 이미 그렇게 쓴다) | ✅ 사실 |
| **`PP_TXOFFSET` 비트 2 가 macro, 비트 3 이 micro 타일링이고 둘 다 0 이면 선형** (`radeon_reg.h:2759`) | 정확.  **내가 못 가졌던 메커니즘** — 우리는 "선형이더라" 만 알았고 *무엇이 그것을 정하는지* 는 몰랐다 | ✅ **채택** |
| `TXOFFSET` 하위 5 비트는 endian·타일링 제어이고 주소는 32 바이트 정렬 (`r200_reg.h:1070`, `radeon_macros.h:168`) | 두 곳 다 정확 | ✅ **채택** |
| `TXPITCH = 바이트 피치 − 32` (`r200_texstate.c:380`, `radeon_exa_render.c:890`) | 정확.  우리 T4 와 같다 | ✅ 사실 |
| `TXSIZE = (w−1) | ((h−1)<<16)`, 폭·높이 각 11 비트 (`r200_texstate.c:377`, `radeon_reg.h:1951`) | 정확.  우리 T3 과 같다 | ✅ 사실 |
| DDX XAA 합성이 **CPU memcpy 로 선형 텍스처를 VRAM 에 올린다** (`radeon_render.c:743`·`:779-810`·`:818`) | 정확.  M1f 때처럼 **실제 출하 경로**를 가져왔다 | ✅ **채택** |
| **"`TXSIZE`/`TXPITCH` 를 쓰려면 `NON_POWER2` 를 설정하라 — 32×32 가 POT 여도 그 경로를 쓸 수 있다"** | 참조에서는 맞는 말이고 `radeon_render.c:768-774` 가 두 경로를 그대로 보여 준다.  **그러나 우리가 잰 것은 POT 경로다**: R6h 의 `TXFORMAT = 0x3346` 은 python 으로 분해하면 **`NON_POWER2` = 0, log2 폭·높이 = 3·3** 이다 | ⚖️ **부분 채택** — 사실은 맞고 **권고는 따르지 않는다** |

**왜 따르지 않는가**: `NON_POWER2` 로 가면 크기가 `TXSIZE` 에서 오고, 그건 **우리가 재 본 적 없는 경로**다.
R6h·R6i 의 표본 위치·클램프·필터 측정은 전부 POT 경로에서 나왔다.  이 칸의 게이트는
그 측정과 대조하는 것이므로, 경로를 바꾸면 **대조할 예측이 그 상태의 것이 아니게 된다** —
M1e 에서 `SE_CNTL` 을 두 필드만 바꾼 것과 같은 이유다.  NPOT 은 그것을 재는 칸에서 연다.

*(그리고 T5 와 codex 의 "NPOT only" 주석은 서로를 확인한다: 헤더가 그 레지스터를 NPOT 전용이라
적어 두었고, 우리는 POT 에서 실제로 안 읽힌다는 것을 XE 로 쟀다.)*

## 5. 설계 (요약)

1. 생성기: `PP_CNTL`·`TXFORMAT`·`TXFILTER`·`TXSIZE`·`TXPITCH`·`TXOFFSET` 슬롯, 값은 R6h 표에서.
2. 표면 단위: 창 전체를 매핑, 텍스처 자리를 노출.
3. 새 단위 `OSRDNMesaTex`: Mesa 의 텍스처 이미지를 창에 올리고 **되읽어 확인**.
4. 분류기: `RM_KNOWN |= TEXTURE_BIT`? — **아니다.** `texture` 는 이미 별도 입력이고
   지금 거절 사유다.  그 조건을 **한 경우만** 열어 준다: 2D·POT·ARGB8888·최근접·WRAP.
5. 판정기: R6h·R6i 오라클로 예측.

## 6. 이 칸이 하지 않는 것

- 이중선형 필터(다음 칸), 밉맵, 여러 텍스처 유닛, NPOT, ARGB8888 아닌 형식.
- 깊이(재부팅이 필요한 칸과 함께).
- 드라이버 변경 → **재부팅이 필요 없을 것으로 본다**(T8 이 그 근거).

## 7. 구현하면서 드러난 계약 구멍 셋 — 전부 실기 전에 닫았다

세 가지 다 "그림은 그럴듯한데 계약이 틀린" 종류다.  픽셀이 맞아 보이는 상태에서
틀린 약속을 남겨 두면, 그 약속을 믿는 다음 장면에서 조용히 깨진다.

**T14 — 프롤로그는 CLAMP 인데 분류기는 REPEAT 만 받고 있었다.**
프롤로그는 `tex_oracle` 의 케이스 **XA** 에서 그대로 떠 왔고, `TCASES['XA']` 의 클램프 모드는
`'clamp'` 다(`tex_oracle.py:86`).  그래서 스트림은 `CLAMP_S_CLAMP_LAST |
CLAMP_T_CLAMP_LAST` 를 보내고 있었다.  그런데 분류기는 `GL_REPEAT` 만 받는다
(`OSRDNMesaClass.c:228-279`), 그리고 §5.4 의 설계도 **WRAP** 이라고 적혀 있다.
ST 가 [0,1] 안에 있으면 둘은 같은 텍셀을 고르므로 **그림으로는 절대 안 드러난다**.
고친 쪽은 하드웨어다: `tools/mesa/gen_tri_prologue.py` 가 이제 `te.txfilter('wrap')` 을 써서
넣는다.  wrap 도 R6h 가 XC·XG 로, 같은 8×8·stride 32 텍스처에서 실측한 값이다
(`tex_oracle.py:88` 과 `tex_oracle.py:92`).  자기검사 두 줄이 그 값을 스트림에서 도로 읽어 대조한다.

**T15 — 텍스처 환경 모드를 아무도 안 보고 있었다.**
프롤로그의 스테이지 0 은 `out = R0 * (1 − 0) + 0`, 즉 **REPLACE** 다
(`tex_oracle.py:63-70`).  Mesa 의 기본값은 **`GL_MODULATE`**
(`context.c:602`) 이고, 소프트웨어는 그 모드에서 텍셀에 프래그먼트 색을
곱한다(`texture.c:2434` 이하의 `PROD`).  REPLACE + `GL_RGBA` 는 `Cv = Ct`,
`Av = At` 로 카드와 정확히 같다(`texture.c:2418-2427`).
즉 **아무것도 안 한 응용**이 우리 가속 경로에 들어와 곱셈 없이 그려졌을 것이다 —
정점 색이 흰색이면 그것마저 같아 보인다.  분류기에 `texEnvMode != GL_REPLACE` 를 넣었고,
`sim_class` 에 그 상태를 그대로 담은 행("MODULATE, Mesa 의 기본값")과 변이 하나를 넣었다.

**T16 — s·t 말고 더 오는 삼각형.**
우리는 두 성분을 보내고 카드는 아핀으로 보간한다.  Mesa 는 **응용이 실제로 준 개수**를
들고 다니고(`vbxform.c:458-465`, 표는 `vbxform.c:433-437`), 네 개면 네 번째를 픽셀마다 보간해
나눈다(`tritemp.h:462-465`).  투영 텍스처 행렬도 같은 결과를 낸다: `ENABLE_TEXMAT0` 은
**항등이 아니라는 뜻**이고(`types.h:776`, 세우는 곳 `state.c:948-950`),
변환은 목적지 벡터를 새로 가리키게 한다(`stages.c:518-522`, `xform.h:175`).
그래서 훅은 **플래그가 아니라 데이터**를 본다 — 우리가 읽는 포인터는 이미 texgen 과
행렬을 지난 것이다(`texgen_tmp.h:381`, `stages.c:519`) — 그리고 `size > 2` 면
소프트웨어로 넘긴다.  넘긴 개수는 세어서 `refused + not-bound + projective == delegated`
로 계속 맞춘다.

*(T16 의 근거 일곱 줄은 codex 요청 `kvs2cprsu` 의 회신과 겹친다.  일곱 인용을 전부 열어
확인했고 전부 정확했다.  결론 자체는 회신 전에 `stages.c`·`texgen_tmp.h` 를 읽어
같은 것을 얻어 두었으므로, 회신은 확인으로만 쓴다.)*

## 8. 판정기와 재계수 — 텍스처 칸

예측은 **R6h 의 최근접 규칙**이되, 표본 위치는 **R6i 가 정정한 픽셀 중심**을 쓴다:
`persp_oracle.MEASURED_OFF = 1/2`(boot ff78c18a, `docs/R6I_PLAN.md 199`).
`tex_oracle.MEASURED` 는 R6h 가 가르지 못한 모서리 값이라 **읽지 않는다**(T13).

## 10. 실기가 가르쳐 준 것 — 호스트가 못 본 세 가지

세 번의 실기 왕복이 필요했다.  전부 **두 도구가 각자 맞았는데 이음매를 아무도 안 본** 자리다.

**(1) 훅이 분류기에 불리언을 넘겼다.**  `s.texture = ...ReallyEnabled ? 1 : 0` 인데
분류기는 `!= TEXTURE0_2D`(2) 로 묻는다.  모든 텍스처 삼각형이 거절됐고, 로그는
`tex=1` 이라고 적었다 — 불리언이 기록한 값이고, 사실이고, **넘어간 값이 아니다**.
`sim_class` 는 분류기에 열거값을 먹여 검사하므로 볼 수 없었고, `check_hook` 은
그 필드가 대입된다는 것만 봤다.  둘 다 자기 몫에 대해 틀리지 않았다.
→ 새 규칙 `m1g-no-boolean-for-a-constant`: 분류기가 **0·1 이 아닌 상수**와 비교하는
필드에 훅이 `? 1 : 0` 을 대입하면 실패한다(산술적으로 절대 참이 될 수 없으므로).

**(2) `TEXTURE_BIT` 를 RasterMask 가 세운다.**  `types.h:1462` = 0x1000, `state.c:817`.
텍스처 절을 통과시키자 거절이 RASTER 로 옮겨갔다.  `RM_KNOWN` 에 넣되,
비트와 필드가 **같은 식에서 나오므로 어긋나면 거절**하는 절을 함께 넣었다.
그리고 이번 일 때문에 **RasterMask 를 기록에 남긴다**(`rmask=%08lx`) — 값 없는
거절은 다음 걸음을 추측으로 만든다.

**(3) 정점 워드가 겹쳐 쓰였다.**  훅이 5 워드 슬롯을 무조건 먼저 쓰고 7 워드 슬롯을
뒤에 썼다.  `i = 2` 의 5 워드 쓰기가 정점 1 의 7 워드 블록 안에 떨어져, 카드는
색 자리에서 `28.0` 을 받았다.  → 배치를 순수 C 단위의 `osrdn_tri_vertex` 로 옮겼고
(스트라이드를 **한 번** 고른다), `sim_pack.py` 가 호스트에서 **실행해** 두 모양의
모든 워드를 확인한다 — 건드리면 안 되는 워드까지.  훅은 이제 `vtx` 를 색인하지
않으며 `m1g-hook-does-not-pack` 이 그것을 지킨다.

**그 밖에 실기 전에 잡은 것**: 타깃 빌드가 `OSRDNMesaTex.c` 를 컴파일하지 않았고
(`check_units.py`), 스텁이 생성 테이블을 include 하지 않았으며(`check_compile.py`),
타깃 `/bin/sh` 는 **따옴표가 든 단어의 글롭을 확장하지 않는다**(`check_target_sh.py`,
다섯 형태를 실기에서 측정).

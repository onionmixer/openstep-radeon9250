# M2c — 계측기가 클라이언트 경로에서 돈다 (드라이버, 재부팅 필요)

## 1. M2b 가 찾으려던 30 us 는 **내 자()** 였다

M2b 는 링 제출에서 fence·wait·put 을 뺀 **43.56 us** 를 "도어벨 + posting" 이라 부르고
"MMIO 여섯이면 6.6 us 여야 하는데 안 닫힌다" 고 적었다.  닫힌다:

| REST 43.56 us 의 내역 | us | 비중 |
|---|---:|---:|
| **내 `IOGetTimestamp` 여덟 번** | **29.90** | **69 %** |
| MMIO 여섯(1.1 us 씩, `s1read` 로 실측) | 6.60 | 15 % |
| 아직 이름 없는 것 | 7.06 | 16 % |

**미설명은 30 us 가 아니라 7 us 였다.**  나머지는 재는 도구였다.

## 2. 그리고 그 도구가 **손잡이 없이** 돈다

> **이 절의 줄번호는 M2c 를 넣기 _전_, 설치돼 있던 빌드 `a361877b` 의 것이다.**
> 진단을 적은 자리이므로 그대로 둔다 — 고쳐 놓으면 "조건이 없다" 가 거짓이 된다.
> 고친 뒤의 자리는 §3-1 에 적는다(`osrdn_cp.m:3165-3169`).

`cpZclear` 의 R7 분기(M2c 전, 빌드 `a361877b`; 지금 그 자리는 `osrdn_cp.m:3156-3169`):

    IOGetTimestamp(&tmark);
    timing = 1;
    c->tOn = 1;                         /* M1z: cpR6Submit reads this one */

**조건이 없다.**  클라이언트가 그리는 모든 제출이 계측기를 짊어진다:

| | 개수 |
|---|---:|
| `tmark` 첫 읽기(`osrdn_cp.m:3167`) | 1 |
| M1x 사슬 표식 | 8 |
| M1z 펜스 쌍 × 2 제출 | 4 |
| M2b put 쌍 × 2 제출 | 4 |
| **합** | **17** |

`IOGetTimestamp` 한 번의 값은 **세 번 재서 세 번 다르다**:

| 근거 | us |
|---|---:|
| M1z: 커널 연산이 4 회에 +18.29 | 4.57 |
| M2b: 커널 연산이 4 회에 +14.95 | 3.74 |
| `nowb` 연산 9 us = 2 회 + MMIO 4 | ≤ 2.84 |

**띠는 2.84 ~ 4.57 us.**  **17 회**(§2-2)면 **48 ~ 78 us**, 커널 연산 225.4 us 의 **21 ~ 34 %**.

남은 어떤 항목보다 크고(대기 58.4, tail 46.8), 그 둘과 달리 **클라이언트에게 아무 값도
주지 않는다**.

## 2-1. 코딩 전 전수 — 손잡이가 닿는 자리

| 물음 | 확인한 것 | 답 |
|---|---|---|
| `tAccN` 은 어디서 움직이나 | `osrdn_cp.m:3695-3697` — `if (timing)` **안**에서 표식 7 과 함께 | 손잡이가 꺼지면 **누적기도 계수도 안 움직인다**.  0 으로 나눌 일이 없다 |
| `timing` 과 `c->tOn` 이 엇갈릴 수 있나 | 둘 다 `osrdn_cp.m:3168-3169` 에서 나란히 서고, `timing` 은 사슬 표식 여덟 개를, `c->tOn` 은 `cpR6Submit` 의 다섯 가드(`osrdn_cp.m:2378`, `osrdn_cp.m:2382`, `osrdn_cp.m:2396`, `osrdn_cp.m:2399`, `osrdn_cp.m:2433`)를 지킨다 | 같은 곳에서 같은 값을 받으면 엇갈리지 않는다 |
| 손잡이는 어디 살아야 하나 | `c->doWb`(`osrdn_cp.m:2978`, M2c 당시엔 `c->noWb`)와 `c->spin`(`osrdn_cp.m:2999`)은 자기 연산이 세우고 **연산마다 안 지워진다**.  지워지는 것은 `c->tOn` 하나뿐(`osrdn_cp.m:4151`) | `c->timeOn` 은 **noWb·spin 과 같은 자리**.  `c->tOn` 은 계속 연산마다 지워지되 이제 `timeOn` 에서 값을 받는다 |
| 손잡이가 꺼진 채 부팅을 돌다 켜면 첫 덤프가 옛것을 보나 | 누적기가 한 번도 안 움직였으니 0.  게다가 팔은 `tdump` 로 먼저 비운다 | 아니오 |
| 전부 0 인 실행을 잘못 읽는 곳이 있나 | `judge_m1l.py:1193` 가 **`ops=0` 을 FAIL 로** 본다 | 그것이 바로 원하는 그물이다 |

**한 가지 더**: 빌드 `a361877b` 에서는 `IOGetTimestamp(&tmark)` 가 `timing = 1` **앞**,
가드 밖에 있었다.  손잡이가 꺼져도 그 한 번은 돌았을 것이다.  세 줄을 함께 묶었다
(`osrdn_cp.m:3165-3169`):

    if (c->timeOn) {
        IOGetTimestamp(&tmark);
        timing = 1;
        c->tOn = 1;
    }

`tmark` 은 `if (timing)` 안에서만 읽히지만, 선언에서 0 으로 두어 컴파일러가 경고할 여지를 없앤다.

## 3. 이 칸이 하는 일

### 3-1. 계측기를 손잡이 뒤로, **기본 꺼짐**

    /* a361877b */                  /* M2c -- osrdn_cp.m:2619-2623 */
    IOGetTimestamp(&tmark);         if (c->timeOn) {
    timing = 1;                         IOGetTimestamp(&tmark);
    c->tOn = 1;                         timing = 1;
                                        c->tOn = 1;
                                    }

세 줄을 **모두** 안에 넣었다: 첫 시계 읽기를 밖에 두면 켬/끔 차이가 자기 값을
빼놓게 된다(§2-1 의 마지막 항목, codex 가 잡은 것).

- 새 연산 `CP_OP_TIME`(len 0/1).  기본 **0**.
- 손잡이가 꺼져 있으면 `cpTMark` 도 `cpR6Submit` 의 네 쌍도 **한 번도 안 불린다**.
- 누적기는 0 으로 남고, `tAccN` 도 0 이다 — 그리고 **판정기가 이미 `ops=0` 을 FAIL 로 본다**
  (M1x 자체시험).  팔이 손잡이 켜기를 잊으면 그 검사가 잡는다.

### 3-2. 그 값을 **정확히** 잰다

같은 팔을 손잡이 끄고 한 번, 켜고 한 번.  차이가 계측기의 값이다 —
세 번 재서 세 번 달랐던 수가 **하나**가 된다.

`tstage` 줄은 손잡이를 켠 팔에서만 나오므로, 두 팔의 비교는 **클라이언트 벽시계**
(`us = a + b*n`)로 한다.  판정기에 짝을 하나 더 넣는다(`t-stage` 대 `t-notime`),
그리고 그 짝은 M2a·M2b 와 같은 모양이다: **고정비가 결과**, 한계비는 안 움직여야 한다.

### 3-2. 걸쇠 난 제출은 **아무 누적기에도** 안 남긴다

오늘 `cpR6Submit` 은 put 과 fence 를 **더한 뒤** 대기에서 걸쇠가 나면 돌아간다.
그러면 `tAccN` 은 안 늘고 누적기만 늘어 — 분모 없는 분자가 된다.

    /* 오늘 */                          /* M2c */
    put 더하기                           put 을 지역 변수에
    fence 더하기                         fence 를 지역 변수에
    대기 -> 실패하면 return              대기 -> 실패하면 return (아무것도 안 남음)
    wait 더하기                          세 개를 여기서 함께 더한다

이러면 `tAccN` 과 세 누적기가 **같은 집합의 제출**을 센다.  오늘 그 어긋남이 실제로
일어나지는 않았다(실기 로그 848 줄 전부 `failed=0`) — 그러나 그것은 운이지 설계가 아니다.

### 3-3. 팔의 순서 — 판정기가 **마지막** `tstage` 줄을 읽는다

`judge_m1l` 은 로그를 훑으며 `tstage` 를 만날 때마다 덮어쓰므로 **마지막 것**을 쓴다
(`judge_m1l.py:1176-1182`).  그리고 `ops=0` 을 FAIL 로 본다(`judge_m1l.py:1193`).

그러므로 계측을 **끈** 팔(`t-notime`)은

- **`tdump` 를 내면 안 된다** — 냈다면 `ops=0` 줄이 마지막이 되어 판정기가 정당하게 FAIL 한다
- 계측을 **켠** 팔(`t-stage`) **뒤에** 와야 한다

두 팔의 비교는 `tstage` 가 아니라 **클라이언트 벽시계**로 한다: 끈 팔에는 단계 수가
아예 없는 것이 정상이기 때문이다.  그 짝이 M2a·M2b 와 같은 모양(고정비가 결과)이므로
판정기의 `fixed_moves` 집합에 `t-notime.out` 을 더하면 된다.

## 4. 이 칸이 **안 하는** 것

- **RDTSC 로 시계를 바꾸기.**  P4 이므로 쓸 수 있고(CPUID edx 비트 4 = 1) 166 배 싸지만,
  64 비트 나눗셈이 cc 2.7.2.1 에서 위험하고 누적기의 단위가 바뀌어 판정기 전부를
  건드려야 한다.  **손잡이가 같은 문제를 더 싸게 푼다**: 클라이언트는 0 을 내고,
  측정 팔만 낸다.  RDTSC 는 그 다음에 필요하면.
- **스핀 켜기** — M2b 가 음성으로 재고 닫았다(−3.3 %).

## 6. 실측 (2026-09-24, 부팅 `00a7424d`, run 790188919, 재부팅 0 회)

### 6-1. 계측기의 값

| 팔 | 고정비 us/제출 | 한계비 us/삼각형 |
|---|---:|---:|
| `t-stage` (계측 켬) | **491** | 2.039 |
| `t-notime` (계측 끔) | **431** | 2.052 |
| **차이** | **−60** | +0.013 (안 움직임) |

**한 제출에 60 us, 읽기 17 회 → `IOGetTimestamp` 한 번에 3.53 us.**
세 번 재서 세 번 달랐던 수(4.57 / 3.74 / 2.84)가 하나가 됐다 — 가장 가까웠던 것은
M2b 의 3.74(0.94 배), 가장 멀었던 것은 `nowb` 연산에서 뺀 2.84(1.24 배).

계측기는 클라이언트 고정비의 **12.2 %** 였다.

### 6-2. 잡음은 얼마인가 — 같은 실행 안에서

이 실행에는 **값이 거의 0 인 손잡이**가 하나 더 있다: `spin`(M2b 가 −3.3 % 로 닫음).
`t-stage` 대 `t-spin` 의 고정비 차이는 **−3 us** 였다.  같은 모양의 짝에서 관측된
잡음이 3 us 이고 계측기는 60 us — **20 배**다.  추정이 아니라 이 실행의 수다.

### 6-3. 그림은 안 움직였다

`t-stage.out` 대 `t-notime.out`: 기록된 삼각형 8 개가 **워드 단위로 동일**.
계측기를 떼는 것이 카드가 보는 것을 하나도 바꾸지 않았다.

## 7. 이 칸이 덤으로 잡은 것 — `read_drv` 가 조용히 0 줄을 읽고 있었다

`judge_m1l` 의 `t-grid.drv` 규칙이 FAIL 했다: "(stage, wait) 짝이 없다".
원인은 M2c 가 아니라 **M2b** 다 — M2b 가 `RDN-R5 wait` 의 모든 칸에 `/t<turns>` 를
붙였는데 `read_drv` 의 정규식은 그 앞에 쓰여 있었다:

    idle=\d+/-?\d+/(\d+) rptr=...        # 실제: idle=2/0/3310/t7 rptr=...

`t-grid.drv` 455 줄 전부가 안 읽혔고, 규칙은 그것을 "드라이버 로그가 꺼져 있었다" 로
읽었다.  **왜 자체시험이 안 잡았나**: 고정물(fixture)이 M2b 전 모양 그대로였다.

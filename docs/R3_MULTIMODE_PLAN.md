# R3 계획 — 다중 모드·심도·Configure (초안 0, 2026-09-17)

`PLAN.md` §5 R3 를 구체화한다.  **심도는 Matrox 드라이버를 따른다**(operator 지시, 2026-09-17).
코딩 전에 교차검토를 거친다.

## 1. 목표와 게이트 (PLAN.md 그대로)

해상도표 × 포맷표, `setTransferTable:count:`, `IO_DISPLAY_HAS_TRANSFER_TABLE` 광고,
`Display.modes`, (필요하면) 인스펙터.

**게이트**: **광고하는 조합(`Display.modes`) 전부**를 실기에서 확인한다 — 확인 못 한 조합은
광고에서 뺀다.  각 조합에서 모드 레지스터 되읽기, 팔레트/전달표 픽셀 확인, 재부팅 뒤 설정 유지.

## 3. NeXT 순정 S3 예제 (1 차 출처)

`ref/openstep/examples/S3/` — 같은 포맷 셋(`Display.modes`: `RGB:555/16`·`RGB:256/8`·`BW:8`).

- `setTransferTable` (`S3.m` 59–95): BW 8bpp 는 하위 바이트, RGB 8·15·24 는 R/G/B = 31–24/23–16/15–8.
  그 밖의 조합은 표를 버린다.
- 적용 (`S3ProgramDAC.m` 195–240): **각 항목을 `256 / 항목 수` 번 반복**해 LUT 256 칸을 채운다.
  표가 없으면 24·8bpp 는 감마 256 표, 15bpp 는 16 단계 표를 32 × 8 로.
- `setBrightness:token:` (`S3.m` 44–55): 밝기를 저장하고 감마표를 다시 쓴다
  (`EV_SCALE_BRIGHTNESS(level, v)`).  **우리 드라이버는 지금 빈 함수다.**
- OPENSTEP 헤더에는 **16 비트 565 가 없다**: `displayDefs.h` 19–23 의 `IO_2/8/12/15/24BitsPerPixel`.
  → 16bpp 는 555.

## 4. Radeon 이 Matrox 와 다른 점 (참고 구현으로 확인)

| 항목 | 근거 | 결론 |
|---|---|---|
| CRTC 픽셀 형식 | xf86 `legacy_crtc.c` 889–894: 8→2, 15→3(555), 16→4(565), 32→6 | 32→6(지금), 16→**3**, 8→2 |
| **15/16bpp LUT 색인** | xf86 `radeon_driver.c` 3327–3350: 15bpp 에서 컬러맵 항목 `index` 를 LUT `index*8 … index*8+7` 에 쓴다.  **주의: 그 `switch` 에는 `break` 가 없어** 15 는 16·기본 경로로 떨어져 녹색(`index*4`)과 앞 칸(`index`)을 다시 덮는다 — 실행되는 결과는 깨끗한 증거가 아니고, **case 15·16 블록의 의도**(5 비트 → ×8, 6 비트 → ×4)가 증거다 | **Radeon LUT 는 8 비트로 늘린 값으로 찾는다** → 256 선형 램프가 15bpp 에서도 맞다.  **Matrox 의 32 단계 수정을 옮기면 안 된다.**  S3 의 "`256/항목 수` 반복" 과 같은 모양 |
| 그 근거의 폭 | NetBSD `radeonfb.c` 932–935 는 형식 2·6(8·32bpp)만 쓴다 | **15bpp LUT 동작은 xf86 한 출처** → 실기에서 밝기로 확인해야 한다 |
| 피치 | `crtc_pitch = (width*bpp + 255) / 256` (오라클) | 다섯 해상도 × 8/16/32 모두 정확히 떨어진다(python) |
| 분주 | 오라클 `pll_table` | 다섯 모드 모두 refdiv 6·12 행이 있다.  640×480 은 refdiv 8, 1024×768 은 refdiv 3 에 **구멍** — "연속" 검사는 "오라클 집합과 같음" 으로 바꾼다 |
| VCO 여유 | 1024×768 refdiv 6: VCO **391 500 kHz**(한도 400 000) | 가장 빠듯하다 |
| 1024×768 교차 확인 | refdiv 12 행 `000600ad` = xf86 iBook 하드코딩 값(오라클 자체검사 1 번) | 좋다 |
| 매핑 길이 | 1600×1200×4 = 7 680 000 B | `OSRDN_FB_LENGTH` 3 MiB → **8 MiB 이상**.  0 단계 `apersize`·`memsize` 게이트가 이 값과 비교 |
| 수평 주파수 | 31.47 / 37.88 / 48.36 / 63.98 / **75.00 kHz** | **모니터가 받아야 한다** — operator 결정 |

## 5. 설계 초안

1. **모드 표** — 해상도 × 포맷, 모두 오라클에서 생성(CRTC 워드, 모드별 분주 표, 폭 × 바이트별
   FIFO, 폭 × bpp 별 피치, 조합별 `displayInfo`).  사람이 승인하는 것은 R2B §14 의 방식(규칙·
   개수·지문 + 실측 앵커)을 모드마다.
2. **선택** — Matrox 식, 부팅 때 한 번.  파싱 실패·피치 불일치·표에 없는 조합이면 **R2 에서 증명된
   800×600 `RGB:888/32`** 로.
3. **진입** — 지금 절차 그대로, 모드 의존 값만 표에서.  0 단계 18 게이트·스냅샷·복귀·순환은
   **모드와 무관하게 그대로**.
4. **팔레트·전달표** — S3 계약: 표를 받아 보관, `256/항목 수` 반복으로 LUT 구성, 밝기 적용.
   PseudoColor 는 즉시 기록.  표가 없으면 선형 램프.  BW:8 은 회색 램프(+선택: Gray Levels).
5. **시험 패턴** — 포맷마다 그 형식으로(32/16/8, PseudoColor 는 램프가 들어간 색인).
6. **`setBrightness:token:`** — S3 처럼 구현할지 결정 필요(아래 7).

## 6. 확인 방법 — 게이트를 채우는 비용

모드는 부팅 때 고정되므로 **조합마다 부팅이 필요**하다(20 회).  대안:

- **(가) 20 부팅** — 조합마다 Configure 전환 + 재부팅 + 되읽기 + operator 육안.  게이트 문장 그대로.
- **(나) 한 부팅 스윕 + 포맷·해상도 부팅** — 순환과 같은 통로로 **스윕 verb**: 20 조합을 차례로
  프로그램 → 형식별 시험 패턴 → N 초 노출(operator 가 사진) → 되읽기 기록 → 부팅 모드로 복귀.
  레지스터·패턴은 한 부팅에 전부.  창 서버 경로(전달표·PseudoColor)는 **포맷 4 개 × 1 해상도** 와
  **해상도 5 개 × 1 포맷** 부팅(겹침 하나 → 8 부팅)으로.  스윕 뒤 화면은 패턴으로 덮이므로
  **그 부팅은 재부팅으로 끝낸다**(R2c 에서 배운 것).
- **(다) 광고를 줄인다** — 모니터·시간이 허락하는 조합만.

## 7. operator 결정이 필요한 것

1. **모니터가 받는 해상도** — 특히 1280×1024@60(64 kHz)·1600×1200@60(75 kHz).
2. **확인 방법** — (가)·(나)·(다).
3. **`Gray Levels`**(BW:8 의 16/4/2 단계 회색) — Matrox 에는 있다.  넣으면 Configure 인스펙터가 필요하다.
4. **밝기(`setBrightness:token:`)** — S3 는 구현했고(`S3.m` 44–55), **Matrox 는 빈 함수다**(`OpenStepMGAReplacementDisplay.m` 7655–7660).  `EV_SCALE_BRIGHTNESS` 는 `bsd/dev/ev_types.h` 170.

## 8. 위험

- 15bpp 가 어둡게 나올 위험 — 근거가 xf86 한 출처(4 절).
- 1024×768 refdiv 6 의 VCO 391.5 MHz — 한도 근처.  Matrox 는 162 MHz 에서 지터 문제를 겪었다.
- 1600×1200 의 매핑 8 MiB — `mapFrameBufferAtPhysicalAddress` 가 받는지 실기에서 확인.
- PseudoColor 에서 창 서버가 컬러맵을 실제로 보내는지 — Matrox 측정은 "광고해야 보낸다".
- 스윕(나)은 창 서버가 쓰는 프레임버퍼를 덮는다 — 그 부팅은 재부팅으로만 회수.

## 9. operator 결정 (2026-09-17)

| 질문 | 결정 |
|---|---|
| 모니터 범위 | **1600×1200 까지 전부** — 5 해상도 |
| 확인 방법 | **한 부팅 스윕 + 8 부팅** |
| Gray Levels | **Matrox 처럼 넣는다**(설정 키 + 인스펙터) |
| 밝기 | **S3 처럼 구현한다** |

따라서 광고 조합은 **5 × 4 = 20**, Matrox 의 `Display.modes` 와 같은 20 줄.

## 10. 설계 (결정 반영)

### 10-1. 단계 나눔

| 단계 | 내용 | 실기 |
|---|---|---|
| **R3a** | 오라클·생성기: 5 모드 × 4 포맷의 모든 값(CRTC 워드, 모드별 분주 표, FIFO, 피치, `displayInfo`, 픽셀 형식), 모드마다 규칙·개수·지문 + 실측 앵커 | 없음 |
| **R3b** | 드라이버: 설정에서 조합 선택(Matrox 파싱), 포맷별 진입(CRTC 형식·DAC·팔레트·패턴), 매핑 8 MiB, `HAS_TRANSFER_TABLE`, S3 식 전달표·밝기, `Gray Levels` 키 | **8 부팅** |
| **R3c** | 스윕 verb + 도구 | **1 부팅**(끝은 재부팅) |
| **R3d** | 인스펙터(Gray Levels) + `Display.modes` + "재부팅 뒤 설정 유지" | R3b 의 부팅에 겹친다 |

### 10-2. 스윕은 커널 안에서 기다리지 않는다

한 조합의 노출이 수 초이고 20 조합이면 커널 안 대기가 수십 초가 된다 — `setIntValues` 문맥에서
600 ms 도 조심했던 것과 맞지 않는다.  그래서:

- **커널 호출 하나 = 조합 하나**: 복귀 본체 → 그 조합으로 진입 본체(노출 대기 없음) → 되읽기 기록 → 반환.
  호출 하나의 대기는 지금 순환과 같은 크기(수백 ms).
- **기다림은 사용자 도구에서** `sleep` 으로.  operator 가 사진을 찍는 시간.
- 마지막 호출이 **부팅 모드로 되돌린다**.  그래도 화면은 패턴으로 덮여 있으므로 그 부팅은 재부팅으로 끝낸다.
- 걸쇠: 순환과 같은 시퀀스 claim.  스윕 진행 중에는 순환·다른 스윕을 거절.
- 창 서버는 그동안 **부팅 모드라고 믿고** 그릴 수 있다 — 형식이 다른 화면 위에 그리면 패턴이 일부 깨진다.
  operator 는 스윕 중 마우스·키보드를 건드리지 않는다.  판정은 되읽기 기록이 주, 사진은 보조.

### 10-3. 8 부팅의 구성

포맷 4 개를 한 해상도에서(창 서버 경로: 전달표·PseudoColor·BW·Gray Levels), 해상도 5 개를 한 포맷에서.
겹침 하나를 빼면 8 부팅.  부팅마다: 되읽기 = 오라클, 전달표 호출 횟수와 적용 여부, operator 육안,
설정이 재부팅 뒤에도 그 조합인지(Configure 가 쓴 표).

### 10-4. 전달표·밝기 (S3 계약 + Radeon LUT)

- 받은 표를 보관(RGB: R/G/B = 31–24/23–16/15–8, BW 8bpp: 하위 바이트).
- LUT 256 칸 = 각 항목을 `256 / 항목 수` 번 반복(S3).  표가 없으면 선형 램프.
- BW:8 에 `Gray Levels` < 256 이면 **표를 무시하고 양자화 램프**(Matrox 계약 — 고른 사람의 의도가 이긴다).
- 밝기: 각 값에 `EV_SCALE_BRIGHTNESS(level, v)`(`bsd/dev/ev_types.h` 170) 를 적용.
- 기록 시점: 진입(모드가 선 뒤)과 `setTransferTable`·`setBrightness` 가 **모드가 살아 있을 때**.
  모드가 없을 때 온 호출은 보관만 한다.
- 쓰기 경로는 지금의 `osrdn_palette_put`(클럭 게이트 처리 포함) 하나 — 새 쓰기 경로를 만들지 않는다.
- 이 호출들도 커널이 직렬화하지 않는다 → **시퀀스 claim 을 잡고** 쓴다.  잡지 못하면 보관만 하고
  진입이 끝날 때 반영.

### 10-5. 포맷별 진입에서 바뀌는 것

| 항목 | 32 | 16(555) | 8(RGB·BW) |
|---|---|---|---|
| `CRTC_GEN_CNTL` 형식(bit 8–11) | 6 | 3 | 2 |
| `CRTC_PITCH` | 오라클 | 오라클 | 오라클 |
| FIFO | 오라클(폭 × 4) | 오라클(폭 × 2) | 오라클(폭 × 1) |
| `rowBytes` / `memorySize` | 폭 × 4 | 폭 × 2 | 폭 × 1 |
| 패턴 | 32 비트 색 | 555 색 | 색인(PseudoColor 는 램프, BW 는 회색) |
| LUT | 선형/전달표 | 선형/전달표(**8 비트 확장 색인**, xf86) | 컬러맵 / 회색 램프 |

`DAC_CNTL` 의 8 비트 DAC 는 모든 포맷에서 그대로.  0 단계 18 게이트, 스냅샷, 복귀, 순환은 **포맷과 무관**.

### 10-6. 인스펙터

Matrox `OSMGADisplayInspector` 에서 **Gray Levels 컨트롤만** 옮긴다.  nib 는 Matrox 처럼 파이썬으로
생성(openstep-nibmaker).  인스펙터가 쓰는 값과 드라이버가 읽는 규칙을 **같은 함수**로 맞춘다
(Matrox 인스펙터 머리말의 원칙: "패널이 보여주는 것은 다음 부팅에 드라이버가 할 일이어야 한다").

## 11. 교차검토에 물을 것

1. 2·3·4 절의 사실 주장 — 각 인용이 맞는가, 특히 **Radeon LUT 의 8 비트 확장 색인**(4 절)이
   xf86 코드에서 정말 그렇게 읽히는가(그 `switch` 에는 `break` 가 없다).
2. 스윕(10-2)이 안전한가 — 한 호출 안에서 복귀 → 다른 형식으로 진입을 반복하는 것이, 순환에서 증명한
   것 이상으로 무엇을 건드리나.  창 서버가 그리는 중인 형식 불일치의 위험.
3. 전달표·밝기(10-4)의 직렬화와 기록 시점.
4. 게이트 해석 — "한 부팅 스윕 + 8 부팅" 이 "광고하는 조합 전부를 실기에서 확인" 을 채우는가.
5. 빠진 것.

### 12-4. 게이트 해석 — operator 에게 알릴 것

"한 부팅 스윕 + 8 부팅" 으로는 **20 조합 중 12 개**가 **레지스터 되읽기만** 받고,
창 서버 경로(전달표·컬러맵)와 "재부팅 뒤 설정 유지" 는 받지 않는다.  게이트 문장 그대로는
**12 개에 대해 충족되지 않는다**.  제안:

1. 전달표 경로는 **포맷에만** 의존한다는 것을 코드 구조로 보이고(해상도 무관), 8 부팅이 포맷 4 개를
   전부 창 서버 경로로 확인한다.
2. "설정 유지" 는 **Configure 가 쓴 문자열을 파서가 같은 조합으로 읽는가** 이므로, 호스트에서 **20 줄
   `Display.modes` 문자열과 표에 쓰이는 띄어쓰기 형식** 전부로 파서를 시험한다.
3. 계획서와 결과 문서는 이 두 논증에 기대고 있다고 **명시**한다 — "20 조합 전부 실기 확인" 이라고
   쓰지 않는다.

## 14. 순서 1·2 완료 (호스트, 2026-09-17)

### 14-1. H1 — 재진입 중 커널 복귀

- `modeReleaseOrRevert`: 걸쇠 해제와 "커널이 복귀를 요구했고 우리 모드가 카드에 있다" 확인을 **같은
  `splhigh` 구간**에서.  요구가 있으면 놓지 않고 1 을 돌려준다.
- `modeFinish`: 그동안 요구된 만큼 복귀를 돌리고 놓는다.  순환과 부팅 진입 둘 다 이것으로 끝낸다
  (커널 자신의 복귀 경로는 그대로 `modeRelease`).
- 시뮬레이터: 가짜 카드의 **갈고리**가 순환의 복귀 절반이 `modeWritten` 을 내린 뒤 재진입이 다시 올린
  순간에 `osrdn_mode_revert` 를 끼워 넣는다(걸쇠를 쥔 상태라 깃발만 선다) → 순환이 끝났을 때
  카드가 콘솔 상태이고 `live=0`, `why=12`, 걸쇠 풀림.
- **변이**(수정 전 모양 — 그냥 놓기)는 `written=1`, 즉 **카드가 리니어로 남는 것**으로 잡힌다.
  처음 만든 갈고리는 쓰기 횟수로 발동해 복귀 절반에서 터져서 변이를 못 잡았다 — 상태 기반으로 바꿨다.

### 14-2. E1 — 오라클 피치

- `crtc_pitch` = `(w·bpp + bpp·8 − 1) // (bpp·8)` (xf86 `legacy_crtc.c` 955–957).
- 자체검사: 800 px 에서 32·16·8 이 **모두** `00640064`, 폭 1024 는 `00800080`, **옛 공식은 16bpp 에서
  다른 값**(구별됨), 다섯 폭 모두 8 의 배수.
- 생성 헤더(32bpp)의 값은 그대로 — R2 드라이버에 변화 없음.

## 15. R3a 설계 — 모드 표와 생성기 (코딩 전, 검토 대상)

### 15-1. 생성 헤더의 모양

`osrdn_mode_expect.h` 를 단일 모드에서 **표**로 바꾼다.  모두 오라클에서 나온다.

| 표 | 행 | 내용 |
|---|---|---|
| `osrdnRes[5]` | 해상도 | 이름, 폭·높이, CRTC 4 워드, 피치(⌈w/8⌉, 모든 심도 공통), 실현 도트 클럭(Hz), 분주 표 조각(시작·개수) |
| `osrdnFmt[4]` | 포맷 | `ColorSpace` 토큰, 바이트 수(4·2·1), CRTC 형식(6·3·2), 비트 수 열거·색공간·`pixelEncoding` 의 **숫자 코드**(헤더는 호스트 시뮬레이터도 읽으므로 DriverKit 열거를 직접 쓰지 않고 클래스가 옮긴다), PseudoColor 여부 |
| `osrdnFifo[5][3]` | 해상도 × 바이트 수 | FIFO set/clear/preserve(`fifo(mode, bytes)`) |
| `osrdnPllRows[824]` | 모드별로 이어 붙임 | `{refdiv, div3}` |
| 기본 조합 | — | 800×600 `RGB:888/32`(R2 에서 증명된 것) |

`OSRDN_MODE_*`·`OSRDN_CRTC_*` 단일 매크로(D13)는 R3a 에서는 **기본 조합의 행에서 생성해 그대로
둔다** — 쓰는 곳(`OSRDNDisplay.m`, `osrdn_mode.m`, 시뮬레이터, 소스 규칙)이 아직 있으므로, 없애면 R2
드라이버가 빌드되지 않는다.  생성기는 **매크로 값 = 기본 조합의 표 행**을 확인한다.  매크로는 R3b 가
사용처를 표로 옮길 때 없앤다.

### 15-2. 사람이 승인하는 것 — 항등식이 되지 않게

생성물끼리 비교하면 항등식이다.  사람이 따로 쓴 원본과 대조한다:

1. **타이밍 입력**: 오라클 `MODES` 를 **Matrox 의 `osmgaRes`**(독립적으로 손으로 쓴 VESA DMT 표)와
   11 필드씩 대조 — 오늘 python 으로 5 모드 전부 같음을 확인했다.  생성기가 매번 파싱해 대조한다.
2. **CRTC 워드**: 오라클의 두 공식(NetBSD 식·xf86 식)이 모든 모드에서 같아야 한다(지금도 있음).
3. **분주 표**: 모드마다 **규칙·개수·지문·범위**를 이 문서에 적고 대조(R2B §14 방식).  "연속" 이
   아니라 "오라클 집합과 같음"(640×480 은 refdiv 8, 1024×768 은 refdiv 3 이 빠진다 — 이것도 적는다).
4. **실측·외부 앵커**: 800×600 은 R2 실측 값 그대로(`00630083` …, `00030047`·`0003008e`), 1024×768
   refdiv 12 는 **xf86 이 하드코딩한 `000600ad`**.
5. **피치**: xf86 식과 NetBSD 식이 다섯 폭 × 세 심도에서 같아야 하고, 유일한 차이(800 px 8bpp:
   NetBSD 104, xf86 100)는 NetBSD 의 64 바이트 행 올림 때문이라고 **적고 예외로 명시**한다.
6. **FIFO**: 32bpp 800×600 은 R2 실측 `20005c5c`/`0f808080`.  나머지는 오라클 식(정수 전용, xf86
   "HIGH" 경로) — 식 자체가 R2B §12-10 에서 검토됐다.

### 15-3. 매핑 길이 3 MiB → 8 MiB (D12)

함께 옮길 것: `osrdn_record.h` 의 `OSRDN_FB_LENGTH`, `check_r2b0_src.py` 105 의 고정값,
`parse_r2b0.py` 66 과 자체검사 고정 줄(543·657), `simworld2b.c` 323.  과거 R2b-0 기록은
`check-all` 이 다시 판정하지 않으므로(자체검사만 돈다) 기록 판정은 `R2B0_RESULT.md` 에 남은 그대로다.
0 단계 `apersize`·`memsize` 는 128 MiB 대 8 MiB 로 여전히 통과한다(두 부팅 실측).
`osrdn_record.m` 은 **바꾸지 않는다** — 그 값은 헤더에서 온다.  단 `sim_r2b0.py` 가 추적하는 것은
`.m` 의 해시이므로 영향 없음을 확인한다.

### 15-4. 검사

- 생성기 `--check`: 위 1–6 전부, 기본 조합 행 = 옛 매크로 값.
- 오라클 자체검사: 새 표 함수마다 음성 대조(입력을 틀리면 실패).

## 17. R3a 확정 범위 (개정)

1. 오라클: `pll_table` 을 모드마다, 형식 표, 조합별 `displayInfo`.  자체검사에 음성 대조.
2. 생성기: 기존 단일 매크로(기본 조합 행)는 **그대로**, 새 표는 `OSRDN_MODE_TABLES` 가드 뒤에 **다른
   이름**으로(`osrdnPllAll` 등).  검사: B2 되풀이, B3 FAIL, B4 형식 표 대조, 16-3 FIFO 대조, 피치
   두 공식, CRTC 두 공식, 모드별 분주 규칙·개수·지문, 기본 조합 = 옛 매크로.
3. **매핑 길이 변경은 R3b**(A6).
4. B8: R3a 전후 호스트 목적 파일 비교.
5. B9: NetBSD `videomode` 확보 시도 — 되면 타이밍의 **진짜 독립 대조**로 넣는다.

## 20. R3b 설계 (코딩 전, 교차검토 대상, 2026-09-17)

범위: 설정에서 조합 선택, 형식별 진입과 확장 되읽기(H2), 매핑 8 MiB, S3 식 전달표·밝기,
`Gray Levels`, `HAS_TRANSFER_TABLE`, **`Display.modes`**(Configure 에서 조합을 고르려면 필요하므로
R3d 에서 당겨 온다 — 인스펙터는 R3d 그대로).  스윕은 R3c.

### 20-1. 조합 선택 (init, 부팅당 한 번)

- 새 단위 `osrdn_modesel.m`(순수 C, 로그 없음): `"Display Mode"` 문자열 → `(resIndex, fmtIndex)`,
  `"Gray Levels"` 문자열 → `{0, 16, 4, 2}`.  **Matrox 규칙을 그대로, 코드는 새로**(D14):
  해상도는 `Height:` `Width:` `Refresh:` `Hz` [`ColorSpace:`] 파싱(공백 허용, `edid/OpenStepMGAEDID.c`
  270–320 과 같은 문법) 후 폭·높이 일치, 형식은 **표 순서로 첫 부분문자열**(`OpenStepMGAReplacementDisplay.m`
  4572–4591), `Gray Levels` 는 `256/16/4/2` 정확 일치만, 그 밖은 256(4537–4563).  옛 철자 `BW:4` 는
  이 드라이버에 설정된 적이 없으므로 받지 않는다.
- 실패·표에 없음 → **기본 조합(800×600 `RGB:888/32`, `OSRDN_RES_DEFAULT`/`OSRDN_FMT_DEFAULT`)**.
  결과가 폭 % 8 ≠ 0 이거나 `memorySize > mappedLength` 이면 **조합 전체를** 기본으로(Matrox
  4608–4630 의 모양, 우리 CRTC 단위는 8 화소라 조건은 `w % 8`).
- 결과는 클래스가 `rdnMode.res`/`rdnMode.fmt`/`rdnMode.grayLevels` 에 넣고, **선택 증거 한 줄**
  (`RDN-R3 select boot= res= fmt= gray= dflt= why=`)을 init 에서 찍는다.
- `displayInfo` 는 선택된 행에서: 폭·높이·`rowBytes`·`bitsPerPixel`·`colorSpace`·`pixelEncoding`·
  `memorySize`·`dotClockRate`·`screenWidth/Height`, `flags = IO_DISPLAY_HAS_TRANSFER_TABLE`(D15 —
  `setTransferTable:count:` 가 같은 빌드에 있다).
- C89 컴파일 시간 단언: 생성 표의 `ioBpp`/`ioColorSpace` 정수가 `displayDefs.h` 열거와 같다
  (`typedef char a[(IO_24BitsPerPixel == 4) ? 1 : -1];` 식, 네 값 × 둘).

### 20-2. 매핑 8 MiB (D12, A2)

`OSRDN_FB_LENGTH` 0x300000 → **0x800000**(1600×1200×4 = 7 680 000 이 들어가는 가장 작은 MiB 단위).
같은 커밋에서 옮길 곳(전수 grep, 2026-09-17): `osrdn_record.h` 15, `osrdn_record.m` 576·766·768(상수
이름으로 참조 — 값만 바뀜), `OSRDNDisplay.m` 156·163·177, `check_r2b0_src.py` 105, `parse_r2b0.py` 66,
`simworld2b.c` 336.  **R2b-0 기록 모듈의 목적 파일이 바뀐다**(A2) — 의도된 변화이고, 상수 하나만
바뀌었음을 objsnap 비교로 보인다(바뀐 단위·섹션 목록이 예상과 같아야 한다).
근거: Matrox 는 같은 기계에서 16 MiB 를 `mapFrameBufferAtPhysicalAddress` 로 매핑했다
(`OpenStepMGAReplacementDisplay.m` 4055–4083), 우리 두 부팅의 `CONFIG_APER_SIZE`·`CONFIG_MEMSIZE` 는
128 MiB.  시뮬레이터에 3 MiB·8 MiB 사이 애퍼처 세계를 넣어 거절을 증명한다.

### 20-3. 형식별 진입 (단계 번호는 그대로)

| 단계 | R2 | R3b |
|---|---|---|
| 5 CRTC | 단일 매크로 | `osrdnResAll[res]` 네 워드·피치, `CRTC_GEN_CNTL` 형식 = `osrdnFmtAll[fmt].crtcFormat << 8` |
| 6 PLL | 스냅샷 때 고른 `div3` | **진입마다** `osrdnPllAll[res 조각]` 에서 `refdiv` 로(D1).  없으면 `MODE_WHY_REFDIV` 로 **쓰기 전에** 거절.  `HTOTAL_CNTL` 은 표의 새 칸(`htotal & 7`, 다섯 모드 모두 0 — python) |
| 7 FIFO | 단일 매크로 | `osrdnFifoAll[res][bytes 칸]` |
| 8 DAC | 그대로 | 그대로(8 비트 DAC, 모든 형식) |
| 9 LUT | 선형 램프 | 20-4 의 LUT |
| 10 패턴 | 32 비트 800×600 | 형식별, **32 비트 쓰기만**: 16bpp 는 화소 둘, 8bpp 는 화소 넷을 한 워드로(폭이 8 의 배수라 행 끝을 넘지 않는다, D4).  접근자는 그대로 셋(`RDNR2aMMIO.m` 규칙).  마지막 쓰기 끝 ≤ `memorySize` ≤ `mappedLength` 를 시뮬레이터가 잰다 |
| 12 되읽기 | 7+PLL | + **형식 비트**(`CRTC_GEN_CNTL & 0xf00`), **FIFO**(`(got & clear) == set`), **DAC**(`DAC_8BIT_EN`·`DAC_MASK_ALL`), **LUT 256 칸 되읽기 = 쓴 값**(`revertPaletteBad=0` 이 읽기=쓰기를 이미 보였다) — H2 |

- 스냅샷의 `div3` 선택은 없앤다(스냅샷은 `refdiv` 만 기록).  "0 단계 18 게이트, 스냅샷, 복귀, 순환은
  형식과 무관" 은 그대로.
- xf86 에서 심도에 따라 달라지는 것은 형식·피치·FIFO 뿐임을 원문으로 확인했다: `legacy_crtc.c` 889–894
  (형식), 955–957(피치), 1598(FIFO), `RADEONInitSurfaceCntl` 의 스왑은 빅엔디안만(745–757), 오프셋은
  x=y=0 이라 0.

### 20-4. 전달표·밝기·Gray Levels (D6–D10)

상태(클래스 인스턴스 안, 스택 아님): `xferRgb[256][3]`(8 비트), `xferCount`(0 = 없음),
`brightness`(초기 `EV_SCREEN_MAX_BRIGHTNESS` = 64, D9), `grayLevels`, `lutPending`.

- `setTransferTable:count:`(S3 `S3.m` 59–95 의 해석): 표가 없거나 개수 ≤ 0 이면 **무시**(Matrox 7572–7573).
  개수 > 256 이면 256 으로 자른다(D10).  BW 형식이면 하위 바이트를 세 채널에, RGB 면 31–24/23–16/15–8.
  저장과 `lutPending = 1` 은 **한 splhigh 구간**(256 × 3 바이트 복사).  호출 횟수·마지막 개수를 센다.
- `setBrightness:token:`: 0..64 밖이면 `nil`(S3 46–51), 아니면 저장 + `lutPending = 1`(splhigh).
- **적용**: `modeLutApply` — claim 을 잡은 경우에만.  splhigh 안에서 `lutPending = 0` 과 표·밝기·
  회색 단계 **복사**를 함께 하고, splhigh 밖에서 LUT 를 만들고 `modePalette` 로 쓴다.
  **`modeWritten && !kernelRevertSeen` 일 때만** 쓴다(D8).
- **잃어버린 갱신 막기**(D7): claim 을 못 잡은 호출은 저장만 하고 돌아간다.  해제 함수
  `modeReleaseOrWork` 가 한 splhigh 구간에서 "커널 복귀 요구" 와 "`lutPending`" 을 보고, 둘 다
  없을 때만 놓는다.  복귀 요구가 우선(H1), 그다음 `lutPending` 이면 claim 을 쥔 채 적용하고 다시 본다.
  진입의 9 단계도 같은 적용 함수를 쓰므로(대기 깃발을 먼저 지우고 복사) 진입 도중 온 표는 해제 때
  다시 적용된다.
- **LUT 만들기** (256 칸, 8 비트 → 팔레트 워드 `(r<<22)|(g<<12)|(b<<2)`, 지금 램프와 같은 모양):
  1. BW 형식이고 `grayLevels ∈ {16,4,2}`: `lvl = i·n/256`, `v = lvl·255/(n−1)` — **표를 무시**(Matrox
     4775–4790, 7556–7562).
  2. 아니면 표가 있으면 `rep = 256/개수`, 항목 k 를 `k·rep … k·rep+rep−1` 에, **남는 꼬리는 마지막
     항목으로**(D10 — S3 는 남긴다).
  3. 아니면 선형 램프(모든 형식; 15bpp 도 — 4 절, D11).
  4. 밝기: 각 성분 `v·level >> 6`(`ev_types.h` 170).
- 모든 부동소수점·64 비트 나눗셈 없음.  `256/개수` 는 32 비트 정수.
- 커널 복귀·스냅샷 복원은 이 LUT 와 무관(스냅샷 팔레트를 쓴다).

### 20-5. 클래스

- `setTransferTable:count:`·`setBrightness:token:` 구현(각각 한 줄 증거 `RDN-R3 xfer`/`RDN-R3 bright`
  — **호출 뒤에**, 적용 결과 `applied=0/1`·`why`).  둘 다 하드웨어 접근은 모드 모듈만.
- `Display.modes`: Matrox 와 같은 20 줄(해상도 순서 640·800·1024·1280·1600).  `Default.table`·
  `Instance0.table` 에 `"Gray Levels" = "256";`.
- `rdnr2b0` 의 `WANT_WIDTH 800`/`WANT_HEIGHT 600`(순환 도구의 확인)은 **State 가 알려주는 선택
  조합**과 비교하도록 바꾼다(State 워드 추가 여부는 코딩 때 `osrdn_state_words` 를 보고 결정 —
  R2b-0 모듈의 워드 수를 바꾸면 파서·검사도 따라 바뀐다).

### 20-6. 호스트 검사 (코딩과 같이)

- **파서 시험**: `Display.modes` 20 줄, 표에 쓰이는 띄어쓰기 형식 20 줄, 깨진 입력(빈 문자열, `Width`
  없음, 모르는 해상도, 모르는 형식, 숫자 넘침, `Gray Levels` 의 `8`/`0`/`256 `) → 기대 결과표(파이썬
  오라클이 **같은 문법을 따로 구현**해 만든다).  12-4 제안 2.
- **시뮬레이터**(`simworld2b.c` 확장): 가짜 카드가 형식 비트·FIFO·DAC·LUT 되읽기·패턴 쓰기 최대 끝을
  기록, 20 조합 진입 세계.  변이: 형식 비트를 32 로 고정, FIFO 를 바이트 4 칸으로 고정, `div3` 를
  기본 해상도에서(D1), 패턴을 32 비트 화소 간격으로, `rep` 을 S3 그대로(개수 > 256 이면 0 회),
  꼬리 안 채움, 밝기 미적용, `Gray Levels` 무시, 대기 깃발 없이 claim 실패 시 버림(잃어버린 갱신 —
  갈고리가 적용 도중 새 표를 넣는다), `modeWritten` 없이 적용, 애퍼처 4 MiB 를 받음.
- 역어셈블 게이트: 새 단위의 호출자·필수 간선(`modeLutApply → osrdn_palette_put` 은 `modePalette`
  경유), `osrdn_modesel` 은 하드웨어 접근 0.
- `objsnap`: R3a 의 `--r3-inert` 는 **은퇴**(가드를 켠다).  대신 "바뀐 단위 목록이 예상과 같다" 는
  한 번의 비교를 결과에 남긴다.

### 20-8. 교차검토에 물을 것

1. 20-4 의 잃어버린 갱신 논증 — claim·splhigh·대기 깃발의 순서에 빈틈이 있는가.  `setBrightness` 가
   **어떤 문맥에서** 불리는지(이벤트 드라이버, spl 모름) — splhigh 복사 + MMIO 쓰기로 충분한가.
2. 전달표를 **RGB 형식에도 적용**하는 것(S3)과 **보관만** 하는 것(Matrox) 중 무엇이 맞는가.
   창 서버가 32bpp 에서 보내는 표가 무엇인지 측정된 적은 있는가(Matrox `TEST_STATUS.md`).
3. 형식별 패턴을 32 비트 쓰기로 묶는 것 — 8/16bpp 의 바이트 순서 가정(`SURFACE_CNTL` 스왑 0,
   리틀엔디안)이 맞는가.
4. 되읽기에 LUT 256 칸을 넣는 것 — 쓴 값과 읽은 값이 같다는 근거(R2c `revertPaletteBad=0`)가
   **램프가 아닌 값**에도 성립하는가.
5. `Display.modes` 를 R3b 로 당기는 것, `fresh` 재설치가 선택을 지우는 문제, 순환 도구의 800×600 고정.
6. 빠진 것.

### 21-3. 전달표를 RGB 에도 적용할 것인가 (D2)

`displayDefs.h` 163–177: 플래그의 뜻이 "**하드웨어 감마 보정** 전달표(CLUT)" 이고, "32/24 비트 색·8 비트
흑백은 256 항목, **15 비트 색은 32 항목**".  → S3 처럼 **적용한다**(창 서버는 적용을 전제로 보낸다).
15 비트의 32 항목은 `256/32 = 8` 반복으로 LUT 256 칸을 채우므로 8 비트 확장 색인과 맞는다.
Matrox 의 측정(`TEST_STATUS.md` 84)은 **개수만**이고 내용은 기록되지 않았다 → 매 호출에 **요약 한 줄**
(개수, 합계, 항등 여부, 첫·끝 항목)을 남긴다.  밝기·자동 어둡게 하기로 화면이 어두워지는 것은 의도된
동작이다(`IOFrameBufferDisplay.h` 117 "Subclasses must override setBrightness").
PseudoColor 에서 개수 < 256 인 경우(B8)는 S3 규칙대로 늘린다 — Matrox 부팅에서 256 만 관측됐다.
표가 오기 전 기본 LUT 는 선형(S3 의 감마 2.2 가 아니라 R2·Matrox 와 같게, B9).

### 21-4. 순서 (개정 2)

1. **R3b-0 — 팔레트 읽기 측정(읽기 전용)**.  스냅샷 때 기존 방식(A: 하위 바이트 `k`)에 더해
   **방식 C**(`k << 16` 를 매 항목마다, xf86 디버그 함수 모양 — 자동 증가에 기대지 않는다)로 256 칸을
   **따로** 읽어 두고, 순서 끝의 증거 줄에 두 방식의 요약(항목 0·1·7·15·16·255, 서로 다른 값의 수,
   두 방식이 다른 칸의 수)을 찍는다.  쓰기 경로·복귀는 **바꾸지 않는다**.  색인 레지스터 쓰기는
   지금도 하는 일이라 새 쓰기 종류가 없다.  부팅 1 회.
   - **A 가 한 값(`distinctA=1`), C 가 여러 값, `differ` 큼** → P1 확정(읽기 색인은 비트 16–23) →
     R3b 에서 스냅샷 읽기를 C 로 고치고 시뮬레이터 모델을 비트 16–23 으로, 복귀 검사를 다시 증명.
   - **C 가 한 값(`distinctC=1`), A 가 여러 값** → P1 기각(이 칩은 하위 바이트로 읽는다 — C 는 하위
     바이트에 0 을 쓰므로 매번 0 번 항목을 읽는다) → 기록하고 그대로.
   - **그 밖**(둘이 같음 `differ=0`, 둘 다 한 값, 둘 다 여러 값인데 다름) → 두 모델 어디에도 맞지 않는다.
     판정하지 않고 덤프로 분석한다.  (처음 적은 "둘이 같으면 기각" 은 틀렸다 — 21-5.)
2. R3b-1 — 매핑 8 MiB(단독 단계, objsnap 전후).
3. R3b-2 — 선택·형식별 진입·전달표·밝기·`Display.modes`·도구.
4. 8 부팅.

  Matrox 는 같은 기계·커널에서 16 MiB 를 같은 메서드로 매핑했다(4086–4087).
- `memorySize`(발행 값)는 1 920 000 그대로 — 매핑이 더 커도 된다(Matrox 도 16 MiB 매핑 · 모드 크기 발행).
- 패턴은 여전히 `memorySize` 안에만 쓴다(800×600×4).  매핑 길이는 **쓰기 범위가 아니다**.
- **판정**: B 뒤 objsnap 이 A 뒤와 비교해 **`osrdn_record.m`·`OSRDNDisplay.m` 만** 바뀐다(다른 여섯
  단위는 같다).  목록이 다르면 멈춘다.

### 22-3. 실기 (한 부팅)

`init ... ok`(BAR0 검사가 8 MiB 창으로 통과), 0 단계 18 게이트 통과, `enter live=1`, `bad=0`,
화면(시험 패턴·로그인) 평소대로.  `RDN-R3B0` 줄이 **없어야** 한다(제거 확인).  기록 verb 는 돌리지 않는다.

### 23-2. 선택: 자체 파서, 커널의 `selectMode:` 는 쓰지 않는다

`IOFrameBufferDisplay.h` 77–87 의 `selectMode:count:valid:` 는 NeXT 의 파서지만 (1) 이 기계에서 측정된
적이 없고, (2) 129–133 행: "슈퍼클래스는 `selectMode` 에 넘긴 목록을 쓴다" — 목록을 넘기면
`setPendingDisplayMode:`(121–126)의 **실행 중 모드 전환** 경로가 열릴 수 있다.  스톡 S3 는 쓰지만
(`S3SetMode.m` 134) Matrox 는 쓰지 않았다.  operator 지시(심도는 Matrox)대로 **Matrox 식 자체 파서**,
`displayModeCount` 는 계속 0.

새 단위 **`osrdn_modesel.m`**(순수 C, 하드웨어·로그 없음):
- 규칙(Matrox, 21-1 P3 반영): 해상도는 `Height:` `Width:` `Refresh:` 숫자 `Hz` [`ColorSpace:` 비지 않음]
  (공백 허용, `Hz` 는 숫자 바로 뒤 — `OpenStepMGAEDID.c` 269–321) 파싱 뒤 **폭·높이 일치**(재생률 값은
  보지 않는다, Matrox 와 같음 — 표는 모두 60 Hz); 형식은 **파싱 성공과 무관하게** 표 순서의 첫
  부분문자열(`OpenStepMGAReplacementDisplay.m` 4579–4583); 실패한 쪽만 기본값.
- 조합 검사: 폭 % 8 ≠ 0 또는 `rowBytes × 높이 > OSRDN_FB_LENGTH`(상수, 21-1 P4) → **조합 전체** 기본값
  (Matrox 4608–4630 모양).  다섯 해상도 × 네 형식은 모두 통과(python, 18-4 표 최대 7 680 000).
- 출력 `osrdn_modesel { res, fmt, resDefault, fmtDefault, pairDefault }`.  `Gray Levels` 는 2b.
- **표 소유**: 해상도·형식 표(작다)는 이 단위만 정의(`OSRDN_MODE_TABLES_SEL`), 접근자
  `osrdn_res(i)`·`osrdn_fmt(i)` 로 내준다.  분주·FIFO 표는 `osrdn_mode.m` 만(`OSRDN_MODE_TABLES_R3`).
  생성기는 가드를 둘로 나누고 해상도 행에 `htotalCntl`(= `htotal & 7`, 다섯 모두 0) 칸을 더한다(21-1 P6).
  R2 의 단일 모드 매크로·`osrdnPllRows` 는 헤더에 남기되 **드라이버는 더 쓰지 않는다**(도구 검사 기준).
- 호스트 시험(12-4 제안 2): 파이썬 오라클이 **같은 문법을 따로 구현**(`tools/r3/modesel_oracle.py`)해
  기대값을 만들고, gcc 로 컴파일한 `osrdn_modesel.m` 을 입력 묶음으로 돌려 대조: `Display.modes` 20 줄,
  표에 쓰이는 띄어쓰기 형식 20 줄, 공백 변형, 깨진 입력(빈 문자열, NULL, `Width` 없음, `Hz` 앞 공백,
  모르는 해상도, 모르는 형식, 숫자 넘침 `99999999999`, `ColorSpace:` 뒤 비어 있음, 해상도만 틀리고 형식은
  맞음 → 형식만 적용).  변이(형식 순서를 뒤집음, 폭·높이 바꿔 비교, 부분문자열을 앞부분 일치로)도.

### 23-6. 시뮬레이터 (`simworld2b.c`)

- `modeInit` 에 `res/fmt` = 기본값.  세계: **20 조합 전부 진입** — 가짜 카드가 형식 비트·네 CRTC 워드·
  피치·`div3`(그 해상도·그 refdiv 의 행)·FIFO·DAC·LUT 를 **파이썬 오라클이 만든 기대표**(생성 헤더가
  아니라 `radeon_modeset.py` 에서 직접, `-D` 로 넘기지 않고 별도 생성 C 조각)와 대조, 패턴 최대 끝 ≤
  `memorySize`, 쓰기 오프셋이 4 의 배수.  구멍 세계: 640×480 + refdiv 8 → 쓰기 0 으로 거절.
- 변이: 형식 비트 32 고정, FIFO 를 바이트 4 칸 고정, `div3` 를 기본 해상도 조각에서, 패턴을 4 바이트
  화소 간격으로, 램프를 800 기준으로, 행 조회를 4 단계 뒤로, LUT 비교 없음, 형식 비트 비교 없음,
  `osrdn_palette_get` 이 색인을 안 올림.

### 23-7. 실기 (2a, 3 부팅) — 화면 확인 필요

1. 설치(`closed=yes fresh live`) → 재부팅: 기본 800×600 32.  `select` 기본·되읽기 확장 항목 통과·패턴·로그인.

- 부팅 사이 재설치 없음.  고쳐야 하면 `fresh` 없이 설치(기계의 표 유지).
- 실패 예상 증상: 되읽기 불일치 → 걸쇠·복귀 → **콘솔 화면으로 돌아오고 창 서버는 발행된 모드로 그리려
  한다**(R2 에서 알려진 한계: `enterLinearMode` 는 실패를 알릴 수 없다).  그 경우 Configure 로 800×600 32
  복귀가 탈출구 — 화면이 안 보이면 telnet 으로 `Instance0.table` 의 `Display Mode` 를 되돌리는 절차를
  미리 준비한다(`tools/r3/target-mode-reset.sh`, 되돌리기 전 사본 보관).

### 24-1. 커널 쪽 사실 (원문)

### 24-2. 상태 (모드 상태 구조체 안, 스택 아님)

`xferRgb[256×3]`(8 비트), `xferCount`(0 = 표 없음), `xferMono`(저장할 때의 해석), `brightness`

검사: 선택 전에는 적용 거절), `grayLevels`(0/16/4/2), `lutPending`, 계수(`xferCalls`, `brightCalls`,
`lutApplied`, `lutDeferred`), 마지막 적용의 되읽기 결과.

### 24-3. LUT 만들기 (순수 함수, 호스트 오라클로 따로 구현)

`modeLutBuild(fmt, grayLevels, xferRgb, xferCount, brightness, out[256])`:
1. BW 형식(`ioColorSpace == IO_OneIsWhiteColorSpace`)이고 `grayLevels ∈ {16,4,2}`: `lvl = i·n/256`,
   `v = lvl·255/(n−1)` — 표 무시(Matrox `OpenStepMGAReplacementDisplay.m:4783-4786`).
2. 아니면 `xferCount ≥ 1`: `rep = 256/count`, 항목 k 를 `k·rep … k·rep+rep−1` 에, 남는 꼬리는 마지막 항목.
3. 아니면 선형 램프.
4. 성분마다 `v·brightness >> 6`, 워드 `(r<<22)|(g<<12)|(b<<2)`.

### 24-4. 직렬화 (21-2 B2–B5 반영)

- **저장 먼저**: `osrdn_mode_set_transfer`/`osrdn_mode_set_brightness` 는 splhigh 한 구간에서 저장과
  `lutPending = 1`, 그다음 claim 시도(B3).
- **claim 성공**: `noSleep = 1`(B2 — 이 경로의 복귀 본체는 IODelay 만), `modeFinish` 의 새 모양
  `modeReleaseOrWork` 로 끝낸다.
- **`modeReleaseOrWork`**(한 splhigh 구간): ① 커널 복귀 요구 && `modeWritten` → 복귀 먼저(H1),
  ② `lutPending && modeWritten && !kernelRevertSeen` → 대기 깃발을 지우고 적용(클레임 쥔 채),
  ③ 그 밖은 `inSequence = 0` 과 **호출자가 넘긴 `noSleep` 복원값**을 같은 구간에서 쓴 뒤 놓는다
  (놓은 뒤에 쓰면 다음 소유자의 `noSleep` 을 덮는다).
- **적용**: splhigh 에서 표·밝기·단계 복사 + `lutPending = 0`, splhigh 밖에서 LUT 만들기 → `modePalette`
  → 되읽기(`osrdn_palette_get`, 상위 8 비트) 결과를 상태에 남긴다.  모드가 없으면(`!modeWritten` 또는
  `kernelRevertSeen`) 저장만(D8).
- **claim 실패**: 저장만 하고 반환(소유자가 놓을 때 ②에서 적용).  `lutDeferred++`.
- **진입 9 단계**: 대기 깃발을 먼저 지우고 복사 → 만들기 → **무조건** 쓴다(B4).  12 단계의 LUT
  되읽기는 **판정으로 승격**(23-14·23-16: 세 부팅 모두 0) — 비교 대상은 만든 LUT.
- `osrdn_mode_revert` 의 "claim 실패 → 깃발" 을 한 splhigh 구간으로(B5).
- 기록 verb(R2b-0) 의 PLL 읽기와 인터럽트 수준 밝기 적용의 충돌(B6)은 위험으로 남긴다 — 기록 verb 는
  2b 부팅에서 돌리지 않는다.

### 24-15. FIFO 양자화 고침 (2026-09-18)

- 교차검토(내부 agent) 판정: **A 채택**.  근거 보강 — 참고 네 트리 어디에도 입자성 문서가 **없고**
  (`radeon_reg.h:348-358` 등은 7 비트 평면 필드), xf86 은 값을 **상한**으로 적는다("GRPH_STOP_REQ <=
  MIN[...]", `legacy_crtc.c` 1595) 이며 되읽지 않는다, NetBSD 는 이 레지스터를 쓰지 않는다.
  **입자성 4 는 실측으로 확정**(50 은 짝수인데 48 이 됐으므로 2 아님; 92 가 여섯 부팅에서 보존됐으므로
  8·16·32 아님).  내림·반올림 중 무엇인지는 이 표본으로 못 가르지만 **4 의 배수는 어느 쪽이든 보존**된다.
- 반영: 오라클 `fifo()` 가 두 요청 필드를 4 의 배수로 내리고(`stop_req < 4` 면 예외 — 오늘 최소는 40),
  16-3 표의 800×600 8bpp 칸을 `20003030` 으로(유도 과정과 실측 부팅 번호를 함께), 가짜 카드가
  **두 요청 필드만** 양자화(임계점은 우리가 늘 0 이라 규칙을 모른다).
- 자체검사가 항등식이 되지 않도록: 오라클의 `%4` 단언은 불변식일 뿐이고, **판정은 사람이 적은 16-3 표와의
  대조**다.  시뮬레이터의 기대표도 같은 오라클에서 나오므로 "오라클 = 하드웨어" 의 증명이 아니라 회귀
  걸쇠다 — 오라클이 내림을 잊으면 가짜 카드(양자화)와 어긋나 세계가 실패한다(음성 대조로 확인).
- **부수 발견**: 가짜 카드에 양자화를 넣자 복원 항등성 세계가 깨졌다 — 그 세계가 이 레지스터에 심던
  임의값(`…0b`)은 4 의 배수가 아니라 **카드가 담을 수 없는 값**이었다.  시드를 4 의 배수로 바꿨다.
  실기 한계로 기록: **콘솔 값의 두 요청 필드에 하위 2 비트가 서 있으면 복귀는 그것을 정확히 복원할 수
  없다**.  이 기계의 콘솔 값은 `20205c5c`(둘 다 `5c`, 4 의 배수)라 해당 없음.
- 잔여 위험(행동 아님, 기록): 하위 2 비트가 "쓰이지만 0 으로 읽히는" 비트라면 A 는 실제 워터마크를
  50 → 48 로 옮기는 셈이다.  되읽기로는 반증할 수 없고, 크기는 16 바이트 단위 2 개 = 32 바이트다.

남은 14 조합은 "광고는 하되 부팅 확인은 뒤로"(24-21) 상태로 그대로 둔다.

R3d 는 접지 않는다 — 다만 **범위를 Gray Levels 하나로 줄인다**(25-1).  이유: `Gray Levels` 는
`Display.modes` 에 실을 수 없는 유일한 설정이다.  256/16/4/2 는 같은 BW:8 스캔아웃이고 `IODisplayInfo`
가 같아서 모드 문자열로는 구분되지 않는다(24-5).  인스펙터가 없으면 operator 는 이 값을 telnet 으로
표를 고쳐야만 바꿀 수 있다.

### 25-1. 범위

**하는 것**
- 번들에 `OSRDNDisplayInspector : IODisplayInspector` 하나와 그 `DisplayInspector.nib`.
- 패널에 두 줄: `Gray levels:` 라벨 + 4 칸 라디오(`256 16 4 2`), 그리고 캡션 한 줄.
- 고른 값은 인스턴스 표의 `"Gray Levels"` 로 **저장만** 된다.

**안 하는 것 (그리고 그 이유)**
| 안 하는 것 | 이유 |
|---|---|
| 해상도·형식 고르기 | 스톡 `IODisplayInspector` 가 `Display.modes` 로 이미 한다(24-21에서 20 줄 전부 광고).  우리가 손대면 그 20 줄과 어긋날 수 있다 |
| 상태 줄("이 모드면 …가 된다") | Matrox 는 `OSMGAAccelVerdict` 를 번들과 커널에 **같이 컴파일**해서 만든다.  우리 쪽 같은 물건은 `osrdn_modesel` 인데, 그러자면 `OSRDN_FB_LENGTH`(지금 `osrdn_record.h` 안, `<driverkit/kernelDriver.h>` 를 import 한다)를 드라이버킷 없는 헤더로 옮겨야 한다.  이번 범위 밖 |
| live 반영 | 드라이버는 `Gray Levels` 를 `OSRDNDisplay.m` 의 `initFromDeviceDescription:` 에서 한 번 읽는다.  패널이 살아 있는 척하면 안 되므로 캡션이 "다음 부팅부터"라고 말한다 |
| `RDN R2B0 Record` 스위치 | 개발용 opt-in 키다.  패널에 올리면 operator 가 끌 수 있고, 끄면 드라이버가 화면을 안 그린다(`OSRDNDisplay.m` 의 `enterLinearMode` 첫 분기 refused 경로).  올리지 않는다 |

### 25-2. 구조 — 번들 실행 파일과 커널 reloc 은 별개

Configure.app 은 구 AppKit(libNeXT) 응용이고, 인스펙터는 드라이버 `.config` 번들의 **실행 파일**에서
읽힌다.  커널 드라이버는 `TOOLS = OSRDNDisplay_reloc.tproj` 서브프로젝트가 따로 만든다.  Matrox
`matrox-OSMGADisplay-Makefile:12-16` 은 *"common.make 의 재귀 규칙은 CLASSES 도 OTHER_CFLAGS 도 서브프로젝트로
내려보내지 않으므로 인스펙터를 더해도 커널 빌드는 영향받지 않는다"* 고 적는다 — **이 주장은 우리 쪽에서
실측으로 확인한다**(25-6 H4: 인스펙터를 넣기 전/후 reloc 바이너리가 바이트로 같아야 한다.
`tools/r3/objsnap.py` 가 이미 그 비교를 한다).

`<driverkit/IODisplayInspector.h>` 가 `<appkit/appkit.h>` 를 import 하는데 OPENSTEP 4.2 개발 트리에는
그 헤더가 없다.  Matrox 와 spacesaver2ps2 가 똑같이 `compat/appkit/appkit.h` 로 필요한 만큼만 선언하고
`OTHER_CFLAGS = -I./compat` 를 준다.  같은 방법을 쓴다(선례 2 건).

### 25-3. 값 표는 공유하지 않고, 같다는 것을 검사로 증명한다

드라이버의 규칙은 `osrdn_modesel.m` 의 `osrdn_modesel_gray()` 한 곳이다.  반환값 그대로 적으면
`{"256":0, "16":16, "4":4, "2":2}`, 키 없음 → `0`(refused 0), **그 밖의 것 → `0` + refused 1**.
`0` 은 "256 단계(=감쇠 없음)" 라는 뜻이다(`tools/r3/modesel_oracle.py` 의 `gray()` 도 같은 값).
비교는 정확 일치·대소문자 구분이다(`sameText`).

인스펙터는 이 네 문자열 표를 **자기 안에 다시 갖는다**(Matrox `osmgaGrayValues[]` 와 같은 방식).
파일을 공유하지 않는 이유: `osrdn_modesel.m` 을 번들에도 컴파일하려면 (a) 파일이 reloc 서브프로젝트
안에 있어 빌드 때 복사가 필요하고, (b) `.m` 확장자라 `CLASSES`/`CFILES` 중 어디에도 깔끔히 안 맞으며,
(c) `osrdn_mode_expect.h` 까지 따라 들어온다.  네 개짜리 문자열 표를 위해 치를 값이 아니다.

대신 **동치를 검사로 증명한다**(25-6 H1): 호스트에서 인스펙터의 매핑 함수(`osrdnGrayTagFor`,
`osrdnGrayValues[]`)만 32 비트로 컴파일해 돌리고, 같은 입력을 `tools/r3/modesel_oracle.py` 의
`gray()` 와 대조한다.  입력에는 네 값, 없는 키, 공백·대문자·`"8"`·`"256 "` 같은 쓰레기를 넣는다.
왕복도 본다: **tag → 값 → 드라이버 규칙**이 다시 그 tag 를 가리켜야 한다(패널이 저장한 값을 다음에
열었을 때 같은 칸이 선택돼야 한다).  변이 시험으로 이 검사가 실제로 실패할 수 있음을 보인다.

`"BW:4"` 같은 옛 철자는 **없다**.  Matrox 는 그 철자를 아직 인정해서 `osmgaGrayTagFor` 가 모드 문자열도
본다.  우리 `Display.modes` 20 줄의 형식 토큰은 `RGB:888/32 RGB:555/16 RGB:256/8 BW:8` 넷뿐이므로
(18-1 표), 인스펙터는 모드 문자열을 보지 않는다.  이것도 검사로 고정한다(H2).

### 25-4. nib

**입력 셋 (전부 이 워크스페이스 안에 있거나 실기에서 한 번 가져온다)**
1. 스톡 `DisplayInspector.nib` — Configure.app 자신의 것, `/NextAdmin/Configure.app/English.lproj/`.
   실기에서 **읽기만** 해서 `build/stocknib/` 로 가져온다(tar 로: 444 파일을 NFS 로 직접 복사하면 막힌다
   — 기억 `openstep-nfs-cp-readonly-denied`).  가져온 뒤 sha256 을 기록하고, matrox 가 같은 기계에서
   가져온 사본(`380bb6ed…` = `data.nib`)과 **같은지 확인**한다.  다르면 그 자리에서 멈추고 사람에게 묻는다.
2. 스위치/라벨 템플릿 — `openstep-spacesaver2ps2/ref/nibtemplates/PS2MouseInspector.xml`(라벨 23 을 쓴다).
3. 라디오 템플릿 — 같은 폴더의 `radio-template-BusLogicIntrInspector.xml`.
4. `openstep-nibmaker` 의 `nib2xml`/`xml2nib`/`nibroundtrip`/`tools/nibgraft.py`, `tools/validate-xml.py`.

2·3·4 는 호스트 도구·참고 자료라 배포 저장소에는 들어가지 않는다.  **배포물에 들어가는 것은 만들어진
nib 세 파일**(`OSRDNDisplay/English.lproj/DisplayInspector.nib/{data.nib,data.classes,data.dependency}`)
이고, 만드는 방법은 `OSRDNDisplay/nib-src/build-inspector-nib.py` + `tools/r3/rebuild-inspector-nib.sh`
가 적는다.  Matrox 와 같은 구성이다.

**그래프트할 자리** — 스톡 nib 의 구조는 matrox 스크립트가 적어 둔 그대로다(같은 파일이므로 객체 번호도
같아야 한다.  스크립트는 번호를 상수로 두되 **클래스 이름으로 찾아 확인**한다):
`65` WindowTemplate → `49` content view → `48` Box(outlet `displayMode`) → `52` view.
스위치·라벨은 **박스 48 안**에 넣는다.  matrox 가 실기에서 확인한 사실: `IODisplayInspector` 는
`displayMode` 박스만 베이스 인스펙터의 accessory 자리에 끼우고 이 nib 의 content view 나머지는 버린다.

**레이아웃 (python 계산, `tools/r3/nib_layout.py --self-check`)**
y 는 위로 센다.  박스 48 이 `GROW` 만큼 커지고 원래 자식(54·55)은 `GROW` 만큼 올라간다.
matrox 규칙: 원래 자식이 y=9 에 있었으므로 *우리 맨 윗줄 위 여백* = `(9 + GROW) − top` 이 스톡 패널이
이미 갖고 있던 **23** 이어야 한다.

| 줄 | y | 높이 | 위끝 |
|---|---:|---:|---:|
| 캡션 | 6 | 14 | 20 |
| `Gray levels:` 라벨 + 라디오 | 28 | 15 | 43 |

`top = 43` → `GROW = 23 + 43 − 9 = **57**`.  같은 식을 matrox 수치(top 160)에 넣으면 174 가 나오고,
그 스크립트가 쓰는 값이 174 다 — 식이 맞다는 확인이다.

라디오: 칸 54×15, 간격 4, 4 칸 → 폭 `4×54 + 3×4 = 228`, x=112 → 오른끝 340 (박스 내용 폭 382).
라벨 `Gray levels:` = 63.3 px (96 px 자리).
캡션 `Applies to BW:8 modes; takes effect after the next reboot.` = **306.8 px** (340 px 자리).
폭은 URW Nimbus Sans(= NeXT 의 Helvetica 메트릭 클론) 12 pt advance 합으로 쟀다 — matrox R13 과 같은 방법.

**`data.classes` 는 손으로 유지한다.**  스톡의 것은 `IODisplayInspector` 까지만 알고 우리 클래스를 모른다.
`OSRDNDisplayInspector = { ACTIONS = { "grayChanged:"; }; OUTLETS = { grayMatrix; }; SUPERCLASS =
IODisplayInspector; }` 를 더한다.  **연결되지 않은 outlet 은 nil 이고 nil 에게 보낸 메시지는 조용하다** —
그래서 25-6 H3 이 `.h`·`.m`·`data.classes`·만들어진 nib 의 connector 를 네 방향으로 대조한다.

### 25-7. 실기 절차

1. 스톡 nib 가져오기 — 읽기만, `gcds` 로 tar → `build/stocknib/`, sha256 대조(25-4).

3. **재부팅은 operator.**  부팅 뒤 로그의 `RDN-R3 select … gray=256 gbad=0` 이 그대로인지 확인
   (인스펙터를 넣었다고 드라이버 동작이 바뀌면 안 된다).
4. operator 가 Configure.app 을 열어 이 드라이버를 고르면 `Gray levels:` 줄이 보여야 한다.

5. 되돌리기: Configure 에서 `256`, 또는 telnet `tools/r3/target-mode-set.sh`, 또는 부트 프롬프트
   `config=Default`.

### 25-9. 교차검토에 물을 것

1. 상태 줄을 빼고 Gray Levels 만 두는 것이 맞나 — `OSRDN_FB_LENGTH` 를 드라이버킷 없는 헤더로 옮겨
   `osrdn_modesel` 을 번들에도 컴파일하는 쪽이 더 나은가?
2. 값 표를 복제하고 검사로 동치를 증명하는 것(25-3) 이 파일 공유보다 안전한가.
3. `GROW = 57` 과 두 줄 배치가 matrox 규칙을 옳게 적용한 것인가.  캡션 문구가 `Gray Levels` 의
   적용 조건(BW:8 전용)과 시점(다음 부팅)을 다 말하나.

### 24-15. 결정 갱신 (2026-09-26, G2) — 직접색 형식은 전송표를 LUT 에 싣지 않는다
24-3 의 규칙 2("표가 있으면 표")는 **RGB:256/8·BW:8 에만** 남긴다.  888/32·555/16 에서는 WindowServer 의 표(감마 2.2 리프트, `floor(255·(k/255)^(1/2.2))`)를 8비트 LUT 에 싣자 계조가 뭉개져 사용자가 "16비트처럼" 보았고, 항등표로 바꾸자 "Matrox 처럼" 보였다(`docs/G2_LUT_PLAN.md` 3·5).  NeXT 의 S3·QVision 예제는 24bpp 에도 표를 싣지만, 이 프로젝트는 눈으로 받아들여진 형제 드라이버(Matrox 재작 `OpenStepMGAReplacementDisplay.m:4751`, `:4775-4789`)를 따른다.  555/16 의 램프는 `((k>>3)*255)/31` (Xorg `drmmode_display.c:1643-1651`: 5비트 성분이 `index*8+j` 로 LUT 를 찾는다).

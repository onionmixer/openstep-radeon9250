## 1. 대기 59.27 us 는 무엇인가 — 모형이 93 % 안에서 닫힌다

`cpWait`(`osrdn_cp.m:231-287`)은 호출마다
**진입 시계 1 회 + `evals` 번의 `cpCond`(MMIO) + `evals`−1 번의 `IODelay(10)` + 탈출 시계 1 회**.
이 부팅의 로그를 제출과 짝지어 센 실제 `evals`(그린 제출 317 건): **rptr 2.18, idle 1.23**.

| | us/ZCLEAR | 비중 | |
|---|---:|---:|---|
| **`IODelay(10)` 잠** | **28.2** | **48 %** | **정책이다, 물리량이 아니다** |
| 시계 읽기 | 21.1 | 36 % | 그중 **제거 가능한 것은 5.5** |
| `cpCond` MMIO | 5.7 | 10 % | 줄일 수 없다 — 그게 질문이다 |
| 합 | 55.0 | | 실측 59.27, **93 % 에서 닫힘** |

### 1-1. 시계 읽기는 생각보다 적게 남는다

처음엔 "바퀴마다 시계를 읽으니 그게 크다"고 봤다.  **다시 읽으니 아니다**: 조건이 첫
질문에 참이면 루프는 **진입·탈출 두 번만** 읽는다.  바퀴마다의 읽기는
`evals − 1` 번뿐이고, 평균 evals 가 2.18/1.23 이므로 ZCLEAR 당 2.8 회 ≈ **5.5 us**.

### 1-2. 그리고 그 읽기를 없애면 **시간 한도가 풀린다**

`maxTurns = (limitUs / C_TICK_US) * C_TURN_FACTOR + C_TURN_SLACK` 이고
`C_TURN_FACTOR = 2`(`osrdn_cp.m:153-154`).  즉 턴 한도는 **일부러 시간 한도의 두 배**다 —
100 ms 한도에 턴만으로는 200 ms 까지 돈다.  **실제 한도를 강제하는 것은 시간 검사**이고,
턴 검사는 **시계가 얼어붙었을 때**의 대비다(그 변이가 `sim_r5` 에 있다).

그러므로 "바퀴마다의 시계 읽기를 빼자" 는 **한도를 100 ms 에서 200 ms 로 푸는 일**이다.
**그렇게 하지 않는다.**

## 2. 그래서 이 칸이 하는 일

### 2-1. `IODelay` 정책 (손잡이) — 자는 대신 몇 번 더 묻는다

`IODelay(10)` 한 번은 **10 us 를 버린다**.  `cpCond` 한 번은 **0.83 us** 다.
잠들기 전에 몇 번 더 물으면, 카드가 그 사이에 준비되는 경우 10 us 대신 몇 us 만 쓴다.

    turns++;
    w->turns = turns;                          /* M2b */
    if (turns >= maxTurns)
        break;
    for (k = 0; k < cpSpin; k++) {             /* 손잡이: 기본 0 = 오늘 그대로 */
        w->evals++;
        if (cpCond(base, kind, need)) {
            IOGetTimestamp(&t1);               /* 갱신 -- 없으면 과소 계상(§2-3) */
            w->us = cpElapsedUs(t0, t1);
            return 1;
        }
    }
    IODelay((unsigned)C_TICK_US);

- **한도는 안 건드린다**: 시간 검사도 턴 검사도 그대로.  스핀은 `cpCond` 를 더 부를 뿐이고
  그것은 `evals` 에 그대로 세어진다.
- 손잡이 기본 **0** = 오늘과 바이트 단위로 같은 동작.
- 값: `IODelay` 28.2 us 중 카드가 10 us 안에 준비되는 몫.  **얼마나인지는 모른다** —
  그래서 `evals` 와 `wait` 누적기가 그것을 잰다.

### 2-2. 아직 안 잰 44 us 를 잰다 (계측만)

`puts + 도어벨` 44.12 us 는 **뺄셈**이다(링 − fence − wait).  이 프로젝트에서 뺄셈에
이름을 붙였다가 여섯 번 틀렸다.  누적기 하나를 더 둔다:

| 새 누적기 | 무엇 | 비용 |
|---|---|---|
| `put` | `cpPut` 루프(링 + 그림자) 양쪽 제출 합산 | 제출당 시계 2 회 ≈ 4 us |

그러면 `도어벨 + posting` 은 `링 − fence − wait − put` 으로 결정된다 — **뺄셈 하나에
이름 하나**, 그 이상은 없다.

예측은 적지 않는다.  워드당 11.6 ns × 1,108 워드 × 2 제출 = 25.7 us 라는 **모형**이 있지만,
이 프로젝트에서 그런 모형은 여섯 번 중 한 번 맞았다.

## 2-3. codex 교차검토 — 판정표

물은 것: 두 한도 중 어느 것이 100 ms 를 강제하는가, 그리고 스핀이 무엇을 깨는가.
전건을 원문에서 열어 확인했다([[codex-cross-review-practice]]).

| codex 주장 | 내가 확인한 방법 | 판정 |
|---|---|---|
| (a) 시간 검사가 100 ms 를 강제하고, 턴 캡은 **얼어붙은 시계**용이다 | `osrdn_cp.m:139-140` 의 주석이 문자 그대로 "a turn cap for a clock that does not advance" | ✅ 사실 — §1-2 와 일치 |

| (e) 턴 캡 자체는 안 넘지만, **얼어붙은 시계에서 같은 20,008 턴이 더 많은 실시간을 쓴다** | python 으로 계산: spin 4 이면 한 턴이 10 → 13.32 us, 최악 200.1 → **266.5 ms**(1.33 배) | ✅ 채택 — §2-5 에 적는다 |
| **(e) 스핀이 `t1`/`w->us` 를 갱신하지 않고 빠져나가면 대기가 과소 계상된다** | 성공 경로(`osrdn_cp.m:253-260`)가 바로 그것을 한다.  **내 스케치에 그 버그가 있었다** | ✅ **채택 — 고친다** |

**내가 틀렸던 것**: §2-1 의 스케치가 스핀 성공 시 시계를 갱신하지 않았다.  그대로 짰으면
스핀 팔의 `wait=` 가 **작게 나와** "스핀이 대기를 줄였다" 고 읽혔을 것이다 — 측정이
자기 자신을 속이는 모양이다.

## 2-4. 그래서 구조체에 **턴 수를 넣는다**

    typedef struct {
        unsigned long   evals;
        unsigned long   turns;      /* M2b: 바깥 바퀴.  스핀이 켜지면 evals 는 이것이 아니다 */
        unsigned long   us;
        int             limit;
    } osrdn_cp_wait;

이것이 없으면 스핀 팔의 로그를 **해석할 수 없다**: 오늘 내가 쓴
"`IODelay` 횟수 = `evals` − 1" 이 스핀에서는 거짓이 된다.  `turns` 가 있으면
잠든 횟수는 언제나 `turns` 이고, `evals` 는 물어본 횟수다 — **두 수가 각자 한 가지를 뜻한다.**

## 2-5. 스핀이 **약화시키는 것 하나**, 숫자로

얼어붙은 시계에서 턴 캡이 허용하는 실시간:

| spin | 한 턴 | RPTR 최악 | 배수 |
|---:|---:|---:|---:|
| 0 (오늘) | 10.00 us | 200.1 ms | 1.00x |
| 2 | 11.66 | 233.3 | 1.17x |
| 4 | 13.32 | 266.5 | 1.33x |
| 8 | 16.64 | 332.9 | 1.66x |

**시계가 도는 한 실제 한도는 100 ms + 한 턴**으로 거의 안 움직인다.  커지는 것은
**얼어붙은 시계의 최악**뿐이고, spin 4 에서 1.33 배다.  손잡이 기본은 0 이므로
오늘과 바이트 단위로 같고, 켜는 팔만 이 값을 진다.

### 6-1. 스핀은 **거의 아무것도 못 얻었다** — 그리고 그것이 답이다

    wait 57.96 -> 56.02 us a ZCLEAR   (-1.94, -3.3 %)
    커널 연산은 -2.00 us

여덟 번 더 물어도(≈6.6 us) 카드는 준비돼 있지 않다.  **`IODelay(10)` 의 잠은 낭비가 아니라
카드가 실제로 쓰는 시간이다.**  그러므로 **손잡이는 켜지 않는다** — 값이 3 %이고, 그 대가로
얼어붙은 시계의 최악이 1.66 배가 된다(§2-5).  측정된 음성 결과다.

### 6-2. `put` 은 17.94 us 였다 — 그리고 **모형이 안 닫힌다**

44 us 의 절반이 워드 쓰기였다.  남는 것은 **43.56 us**이고, 그 안에 있는 것은
ZCLEAR 당 **MMIO 여섯 번**(WPTR 쓰기 둘, RPTR 읽기 넷)뿐이다.  레지스터 읽기 하나는
`s1read` 로 재면 **1.1 us**(10 회에 10.95 us)이므로 여섯이면 6.6 us 다.

계측기 자신의 몫을 빼도 닫히지 않는다: M2a 부팅의 같은 팔과 견주면 이 칸이 더한
타임스탬프 넷이 **+13.1 us** 였으므로, 남는 것은 여전히 **약 30 us**.

**이것을 이름 붙이지 않는다.**  다음 칸의 첫 질문이다.

### 6-3. 새 계수기가 **자기 버그를 드러냈다**

로그를 짝지어 보니 `evals − turns` 가 315 건에서 정확히 1(예측대로)인데
**84 건이 `evals=0 turns=2`** — 불가능한 값이었다.  그 84 건은 전부 **거절된 제출**이고,
거기서는 `cpWait` 이 아예 안 돈다.  원인: `turns` 를 구조체와 로그에는 넣었는데
**연산 시작의 초기화에는 안 넣었다** — 이전 연산의 값이 이번 것으로 보고됐다
([[log-as-evidence]] 의 축소판).

측정 자체는 온전하다(대기가 실제로 돈 315 건은 전부 맞다).  그래도 고치고,
**구조체를 읽어 모든 필드가 지워지는지 보는 규칙**을 넣었다 — 다음에 필드를 더해도
누가 기억하지 않아도 된다.  변이 하나로 발동을 증명.

(그 규칙을 처음 쓸 때 `typedef struct` 를 비탐욕으로 잡아 **다른 구조체의 필드**까지
끌어왔다.  검사기가 그것을 `nvals is never cleared` 로 즉시 보고해서 고쳤다.)
